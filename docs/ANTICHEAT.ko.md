# 안티치트 호환

> 안티치트 게임과 관련해 AsterCache 가 하는 일과 하지 않는 일입니다. 데이터를 지키는 방법은 [안전 장치](DEVELOPMENT.ko.md#안전-장치)에 있습니다.

요즘 게임 대부분은 커널 수준 안티치트를 씁니다. 이 문서는 AsterCache 가 하는 일과 하지 않는 일을 적어, 게임에 쓸지 판단할 수 있게 합니다. 안티치트 정책은 게임마다 다르고 바뀔 수 있습니다. 한 PC 에서 Vanguard 게임(League of Legends)과 Ricochet 게임(Call of Duty)을 설치본으로 플레이한 사용 기록이 있습니다([이 PC 의 사용 기록](#이-pc-의-사용-기록)). 통제된 검증은 아니며, 계정 제재 여부는 보증하지 않습니다.

## 하는 일

- 서비스가 자기 프로세스 안에서 게임 파일을 읽기 전용, 공유 모드(읽기·쓰기·삭제 공유)로 읽거나 매핑만 합니다.
- 첫 실행의 선행 읽기도 서비스 자기 프로세스의 파일 읽기입니다. 게임의 읽기는 실시간 ETW 커널 세션으로 관찰만 하며, 게임 프로세스에 대한 핸들은 필요하지 않습니다.
- 트레이스가 허용된 게임(예: Ricochet 게임)에서는 ETW 세션이 기록을 시작한 때부터 게임이 종료되거나 마지막 추가 창이 끝날 때까지 열려 있습니다. 추가 창마다 세션을 다시 여는 방식이 아닙니다. `auto.io_summary_enabled`(기본 켜짐)가 켜져 있으면 같은 세션이 디스크 읽기 완료(`DiskIORead`: 디스크 번호, 바이트 위치, 크기, 지연)도 관찰하고 게임이 끝날 때까지 열려 있습니다. 원시 기록은 마지막 추가 창이나 상한에서 끝나며, 그 뒤에는 디스크 읽기 완료 말고 모든 이벤트를 바로 버립니다. 세션은 게임 프로세스 핸들이 필요 없고 게임 프로세스를 열지 않습니다. 파일은 게임이 종료된 뒤에만 디스크에 씁니다.
- 게임이 끝난 뒤 같은 단계에서 게임 폴더 아래 파일의 배치를 파일 속성 조회(`FILE_READ_ATTRIBUTES` 로 열기, `FSCTL_GET_RETRIEVAL_POINTERS`, 볼륨의 디스크 위치)로 읽어 디스크 위치를 파일로 바꿉니다. 파일 내용은 읽지 않고, 게임·런처·안티치트 프로세스를 열지 않으며, 심볼릭 링크와 정션은 건너뜁니다.
- Windows 프리페치 기록(`C:\Windows\Prefetch\*.pf`)을 읽기 전용으로 읽고, 공유 프로필 zip 을 주 1회 HTTPS 로 내려받습니다. 둘 다 게임 프로세스에는 손대지 않습니다.
- 게임이 완전히 종료된 뒤에만 NTFS 조각 모음 API(`FSCTL_MOVE_FILE`)로 클러스터 위치를 옮깁니다. 파일 내용·크기·수정 시각은 바뀌지 않으며, 옮기기 전에 계획의 지문(크기와 수정 시각)을 확인합니다.
- 게임 세션 동안 [배경 메모리 양보](AUTO_MODE.ko.md#배경-메모리-양보)가 게임과 무관한 다른 프로그램을 열어 그 메모리 우선순위를 낮추고, 메모리가 모자라거나 캐시가 실제로 재사용될 때만 작업 집합을 비웁니다. 기본으로 켜져 있습니다. 프로그램의 경로·작업 집합 크기·생성 시각·부모 프로세스 번호는 `PROCESS_QUERY_LIMITED_INFORMATION` 으로 읽고, 작업 집합을 비울 때는 `PROCESS_SET_QUOTA` 를, 메모리·디스크(I/O)·CPU 우선순위를 낮출 때는 `PROCESS_SET_INFORMATION` 을 더합니다(CPU 우선순위 등급을 읽는 데는 위의 조회 권한만 씁니다). AsterCache 가 다른 프로그램의 프로세스에 하는 일은 이것뿐입니다.
- 예열한 캐시를 유지하려고 [SOLAR](SOLAR.ko.md)가 게임 파일을 읽기 전용으로 잠깐 매핑해 서비스 자기 프로세스에서 읽고 바로 풉니다(이 문서는 이 동작을 만지기라고 부릅니다). 예열과 같은 종류의 읽기이며, 게임이 실행 중인 디스크에서는 하지 않지만 그 게임 자신의 예열 캐시를 게임이 시작될 때와 실행되는 동안 만지는 것은 예외입니다. 읽기는 서비스 자기 프로세스의 핸들로 `ReadProcessMemory` 를 거치므로 디스크 오류가 예외가 아니라 반환값으로 옵니다. 다른 프로세스의 핸들은 쓰지 않습니다. 이 부분은 매핑을 남겨 두지 않으며, 선택 기능 [고정](AUTO_MODE.ko.md#고정선택)과 다릅니다. 게임이 실행되는 동안 뷰를 열어 두는 붙들기는 "한계와 권고"에서 설명합니다.
- 시스템 전체 Windows 통계 두 가지를 `NtQuerySystemInformation` 으로 조회합니다. 대기 목록 수치(메모리 목록)와 시스템이 디스크에서 읽어 들인 페이지 수의 누계입니다. 둘 다 시스템 전체 값이고 프로세스를 열지 않습니다. 앞의 것은 서비스가 스스로 켜는 권한(`SeProfileSingleProcessPrivilege`)이 필요합니다.
- 다른 프로그램이 같은 디스크를 읽는 동안 예열이 자기 읽기 스레드의 I/O 우선순위를 낮춥니다(서비스 자기 스레드에 `NtSetInformationThread`). 다른 프로세스에는 아무것도 바꾸지 않습니다.
- 시작 스트림(게임 시작 직후 기록된 시작 데이터를 순서대로 읽는 동작)과 단계 스트림(같은 게임이 뒤이어 띄우는 실행 파일이 처음 읽는 블록을 읽는 동작, [자동 모드](AUTO_MODE.ko.md#6-게임-실행-중) 참고)은 서비스 자기 프로세스에서 게임 파일을 읽습니다. 게임이 나중에 띄운 프로그램의 스트림은 낮은 I/O 우선순위로 시작해 게임 자신의 읽기가 조용한 동안 보통으로 올리고, 첫 시작 스트림에는 이런 우선순위 조절이 없습니다. 단계 스트림은 서비스가 이미 보고 있는 시작 이벤트에서 같은 게임의 다른 등록 실행 파일이 나타나면 시작합니다. 읽기 증거와 로딩 경계를 판단하려고, 시작 스트림이 전부터 쓰던 것과 같은 조회 전용 핸들(`PROCESS_QUERY_LIMITED_INFORMATION`)로 게임 프로세스의 I/O 카운터를 읽으며, 그 밖의 프로세스 접근은 더하지 않습니다. 보호된 프로세스가 그것마저 거부하면 그 프로세스는 카운터에서 빠질 뿐입니다. 스트림이 도는 동안에는 표본마다 같은 조회를 다시 시도합니다. 단계 색인이 없으면 단계 스트림은 로딩 증거를 찾지 못해 건너뛰고, 로딩 경계 멈춤은 그 프로세스에서 잴 것이 없습니다. 프로세스의 메모리를 읽거나 바꾸지 않습니다.
- 서비스는 게임 파일을 매핑하거나 읽기 전에 Windows 에 그 파일의 속성(`GetFileAttributesW`)을 물어 스파스 파일인지 봅니다. 속성을 읽기만 하고 바꾸지 않으며, 판정은 속성만으로 하고 게임 이름이나 파일 확장자는 보지 않습니다. 스파스 파일은 매핑 대신 서비스 자기 프로세스에서 일반 버퍼드 읽기로 읽습니다.
- 게임이 실행 직후 꺼지면, 서비스는 마지막 정상 실행 뒤 새로 올라온 드라이버를 보여 주려고 올라와 있는 커널 드라이버 목록(`EnumDeviceDrivers`, `GetDeviceDriverBaseName`, `GetDeviceDriverFileName`)을 게임이 시작될 때마다, 그리고 짧은 종료가 두 번 연속 기록될 때 한 번 더 조회합니다. 읽기 전용의 시스템 전체 목록이며 프로세스를 열지 않고 드라이버를 건드리지도 않습니다. 게임이 꺼지는 것을 막지 않고 프로그램 이름을 지목하지도 않습니다.

## 하지 않는 일

- 게임 프로세스에 코드 주입, 스레드 생성, 메모리 읽기·쓰기, 디버그 권한, 후킹, 오버레이, 핸들 복제를 하지 않습니다.
- 게임 프로세스는 `PROCESS_QUERY_LIMITED_INFORMATION`(조회 전용)으로만 열어 이름·경로·읽은 바이트를 봅니다. 자동 발견은 프로세스를 처음 본 뒤 20초가 지나면 조회 전용 핸들로 읽은 바이트를 봅니다. 보호된 프로세스가 이것마저 거부하면 그 프로세스는 판정하지 않고 건너뛰며, 다시 열지 않고 커널 ETW 세션도 걸지 않습니다(시작 스트림과 단계 스트림은 표본마다 다시 조회합니다).
- 커널 드라이버를 쓰지 않습니다.
- SOLAR, 쿨다운 표본, 예열 읽기 스레드의 낮춘 I/O 우선순위, 런처 예열 우선은 게임·런처·안티치트 프로세스를 열지 않으며 다른 프로세스의 메모리를 읽거나 바꾸지 않습니다.
- 실행 직후 종료 감지와 디스크 활동 조회는 프로세스를 열지 않습니다. 단계 스트림은 위에 적은 조회 전용 핸들 말고는 아무것도 열지 않으며, 셋 모두 다른 프로세스의 메모리를 읽거나 바꾸지 않습니다.
- 배경 메모리 양보는 게임·런처·런처 보조·안티치트(EasyAntiCheat, BattlEye, Vanguard, 아래 표의 나머지)·세션 0 프로세스를 아예 열지 않습니다. 핸들을 요청하기 전에 이름이나 세션으로 걸러 냅니다. 그 밖의 프로그램은 먼저 조회 전용으로 열어 경로만 읽습니다. 경로가 Windows 폴더, 게임 폴더, 알려진 게임 라이브러리·런처·안티치트 폴더 안이면 바로 닫고 다른 권한으로는 열지 않습니다. 예외가 하나 있습니다. 우선순위를 낮춘 프로그램이 띄운 Windows 폴더 안의 프로그램은, 세션이 끝날 때 물려받은 우선순위를 되돌리려는 목적으로만 `PROCESS_SET_INFORMATION` 으로 엽니다. 이 권한으로는 프로그램의 메모리를 읽거나 쓸 수 없고, 스레드를 만들거나 핸들을 복제하거나 프로세스를 일시 중지하거나 끝낼 수도 없습니다.

## 건너뛰거나 표시하는 파일

- 게임이 배타적으로 연 파일은 건너뜁니다.
- 자동 발견 때 설치 폴더 아래 깊이 4까지의 파일·폴더 이름만 봅니다. EasyAntiCheat, BattlEye, Vanguard(`vgc`, `vgk`), Ricochet 는 인식하고, 아래 표의 마지막 여덟 행(BlackCipher 부터 FACEIT 까지)의 정확한 이름은 `kernel` 로 표시하며, 그 밖에 anticheat, anti-cheat, xigncode, nprotect, gameguard 가 들어간 이름은 `unknown` 으로 표시합니다. 그런 이름이 있는 게임은 게임 탭과 `anticheat` 설정에 표시되고 로그 한 줄이 남습니다. 표시된 종류는 안티치트 게이트에도 쓰여 그 게임의 자동 추적·고정·SSD 보조 저장 허용 여부를 정합니다(아래 표, `unknown` 은 금지로 봅니다). 예를 들어 `aster discover` 에서 Steam 게임 The Outlast Trials 가 `eac` 로 표시되었습니다.

## 속도 기능별로 안전하다고 보는 이유

아래는 각 기능을 안전하다고 보는 이유이며, 검증된 결과가 아닙니다.

- **예열:** 서비스 자기 프로세스에서 일반 파일 읽기를 합니다.
- **예열 유지:** 1 MiB 일반 파일 읽기 표본을 잽니다.
- **고정:** 서비스 자기 프로세스의 읽기 전용 매핑이며, 게임이나 런처가 시작되면 해제합니다.
- **재배치:** 게임이 종료된 뒤에만 하며, 파일 내용은 바뀌지 않습니다.
- **프리페치 기록과 공유 프로필:** `.pf` 파일은 서비스만 읽고, 내려받기는 주 1회 파일 하나입니다.
- **감지:** 조회 전용 프로세스 핸들 또는 ETW 이벤트로 합니다.
- **배경 메모리 양보:** 게임과 무관한 프로그램만 위의 세 권한으로 바꾸며, 게임·런처·안티치트 프로세스는 열지 않습니다.
- **게임 실행 중 붙들기:** 서비스 자기 프로세스에서 일반 게임 파일을 읽기 전용으로 매핑하며, 다른 프로세스의 핸들은 쓰지 않고, 트레이스와 같은 게이트를 따릅니다(안티치트가 트레이스를 금지하는 게임은 붙들지 않음). 이런 접근에 대한 안티치트 제조사의 공개 설명은 찾지 못했습니다.
- **캐시 유지(SOLAR):** 서비스 자기 프로세스의 일반 게임 파일 읽기 전용 매핑을 바로 풀며, 다른 프로세스의 핸들을 쓰지 않고, 게임이 실행 중인 디스크에서는 하지 않습니다.
- **예열 읽기 스레드의 낮춘 I/O 우선순위:** 서비스 자기 읽기 스레드의 I/O 우선순위만 바뀝니다.
- **단계 스트림과 스파스 파일:** 서비스 자기 프로세스에서 게임 파일을 일반 읽기로 읽는 것이며, 새로 하는 조회는 파일 속성과 올라와 있는 커널 드라이버의 시스템 전체 목록(둘 다 프로세스를 열지 않음), 그리고 기존 조회 전용 핸들로 읽는 게임 프로세스의 I/O 카운터입니다.

## 서명

실행 파일에는 코드 서명이 없어 SmartScreen 경고가 뜰 수 있습니다. 지금까지 확인된 영향은 이 경고뿐입니다. 서명 여부와 안티치트 판정의 관계는 확인하지 않았습니다.

## 이 PC 의 사용 기록

한 PC 의 2026-11-02 ~ 2026-11-10 서비스 로그를 집계한 것입니다. 통제된 검증이 아니며, 계정 제재 여부는 로그로 알 수 없고 보증하지 않습니다. 표본 수와 줄 형식은 [RESULTS_SUMMARY.ko.md](RESULTS_SUMMARY.ko.md#실사용-기록)에 있습니다.

- **League of Legends.** `vanguard` 로 판정됐습니다. Vanguard 가 있는 PC 의 Riot 게임이라는 조건으로 판정하며 설치 폴더 이름으로 잡은 것이 아닙니다. 게임 시작 감지 10회 동안 트레이스 2회 수집 뒤 8회 건너뜀, 고정 건너뜀 4회, 재배치 완료 4회였습니다.
- **Call of Duty.** 설치 폴더의 `ricochet` 이름으로 `ricochet` 판정됐습니다. 게임 시작 감지 62회 동안 트레이스 수집 14회 시작, 고정 건너뜀 7회, 재배치 완료 5회였습니다.
- 예열은 두 게임 모두 적용했습니다.

## 한계와 권고

- 자동 모드는 기본으로 켜져 있습니다. 안티치트가 있는 게임은 플레이 전에 설정 탭에서 자동 모드를 끄거나, 그 게임의 exe 를 `auto.ignore_exes` 에 넣으십시오. 이미 등록된 게임은 자동 모드 스위치만으로 모든 동작이 멈추지 않으므로 게임 탭에서 일시 중지하거나 정책을 **끔**으로 함께 두십시오.
- 자동 트레이스도 수동 방식과 같은 종류의 ETW 수집을 씁니다. 그래서 [안내서](GAME_GUIDE.ko.md#안티치트-게임)의 Ricochet·Vanguard 주의(와 League of Legends 참고 절)가 그대로 적용됩니다.
- SSD 보조 저장은 안티치트 폴더가 있는 게임을 건너뛰며, 게임의 exe·dll 파일은 복사하지 않습니다.
- 게임 정책, 일시 중지, 설정 탭의 다른 옵션으로도 안티치트 게이트와 고정 금지는 풀리지 않습니다. 설정을 바꾸는 것으로 이 문서의 규칙을 우회할 수 없습니다.
- 안티치트가 트레이스를 금지하는 게임(위 표에서 Ricochet 을 뺀 모든 행)은 전과 같이 기록하지 않으며 트레이스 세션도 열지 않습니다. 오래 열려 있는 세션은 트레이스가 허용된 게임에만 해당합니다.
- 배경 메모리 양보는 기본으로 켜져 있고 안티치트 게임을 하는 동안에도 동작합니다(그 게임의 안티치트 프로세스는 열지 않습니다). 실제 안티치트 게임을 하는 동안의 동작은 확인하지 않았습니다. 다른 프로그램을 건드리지 않기를 원하면 `memory.background_yield` 를 `false` 로 두십시오([설정](CONFIGURATION.ko.md)).
- SOLAR 는 기본으로 켜져 있습니다. 게임이 실행 중인 디스크에서는 돌지 않지만, 안티치트 게임을 하는 동안 다른 디스크에서는 돌 수 있습니다. 실제 안티치트 게임 옆에서의 동작은 확인하지 않았습니다. 돌지 않기를 원하면 `memory.standby_ladder` 를 `false` 로 두십시오([설정](CONFIGURATION.ko.md)).
- 게임이 실행되는 동안 유지 목록을 서비스의 매핑 뷰로 붙들어 두는 기능(`memory.keep_hold`, [SOLAR](SOLAR.ko.md))은 서비스 자기 프로세스 안의 읽기 전용 매핑이며 게임·런처·안티치트 프로세스를 열지 않고 파일 핸들은 닫습니다. 게임 중 다시 만지기가 이미 하던 잠깐의 읽기 전용 매핑(읽고 바로 풂)과 같은 종류의 접근을 게임이 끝날 때까지 유지하는 것입니다. 별도의 게이트가 있고 범위는 트레이스 게이트와 같습니다: 트레이스를 금지하는 안티치트(EAC, BattlEye, Vanguard, 커널 수준, 탐지 실패)에서는 붙들지 않고 `cache hold while playing skipped (...: anti-cheat: ...)` 를 남기며, Ricochet 게임과 안티치트가 없는 게임은 붙듭니다(시작 줄에 `(anti-cheat: ricochet, hold allowed)` 가 붙음). 고정은 Ricochet 에서 계속 금지입니다. 설정에 적힌 종류와 감지한 종류를 모두 보고 어느 하나라도 금지 종류면 막습니다. 안티치트 구성요소 파일(예: Ricochet 드라이버), 실행 가능한 이미지(`MZ` 로 시작하는 파일), 16 MiB 보다 작은 파일, 게임이 주로 파일 캐시 없이 읽는 파일(붙들면 얻는 것보다 잃는 것이 큽니다)은 붙들지 않습니다. 안티치트 제조사가 이런 접근을 허용하거나 금지한다고 밝힌 공개 자료는 확인하지 못했습니다. 게임이 세션 중 스스로 쓰는 파일(트레이스가 쓰기로 열렸거나 플레이 사이에 바뀐 것으로 가변 표시한 파일)도 NTFS 변경 저널에서 3 플레이 이상 잘라내기가 없었고(저널 정보가 없으면 기록된 3 플레이에서 크기가 줄어든 적이 없고), 마지막으로 끝난 플레이 뒤 게임이 업데이트되지 않았고, 그 플레이에서 바뀌지 않으면 붙듭니다(5 초마다 파일을 열지 않는 속성 조회로 비교하고, 바뀐 파일의 뷰는 바로 닫음). 이것은 게임이 쓰는 파일을 서비스가 매핑해 두는 일이라 다른 붙든 파일보다 한 단계 더 나아간 것이고, 안티치트 제조사의 공개 자료는 찾지 못했습니다(`memory.keep_hold_written_files`, 기본 켜짐). 붙든 파일에 게임이 크기를 줄이는 쓰기를 하면 뷰를 닫을 때까지 오류 1224 로 실패합니다. 붙들기를 끄려면 `memory.keep_hold` 를, 게임이 쓰는 파일만 끄려면 `memory.keep_hold_written_files` 를 `false` 로 두십시오. 붙들기가 돌지 않는 게임에서는 게임 실행 중 다시 만지기([SOLAR](SOLAR.ko.md#게임이-실행되는-동안의-캐시-유지))만 합니다.
- 단계 스트림과 실행 직후 종료 감지도 안티치트 게임을 하는 동안 동작합니다. 단계 스트림은 기존 조회 전용 핸들로 그 게임 프로세스의 I/O 카운터를 읽고, 실행 직후 종료 감지는 프로세스를 열지 않습니다. 실제 안티치트 게임 옆에서의 동작은 확인하지 않았습니다. 단계 스트림을 끄려면 `auto.stage_stream_enabled` 를 `false` 로 두십시오([설정](CONFIGURATION.ko.md)).
- 프레임 간격 측정(`play.frame_times`, 기본 켬)은 자동 트레이스와 같은 판정으로 게이트를 지납니다. 트레이스가 금지된 안티치트 게임, 탐지에 실패한 게임, 추적을 끈 게임에서는 세션을 열지 않으며, 설정으로도 이 게이트를 풀 수 없습니다. 허용된 게임에서는 게임이 실행되는 동안 `Microsoft-Windows-DXGI` 의 Present 시작 이벤트(번호 42)만 받는 일반 ETW 실시간 세션 하나(`AsterCache-FrameTimes`)를 엽니다. 커널 로거는 쓰지 않고, 게임·런처·안티치트 프로세스를 열지 않으며, 후킹·주입·외부 실행 파일도 없습니다. 이벤트 머리의 프로세스 번호와 시각만 읽고, 서비스가 이미 아는 게임 프로세스의 이벤트만 집계합니다. 이 세션은 게임 하나만 보는 것이 아니라 시스템 전체의 DXGI 이벤트를 켜므로, 다음 규칙으로 더 엄격하게 엽니다. (1) 그 게임이 게이트를 통과하고, 동시에 게이트가 막는 등록 게임의 프로세스가 지금 하나도 실행 중이 아닐 때만 엽니다. (2) 세션이 열려 있는 동안 게이트가 막는 게임이 시작하면(설정을 다시 읽어 게임이 막히게 바뀐 경우 포함) 즉시 세션을 닫고, 그 뒤 구간은 `blocked` 로 기록합니다(그 앞의 값은 그대로 남고 `frameStoppedAtSeconds` 에 멈춘 시각이 남습니다). (3) 게임 프로세스가 사라지면 종료 유예(60~90초)를 기다리지 않고 바로 닫습니다(유예 중에 같은 게임이 다시 뜨면 다시 엽니다). 이 판정에는 자동 트레이스가 쓰는 기존 함수만 쓰며 게이트는 고치지 않았습니다. Ricochet 게임은 자동 트레이스가 허용되므로 이 세션도 열립니다. 실제 안티치트 게임 옆에서의 동작은 확인하지 않았습니다. 플레이의 매초 기록(`play.series`)은 이 세션이 열린 플레이에서만 남기므로 같은 게이트를 따르고, 이것도 프로세스를 열지 않으며 시스템 전체 조회와 성능 카운터만 씁니다. 끄려면 `play.frame_times` 를 `false` 로 두십시오([설정](CONFIGURATION.ko.md)). 매초 기록만 끄려면 `play.series` 를 `false` 로 두십시오.
- 그 밖의 안티치트 게임은 시험하지 않았습니다.
