# 자동 모드

> README 의 [시작하기](../README.ko.md#시작하기)에서 이어지는 상세 설명입니다. 서비스가 자동으로 하는 일의 단계, 지원 런처, 설정 키가 들어 있습니다.

자동 모드는 기본으로 켜져 있습니다. 보통은 게임을 등록하거나 따로 설정할 필요가 없습니다. 각 부분은 설정 탭의 **자동 모드** 묶음이나 `config.json` 에서 끌 수 있습니다. 여기서는 설정 이름만 적고, 뜻과 기본값은 [CONFIGURATION.ko.md](CONFIGURATION.ko.md)에 있습니다. 접힌 블록(눌러서 펼침)에 조건, 예외, 수치가 들어 있습니다.

게임마다 범위를 더 좁힐 수도 있습니다. **정책**(`games[].mode`: `inherit`, `prewarm_only`, `relocate_only`, `off`)은 각 단계가 그 게임에 무엇을 할 수 있는지 정하고, **일시 중지**(`games[].paused`)는 그 게임의 새 작업을 멈춥니다. 일시 중지한 게임과 `off` 인 게임은 추적, 예열, 재배치를 하지 않습니다. `prewarm_only` 는 예열과 계획은 허용하고 재배치나 정기 재적용은 허용하지 않습니다. `relocate_only` 는 재배치는 허용하고 예열, 시작 스트림, 고정은 허용하지 않습니다. 두 설정 모두 안티치트 게이트와 고정 금지를 풀지 않습니다. 예열이 허용되지 않은 게임은 기다리던 예열 항목을 버리며, 다시 허용되면 다음 점검부터 이어 갑니다.

## 단계 한눈에 보기

| 단계 | 한 줄 설명 |
|---|---|
| 1. 발견 | 런처 라이브러리에서 HDD 게임을 찾아 등록합니다. |
| 2. 읽기 기록 | 게임이 로딩 중에 읽는 것을 기록합니다(트레이스). |
| 3. 재배치 | PC 가 한가할 때 게임이 읽는 조각을 한 존(디스크 위의 연속 영역)에 모읍니다. |
| 4. 예열 | 게임을 켜기 전에 그 존을 RAM 에 읽어 둡니다. |
| 5. 유지 | 재예열, 보충, 재시도, 배치 재검사를 하고, 예열한 캐시를 순서대로 유지합니다([SOLAR](#solar-캐시-유지와-순서)). |
| 6. 게임 실행 중 | 디스크를 게임에 양보하고, 게임과 무관한 배경 프로그램이 메모리를 양보하게 하며, 디스크가 어떻게 움직였는지 기록합니다. |
| 7. 드라이브 회복 대기 | 대량 쓰기 뒤 SMR 드라이브가 안정되기를 기다립니다. |

"한가함"은 [한가함의 뜻](#한가함의-뜻)에 정의돼 있습니다.

## 첫 실행 전에 쓰는 자료

기록이 없는 게임은 공유 프로필, Windows 프리페치 기록, 엔진 프로필, 폴더 전체 중 해당하는 첫 번째 것으로 처음 배치 정보를 얻습니다. 첫 실제 트레이스가 생기면 그것이 대신합니다.

<details>
<summary>세부: 네 가지 자료</summary>

첫 실행에서 실제 기록(트레이스)이 생기면 그것으로 만든 계획이 앞의 계획을 대신하며 같은 존 위치를 먼저 시도하고, 옛 계획은 `.stale` 로 남깁니다.

- **공유 프로필** (`auto.shared_profiles`, 기본 켬). 주 1회 공유 프로필 묶음 zip 하나를 HTTPS 로 받고, Steam 앱 ID와 디포 매니페스트 ID, Epic 앱 이름과 버전, 또는 exe 크기와 표본 SHA-256 으로 게임을 찾습니다.
- 이 PC 의 파일 크기와 표본 해시가 맞을 때만 씁니다. 오프라인이거나 404 면 조용히 건너뜁니다. 내려받기는 64 MiB 로 제한합니다. 공유 저장소는 아직 준비 중입니다.
- **Windows 프리페치 기록** (`C:\Windows\Prefetch\*.pf`). SysMain 서비스가 돌고 `EnablePrefetcher` 의 응용 프로그램 비트가 켜져 있을 때 씁니다. 서비스는 게임의 `.pf` 파일만 읽습니다.
- 설치 폴더 안의 파일로 부트 트레이스를 만들며 "미리 읽지 않음" 표시가 있는 파일은 뺍니다. 기록이 참조한 범위와 그 앞뒤 64 MiB(겹치면 합침, 파일 크기 상한 없음)를 물리 순서로 존에 모읍니다.
- 존이 플레이에서 읽은 양의 30% 미만만 덮으면 상태 detail 에 `partial (N%)` 로 표시합니다. 관리 창에는 "재배치됨(프리페치)"로 표시됩니다.
- **엔진 프로필** (Unity, Unreal, Source). 기록 없이 예열합니다.
- **폴더 전체.** 폴더가 RAM 예산 안에 들면 기록 없이 예열합니다.

</details>

## 단계

### 1. 발견

- **언제.** 서비스가 시작한 10초 뒤와 그 뒤 1시간마다.
- **무엇을.** [지원 런처](#지원-런처)를 읽어 HDD 게임을 `"source": "auto"` 로 등록합니다. 시작 뒤 많이 읽는 프로세스는 [휴리스틱](#휴리스틱-감지)으로 잡습니다.
- **하지 않는 것.** SSD 게임, 상주 유틸리티, 직접 등록한 게임과 같은 폴더의 게임은 등록하지 않습니다. Windows 드라이브의 게임은 예열만 합니다.
- **설정.** `auto.discover`, `auto.ignore_exes`.
- **로그.** `auto <런처>: registered <이름> (<exe>)`

<details>
<summary>세부: 상한, 건너뛰는 경우, 상주 유틸리티</summary>

**상한과 건너뛰기**

- 게임 목록 상한은 32개입니다. 가득 차면 런처 발견은 멈추고, 실제로 실행되어 잡힌 게임이 가장 오래 쓰지 않은 자동 항목을 밀어냅니다.
- 볼륨 레이블이 비었거나 32자를 넘으면(로그 한 줄), 같은 exe 이름이나 겹치는 폴더가 이미 등록되어 있으면 건너뜁니다.
- SSD 의 게임은 자동 등록·트레이스·재배치 대상이 아닙니다. Windows 가 있는 드라이브가 HDD 이면 그 게임은 발견과 예열만 합니다(상태 "prewarm only (system drive)").
- 관리 창에서 지운 게임은 exe 가 `auto.ignore_exes` 에 들어가 다시 자동 등록되지 않습니다(최대 64개, 넘으면 오래된 것부터 빠짐).
- 다른 로그 줄: `auto <런처>: skipped <이름>: volume has no usable label`, `auto discovery: game list is full, skipping the rest`.

**상주 유틸리티**

- 게임이 아니고 한 번 띄우면 계속 켜져 있는 데스크톱 유틸리티(Wallpaper Engine, YoloMouse, Lossless Scaling, OBS Studio, SteamVR 등)는 자동 등록하지 않습니다.
- 고정된 Steam appid·exe 이름 목록이 런처 발견과 휴리스틱 양쪽에서 이들을 제외합니다. 이 목록은 `auto.ignore_exes` 와 별개입니다.
- 이미 자동 등록된 항목은 서비스가 시작된 뒤 실행 중이어도 한 번 등록 해제합니다(파일을 옮기는 중이면 다음 발견 때). 직접 등록한 항목은 건드리지 않습니다.
- 이미 옮긴 파일은 그대로 둡니다. SSD 보조 저장(`auto.ssd_tier`)을 쓰고 있었다면 등록이 사라진 게임의 링크는 되돌립니다. 등록이 사라진 게임은 예열이나 고정도 하지 않습니다.
- 로그: `auto: unregistered <게임> (resident utility, not a game)`.

</details>

### 2. 읽기 기록(트레이스)

- **언제.** 트레이스가 없는 등록 게임이 처음 시작될 때(감지한 실행은 이미 로딩이 시작된 뒤라 다음 실행부터 기록). 몇 번의 플레이에 걸쳐 되풀이합니다.
- **무엇을.** 실시간 ETW 세션으로 게임의 읽기를 기록해 `plans\<이름>.trace.json` 에 저장합니다. 수동 **트레이스 수집** 버튼과 같은 파일입니다.
- **하지 않는 것.** 안티치트가 금지한 게임은 기록하지 않고([ANTICHEAT.ko.md](ANTICHEAT.ko.md)), 게임 프로세스는 열지 않습니다. ETW 로만 관찰합니다.
- **설정.** `auto.trace`, `auto.io_summary_enabled`, `trace_cap_seconds`, `trace_cap_mib`, `trace_runs`, `trace_merge_min_mib`, `trace_late_*`.
- **로그.** `<게임>: auto trace started (run 2/3)`, `<게임>: auto trace ended (<사유>), N read events saved`

<details>
<summary>세부: 상한, 여러 번의 플레이, 존 확장, 첫 실행 학습</summary>

**기록**

- 세션 이름은 `AsterCacheAutoTrace` 입니다. 원시 기록 창은 게임 종료, 1800초(`trace_cap_seconds`), 6144 MiB와 존 상한의 2배 중 큰 값(`trace_cap_mib`) 중 먼저 오는 시점에 닫힙니다.
- 상한에 닿았는데 게임이 아직 실행 중이면 원시 기록 창만 닫습니다. 정리·저장·병합은 게임이 끝난 뒤에 하며, `auto.io_summary_enabled` 가 켜져 있으면 같은 ETW 세션의 관찰을 게임 종료까지 이어 갑니다. 읽기 방식 판정에 필요한 대상 프로세스와 파일 이름은 계속 추적하지만 동결된 원시 기록에는 더하지 않습니다.
- `auto.io_summary_enabled` 가 켜져 있으면 세션이 `DiskIORead` 완료(추가 키워드는 이것 하나)와 대상 프로세스의 `FileIORead` 요청 표시를 수집합니다. 게임이 도는 동안 디스크 완료는 요청(디스크 번호, 바이트 위치, 크기)별 횟수·지연 합과 최댓값·처음 읽힌 시각·페이징 횟수(IRP 플래그 0x2)만 더합니다. 디스크 읽기의 IRP 는 파일 읽기의 IRP 와 다른 객체라 이벤트 시점에 IRP 로 잇는 방법은 통하지 않았고(실측: 49,266건 중 0건 일치) 이벤트 시점에는 파일을 알 수 없습니다.
- 파일 읽기 표시는 비트로 분류합니다. 0x02(`IRP_PAGING_IO`) 또는 0x40(`IRP_SYNCHRONOUS_PAGING_IO`)이 있으면 페이징, 페이징이 아니면서 0x01(`IRP_NOCACHE`)이 있으면 캐시 없음, 그 밖은 캐시 사용입니다. 파일별 요청 수와 바이트를 세 분류마다 더하고, 끝내 이름을 찾지 못한 읽기 수와 표시 값 종류별 건수를 기록합니다(표시 종류는 최대 32개와 그 밖 한 칸). 원시 창이 동결되거나 읽기 구간이 닫힌 동안에도 집계합니다.
- 게임이 끝난 뒤 서비스는 허용 루트 아래 모든 파일의 배치를 파일 속성 조회로(파일 내용은 읽지 않음) 읽어 요청을 (파일, 64 KiB 블록) 행으로 바꾸고 회차 파일 곁의 `.io.json` 에 씁니다. 한 요청이 구간·블록·파일 경계를 넘으면 바이트는 겹친 만큼, 지연은 바이트 비례로 나눠 총합을 보존합니다. 블록 행의 횟수는 그 블록에 닿은 요청 수이고 요청 단위 총계는 품질 값에 있습니다. 변환은 낮은 우선순위 스레드에서 돌고 훑은 파일 수와 걸린 시간을 로그에 남깁니다. 같은 디스크에서 게임이 이미 돌고 있으면 건너뛰고, 서비스가 멈추거나 등록 게임이 시작되거나 30초 예산을 넘기면 멈춥니다(요약만 버리고 원시 기록 저장은 계속하며, 로그에 사유가 `I/O summary not built (service shutdown / a game started / time budget / a game is running)` 로 남습니다). 재배치·재계획·확장은 게임이 끝난 뒤 `rewarm_after_exit_min` 이 지나야 시작하고, 변환 앞뒤의 계획·저널 상태를 비교해 달라졌으면 요약을 버립니다. 큰 게임에서의 변환 시간은 재지 않았습니다.
- `.io.json` 버전 4에는 허용 루트 안에서 읽힌 파일마다 캐시 사용·캐시 없음·페이징 요청 수와 바이트를 담는 `read_modes` 가 있습니다. 품질에는 파일 수 상한 262,144개에서 버린 파일 수, 이름을 끝내 못 찾은 읽기 수, 표시 값별 건수, 읽기 방식 관측 종료 시각이 들어갑니다. 버전 3도 계속 읽으며 읽기 방식은 모름으로 처리합니다. 서비스는 서로 다른 플레이 세션 ID 두 개의 유효한 읽기 방식 집계가 모일 때까지 추적합니다. 같은 세션을 다시 저장해도 새 플레이로 세지 않습니다. 서비스와 `aster trace --live --io-summary-root` 는 `I/O summary:` 바로 뒤에 `read modes:` 로그를 남깁니다. 각 행에는 `open_options` 도 있습니다(선택 항목, 모르면 0 이거나 없음): 대상 프로세스가 파일을 열 때 준 옵션 가운데 순차(0x4)·캐시 없음(0x8)·임의 접근(0x800) 비트이며 커널 파일 생성 이벤트에서 얻으므로, 관찰이 시작되기 전에 이미 열려 있던 파일은 0 입니다. `read modes:` 로그는 끝에 `opened with sequential N, random access M, no buffering K files` 를 붙입니다. 이벤트 정의를 따라 만들었고 실제 추적에서는 확인하지 못했습니다.
- 서비스가 스스로 발행한 읽기(시작 스트림·예열)는 블록 행에서 뺍니다. 디스크 읽기 이벤트는 요청한 프로세스를 알려 주지 않습니다. 매핑·캐시 읽기는 페이징 읽기로 내려가고 흔히 시스템 스레드가 발행하므로 프로세스·스레드 ID 로는 서비스와 게임을 가를 수 없습니다(세션은 스레드 이벤트도 켜지 않습니다). 그래서 트레이스 세션이 관찰하는 동안 서비스가 끝까지 읽은 묶음마다 파일·바이트 구간(4 KiB 페이지로 넓힘)·시작과 끝 시각을 적어 둡니다(`SelfReadLog`, 멈췄거나 못 연 파일이 있던 묶음은 적지 않음). 관찰마다 따로 524,288개까지 보관하고, 넘으면 늦은 것을 버리며 몇 개인지 로그에 남깁니다. 요약을 만들 때 다음을 모두 만족하는 디스크 읽기만 뺍니다: 그 디스크 구간을 한 번만 읽었고(횟수 1), 페이징 읽기이며, 원시 기록 창 안에서 시작했고(창 밖에서는 게임의 읽기가 기록되지 않아 확인할 수 없으므로 남김), 그 구간 전체가 적어 둔 묶음의 시간(매핑 읽기는 호출이 끝난 뒤에도 이어질 수 있어 10초를 더함)과 구간으로 덮이며, 게임 트레이스에 그 시간대 겹치는 구간의 읽기가 없습니다. 일부만 덮인 읽기는 남깁니다. 같은 시간대에 게임이 같은 구간을 읽었으면 남깁니다. 로그 줄 끝에 뺀 읽기 수와 MiB 가 남고, `.io.json` 에는 `self_read` 로 저장하며 `linked` 에는 들지 않습니다. 새 요약부터 적용하고 저장된 것은 다시 쓰지 않으며, 병합이 옛 섞임을 줄여 주지는 않습니다. 한계: 서비스의 학습용 미리 읽기는 적지 않습니다. 캐시 관리자가 적어 둔 구간 밖으로 덧붙인 미리 읽기는 남습니다. 게임이 같은 파일을 메모리 매핑으로 읽으면(페이지 폴트 읽기는 파일 읽기 기록이 없음) 창 안에서도 서비스 읽기로 잘못 빠질 수 있습니다. 경로는 대소문자만 무시하고 비교하므로 같은 경로의 다른 표기(`\?\`, 슬래시, 8.3 이름)는 맞추지 못합니다. 이 규칙을 실제 게임으로 돌려 보지는 않았습니다.
- 읽기는 다음으로 나눕니다: 블록에 연결됨, 다른 디스크(게임 폴더가 있는 디스크가 아님), 같은 디스크지만 어떤 파일 구간에도 들지 않는 위치, 변환 안 함(NTFS 압축·암호화 파일, 여러 디스크에 걸친 볼륨, NTFS 가 아니거나 파일 시스템을 읽지 못한 볼륨, 폴더 자신이나 그 조상이 정션·심볼릭 링크·마운트 지점인 게임 폴더는 건너뛴 볼륨으로 셈), 요청 표 상한 초과로 버림(고유 요청 262,144개, 버린 건수·바이트·지연 합은 남기고 `truncated` 표시). 스파스 구멍은 배치에 없으므로 아무것도 귀속하지 않습니다. 관찰이 시작된 뒤에 쓰인 파일은 파일 표에 "세션 중 변경됨" 으로 표시합니다. 지연은 요청이 디스크 스택에 내려간 때부터 완료까지라 장치 앞 대기를 포함하고 순수 서비스 시간이 아니며, 겹친 요청이 많으면 합이 실제 정지 시간보다 커질 수 있습니다. 같은 디스크 구간을 여러 파일이 공유하면(하드 링크·블록 복제) 그 구간은 한 파일에만 붙거나 "파일 구간 밖"으로 세므로 총합은 정확해도 파일별 나눔은 정확하지 않습니다. 이 요약은 기존 트레이스나 계획 입력을 바꾸지 않습니다.
- 회차로 저장하기엔 너무 작은 측정 전용 추가 실행은 추적 파일 곁의 제한된 `.io-only.NN.json` 파일에 요약을 저장합니다. 각 요약에는 세션 ID 와 원시 추적 지문이 있어 다른 추적 내용에 오래된 집계가 붙지 않습니다. 게임 업데이트가 요약의 파일 표에 없는 파일만 바꾸면 요약은 남기고 지문만 새로 맞춥니다.
- 트레이스에는 디스크까지 간 읽기만 기록되므로 이미 캐시에서 처리된 읽기는 빠질 수 있고, 세션이 시작되기 전의 첫 읽기 일부도 빠질 수 있습니다.

**추가 창**

- 첫 창이 끝났는데도 게임이 실행 중이면 첫 추가 창을 첫 창 바로 뒤에 열어 `auto.trace_late_window_seconds`초 동안 수집합니다. 이후 창은 앞 창이 끝난 뒤 `auto.trace_late_interval_min`분 뒤에 열며, 창은 모두 합쳐 최대 `auto.trace_late_windows`개입니다. 창 수, 창 길이, 트레이스를 막는 게이트는 그대로입니다. 간격은 첫 창이 아니라 첫 추가 창이 끝난 뒤부터 셉니다.
- 세션은 첫 창부터 게임이 끝날 때까지 열어 둡니다. 마지막 추가 창이나 상한 뒤에는 원시 기록 창이 닫히지만, 설정이 켜져 있으면 디스크 읽기 완료 집계는 종료 때까지 계속됩니다. 열린 창 밖의 읽기는 원시 트레이스에서 빼고, 파일은 게임이 끝난 뒤에만 저장합니다. 원시 기록이 끝난 뒤 서비스가 종료돼도 원시 트레이스는 저장하고 요약은 만들지 않습니다. 창마다 세션을 새로 열면 창이 시작되기 전에 게임이 연 파일의 읽기는 어느 파일인지 알 수 없어 버려졌고 추가 창이 아무것도 저장하지 못했습니다. 세션을 하나로 유지하면 뒤의 창이 그 읽기를 저장합니다. 이 문제는 시험 프로그램으로 재현했고, 실제 게임에서는 아직 확인하지 않았습니다.
- 원시 읽기 상한은 열린 창 안의 읽기만 셉니다. 디스크 요약에는 전체 세션의 디스크 읽기를 담고, 이벤트 유실·요청 표 상한·블록 표 상한을 품질 값으로 남깁니다.
- 세션을 열어 두면 창 밖에서도 플레이 내내 Windows 가 파일 이벤트를 서비스에 전달합니다. 이 CPU 비용은 측정하지 않았습니다. 창이 닫힐 때마다 서비스 로그에 `<게임>: trace window ended, N reads, P target processes, L events lost so far` 가 남으며, 추가 창이 아무것도 저장하지 않았다면 `N` 을 보십시오. 세션이 멈출 때는 `trace session stopped: L events lost, M reads dropped (name unresolved), K file names, R records` 로 합계가 남고, `M` 은 전체 읽기에 비해 작아야 합니다.
- 트레이스 세션이 살아 있는 동안 같은 게임의 등록 실행 파일이 새로 시작해도(맵 로드로 게임 프로그램이 다시 뜨는 경우) 추가 창이 열립니다. 그래서 예약 창 사이에 떨어진 로드의 읽기 순서도 기록됩니다. 서비스가 이미 감지하는 이 시작에서, 아직 남은 다음 추가 창 하나를 제 시각을 기다리지 않고 그 순간에 엽니다. 창이 이미 열려 있거나 남은 창이 없으면 아무것도 하지 않으므로, 창 개수·창 길이·메모리와 이벤트 상한·안티치트 게이트·게임 실행 중 게이트는 그대로입니다. 이렇게 연 창이 끝나면 다음 예약 창은 평소처럼 간격 뒤에 열리므로 두 종류가 겹치지 않습니다. 로그는 `<게임>: late window k/N started at a target start (<exe>)` 입니다. 실제 게임에서는 아직 확인하지 못했습니다.
- 안티치트가 트레이스를 금지한 게임은 세션을 열지 않으므로 위 내용이 적용되지 않습니다([ANTICHEAT.ko.md](ANTICHEAT.ko.md)).

**여러 번의 플레이**

- 이후 플레이도 `trace_runs`번이 모일 때까지 같은 방식으로 기록해 `plans\<이름>.trace.runN.json` 으로 저장하고, 자동 디스크 읽기 요약은 곁 파일 `.trace.runN.json.io.json` 에 씁니다.
- `trace.json` 은 그 블록들의 합집합(첫 번째 플레이의 접근 순서 뒤에 이후 플레이에서 처음 본 블록)으로 한 번에 바꿔 씁니다. 그동안 상태 열에 `trace 2/3` 처럼 표시합니다.
- run 파일 번호 상한에 닿으면 가장 오래된 회차를 바꿔 쓰고 병합본 블록은 유지합니다.
- 병합 증가량이 기준에 못 미쳐 수집을 멈춘 뒤에도, 마지막 유효 회차 이후 5회 실행, 7일 경과, 게임 업데이트 감지 중 하나라도 있으면 한 번 더 수집합니다.
- 서비스는 트레이스 곁에 단계 스트림이 쓰는 단계 색인도 만듭니다([게임 실행 중](#6-게임-실행-중)). `.stages.json` 파일과 시도 횟수를 세는 `.stages.tried` 입니다. 색인이 없는 게임은 최대 두 번 더 추적합니다. 유효한 디스크 읽기 요약이 하나도 없으면 최대 두 번 더 추적하며, 단계 색인 추가 추적과는 한 번의 플레이를 함께 씁니다. 로드 구간 목록이 시작 시각이 기록된 플레이 두 번 미만으로 만들어졌을 때도 다음 플레이를 추적하며, 최대 세 번까지입니다(부족한 플레이는 많아야 두 번이고, 시작 시각이 기록되지 못한 플레이를 위한 여유가 한 번입니다). 횟수는 `.loadrefill.tried` 에 셉니다. 서비스가 시작된 게임을 추적하지 않기로 하면 `auto trace not needed (valid 20/limit 8, relearn no (plays 3/5), stage index yes, io summaries 2, load list from 1 timed plays)` 같은 한 줄을 남기며, 같은 게임에 같은 줄은 서비스가 도는 동안 한 번만 남깁니다.

**존 확장**

- 병합한 핫 집합(트레이스가 읽은 블록)이 계획보다 `trace_merge_min_mib` 이상 커졌고 게임이 꺼져 있으면 존을 제자리에서 확장합니다.
- 이미 존에 있는 블록은 옮기지 않고 새 블록만 뒤에 붙이며, `max_zone_mib` 안에서 앞선 플레이의 블록을 우선하고, 유휴·일일 상한·쓰기 예산 검사는 일반 재배치와 같습니다.
- 존 뒤가 비어 있지 않으면 확장을 건너뛰고 이전 계획을 유지하며, 새 플레이로 트레이스가 바뀔 때만 다시 시도합니다. 로그: `<게임>: zone extension blocked: ...`.
- 존이 이미 크기 상한에 닿았으면, 병합 트레이스에는 있지만 존에 더는 들어가지 않는 블록은 옮기지 않습니다. 아무것도 옮기지 않으므로 게임 드라이브에 쓰지 않고, 예열 목록 전체가 캐시 예산(`prewarm.max_cache_mib`, 기본은 물리 RAM 의 절반) 안에 드는 만큼만 그 게임의 예열 목록에 대신 더합니다. 목록을 메모리에 맞춰 자를 때는 존의 관찰된 범위 뒤에 놓이며([순서와 예산](#4-예열) 참고), 시작 스트림은 이 블록을 읽지 않습니다. 로그: `<게임>: prewarm list gained N MiB of blocks outside the full zone`.

**첫 실행 학습(실험 기능, 기본 꺼짐)**

- 트레이스를 기록하는 동안 서비스는 선행 읽기를 할 수 있습니다. 기본으로 꺼져 있습니다(`auto.learn.enabled` 가 `false`, 첫 실행 선행 읽기 실험 E7~E7f 측정에서 이득 없음, [RESULTS_SUMMARY.ko.md](RESULTS_SUMMARY.ko.md#e7-첫-실행-선행-읽기) 참고).
- 켜면 게임이 파일을 순차로 읽는 경우에만 읽습니다. 직전 읽기 끝과 간격 4 MiB 이하로 앞으로 이어지는 읽기가 6회 연속이고 그 파일을 8 MiB 이상 읽었으면 순차로 판정합니다.
- 그런 파일은 게임 읽기의 틈을 기다리지 않고 현재 위치부터 16 MiB 단위로 `auto.learn.window_mib` 까지 앞서 읽습니다(`auto.learn.mode` `"stream"`, 기본). `"gap"` 이면 게임 읽기가 100 ms 동안 조용할 때만 1 MiB 씩 읽습니다.
- 읽기는 서비스 자기 프로세스에서 하며 읽기 스레드는 1개, 선행 읽기 I/O 는 낮은 우선순위, 방금 읽힌 파일부터입니다. 게임이 배타적으로 연 파일은 건너뜁니다.
- 총량은 게임 읽기량 × 1.5 + 64 MiB 를 넘지 않고, `auto.learn.max_total_mib` 와 가용 RAM 여유(`min_free_ram_mib`)를 지킵니다. HDD 이면서 시스템 드라이브가 아닌 드라이브의 게임만 대상입니다.
- `"bounded"`, `"adaptive"` 는 실험용 변형입니다. [CONFIGURATION.ko.md](CONFIGURATION.ko.md)를 보십시오.

</details>

### 3. 재배치

- **언제.** 트레이스가 생기고 게임이 꺼져 있으며 PC 가 한가할 때, 한 번에 게임 하나씩.
- **무엇을.** 존을 계획하고, 조각을 옮기고(저널과 SHA-256 표본 검사), 배치를 확인한 뒤 그 존을 예열합니다.
- **하지 않는 것.** 게임이 실행되는 동안 하지 않고(이동 중이면 지금 조각을 끝내고 멈춤), 압축·암호화 파일과 다른 제외 속성이 함께 있는 스파스 파일은 옮기지 않으며, 스파스 파일의 구멍을 채우거나 속성을 바꾸지 않고, 파일 내용을 바꾸지 않습니다. 검사가 실패하면 저널대로 되돌립니다.
- **스파스 파일을 옮기기 전에 만든 계획.** 이전 버전이 만든 계획에는 스파스 파일의 할당 구간 기록이 없어, 그 계획을 적용할 때는 그 파일을 건너뜁니다. 서비스는 실행당 한 번, 재배치가 끝났고 원본 파일이 바뀌지 않은 게임에 대해 지금의 할당 구간을 기준값으로 더한 뒤 남은 부분만 다시 계획해 계획을 바꿉니다. 이미 제자리에 있는 조각은 그대로 두고, 아직 놓이지 않은 스파스 조각에는 다른 계획이 예약한 존을 피한 새 연속 빈 구간 하나를 정해 줍니다. 로그는 `legacy plan replaced` 로 시작합니다. 빈 구간이 모자라면 `legacy plan not replaced, no free run of N clusters` 를 남기고 다음 서비스 시작 때만 다시 시도합니다. 이 교체는 파일을 옮기지 않고 게임의 상태도 바꾸지 않으며, 실제 이동은 정기 재적용이 평소 한도(디스크 유휴, 게임 미실행, 하루 예산) 안에서 합니다. 목표가 바뀌므로 바로 다음 배치 검사가 `layout degraded` 를 남기고 다시 적용할 수 있습니다. 물리 조각이 16클러스터 이동 단위에 맞지 않는 스파스 파일은 새 계획에서 통째로 빠지며 `<게임>: N sparse file(s) left out of the plan, their pieces do not fit the 16-cluster move unit` 로 남습니다.
- **통째 배치 (`auto.relocate_layout`).** 기본값은 `whole_file` 입니다. `ranges` 는 위에서 설명한 배치입니다. `whole_file` 이면 계획이 플레이가 읽은 조각만이 아니라, 고른 파일을 처음 읽은 순서대로 파일 전체를 한 조각으로 존에 놓습니다. 파일을 고르는 조건은 계획이 그 파일에서 읽는 양의 2배 이하 크기이고, 압축·암호화된 파일이 아니고, 게임이 스스로 다시 쓰는 파일이 아니고, 구멍이 없는 것입니다(구멍이 있는 스파스 파일은 제자리에 둡니다). 처음 읽은 순서대로 존이 찰 때까지 담고(존은 `max_zone_mib` 이하), 그 뒤의 파일은 제자리에 둡니다(이 절에서 제자리에 둔다는 것은 옮기지 않고 지금 있는 자리에 그대로 둔다는 뜻입니다). 하루 전체 예산(`max_relocate_gib_per_day`, 0 이 아닐 때)보다 큰 파일도 제자리에 둡니다. 한 PC 에서 Windows 예약 드라이브 최적화가 켜진 하드디스크의 `ranges` 배치가 되돌려져 다시 놓기가 되풀이되는 것이 관찰됐습니다. `whole_file` 배치는 시험 파일과 게임 하나에서 최적화의 조각 모음 단계 뒤에도 남았지만, 빈 공간 통합 단계가 끝난 뒤 상태는 확인하지 못했고 로딩 시간에 주는 효과도 재지 않았습니다. `config.json` 에 `auto.relocate_layout` 로 `ranges` 가 적혀 있으면 그 값을 따릅니다.
  - **같은 배치를 되풀이해 다시 놓으면 쉼 (두 방식 모두).** 원본 파일이 그대로인데 서비스가 이미 놓았던 조각이 제자리를 잃어 그것을 다시 옮긴 회차를 셉니다. 놓았던 조각은 그 계획 아래 저널에 `done` 으로 기록된 작업이고, 예전 계획이 남은 부분만 다시 계획한 계획이면 거기에 더해 그 계획이 이미 제자리에 있어 그대로 둔 조각 (`in_place_bytes` 로 크기를 적고 작업으로 들어 있음) 입니다. 서비스가 다시 계획할 때 그 조각이 지금 어디 있는지 한 번 확인해, 계획이 둔 자리에 없는 양이 64 MiB (하루 재배치 횟수를 세는 최소량과 같음) 이상이면 그 재계획 뒤의 첫 이동을 한 회차로 셉니다. 새 계획 후보와는 견주지 않으므로 배치 방식, 트레이스, 가변 표시가 바뀌어 후보가 달라진 것만으로는 세지 않습니다. 세는 경우는 둘입니다: 바이트를 옮긴 정기 재적용 (배치 검사가 적용된 배치의 풀림을 확인한 것, 존을 다른 파일이 차지해 정기 재적용이 넘긴 뒤의 첫 이동 포함), 그리고 남은 부분만 다시 계획한 뒤나 적용 도중 존이 막혀 치운 계획을 다시 계획한 뒤의 첫 이동 중 위 확인에서 잃은 것이 나온 경우. 세지 않는 것: 서비스가 놓은 조각이 모두 그대로인 재계획, 게임의 처음 배치 (여러 날이 걸려도), 읽지 못한 파일이나 게임이 다시 쓰는 파일을 빼고 다시 계획한 것, 새 계획으로의 이동. 회당 쓰기 상한이나 취소로 여러 번에 나뉜 회차는 서비스를 다시 시작해도 한 번으로 세고, 나중 회차가 시작할 때 옮길 양이 앞 회차가 남긴 양보다 크면 이미 끝낸 조각이 제자리를 잃은 것이라 그 회차를 새 회차로 셉니다. 7일 안에 3회가 되면 그 게임의 자동 재배치와 재적용을 쉽니다. 로그에는 `<게임>: reapply paused after N unchanged-source rounds in 7 days; ...` 한 줄이 남고, 게임 상태 (`auto_status.json`) 에는 다른 표시 뒤에 `reapply paused after 3 unchanged-source rounds in 7 days` 가 붙고, 트레이에는 짧은 설명으로 보입니다. 예열은 계속합니다. 원본 파일이 바뀌어 (10분마다 확인) 다시 계획하거나, 새 계획이 옛 계획을 대신하거나 (예: 존 확장, 통째 계획으로의 이행), 게임의 배치 방식 설정이 바뀌거나, 7일 창의 횟수가 3회 미만이 되면 쉼이 풀립니다. 존 점유로 남은 부분만 다시 계획하는 것으로는 풀리지 않습니다. 원본이 바뀌어 풀리면 새 계획을 설정의 배치 방식 (기본 `whole_file`) 으로 만들고, 7일이 지나 풀리면 지금 계획의 방식으로 이어 가며 설정이 `whole_file` 이면 범위 계획인 게임은 끝낸 뒤 통째 계획으로 이행됩니다. 하루 한도는 바꾸지 않고, 수동 `aster apply`·`aster revert` 는 쉬지 않습니다.
  - **`whole_file` 일 때 달라지는 것.** 새 계획, 업데이트나 존 확장 뒤 다시 만드는 계획이 이 배치를 씁니다. 적용 전 확인에서 존이 차지된 것이 드러나 남은 부분만 다시 계획하는 것은 다시 계획하는 계획의 방식을 이어 가므로, 범위 계획으로 재배치 중인 게임은 원본이 바뀌거나 재배치를 마칠 때까지 범위 방식으로 남습니다. 적용 도중 존이 막혀 계획을 치우면 그 자리에 다시 만드는 계획은 설정의 방식을 따르고, 가변 파일 때문에 다시 만드는 계획도 같습니다. 배치 검사는 놓은 파일마다 한 조각으로 존 안에 있는지 봅니다. 한 번의 쓰기 상한(2 GiB, SMR 디스크는 1 GiB)보다 큰 파일도 한 회에 끝까지 옮기되, 하루 남은 예산을 넘기지는 않습니다. 오늘 남은 양보다 큰 파일은 다음 날로 미루고 그동안 작은 파일은 계속 옮깁니다. `max_relocate_gib_per_day` 가 0(무제한)이면 한 회에 첫 파일 크기만큼 쓸 수 있습니다. 작업자 하나가 파일 하나를 맡아 끝내고, 그 파일의 남은 양만큼 예산을 잡아 둘 수 있을 때만 시작하므로 `relocate_parallel` 이 1보다 커도 상한 때문에 반쯤 옮겨진 채 남는 파일이 없습니다. 예열 예산은 `ranges` 때와 거의 같습니다. 드라이브 최적화가 끝난 직후에는 통째 계획이 있는 게임의 배치 검사를 앞당깁니다(게임 실행 중이거나 디스크가 바쁜 것 같은 평소 조건은 그대로). 범위 계획인 게임은 앞당기지 않습니다. 그 배치는 최적화가 되돌릴 것으로 보여(아래 "80 MiB 의 근거" 참고) 같은 파일에 하루 한도를 되풀이해 쓰게 되기 때문입니다.
  - **큰 조각.** 통째로 고르지 않은 파일(계획이 그 파일에서 읽는 양의 2배보다 큼)도 일부를 존에 놓을 수 있습니다. 파일을 처음부터 80 MiB(16 클러스터 배수로 올림) 길이의 구간으로 나누고, 끝에 남는 그보다 짧은 구간은 쓰지 않습니다. 계획이 읽는 바이트가 구간의 절반 이상인 구간을 고르고, 이웃한 구간은 하나로 합치므로 조각은 모두 80 MiB 이상입니다. 조각은 하나씩 한 조각으로 존에 놓이며, 통째 파일과 함께 처음 읽은 순서대로 섞입니다. 파일의 나머지는 몇 조각이든 제자리에 두고 크기를 제한하지 않습니다. 압축·암호화된 파일, 게임이 다시 쓰는 파일, 스파스 파일은 이렇게 나누지 않고, 하루 전체 예산보다 큰 조각도 놓지 않습니다. 배치 검사는 조각마다 존 안에서 한 조각인지 보고, 조각은 통째 파일처럼 한 회에 끝까지 옮깁니다(조각이 여러 개인 파일은 파일 하나를 한 덩어리로 끝냅니다). `ranges` 는 이 중 어느 것도 쓰지 않습니다.
    - **80 MiB 의 근거.** 재 본 효과가 아니라 이 PC 에서 한 시험입니다. 조각 크기가 서로 다른 시험 파일을 두고 예약 Windows 드라이브 최적화를 46분 넘게 돌렸습니다. 1~56 MiB 조각은 56개 중 1개만 제자리에 남고 나머지는 한 조각으로 모여 옮겨졌고, 64 MiB 조각은 9개 중 6개, 80 MiB 조각은 9개 중 9개, 128 MiB 조각은 10개 중 10개가 그대로 남았습니다. 처음부터 한 조각인 파일도 그대로였습니다. 큰 조각 하나와 1 MiB 조각 여러 개가 섞인 파일은 작은 조각만 모이고 큰 조각은 남았습니다. 64 MiB 는 경계라 쓰지 않습니다. 끝까지 돈 최적화가 실제 게임 폴더에 하는 일은 아직 보지 못했고, 로딩 시간에 주는 효과도 재지 않았습니다.
    - **알아 둘 점.** 한 조각이던 파일에서 구간을 떼어 내면 그 파일은 여러 조각이 됩니다. 존 밖에 남는 부분은 예약 최적화가 모을 수 있고, 시험에서처럼 존 안의 큰 조각은 그대로 남을 것으로 봅니다.
  - **게임별 배치 방식 (`games[].layout`).** 게임마다 `config.json` 에 자기 `layout`(`whole_file` 또는 `ranges`)을 둘 수 있습니다. 그 게임에 한해 `auto.relocate_layout` 보다 우선하고, 없으면 전역 설정을 따릅니다. 계획을 만들 때, 범위 계획이 있는 게임을 옮길 때, 놓을 파일이 없는 게임의 다시 적용을 쉴지 정할 때 그 게임의 방식을 씁니다. 이미 있는 계획의 이동·검사·다시 적용·부분 재계획은 그 계획에 적힌 표지를 따르므로, 키를 지워도 이미 있는 통째 계획은 범위 계획으로 돌아가지 않습니다. 재배치가 정책으로 막힌 게임(예열만, 일시 중지)은 `layout` 이 `whole_file` 이어도 통째 계획을 만들지 않고 범위 계획을 만듭니다. 그래서 나중에 정책을 풀어도 통째로 옮기는 일이 저절로 시작되지 않습니다(그때는 범위 계획 게임처럼 재배치되고, 그 뒤 통째 계획으로 옮겨질 수 있습니다). 전역 설정의 기본값은 `whole_file` 입니다.
  - **범위 계획이 있는 게임을 옮기기.** `whole_file` 이면 서비스를 시작할 때마다 한 번, 범위 계획으로 재배치를 마친 게임을 가장 최근에 플레이한 것부터 같은 읽기 목록으로 통째 계획을 만들어 새 존에 놓습니다. 예전 존의 조각을 제자리에 고정하지 않습니다. 고정하면 파일이 조각난 채로 남기 때문입니다. 제자리에 두는 파일의 조각은 예전 존에 그대로 있고 되돌려 옮기지 않으며, 예약 드라이브 최적화가 나중에 모을 수 있습니다. 게임은 재배치 단계로 돌아가고, 평소 재배치가 게임을 하나씩 최근에 플레이한 순서로 같은 한가함·하루 한도·쓰기 상한 조건 안에서 옮깁니다. 옮기는 동안 그 게임의 정기 배치 검사는 쉽니다. 예열과 게임 시작은 평소처럼 동작하고, 게임이 실행 중이면 아무것도 건드리지 않습니다. 존만큼 긴 빈 구간이 없으면 한도를 가장 긴 빈 구간으로 줄여 뒤의 파일을 제자리에 두고, 고른 파일이 없으면 이미 적용된 계획을 그대로 두고, `whole_file` 인 동안 그 게임은 재배치도 다시 적용도 하지 않고 예열만 합니다(고른 파일이 없는 새 계획도 범위 계획으로 바꾸지 않고 아무것도 옮기지 않습니다). 이전 저널은 새 저널 옆에 되돌릴 수 있는 기록으로 남습니다.
  - **`ranges` 로 되돌리기.** 새 계획은 다시 범위 방식입니다. 이미 만들어진 통째 계획은 그대로 두고 범위 계획으로 돌리지 않습니다(설정을 바꾸는 순간 대량 이동이 일어나지 않게). 업데이트·존 확장·계획 다시 만들기가 새 계획을 만들 때 바뀝니다. 한 게임을 손으로 되돌리려면 먼저 게임 탭에서 그 게임을 **예열만** 으로 두어 서비스가 배치를 다시 적용하지 않게 한 뒤, 저널을 되돌립니다(**되돌리기**, 또는 관리자 권한으로 연 명령 창에서 `aster revert --journal <ProgramData>\AsterCache\journals\<게임>.jsonl --allowed-root <게임 폴더> --execute`). 되돌리기는 조각을 원래 자리로 옮기며, 그 사이 다른 파일이 원래 자리를 차지했으면 그 조각은 건너뛰어 파일이 이전보다 더 조각날 수 있습니다. 그 뒤 게임은 예열만 하는 상태로 남습니다. `plans\<게임>.plan.json` 을 지워도 서비스가 범위 방식으로 다시 배치하지 않습니다(배치됨으로 표시된 게임은 다시 계획하지 않습니다). 범위 계획은 `auto.relocate_layout` 이 `ranges` 인 채로 게임 업데이트가 계획을 다시 만들게 할 때만 돌아옵니다. 통째 계획이 있는 동안에는 그 배치를 다시 적용하려는 것이 아니라면 정책을 `inherit` 로 돌리지 마십시오.
  - **로그.** `<게임>: whole-file plan, N file(s) X MiB placed in the zone, M file(s) Y MiB hot left in place (<사유>), zone Z MiB of L MiB, K file(s) left in place because of the zone limit, P large piece(s) Q MiB placed in the zone` (사유별 파일 수: `mostly_cold` 는 계획이 그 파일에서 읽는 양의 2배보다 큰 파일, `zone_full` 은 존이 찬 경우, `unmovable` 은 압축·암호화된 파일처럼 재배치가 옮기지 않는 파일, `volatile` 은 게임이 다시 쓰는 파일, `sparse_holes` 는 구멍이 있는 스파스 파일, `over_daily_limit` 는 하루 전체 예산보다 큰 파일), 범위 계획을 옮길 때 `<게임>: plan rebuilt for whole-file placement, N file(s) X MiB whole, M left in place (<사유>), Y MiB to move; old zone pieces of in-place files stay where they are, P large piece(s) Q MiB placed in the zone`, 회당 상한에서 멈췄을 때 `<게임>: whole-file placement in progress, A of B file(s) in one piece, P% of their clusters inside the zone, Y MiB left to move`, 끝나면 `<게임>: whole-file placement complete, A of B file(s) in one piece inside the zone`(큰 조각도 하나로 셈), `drive optimization ended at ..., layout check brought forward for N game(s)`, `<게임>: no file qualifies for whole-file placement, the game is not relocated (prewarm only)` (범위 계획이 적용돼 있었으면 `; the plan already applied is left as it is` 가 붙음), `<게임>: free space is shorter than the whole-file zone (X MiB), limit lowered to Y MiB, later files stay in place`, 그리고 `auto relocation moved ...` 줄 끝의 `, N file(s) larger than the remaining daily write budget deferred`.
- **시간대.** `auto.relocate_hours` 가 있으면 새 재배치와 정기 재적용은 그 현지 시각 안에서만 시작합니다. 이미 시작해 저널이 남은 재배치는 시간대 밖에서도 끝냅니다.
- **설정.** `auto.relocate`, `idle_seconds`, `relocate_hours`, `max_relocations_per_day`, `max_zone_mib`, `max_relocate_gib_per_day`, `relocate_layout`. 쓰는 양은 [하드디스크에 미치는 영향](GAME_GUIDE.ko.md#하드디스크에-미치는-영향)에 있습니다.
- **로그.** `<게임>: auto relocation done`, `[ERROR] <게임>: auto relocation stopped: ...`

<details>
<summary>세부: 상한, 중단되거나 나뉜 이동, 게임 업데이트</summary>

**상한**

- 존 크기는 핫 데이터 × 1.1 이며 `max_zone_mib` 를 넘지 않습니다.
- 24시간에 최대 `max_relocations_per_day`번만 재배치하며 재배치를 시작한 시각부터 셉니다. 64 MiB 미만 회차는 세지 않지만 바이트 예산에는 더합니다.
- 게임마다 자동 첫 재배치는 한 번입니다. 이후 유지는 [유지](#5-유지)의 주기 검사가 맡습니다.
- `auto.relocate` 는 수동 등록 게임에도 적용됩니다. 원치 않으면 `auto.relocate` 를 끄거나, 게임 탭에서 그 게임을 일시 중지하거나 정책을 **예열만** 또는 **끔**으로 두십시오. `auto.ignore_exes` 는 다시 등록되지 않게 할 뿐 이미 등록된 게임을 멈추지는 않습니다.

**중단되거나 나뉜 이동**

- 이동 중 게임이 시작되면 이동 중이던 조각을 끝내고 멈추며, 나중에 저널로 이어갑니다.
- 옮길 존을 다른 파일이 차지했거나 계획이 바뀌면, 이미 옮긴 부분은 다시 옮기지 않고 남은 부분만 새 빈 영역으로 다시 계획합니다.
- 새 존(또는 옮긴 조각 바로 뒤가 비어 있지 않을 때의 남은 부분)은 고른 빈 구간의 맨 앞에 두지 않습니다. 구간이 필요한 길이보다 1 GiB 이상 길면, 남는 길이의 절반(최대 4 GiB)만큼 뒤에서 시작하며 4 클러스터(클러스터가 4 KiB 이면 16 KiB)의 배수로 맞춥니다. 다른 프로그램의 새 파일은 큰 빈 구간의 앞쪽부터 채워지는 경향이 있어, 이 여유가 그 프로그램이 몇 시간 쓰는 동안 존이 겹치지 않게 합니다(한 프로그램이 시간당 약 0.8 GiB 를 쓰는 것을 실측). 더 짧은 구간은 존을 구간 시작에 둡니다. 로그: `<게임>: new zone placed N clusters after the free run start (run R, zone Z) ...`, 남은 부분이면 `<게임>: new place leaves N clusters after the free run start (run R, zone Z) ...`.
- 존이 점유됐다는 사유가 되풀이되면 보류된 재시도는 30분씩 기다립니다. 같은 종류의 사유(`zone_not_free` 또는 `zone region appears occupied`)가 3번째 연속이 되면, 재시도마다 새 계획이 만들어져도 기다림을 두 배씩(1시간, 2시간) 늘려 최대 4시간까지 늘리며, 완전히 멈추지는 않습니다. 한 번에 64 MiB 이상 옮기면 횟수를 지우고, 다른 사유는 따로 셉니다. 다른 계획의 예약과 겹친 사유(`reserved by another plan`)는 세지 않습니다. 로그: `<게임>: zone occupied N times in a row, another program keeps writing to this drive, hold extended to M min`. 존이 점유된 것을 볼 때마다 `<게임>: zone rejected at LCN L: <위치> (zone Z, moved up to P)` 한 줄로 어디였는지(존 앞 여유 안, 옮긴 마지막 조각 바로 뒤, 존 안 그 밖, 존 밖) 남깁니다.
- 존이 이미 최대 크기인 계획은 다시 계획하지 않으며, 화면에는 작업이 자동으로 이어진다고 표시합니다.
- 게임이 꺼진 상태에서 데이터 검사가 실패하거나 오류가 나면 저널대로 되돌리고 실패로 기록합니다. 되돌리는 것은 그 자동 적용분만입니다.

**게임 업데이트**

- 재배치 뒤 게임 파일의 크기나 수정 시각이 바뀌면 옛 계획을 `.stale` 로 치우고(10분마다 확인) 단계를 발견으로 되돌립니다. 작은 업데이트는 바뀐 파일의 범위만 트레이스에서 빼고 나머지는 유지합니다. 바뀐 파일이 계획된 데이터의 절반 미만이면서 전체 트레이스 바이트의 절반 미만일 때만 작은 업데이트로 봅니다. 더 큰 변경은 트레이스 전체도 치웁니다. 안티치트가 트레이스를 금지한 게임은 쓸 수 있는 트레이스를 유지합니다.
- 10분마다 하는 확인은 게임 실행 파일과 가장 큰 파일 3개만 보지 않고 계획의 지문 전체를 비교하므로, 작은 파일만 고치는 업데이트도 잡습니다. 게임이 스스로 다시 쓰는 파일은 비교에서 뺍니다. 이름 규칙에 걸리는 가변 파일과, 트레이스가 실행 사이에 바뀐다고 표시한 파일(`<게임>.trace.volatile.json`)입니다. 계획을 만든 뒤에야 표시된 파일은 업데이트로 보지 않습니다. 대가로, 표시된 실제 패치 파일만 고친 업데이트는 업데이트로 잡히지 않고 그 파일은 계획에서 빠진 채로 남습니다(존 적중률이 조금 줄 수 있음).
- 끝난 계획이 그 뒤 트레이스가 가변으로 표시한 파일을 아직 들고 있으면, 가변 이름 확인과 같은 경로(`.extend`, 같은 존, 같은 유휴·일일 상한 조건)로 한 번 다시 계획하며 새 계획에는 표시된 파일이 빠집니다. 계획은 반영한 표시 수(`volatile_marks`)를 기록하므로, 가변 표시 목록이 바뀌고 표시가 더 늘었을 때만 다시 확인합니다. 읽지 못해 보류로 남은 파일(`held_files`)은 다시 계획해도 남으므로 세지 않습니다. 자동 재배치를 끈 설정에서는 이 다시 계획을 하지 않습니다. 로그 줄: `<게임>: plan holds N file(s) the trace marked as rewritten by the game (<사유>), plan set aside as .extend, will plan again without them (same zone)`.
- 배치 검사와 재적용 직전 검사는 지금도 가변 이름 규칙만으로 비교하므로, 표시된 파일이 든 계획에서 그 파일이 바뀌면 위의 한 번 다시 계획으로 계획에서 빠질 때까지 "바뀜"으로 나옵니다.
- 다음 실행 때 이전 존 위치를 먼저 시도하며 다시 트레이스·재배치합니다.

**그 밖에**

- 옮기는 I/O 에는 낮은 I/O 우선순위 힌트(`FileIoPriorityHintInfo` Low)를 걸었습니다. 문서가 커널의 이동 복사 I/O 에 이 힌트가 적용된다고 보장하지 않으며, 아직 측정하지 않았습니다.
- 옮긴 뒤에는(기록이 있으면 실패했어도) 곧바로 그 존을 예열합니다.
- 다른 로그 줄: `<게임>: partially applied plan replanned, the parts already moved are kept`.

</details>

### 4. 예열

- **언제.** 서비스가 시작할 때, 지원 런처가 뜰 때, 게임이 끝난 뒤.
- **무엇을.** 최근에 플레이한 게임의 존을 RAM 예산 안에서 64 MiB 묶음으로 RAM 에 읽어 둡니다.
- **하지 않는 것.** 게임이 시작된 뒤에도 계속 읽지 않습니다. 어느 게임이든 시작되면 지금 예열 중인 게임도 포함해 다음 묶음 경계에서 멈춥니다.
- **설정.** `auto.full_prewarm`, `auto.full_prewarm_max_mib`, `auto.engine_profiles`, `prewarm_recent`, `prewarm.max_cache_mib`, `prewarm.min_free_ram_mib`, `auto.startup_warm_max_mib`, `auto.rewarm_after_exit_min`.
- **로그.** `<게임>: prewarm done (<사유>): N MiB requested, ... in S s = R hint MB/s, ...`(`hint MB/s` 는 요청한 MiB 를 걸린 초로 나눈 값)

<details>
<summary>세부: 시점, 순서, 예산, 읽기, 기록이 없는 게임</summary>

**정확한 시점**

- 게임 종료는 등록 실행 파일이 모두 사라진 뒤 60초 동안 다시 뜨지 않을 때로 봅니다(런처에서 게임 본체로 넘어가는 틈을 보호). 설치 폴더 아래 미등록 프로세스는 종료를 미루지 않습니다.
- 게임이 끝난 뒤 같은 물리 디스크에서는 재배치, SSD 계층 적용, 새 트레이스에 따른 예열과 재예열을 60초와 `auto.rewarm_after_exit_min`(분) 중 긴 값이 지난 뒤에 시작합니다.
- **게임 전환.** 방금 끈 게임의 60초 종료 확인이 진행되는 동안에도, 그 디스크에 등록된 게임이 이 확인을 기다리는 게임뿐이면 런처가 시작한 예열(트리거 예열)은 읽을 수 있습니다. 그 게임이 다시 뜨거나 다른 게임이 시작하면 예열은 바로 취소됩니다. 게임이 실제로 실행 중일 때는 달라지지 않습니다. 그 디스크에 새 읽기를 하지 않습니다. 재예열 점검, 보충, 재배치는 위처럼 계속 기다립니다.
- 게임이 실행 중이라 거절된 트리거 예열은 기록해 둡니다. 서비스가 그 게임의 프로세스가 사라진 것을 처음 본 때(프로세스는 30초마다 확인합니다) 런처가 아직 실행 중이고 거절된 지 30분이 지나지 않았으면 한 번 다시 시도합니다(로그: `<게임>: retrying the refused trigger prewarm (<exe>) now that the blocking game is gone`). 다시 거절되면 보통의 대기 규칙을 따릅니다. 실제 플레이에서 어떻게 동작하는지는 아직 확인하지 않았습니다.
- **런처의 예열이 먼저입니다.** 런처가 실제로 읽을 예열을 시작하면, 같은 디스크에서 배경으로 도는 다른 게임의 예열(재예열, 보충, 대기 재시도)은 지금 내는 읽기가 끝나는 대로 멈추고 런처의 게임을 먼저 읽습니다(로그: `<게임>: prewarm cancelled (...) after N MiB (preempted by trigger prewarm)`). 멈춘 보충은 나중에 읽던 자리부터 이어 가고, 멈춘 재예열이나 재시도는 보통의 재시도로 돌아갑니다. 멈출 수 없는 읽기를 기다려야 하면 `<게임>: trigger prewarm waited N s for <게임>` 을 남깁니다(1초 이상 기다렸을 때만). 어차피 모두 건너뛸 게임(쿨다운, 그 디스크에서 게임 실행 중)의 런처 예열은 다른 읽기를 기다리지 않고 건너뜀 줄을 바로 남깁니다. 기록이 없는 게임의 예열은 이렇게 멈추지 않습니다. 시험 PC 의 서비스 로그에서 런처의 예열이 다른 게임의 210초짜리 보충 뒤에서 2분 6초를 기다린 적이 있어 넣었으며, 실제 플레이에서 지금은 바로 시작하는지는 확인하지 않았습니다.
- **런처의 예열은 보정 읽기를 하지 않습니다.** 런처가 시작한 예열은 ORBIT 이 예열 전에 하는 짧은 디스크 속도 읽기를 더는 하지 않습니다. 다른 예열은 그 읽기를 5초로 제한하고, 넘으면 표본을 버립니다(로그: `<게임>: device calibration stopped at the 5 s limit, sample discarded`, `prewarm phases` 줄에 `calibration N s` 가 나오고 상한에 닿으면 `(capped)` 가 붙습니다).
- **쿨다운.** `prewarm.cooldown_min`(기본 30분)은 같은 게임을 너무 빨리 다시 예열하지 않게 합니다. 쿨다운 안에서는 먼저 재예열 점검과 같은 종류의 표본을 읽습니다(그 디스크에서 게임이 실행 중이 아닐 때만, 표본은 5분까지 다시 씀). 표본이 캐시가 식었음을 보이면(재부팅이 그렇게 만듭니다) 쿨다운을 무시하고 예열합니다(로그: `<게임>: cooldown ignored, the cache is cold [service start]`, 또는 `[trigger <exe>]`). 캐시가 따뜻하거나 표본을 읽을 수 없으면 전처럼 쿨다운이 적용됩니다(`<게임>: prewarm skipped (cooldown (N min left)) [...]`). 기록이 없는 게임은 표본이 없어 쿨다운이 그대로 적용됩니다.

**순서와 예산**

- 최근에 플레이한 게임부터, 지금 시간대에 자주 한 게임을 앞세웁니다. 런처 등으로 최근 트리거된 게임은 6시간 동안 먼저 예열합니다.
- `prewarm_recent` 가 0 이면 예산 안에 드는 만큼의 최근 게임을, 1~32 면 그 개수만큼만 예열합니다.
- 예산은 물리 RAM 의 절반(또는 `prewarm.max_cache_mib`)과, 가용 RAM 에서 `min_free_ram_mib` 을 뺀 값 중 작은 값입니다.
- 읽기 직전에 가용 메모리를 다시 잽니다. 목록이 더는 들어가지 않으면 들어가는 앞쪽 부분을 읽고 나머지는 나중에 보충합니다. 읽기 직전의 마지막 확인(전체 목록이 아직 들어가는지)과 앞쪽 부분을 고를 때 모두 예비량(`prewarm.min_free_ram_mib`, 기본 4,096 MiB) 위에 256 MiB 여유를 더 두므로, 가용 메모리가 조금 변해도 읽기가 취소되지 않습니다. 예비량과 캐시 예산은 그대로입니다.
- 게임이 부분 예열 상태면 예산을 약 30초마다 다시 계산합니다. 게임마다 쓰는 크기 값(전체 크기와 관찰량)은 입력 파일(계획, 목록, 예열 전용 목록, 가변 파일 목록(게임이 쓰기도 하는 파일의 목록), 원시·부팅 추적)과 그 게임의 설정이 같으면 최대 10분 동안 다시 쓰므로, 매번 계획 파일을 통째로 읽지 않습니다. 예열이 실제로 읽을 범위를 정하는 계획은 매번 새로 읽습니다. 크기 값을 다시 쓰지 않던 때에는 시험 PC 에서 부분 예열 게임이 있는 유휴 상태 450초 동안 CPU 100.7초를 쓰고 30초마다 몰려 1,468 MiB 를 읽었습니다. 다시 쓰는 지금의 값은 재지 않았습니다. 게임 업데이트로 목록의 파일 크기가 바뀌면 추정에 최대 10분 늦게 나타날 수 있습니다.
- 게임 사이의 캐시 예산은 각 게임의 실제 예열 목록 크기로 나눕니다. 일부만 재배치된 계획은 아직 옮길 부분만 담고 있는데, 예전에는 핫 집합 전체 크기로 셌기 때문에 그 게임이 읽는 양보다 큰 캐시 예산을 받았습니다.
- 게임이 뜬 뒤에 남는 양. 게임은 실행 뒤 자기 메모리를 잡고(한 게임의 기록된 세 번의 플레이에서 9~10 GiB), 그 메모리는 대기 목록에서, 곧 예열이 채운 캐시에서 나옵니다. 서비스는 플레이마다 시작 때 가용 RAM 과 시작 뒤 10분 안의 최소 가용 RAM 을 기록하고(`play_samples.json` 의 `minAvailableRamMib`, 로그 `play record:` 줄의 `min RAM`), 그 차이를 게임이 잡는 메모리로 봅니다. 시작부터 10분을 모두 관찰했고 메모리가 바닥나지 않은(최소 가용 1,024 MiB 이상) 플레이만 세며, 값은 그 플레이의 시작 가용을 넘지 않게 자릅니다. 그런 플레이가 3번 이상이면 최근 세 번의 중앙값, 2번이면 작은 쪽, 1번이면 예전 예비와 게임 메모리를 반영한 예비의 중간이 되는 값을 씁니다. 한 번의 플레이에는 다른 프로그램의 메모리나 겹친 게임이 섞일 수 있기 때문입니다. 이런 기록이 있는 게임은 예열 예비가 `max(min_free_ram_mib, 4,096 MiB)` 대신 `max(min_free_ram_mib, 게임 메모리 + 1,024 MiB)` 가 되고, 모든 게임이 나눠 쓰는 캐시 예산도 가용 RAM 에서 곧 플레이할 가능성이 가장 높은 게임(아래 순서의 첫 게임)의 그 예비를 뺀 값으로 줄입니다. 그 넘는 예열은 게임이 뜰 때 밀려나기 때문입니다. 어느 상한도 게임 메모리를 반영하지 않을 때의 절반 아래로는 내려가지 않습니다. 로드 초반에 게임이 읽는 앞부분은 밀려나기 전에 쓰이고, 잘못 배운 게임 메모리 값으로 인한 감소를 절반으로 제한하며, 상한이 0 이 되어 대기 재시도가 끝없이 도는 일을 막기 위해서입니다. 공유 예산은 등록된 게임이 하나라도 실행 중이면(그 게임의 메모리는 이미 가용에서 빠졌으므로) 게임 메모리를 반영하지 않고, 한 번의 점검 안에서 가용 RAM 의 잔 변동으로 흔들리지 않게 10초 동안 값을 유지합니다. 예열 로그에 `<게임>: game footprint F MiB (median of N plays), cap C MiB` 가 남습니다. 쓸 수 있는 기록이 없는 게임은 예전 예비와 예산 그대로입니다. 로딩에 미치는 효과는 아직 재지 않았습니다.
- 가장 나중에 만질 게임과 재배치 뒤 예열. 범위를 만진다는 것은 캐시된 페이지를 메모리에서 접근해 Windows 가 최근에 쓴 것으로 세도록 하는 일이며, 일부러 디스크에서 읽지는 않습니다. 사다리는 예열한 게임들의 캐시 범위를 정한 순서대로 만져, 나중에 만진 것이 나중에 밀려나게 하는 [SOLAR](SOLAR.ko.md)의 과정입니다. SOLAR 가 어느 게임의 캐시를 마지막에 만질지 정하고 재예열 점검이 따르는 예열한 게임의 순서는 이제 캐시 예산을 나누는 순위(최근성과 시간대 습관의 예열 점수)와 같아, 예산을 먼저 배정받는 게임이 가장 나중에 만져지는 게임이기도 합니다(예전에는 마지막 예열 시각 순, 순위가 없으면 지금도 그렇습니다). 다른 게임의 예열 스트림이 끝난 뒤 그 순서의 첫 게임을 한 번 더 만져 가장 나중에 밀려나게 하고, 그 게임의 표본이 식었으면 다음 재예열 점검을 앞당깁니다(게임 종료가 쓰는 것과 같은 당김이며 `auto.rewarm_after_exit_min` 이 0 이면 하지 않습니다). 로그는 `<게임>: ladder ordered, <게임> touched again after it as the first play priority` 입니다. 재배치 뒤(와 새 트레이스 뒤) 예열도 이제 재예열과 같은 캐시 예산 배정을 받습니다. 예전에는 제한 없이 돌아 합계가 예산을 넘을 수 있었습니다. 예산에 들지 못한 게임은 예산의 남은 양을 받습니다. 들어가는 양이 목록보다 작으면 스파스 속성 파일의 범위를 메모리 예열에서 먼저 뺍니다. 사다리가 만지지 못해 그 게임의 가장 오래된 페이지로 남아 먼저 밀려나기 때문이고, 그 양은 다른 파일의 범위가 받습니다. 재예열·사다리 표본, 보충, 고정 목록도 같은 범위를 건너뛰어 읽지 않은 범위 때문에 식었다고 판정하지 않습니다. 로그는 `<게임>: N MiB in sparse files left out of the memory prewarm, the ladder cannot touch them` 이고, 표시는 예열할 때마다 다시 판정하며 재배치 계획은 그대로입니다. 로딩에 미치는 효과는 아직 재지 않았습니다.
- 목록을 잘라야 하면 다음 순서로 먼저 남깁니다. (1) 게임이 쓰기도 하는 파일(존과 함께 옮기지 않고 별도의 예열 전용 목록에 둡니다)의 범위 중 플레이 초반에 처음 읽힌 것(로딩 경계, 곧 로딩 초반의 많은 읽기가 잦아드는 시점까지, 경계를 모르면 120초까지), (2) 관찰된 범위의 앞쪽 중 로딩 앞부분(tier0)만큼, (3) 블록 순위 목록(아래 "블록 순위 목록")이 있으면 그 블록(앞 단계와 겹치는 구간은 한 번만 셉니다), (4) 플레이에서 관찰된 나머지 범위, (5) 나머지 예열 전용 범위를 처음 읽힌 시각 순서로, (6) 추측한 범위. 가득 찬 존 밖에서 더한 범위([존 확장](#2-읽기-기록트레이스) 참고)는 (5) 에만 듭니다. 순위 목록이 없으면 (3) 이 비어 이전 순서와 같고, 목록이 전부 들어가면 자르지 않으므로 쓰이지 않습니다. (1) 의 초반 범위는 먼저 읽기도 합니다. 예전에는 목록 끝에 있어서 자를 때 가장 먼저 잘렸습니다.

**읽는 도중 메모리가 모자랄 때**

- 앞쪽 부분만 읽던 예열이 메모리를 잃으면(가용 메모리가 예비량 아래로 내려가거나 남은 예산이 더는 들어가지 않으면) 이제 읽은 것을 버리지 않습니다. 거기서 끝냅니다. 그 시점의 가용 메모리에 들어가는 양까지만 더 읽고 마무리하며, 읽은 양을 부분 예열(`prewarm_status.json` 의 `partial`, `warmed_mib`, `hot_mib`)로 남깁니다. 아직 아무것도 읽지 못했는데 256 MiB 미만만 들어갈 때, 그리고 읽기에 오류가 있었거나 ORBIT 이 순서를 바꾼 때는 전처럼 취소합니다(그때는 아무것도 남기지 않습니다). 로그: `<게임>: prewarm read the first N of M MiB, the rest does not fit in memory (available A MiB, reserve R MiB) [<사유>]` 다음에 평소의 `prewarm done (...): partial N/M MiB, the rest does not fit in memory: ...`.
- 보충 예열은 이제 들어가는 메모리가 이미 읽은 양보다 `max(256 MiB, 읽은 양의 5%)` 이상 클 때만, 또는 핫 집합의 남은 부분이 그보다 작으면 그 남은 부분만큼 클 때만 시작합니다. 어떤 창의 계획 목록이 창이 차기 전에 끝났으면 읽은 양 대신 그 창의 크기와 비교합니다. 같은 창으로는 같은 목록이 다시 나오기 때문입니다. 그때까지는 디스크에서 아무것도 읽지 않고 `<게임>: supplement waits for memory (read X MiB, room for Y MiB)` 를 읽은 양이 바뀔 때마다 한 번 남깁니다(이 경우에는 `read X MiB of a W MiB window whose plan list ended there`). 시작하면 이미 읽은 부분 다음부터 이어 읽으며, 기억해 둔 창이 지금 들어가는 양보다 커도 읽는 총량은 들어가는 양까지만입니다. 한도에 닿은 보충도 예열처럼 거기서 마무리하고(`<게임>: supplement prewarm read the first X MiB of Y MiB, the rest does not fit in memory (...)`), 다음 보충이 그 뒤부터 이어 읽습니다. 이 규칙은 시험 PC 의 서비스 로그(2026-11-14 에 읽음)에서 본 되풀이 때문에 넣었습니다. 목록이 한도에 가까운 게임의 보충이 계속 취소됐습니다(Call of Duty 는 86회, 그중 79회는 기록에 아무것도 더하지 못함). 그 79회가 읽기로 받아들여진 양은 합쳐 51,624 MiB 이며, 헛되이 HDD 에서 읽힌 양의 상한입니다. 실제 플레이에서 로딩에 미치는 영향은 재지 않았습니다.
- 목록 전체를 읽던 예열(보충 예열 포함)이 메모리 때문에 멈추면, 같은 회에서 한 번만 그 시점의 가용 메모리에 들어가는 앞쪽 부분으로 줄여 다시 읽습니다. 그 뒤는 앞쪽 부분만 읽던 예열과 똑같이 다룹니다. 이미 읽은 부분은 캐시에 있으므로 다시 읽는 데 디스크를 거의 쓰지 않습니다. 게임 시작처럼 다른 이유로 멈춘 때는 다시 읽지 않고, 256 MiB 미만만 들어가면 전처럼 취소합니다. 로그: `<게임>: prewarm stopped by memory before the full list was read; reading the first N MiB of M MiB instead`(보충 예열은 `supplement prewarm stopped by memory ...`).
- 메모리 때문에 멈추면(아무것도 남기지 않은 경우도 포함) 보충과 재시도(대기 목록 재시도, 재예열 점검)는 2분 동안 그 게임을 건드리지 않습니다. 런처 트리거와 서비스 시작은 기다리지 않습니다. 멈추기 전에 읽은 것이 있으면 대기 중인 재시도는 보통 주기(`rewarm_minutes`, 기본 10분) 대신 2분 뒤로 당겨지고, 아무것도 읽지 못하고 멈췄으면 보통 주기를 유지합니다. 부분 예열을 남긴 게임은 대기 목록에서 빠지지 않고 남으며, 가용 메모리가 이미 읽은 양 + 256 MiB + 예비량을 넘으면 나머지를 읽습니다.
- 아직 취소하는 경우의 로그: `prewarm cancelled (...) after N MiB (memory reserve: ...)`(또는 `(memory budget: ...)`) 다음에 `<게임>: prewarm stopped by memory; kept the N of M MiB read as partial`, 그리고 `<게임>: prewarm skipped (stopped by memory less than 2 min ago) [<사유>]`. `prewarm done` 줄은 `room X MiB`(또는 `unlimited`)와 `available Y MiB` 로 끝나고 `rewarm check: cold (...)` 줄은 `available N MiB` 를 담고 있으므로, 그 시점의 메모리를 로그로 알 수 있습니다.
- 목록을 끝까지 읽은 예열은 더 이상 `partial` 로 기록되지 않습니다. 저장된 계획이 아직 옮기지 못한 부분만 담고 있는 게임에서, 읽을 양에 파일의 30% 이상이 필요한 파일의 전체 읽기가 더해져 있었습니다(한 게임에서 배정 1,164 MiB 에 대해 1,306 MiB). 그래서 목록을 모두 읽고도 `partial` 로 기록되고 `rewarm check: the rest of the hot set is not read yet` 가 되풀이됐습니다. 이제 예열 목록을 배정량과 같은 기준으로 세므로 그 전체 읽기가 더해지지 않고, `partial` 은 메모리나 캐시 예산이 실제로 모자랄 때만 나타납니다. `prewarm_status.json` 에 남은 `partial` 은 다음에 예열이 목록 전체를 읽을 때 지워집니다. 로딩에 미치는 영향은 재지 않았습니다.

**읽기**

- 스파스 속성 파일은 매핑 대신 미리 읽기 힌트 없는 일반 버퍼드 읽기로, 같은 순서로 읽습니다. 있었다면 `prewarm done` 줄 끝에 `, K MiB of sparse files by buffered read` 가 붙습니다([SOLAR](SOLAR.ko.md)).
- 디스크 물리 위치 순서로 읽습니다. 묶음에 게임이 둘 이상이면 각 게임의 로딩 앞부분(tier0, 로딩 초반에 읽는 블록)을 최근 순서로 먼저 올리고, 그다음 게임별 존 전체를 읽습니다.
- 예열 목록의 각 범위는 실제 플레이에서 읽힌 범위인지 엔진 프로필로 추측한 범위인지 표시합니다. 예산이 모자라면 모든 게임의 관찰된 범위를 먼저 채우고 남는 예산을 추측 범위에 씁니다.
- 서비스 시작 때는 로딩 앞부분만 `auto.startup_warm_max_mib` 까지 읽고, 나머지는 디스크가 한가해진 뒤에 읽습니다. 어차피 건너뛸 게임(예: 쿨다운 중, 실행 중, 업데이트 뒤 지연 중)은 이 상한을 쓰지 않으므로 다음 게임이 그만큼을 받습니다.
- 관리 창에 `예열 중 x/y MB` 가 나오고, 예열이 끝나면 트레이 알림을 보냅니다(게임당 하루 1회).
- 다른 게임이 시작되면 묶음 경계에서 멈춥니다. 지금 예열 중인 게임이 시작되어도 멈추고 양보합니다(`auto.keep_stream_on_game_start`, 기본 `false`, `true` 면 끝까지 읽음, 실험용).
- **다른 읽기에 양보하기.** 핫 집합 예열(서비스 시작, 런처, 재예열, 보충), 기록이 없는 게임의 예열, 서비스 시작 때 로딩 앞부분 읽기의 읽기 스레드는 다른 프로그램이 같은 디스크를 읽는 동안 자기 I/O 우선순위를 낮음으로 내리고, 디스크가 한가해지면 보통으로 되돌립니다. 약 10초마다 1초 멈춰 자기 읽기 없이 디스크 처리량을 재며, 4 MiB/s 이상이거나 잴 수 없으면 바쁜 것으로 보아 낮은 우선순위로 읽습니다. 같은 디스크에서 다른 게임이 실행 중일 때의 규칙은 그대로입니다. 그때는 여전히 취소합니다. 런처가 시작한 예열이나 부팅 15분 안에 시작한 예열은 첫 10초 간격을 기다리지 않고 첫 묶음 전에 디스크를 한 번 재므로, 바로 양보할 수 있습니다. 디스크가 연속 3번 한가하면 멈춤 간격을 30초로 늘리고, 한가하지 않은 결과(바쁨, 표본 없음, 낡은 표본)가 한 번이라도 나오면 바로 10초로 돌아갑니다. 로그: `<게임>: prewarm yields to other disk activity (low I/O priority)`(읽기당 한 번), `<게임>: prewarm back to normal I/O priority after N.N s at low`(처음 돌아올 때만), 낮은 우선순위를 썼을 때는 핫 집합 예열의 `prewarm done` 줄 끝 `, yielded N.N s` 뒤에 `, read A MiB in S s at normal I/O priority and B MiB in T s at low (K switches)` 가 붙습니다. 같은 `, read ...` 꼬리(`yielded` 없이)가 그 예열의 `prewarm cancelled (...) after N MiB (<사유>)` 줄과 `load head prewarm done`·`cancelled` 줄 끝에도 붙습니다. 기록이 없는 게임의 예열과 보충(`supplement prewarm done`)에는 붙지 않습니다. 우선순위를 낮춰도 읽는 순서, 양, 취소 규칙은 같습니다.

**기록이 없는 게임**

- 작은 게임(폴더가 RAM 예산 안)은 폴더 전체를 `auto.full_prewarm_max_mib` 까지, 큰 게임은 엔진 프로필의 파일을 예열합니다.
- 등록이 사라진 게임은 예열하거나 고정하지 않습니다.
- 다른 로그 줄: `prewarm cancelled <사유>`, `<게임>: prewarm skipped (...)`, 단계별 시간을 담은 `prewarm phases` 줄. 게임별 읽기 전의 준비가 5초 이상 걸리면 `prewarm prepared in N s before the per-game reads [<사유>]: cooldown and cold samples, order, lists and layout lookups, load head plans and layout lookups, load head reads, other waits in load heads` 가 단계별 시간을 나눠 보여 주고(로딩 앞부분 읽기가 취소돼도 남습니다), 게임이 여럿인 묶음의 로딩 앞부분 읽기는 `<게임>: load head prewarm started` 다음에 `done: N MiB in S s`, `cancelled (<사유>) after N MiB in S s`(계획 도중 서비스가 멈추면 `interrupted (caller cancelled) after ...`, 읽지 않았으면 `skipped (<사유>)`)를 남깁니다. 부분 예열이면 앞에 `partial A/B MiB, the rest does not fit in memory:` 가 붙습니다.

### 5. 유지

- **언제.** 재예열 점검은 `rewarm_minutes` 마다, 보충과 재시도는 디스크가 한가한 동안, 배치 검사는 주기적으로.
- **무엇을.** 존의 8곳을 재어 식었으면 다시 읽고, 예산에 안 들어간 핫 집합의 나머지를 읽고, 끊긴 예열을 재시도하고, 흐트러진 배치를 복구하고, 예열한 캐시를 순서대로 두고 메모리 안에서 새로 고칩니다([SOLAR](#solar-캐시-유지와-순서)).
- **하지 않는 것.** 예열 예산 밖 게임을 다시 예열하지 않고, 게임이 실행되는 동안 배치를 건드리지 않습니다.
- **설정.** `rewarm_minutes`, `min_free_ram_mib`, `post_update_delay_min`, `memory.standby_ladder`.
- **로그.** `<게임>: rewarm check skipped (...)`, `<게임>: layout degraded while source files are unchanged (...)`(서비스가 드라이브 최적화의 끝을 본 적이 있으면 괄호 안에 `the last drive optimization the service saw ended at <UTC 시각>` 도 적힘), `<게임>: reapplied, moved N bytes, N failed`(같은 꼬리가 `<게임>: auto relocation moved N bytes, ...` 에도 붙고, 스파스 파일을 옮기거나 보류했으면 `, sparse moved N bytes`, `, K sparse file(s) held (allocation changed)` 로 끝남), `<게임>: K sparse file(s) changed allocation since the plan, held out of the layout check and reapply`(스파스 파일의 할당 구간이 계획과 달라 정기 배치 검사와 다시 적용이 그 파일만 빼고 게임의 나머지는 평소대로 다룸, 수가 바뀔 때만 로그)와 `<게임>: K sparse file(s) changed allocation since the plan, held, will plan again later`(자동 재배치 뒤 같은 상황: 그 파일은 옮기지 않고 한 시간 뒤 다시 계획함), `<게임>: held files remain, plan set aside as .stale, will plan again`, `<게임>: ladder ordered N MiB in S s`

<summary>세부: 재예열, 보충, 재시도, 배치 재검사와 재적용</summary>

**재예열(예열 유지)**

- 존의 8곳(접근 순서 앞 4곳과 균등한 4곳)을 1 MiB씩 읽어 잽니다. 그중 2곳 이상이 2 ms 를 넘으면 파일 캐시에서 밀려난 것이므로, `min_free_ram_mib` 여유를 지키며 다시 예열합니다. 느린 곳으로 세는 것은 읽는 시간이 기준을 넘고 그동안 시스템의 페이지 읽기 수도 표본 크기에 걸맞게(읽은 쪽 수의 4분의 1 이상, 최소 16쪽) 늘었을 때뿐입니다. 다른 작업이 CPU 를 쓰는 중에 캐시에 있는 표본이 느리게 읽혀 식었다고 오판하는 것을 줄이려는 것입니다. 페이지 읽기 수를 읽을 수 없으면 시간만으로 판정합니다. 설치본에서는 아직 확인하지 않았습니다.
- 예열 예산 안에 드는 게임만, 예열 점수(최근 실행·시간대 습관) 순서로 합니다. 예산 밖 게임은 식어도 다시 예열하지 않고 사유를 로그에 남깁니다.
- 실행 중인 게임이 하나 있다고 다른 게임의 점검을 멈추지 않고 대상별로 판단합니다.
- [SOLAR](#solar-캐시-유지와-순서) 사다리가 목록 일부가 캐시에 없음을 발견했으면, 이 점검은 표본이 따뜻해도 그 게임을 다시 예열합니다(로그: `<게임>: rewarm check: part of the list is not in memory (found by the ladder), prewarming again (cooldown ignored)`). 캐시에 있는 부분은 디스크 시간이 거의 들지 않으므로 실제로는 빠진 부분만 읽힙니다. 게임마다 마지막 예열 시도로부터 `rewarm_minutes` 에 한 번을 넘지 않으며, 보충이 대기 중이거나 런처의 예열이 기다리는 동안에는 하지 않습니다. 자동 모드가 꺼져 있거나 `rewarm_minutes` 가 0 이면 하지 않습니다.
- 방금 다시 읽은 게임의 캐시가 다음 점검에서 또 식는 동안(다른 프로그램이 캐시를 계속 쓰는 중)에는 그 게임의 다음 점검까지의 간격을 매번 두 배로 늘립니다(첫 번째 식음은 `rewarm_minutes` 그대로, 그다음 20, 40분, 최대 60분이며 `rewarm_minutes` 가 그보다 길면 그 값). 그 게임이 식지 않은 점검이 한 번 있으면 `rewarm_minutes` 로 돌아갑니다(로그 `<게임>: rewarm check interval raised to N min: ...`, `<게임>: rewarm check interval back to N min: ...`, 간격이 바뀔 때만). 게임마다 따로 세므로 한 게임이 다른 게임을 자기 간격에 묶지 않고, 다른 게임이 식지 않은 것으로 나와도 늘린 간격은 그대로입니다. 실제로 다시 읽은 점검만 세며(메모리 부족이나 디스크 읽기 임대(SOLAR 문서의 임대, 물리 디스크마다 배경 읽기를 중재하는 쪽이 내주는 허가) 거절로 건너뛴 재예열은 세지 않음), 표본이 식어 다시 예열하는 점검과 사다리가 요청하는 재예열을 모두 셉니다. 게임·런처가 시작해 거는 예열, 서비스 시작 예열, 재배치 뒤 예열은 이 간격을 쓰지 않고, 게임 종료로 당겨진 점검도 제때 돕니다. 대가는 다른 프로그램이 캐시를 계속 쓰는 동안 식은 게임 캐시를 더 늦게 다시 읽는다는 점입니다.
- 보충 예열이 아직 남아 있는 동안(핫 집합의 나머지를 아직 읽지 않았을 때: 메모리를 기다리는 중이거나 계획 목록이 창이 차기 전에 끝난 뒤 포함), 이미 읽은 앞부분의 표본이 식었으면 디스크가 한가하고 점검의 다른 조건이 맞을 때 그 앞부분을 다시 읽습니다(로그: `<게임>: rewarm check: the part read into memory went cold (...), reading it again (cooldown ignored)`). 처음 읽은 것과 같은 범위를 읽습니다. 같은 창으로 같은 방식으로 계획 목록을 만들고, 처음 예열이 스파스 파일을 뺐으면 이번에도 뺍니다. 상태 파일이 이에 필요한 값을 남기고 서비스를 다시 시작해도 되살립니다. `warmed_mib` 은 실제로 읽은 양, `window_mib` 은 계획 목록이 창이 차기 전에 끝났을 때의 창 크기, `sparse_out` 은 스파스 파일을 뺐는지입니다. 처음 읽은 범위를 다시 만들 수 없으면 이 점검은 그 앞부분을 읽지 않습니다. 계획 목록이 끝나기 전에 메모리로 멈추거나 메모리 한도에서 끝난 예열(보충 예열이 도중에 끊기거나 메모리 한도에서 끝난 경우도 같습니다), 그리고 `sparse_out` 이 없는 상태 파일(옛 형식)이 그런 경우입니다. 메모리로 멈춘 게임은 이전처럼 통째로 다시 예열하고, 그 밖의 게임은 보충 예열에 맡깁니다. 다시 읽기가 메모리로 줄지 않으면 읽은 양으로 기록한 값은 줄지 않습니다. 메모리로 줄면 그때 읽은 양을 기록하되 핫 집합 전체 크기는 그대로 둡니다. 나머지는 보충 예열이 읽습니다. 한 게임을 이렇게 다시 읽는 것은 24시간에 최대 2번입니다. 이렇게 읽은 뒤 `rewarm_minutes` 의 2배 안에 그 앞부분이 또 식으면, 그 읽기로부터 24시간 동안은 이 게임을 이렇게 다시 읽지 않습니다. 쉬는 동안에는 이 점검이 그 앞부분의 표본을 디스크에서 읽지 않습니다. 이미 읽은 양보다 더 들어가는 메모리가 없을 때는 보충 예열도 앞부분을 표본으로 확인하지 않습니다. 더 들어가면 보충 예열은 평소처럼 진행하며, 읽은 부분의 표본을 읽고 그것이 식었으면 창을 처음부터, 앞부분을 포함해 다시 읽을 수 있습니다. 이 읽기는 이 상한에 들지 않습니다(후속 작업). 로그는 상태가 바뀔 때 남습니다: `<게임>: rewarm check: not reading the part read into memory again until <시각> (...)`. 읽은 시각과 쉬는 기한은 `prewarm_status.json` 의 그 게임 항목에 시계 기준 시각으로 남아 서비스를 다시 시작해도 지워지지 않고, 시계를 뒤로 돌려도 지금으로 봅니다. 이렇게 다시 읽은 것도 바로 위 줄의 점검 간격 늘리기에 셉니다. 그래서 같은 범위를 다시 읽는 디스크 읽기는 하루에 게임마다 창 크기(`window_mib`, 없으면 읽은 양)의 2배까지이고, 메모리로 멈춘 게임을 통째로 다시 예열하는 경우는 그 게임에 배정된 양의 2배까지입니다. 예열 예산에 계속 드는 모든 게임을 합쳐 두 경우를 더해도 예열 예산(기본은 물리 RAM 의 절반)의 2배 안입니다.

**보충 예열**

- 핫 집합 전체가 예산에 안 들어가면, 디스크가 한가한 동안 들어가는 창만 읽습니다. 남은 핫 집합, 가용 RAM 에서 256 MiB 여유와 예비를 뺀 값, 예열 예산 중 가장 작은 값이며 최소 256 MiB 입니다. 그 창이 이미 읽은 양(계획 목록이 창이 차기 전에 끝난 창이 있으면 그 창의 크기가 더 클 때는 그 크기)보다 `max(256 MiB, 5%)` 이상 클 때만 시작합니다. [읽는 도중 메모리가 모자랄 때](#4-예열)를 보십시오.
- 보충이 중간에 끊기거나 메모리 한도에서 끝나면 읽은 위치를 서비스가 켜져 있는 동안 기억해 다음 보충에서 이어 읽습니다. 틈 메우기가 섞인 보충이나 앞쪽 부분이 식은 경우에는 처음부터 다시 읽습니다.
- 읽기 오류가 나거나 설정이 바뀌면 위치를 버리고, 서비스를 재시작하면 위치는 사라집니다.
- 로그: `<게임>: rewarm check: the rest of the hot set is not read yet, supplementing once the drive has stayed idle`, `<게임>: supplement prewarm skipped (...)`.

**끝내지 못한 예열의 재시도**

- 트레이스가 있는 게임의 예열이 끝나기 전에 취소됐거나 서비스 시작 상한에 밀렸으면 대기 목록에 남고, 디스크가 60초 동안 한가하고 그 디스크에서 실행 중인 게임이 없고 캐시 예산에 여유가 있으면 다시 요청합니다.
- 트레이스가 없는 게임은 이렇게 재시도하지 않습니다.
- 취소된 예열은 드라이브가 재배치에서 회복하는 중이어도 다시 읽습니다. 다음 재배치는 여전히 회복을 기다립니다.

**배치 재검사와 재적용**

- 주기 검사(기본 1440분)가 원본 파일은 그대로인데 배치가 흐트러진 것을 찾으면 계획을 다시 적용합니다.
- 일시적 조건(실행 중인 게임, 바쁜 디스크, 드라이브 회복, 배터리 전원, 한가한 시간 부족, 업데이트 뒤 지연)이 검사를 막으면 5분마다 반복합니다. 회차 쓰기 상한에서 멈춘 재적용도 5분 재검사를 유지합니다.
- 다른 파일이 존 일부를 차지해 재적용이 거절되면(`zone_not_free`), 그 게임을 자동 재배치로 넘깁니다. 자동 재배치는 옮긴 부분을 유지하고 남은 부분만 다시 계획하며, 기존 보류와 일일 상한을 따릅니다.
- 자동 재배치가 켜져 있고 트레이스가 있으며 데이터 검사 실패로 멈춘 게 아닐 때만 넘기고, 아니면 전처럼 실패로 끝납니다. 옮기기 전의 거절은 0바이트로 기록합니다.
- 이 검사(extent·지문 조회)는 진행 중에도 약 1초마다 다시 확인해 게임이 시작되면 멈춥니다.
- 다른 로그 줄: `<게임>: reapply blocked by zone_not_free, handing over to auto relocation to replan the remaining part`.

### 6. 게임 실행 중

- **언제.** 게임이 시작될 때부터 종료까지(짧은 유예 시간 포함).
- **무엇을.** 그 디스크의 재배치·재적용·계층 쓰기를 막고, 예열은 양보하며, 게임과 무관한 배경 프로그램이 메모리를 양보하게 하고([배경 메모리 양보](#배경-메모리-양보)), 디스크가 어떻게 움직였는지와 프레임 간격을 기록하고(`play record:`, `play_series` 폴더), 실행 중인 게임의 예열 캐시를 다시 만지거나 붙들어(읽기 전용 매핑을 열어 두어) 메모리에 둡니다([SOLAR](SOLAR.ko.md)). 게임이 뒤에 띄우는 프로그램의 블록도 읽고(단계 스트림), 게임이 실행 직후 계속 꺼지면 그 실행에서 부가 작업을 건너뜁니다.
- **하지 않는 것.** 게임 프로세스의 메모리를 읽거나 바꾸지 않고, 조회 전용 핸들보다 큰 권한으로 열지 않습니다(시작 스트림과 단계 스트림은 그 핸들로 I/O 카운터를 읽습니다). 플레이 기록은 디스크 장치 카운터만 쓰며 그 자체로 게임을 빠르게 하지는 않습니다.
- **설정.** `auto.start_stream_enabled`(`false` 면 시작 스트림을 하지 않음), `auto.stage_stream_enabled`, `auto.start_stream_cap_seconds`, `auto.restream_cooldown_min`, `auto.quick_exit_seconds`, `auto.keep_awake`, `memory.background_yield`, `memory.background_io_priority`, `memory.background_cpu_priority`, `memory.background_yield_fast`, `memory.background_in_use_memory_priority`, `memory.standby_ladder`, `memory.keep_hold`, `memory.keep_hold_written_files`, `play.frame_times`, `play.series`.
- **로그.** `<게임>: start stream skipped (<사유>)`, `<게임>: stage stream ...`, `<게임>: exited quickly (Ns)`, `<게임>: backing off for this run (...)`, `play record: ...`, `background yield ...`

<details>
<summary>세부: 같은 디스크 규칙, 시작 스트림, 단계 스트림, 실행 직후 종료, 플레이 기록</summary>

**같은 디스크**

- 실행 중인 게임 자신의 예열과 재배치·재배치 재적용·계층 이동(쓰기)은 막습니다.
- 같은 디스크의 다른 게임 예열은 실행 중인 게임이 초당 1 MiB 미만으로 읽고 디스크 처리량도 바쁨 기준 미만인 상태가 60초 이어질 때만 합니다.
- 읽는 도중에는 묶음 사이마다 그 게임의 읽기 증가율을 보고, 약 10초마다 1초씩 멈춰 디스크 처리량을 다시 재어 바쁘면 양보합니다. 읽기량 조회가 실패하면 바쁨으로 봅니다.
- 게임이 실행 중이라 예열을 건너뛴 로그 줄에는 실행 중인 게임으로 판정한 프로세스의 이름과 pid 가 남고, 실행 경과 시간은 서비스가 시작을 관측한 시각부터 셉니다.
- 디스크 활동 카운터가 인스턴스 이름에서 드라이브 문자가 빠진 표본을 주면(게임 시작 직후에 보였습니다), 서비스는 문자가 붙어 있을 때 기억한 디스크 번호로 같은 디스크를 이어 읽습니다. 값을 전혀 읽지 못하게 되면 양보 판단은 직전 값을 최대 10초 이어 씁니다. 재예열 점검처럼 "바쁘지 않음"이 분명해야 하는 판단은 그대로이며 모름을 바쁨으로 봅니다. 로그에는 `DiskActivity: D: disk activity unavailable; optimization paused (<사유>)` 와 `DiskActivity: D: disk activity available again after N s (<사유>)` 가 쌍으로 남고, 같은 드라이브는 10분에 한 번까지만 남깁니다. 그 사이의 짧은 끊김은 `, N short outage(s) merged since the last report` 로 합칩니다. 시험 PC 의 로그 세 건(2026-11-11, 2026-11-15 두 번)에서 실제 카운터가 문자를 잃었고, 그 모양을 실제 카운터로 재현하지는 못했습니다. 기억한 디스크 번호에는 시간 제한이 없어서 다른 디스크가 그 번호를 이어 쓰면 한동안 그 디스크의 값을 읽을 수 있습니다.

**시작 스트림**

- 게임이 시작되면 서비스가 그 게임의 핫 집합을 읽을 수 있습니다(시작 스트림). 로딩 경계(10초 이동 읽기율이 최고의 10% 아래로 내려간 지점, 시작 뒤 최대 60초)나 `auto.start_stream_cap_seconds` 에서 멈춥니다.
- 게임에 단계 색인이 있으면 첫 시작 스트림은 로딩 앞부분과 첫 단계만 읽습니다. 아래 단계 스트림을 보십시오.
- `auto.restream_cooldown_min` 안에는 반복하지 않습니다. 로그: `<게임>: start stream stopped at load boundary after N bytes, S s (R MB/s); boundary at B ms, peak P MiB per 10 s, last window W MiB, observed T s`. 세미콜론 뒤의 값은 왜 거기서 멈췄는지 보여 줍니다. 경계 시각, 10초 읽기량의 최댓값과 가장 최근 값, 시작 뒤 관찰한 시간입니다.

**단계 스트림 (게임이 첫 실행 파일 뒤에 띄우는 프로그램)**

- 한 게임이 실행 파일을 차례로 띄울 수 있습니다. 예를 들어 런처 같은 프로그램이 먼저 뜨고 그다음 게임 본체가 뜹니다. 시작 스트림만 있으면 첫 실행 파일에서만 돌고 본체가 뜨기 전에 로딩 경계에서 멈춥니다. 본체가 뜬 뒤에는 `game already running` 으로 시작 스트림을 건너뛰어, 본체가 처음 읽는 블록은 디스크에서 그대로 읽힙니다. 단계 스트림은 등록된 실행 파일이 뜨는 것을 단계 경계로 보고, 그 단계가 처음 읽는 블록을 그 실행 파일이 뜬 직후에 읽습니다. 기본으로 켜져 있고 `auto.stage_stream_enabled` 로 끕니다(끄면 단계 스트림은 돌지 않습니다).
- 단계는 어디서 오는가. 자동 추적이 플레이를 기록하는 동안 서비스가 등록된 실행 파일이 처음 보인 시각을 남기고, 병합 추적 파일 곁에 단계 색인을 만듭니다(추적 파일 이름 뒤에 `.stages.json` 을 붙인 파일이며, 회차별 파일에도 같은 방식으로 표지 파일이 생기고, `.stages.tried` 는 시도 횟수를 셉니다). 이 파일들은 지워도 안전합니다. 다시 만들어지거나 단계 정보가 없는 게임으로 다뤄집니다. 단계 색인이 없는 게임은 보통의 추적 조건을 만족하면 최대 두 번 더 추적합니다(추적이 꺼졌거나 안티치트가 금지한 게임은 하지 않습니다). 수동 추적이나 추적을 다시 쓰는 첫 실행 학습은 옛 색인을 지웁니다.
- 첫 실행 파일. 단계 색인이 있으면 시작 스트림은 로딩 앞부분과 첫 단계(와 어느 단계에도 배정되지 않은 블록)만 읽습니다. 없으면 단계로 나누지 않은 시작 목록 전체를 읽습니다.
- 이후 실행 파일. 런처가 아닌 등록 실행 파일이 뜨면 그 단계의 블록을 낮은 I/O 우선순위로 읽으며, (게임, 실행 파일)마다 60초에 한 번까지입니다. 게임 자신의 읽기가 5초 동안 조용하면 우선순위를 올리고, 바빠지면 다음 묶음부터 다시 낮춥니다. 읽기 항목은 32 MiB 이하로 나누고 약 64 MiB 이상씩 묶어 읽습니다. 묶음마다 메모리를 확인해 가용 메모리에서 예비량(`prewarm.min_free_ram_mib` 과 4,096 MiB 중 큰 값)을 뺀 값이 다음 묶음(최대 96 MiB, 남은 읽기량이 더 작으면 그만큼)보다 작으면 멈추며, 단계 스트림이 켜져 있으면 첫 시작 스트림도 같습니다. 새 프로세스의 읽기만으로 잰 로딩 경계와 `auto.start_stream_cap_seconds` 에서도 멈춥니다. 단계 색인이 없으면 기다리기 시작한 뒤 새 프로세스의 읽기량이 64 MiB 이상 늘고 그 시점에 프로세스가 시작 뒤 10초가 지나지 않았을 때만 시작 목록을 읽습니다. 다른 게임의 시작이 대기 중이면 그 증거를 기다리지 않습니다.
- 무엇을 읽는가. 시작 목록과 그 단계의 블록의 교집합이므로 시작 목록보다 늘지 않습니다. 가변 파일과 배경 목록은 읽지 않고, 스파스 속성 파일은 버퍼드 읽기 경로만 씁니다. 서비스가 부가 작업을 건너뛰는 실행(아래)에서는 단계 스트림도 하지 않습니다.
- 로드 구간 목록. 게임이 도는 동안 예열해 둔 캐시가 밀려나서 두 번째 이후 맵 로드는 디스크에서 읽히므로, 등록된 프로그램이 뜰 때마다 그 뒤 120초 동안 게임이 읽던 데이터를 다시 채웁니다. 서비스는 플레이가 끝날 때마다 앞선 플레이들의 디스크 읽기 요약(`.io.json`)에서 목록을 만듭니다. 등록 실행 파일이 시작한 시각(요약에 `target_starts_us` 로 기록하며, 옛 요약은 그 플레이의 단계 표지 중 두 번째 이후 시작)마다 120초 안에 처음 읽힌 64 KiB 블록을 모읍니다. 파일 캐시를 거치지 않고만 읽힌 블록(페이징 요청 없음)은 메모리에 채워도 게임 읽기에 쓰이지 않으므로 뺍니다. 플레이 중 바뀐 파일, 없어진 파일, 가변 파일, 허용 루트 밖 파일도 뺍니다. 여러 플레이를 합치고, 나온 플레이 수와 읽기 지연 합이 큰 순으로 놓고 4 GiB 에서 자릅니다(실제 한 로드의 최대가 약 4.1 GiB, 세 로드의 합집합이 약 2.9 GiB, 로드 중 사용 가능 메모리가 약 11 GiB 였습니다). 목록은 트레이스 곁에 `<게임>.trace.loadrefill.json` 으로 저장하며(임시 파일에 쓴 뒤 바꿔 끼우고, 지워도 안전하며, 트레이스를 새로 배우면 지워집니다), 이후 프로그램이 뜰 때 목록이 있으면 단계 스트림은 단계 블록 대신 이 목록을 디스크 위치 순으로 읽습니다. 크기는 메모리 게이트가 허용하는 양(가용 메모리 − 예비량)으로도 줄입니다. 64 MiB 읽기 증거를 기다리지 않고, 로딩 경계의 첫 휴지에서 멈추지 않으며, 목록을 다 읽거나 `auto.start_stream_cap_seconds`(기본 120초, 위 창과 같음)가 지나거나 메모리 예비량에 닿거나 게임이 끝나면 멈춥니다. 낮은 I/O 우선순위, 메모리 게이트, 60초에 한 번이라는 제한은 그대로이고, 60초는 이 스트림이 끝난 시각부터 셉니다(같은 로드의 겹친 시작이 두 번 읽지 않게). 시작이 일어난 지 120초 이상 지나 처리되거나 목록이 없는 게임은 단계 블록을 읽습니다. 목록을 만들 때의 로그는 `<게임>: load refill list built from P plays (Q without start times), L loads: N blocks/M MiB, K MiB left out as read only without the cache, J MiB over the 4096 MiB cap` 입니다. 실제 게임에서의 효과는 아직 재지 않았습니다.
- 서비스가 시작될 때도 목록을 만듭니다. 목록 파일이 없거나 그 게임의 가장 새 저장 집계보다 오래된 게임은 저장된 집계로 목록을 만들어, 설치 직후나 목록을 지운 뒤에도 다음 플레이가 끝나기를 기다리지 않습니다. 서비스 시작 예열과 같은 대기 조건(부팅 뒤 대기, 게임 드라이브 유휴)을 따르고, 시작을 막지 않게 백그라운드로 돌며, 게임 폴더 잠금을 같은 규칙으로 잡고, 실행 중인 게임은 건너뜁니다. 저장된 집계가 없는 게임은 건드리지 않습니다. 로그는 평소의 `load refill list built from ...` 줄 끝에 ` (service start)` 가 붙습니다.
- 파일 캐시를 거치지 않고만 읽히는 파일. 게임이 버퍼링 없이 여는 파일은 늘 디스크에서 읽히므로, 메모리로 예열해도 게임에 쓰이지 않고, 캐시를 거치는 블록이 쓸 메모리를 차지하며, 로딩 중 같은 디스크에서 게임의 읽기와 경쟁합니다. 서비스는 플레이가 끝날 때마다 저장된 디스크 읽기 요약(`.io.json`)의 파일별 읽기 방식(`read_modes`)에서 이런 파일을 판정합니다. 서로 다른 플레이(세션 ID 기준) 두 번 이상에서 읽혔고, 그 읽기가 모두 캐시를 거치지 않았으며(캐시 요청도 페이징 요청도 없음), 어느 플레이에서도 캐시를 거쳐 읽히지 않았을 때 판정합니다. 파일이 없거나, 가변 파일이거나, 허용 루트 밖이거나, 그 파일을 읽은 가장 늦은 플레이의 관찰 시작보다 나중에 쓰였으면 판정하지 않습니다. 판정한 파일은 크기·수정 시각과 함께 `<게임>.trace.json.unbuffered.json` 으로 저장합니다(임시 파일에 쓴 뒤 바꿔 끼우며 지워도 안전하고, 판정된 파일이 없으면 빈 목록을 저장합니다). 서비스가 시작될 때도 목록이 없거나 가장 새 집계보다 오래됐으면 로드 구간 목록과 같은 대기 조건·폴더 잠금·실행 중 게임 건너뜀으로 만듭니다. 읽기 목록을 만들 때 지금 파일의 크기나 수정 시각이 저장한 값과 다르면(예: 게임 업데이트) 그 파일은 빼지 않고, 다음 플레이 뒤에 다시 판정합니다. 이 파일은 메모리 예열 목록, 시작 스트림, 단계 스트림(시작 목록의 부분집합), 갱신 읽기, 표본, 고정 파일에서 뺍니다. 메모리 예산 창은 그대로여서 빠진 바이트는 캐시를 거치는 블록이 쓰도록 남습니다. 재배치 계획에서는 빼지 않습니다. 이 파일은 디스크 위 배치로만 빨라지기 때문입니다. 읽기 방식은 게임 프로세스 트리의 읽기만 담으므로 서비스 자신의 읽기는 들어 있지 않습니다. 목록을 만들 때의 로그는 `<게임>: unbuffered file list built from P plays: N files/M MiB read only without the cache` 입니다. 한 번의 플레이만으로는 판정하지 않으며 파일 이름·확장자는 쓰지 않습니다. 실제 게임에서의 효과는 아직 재지 않았습니다.
- 블록 순위 목록. 경기 중 읽기 지연의 대부분은 다른 플레이에서는 로드나 플레이 초반에 처음 읽힌 블록에서 나므로, 경기 구간만으로 만든 목록은 작습니다. 그래서 서비스는 플레이가 끝날 때마다 저장된 디스크 읽기 요약(`.io.json`)의 전체 구간(실행·로드·경기 중)에서 64 KiB 블록을 나온 플레이 수, 읽기 지연 합이 큰 순으로 정렬해 `<게임>.trace.json.ranked.json` 으로 저장합니다. 형식·저장 방식·만드는 시점·폴더 잠금·서비스 시작 때 없거나 오래됐으면 만드는 조건은 로드 구간 목록과 같고, 트레이스를 새로 배우면 지워지며, 지금 파일의 크기나 수정 시각이 저장한 값과 다르면(예: 게임 업데이트) 그 파일 블록은 쓰지 않습니다. 계획과 존 밖 덧붙임이 다시 쓰는 `prefetch.json`·`warmonly.json` 에 섞지 않고 따로 둡니다. 로드 구간 목록처럼 캐시 없이만 읽힌 블록(페이징 요청 없음), 플레이 중 바뀐 파일, 없어진 파일, 가변 파일, 허용 루트 밖 파일을 빼고, 예열 목록에서 어차피 빠지는 캐시 없이 읽는 파일(위)과 스파스 파일(만져도 캐시에 남지 않음), 게임 드라이브 밖 파일도 뺍니다. 8 GiB 에서 자르며, 근거는 게임 사이 예열 예산이 5.8 GiB 안팎(많아야 8~11 GiB)이라 그보다 큰 목록은 읽히지 않는다는 점입니다. 이 목록은 두 곳에 쓰입니다. 예열 목록을 메모리에 맞춰 잘라야 할 때 선택 순서에 들어가며(위), 게임이 실행되는 동안의 캐시 유지가 만지는 범위의 순서를 정합니다([SOLAR](SOLAR.ko.md)). 두 경우 모두 게임 시작 때 요약(`.io.json`)을 다시 읽지 않고 이 파일만 읽으며, 목록이 없으면 지금과 같습니다. 목록이 있으면 일반 예열 스트림, 부분 예열 스트림, 사다리, 시작 때의 만지기, 실행 중 유지가 모두 같은 규칙으로 같은 범위 집합을 고릅니다(목록이 예산보다 크면 일반 예열 스트림도 위 순서로 자릅니다. 스트림이 읽지 않은 블록을 사다리가 만지면 디스크 읽기가 되어 재예열이 되풀이되기 때문입니다). 서비스는 마지막 예열이 읽은 순위 목록을 메모리에 기억해 두고, 순위 파일이 게임이 끝나 새로 만들어져도 다음 예열 한 회가 그 변경을 보기 전까지 사다리·시작 때의 만지기·유지는 기억한 목록을 따릅니다. 서비스를 막 시작해 기억한 것이 없으면 그때의 파일을 읽어 기억합니다. 게임 사이 메모리 예산 배정은 이 목록을 세지 않아 그대로이고, 예산 안에서 무엇을 담을지만 바뀝니다. 목록이 바뀌면 예열 목록 재사용 서명과 예열 표본 세대가 달라져 예열 목록과 표본을 새로 계산합니다. 만들 때의 로그는 `<게임>: ranked block list built from P plays: N blocks/M MiB, K MiB left out as read only without the cache, S sparse files left out, J MiB over the 8192 MiB cap` 이고, 예열 선택이 이 목록에서 담은 양은 `prewarm phases` 줄 끝에 `N MiB selected from the ranked block list` 로 남습니다. 실제 게임에서의 효과는 아직 재지 않았습니다. 저장된 기록 세 개로 순위 앞쪽이 다른 플레이의 경기 중 지연을 얼마나 덮는지만 계산했습니다.
- 이 기능은 "게임이 실행되는 동안 그 디스크에 새 배경 읽기를 하지 않는다"는 규칙의 예외를 넓힙니다. 예외는 같은 게임의 등록 실행 파일이 방금 뜬 순간이며 위 조건 아래에서만입니다. 읽기 증거와 로딩 경계를 판단하려고 시작 스트림이 이미 쓰던 것과 같은 조회 전용 핸들로 게임 프로세스의 I/O 카운터를 읽으며 그 밖의 것은 열지 않습니다. 그것마저 거부하는 프로세스는 카운터에서 빠집니다([ANTICHEAT.ko.md](ANTICHEAT.ko.md)).
- 넣지 않은 것: 첫 스트림이 도는 동안 다음 단계를 미리 읽는 기능. 실제 게임에서의 효과는 아직 재지 않았습니다. 조용함 5초와 증거 기준(10초 안 64 MiB)은 재기 전에 정한 값이고, 읽기 항목을 32 MiB 로 자르는 것이 처리량에 주는 영향도 재지 않았습니다. 읽기 항목이 잘렸다면 로그의 `requests` 수는 예전보다 커집니다.
- 로그: `<게임>: stage stream <exe> N MiB in S s (R MB/s, completed|stopped, <사유>), yielded Y s`(사유는 `load boundary`, `cap`, `memory reserve`, `cancelled` 이며, 가변 파일을 뺐으면 `; skipped volatile N MiB` 가 붙고, 줄 끝에 `; source trace stage`, `; source start list`, `; source load history (P plays, L loads, N MiB planned)` 중 하나가 붙습니다)와 `<게임>: stage stream skipped (<exe>: <이유>)`(이유는 `cooldown N s`(같은 프로그램이 60초 안에 다시 뜸), `no blocks in the start list`, `no load evidence, ...`, `another game started`, `disk yielded` 등).
- 선행 기술. 프로그램이 시작될 때 그 데이터를 미리 읽는 것과 기록한 읽기 순서를 재생하는 것은 오래된 발상입니다. Windows Prefetcher(실행 파일마다 `.pf` 파일 하나, 프로세스가 만들어질 때 읽음), FAST(USENIX FAST 2011), Android iorap 이 비슷한 일을 합니다. 여기서 다른 것은 조합입니다. 한 게임이 차례로 띄우는 실행 파일 각각의 시작을 단계 경계로 보고, 기록된 블록을 처음 읽은 단계별로 나누고, 그 프로그램이 뜰 때 그 단계의 블록을 읽습니다. 시험 PC 에서 한 게임의 기록된 한 번의 플레이에서는 첫 단계와 본체의 블록이 거의 겹치지 않았습니다(자카드 지수 0.023). 정확히 이렇게 하는 공개 자료는 찾지 못했지만 없다는 뜻은 아니며, Windows Prefetcher 가 두 번째 프로세스가 읽는 데이터 파일까지 덮는지는 확정하지 못했습니다.
- 플레이 기록은 이후 실행 파일마다 결과를 남깁니다. `play_samples.json` 에 `stageStarts`(그 실행 파일 시작 기준 스트림 결과와 +30·+60·+120초 구간, 플레이당 최대 20개)와 `periods`(처음 600초 이후 10분 단위 요약)가 붙습니다. 로그 줄은 `play record stage <exe>: ...` 와 `play record periods: ...` 이며, `play record:` 줄과 따로 남습니다.

**게임이 실행 직후 꺼질 때**

- 게임 세션이 `auto.quick_exit_seconds`(기본 90초, 10~600)보다 짧게 끝나면 실행 직후 종료입니다. 짧은 종료가 아니면서 5분 이상이면 정상 세션이라 횟수를 되돌리고(기본값에서는 5분 이상이면 모두 그렇고, `quick_exit_seconds` 를 300 보다 크게 두면 그보다 긴 실행도 짧은 종료로 셉니다), 그 사이는 세지도 되돌리지도 않습니다. 세션은 첫 게임 프로세스가 뜬 때부터 모두 사라질 때까지입니다. 길이는 서비스가 프로세스가 사라진 것을 알아챈 때를 기준으로 하며(점검이 약 30초마다 돕니다), 기준에 가까운 실행은 세지 않을 수 있습니다.
- 첫 번째 짧은 종료는 `<게임>: exited quickly (Ns)` 를 남깁니다.
- 짧은 종료 뒤 10분 안에 그 게임을 다시 실행하면, 서비스는 그 실행에서 부가 작업을 건너뜁니다. 정상 세션으로 연속이 초기화될 때까지 다시 건너뛰지 않습니다. 부가 작업을 건너뛴 실행이 곧바로 짧게 끝나면 그것을 기록하고, 짧은 종료 기준을 넘고 5분이 되기 전에 끝나면 `launched after the service backed off` 로그와 알림을 남기며 건너뜀 표시도 `launched`로 저장합니다. 어느 경우든 그 연속에서는 두 번째로 건너뛰지 않습니다. 부가 작업을 건너뛴 실행에서는 시작 스트림, 단계 스트림, 자동 추적, 로딩 경계 읽기, 배경 메모리 양보, 트리거 예열을 하지 않습니다. 게임에 디스크를 양보하는 동작은 그대로입니다. 로그: `<게임>: backing off for this run (quick exit N in a row, last Ss, M min ago): no start stream, memory yield or trace`, `<게임>: start stream skipped (quick exit guard: backing off)`, `<게임>: auto trace skipped (quick exit guard: backing off)`.
- 짧은 종료가 두 번 연속되면, 서비스는 마지막 정상 실행(5분 이상 간 마지막 세션) 뒤 새로 올라온 커널 드라이버를 찾아 로그, 트레이 알림(알림 스위치를 따릅니다), 상태 탭의 그 게임 카드에 알립니다. 로그: `<게임>: quick exit N in a row (runs 32s, 47s); backed-off run: exited too|launched|not backed off; new kernel drivers since the last normal run: <이름 (경로), ...>|none|unavailable|unknown (no normal run recorded)`. `unavailable` 은 이번에 드라이버 목록을 읽지 못했다는 뜻이고, `unknown (no normal run recorded)` 는 비교할 정상 실행이 없다는 뜻입니다. 부가 작업을 건너뛴 실행이 꺼지지 않고 살아남으면 `<게임>: launched after the service backed off (Ns); the earlier quick exit(s) may involve the service, or the program may restart itself` 를 남깁니다. 서비스가 원인이라고 단정하지 않는데, 스스로 다시 실행하는 프로그램에서도 같은 모양이 나오기 때문입니다.
- 드라이버 목록은 올라와 있는 커널 드라이버를 읽기 전용으로 조회한 것입니다(파일 이름과 경로는 Windows 가 주는 대로). 프로세스를 열지 않고 드라이버를 건드리지도 않습니다. 횟수와 마지막 정상 실행의 드라이버 목록은 데이터 폴더의 `quick_exit.json` 에 남습니다.
- 이 기능이 아닌 것. 게임이 꺼지는 것을 막지 않습니다. 패턴을 알아채고, 서비스를 의심에서 뺄 수 있게 한 실행 동안 부가 작업을 건너뛰며, 마지막 정상 실행 뒤 무엇이 바뀌었는지 보여 줍니다. 원인은 다른 프로그램의 커널 드라이버일 수 있고, 목록의 새 드라이버는 단서이지 원인 확정이 아닙니다.
- 한계. 같은 실행 파일이 다시 뜨면 서비스는 앞 실행이 얼마나 갔는지 봅니다. 5초 미만이면 새 시작을 같은 세션으로 잇고, 5초 이상이며 그 게임의 다른 프로세스가 남아 있지 않으면 세션을 나눠 앞 실행을 따로 판정합니다. 그래서 5초 이상의 짧은 실행 뒤 스스로 다시 시작하는 프로그램은 짧은 종료로 셉니다. 서비스가 시작되기 전부터 돌던 게임은 세지 않습니다. 게임이 꺼진 직후 PC 를 끄면 마지막 횟수가 남지 않을 수 있습니다. 시작 때의 드라이버 목록은 게임이 막 뜬 순간에 조회하므로, 게임과 함께 올라오는 드라이버가 정상 목록에서 빠졌다가 다음에 새 드라이버로 보일 수 있습니다. 같은 런처를 쓰는 다른 게임이 예열되면 전역 배경 메모리 양보는 부가 작업을 건너뛴 실행 동안에도 열려 있습니다. 시험 PC 한 대에서 가벼운 게임을 직접 꺼 보며 횟수 세기, 부가 작업 건너뛰기, 상태 탭 카드, 서비스 계정에서의 드라이버 목록 읽기를 확인했습니다. 스스로 꺼지는 게임으로는 확인하지 않았습니다.

**작은 점검**

- HDD 깨워 두기 읽기, 고정 생성, 부팅 점검은 시작 전에 게임 실행 여부를 확인합니다.
- 깨워 두기 읽기(`auto.keep_awake`)는 런처가 떠 있거나 평소 플레이하던 시간대에 10분마다 4 KiB 를 읽어 HDD 가 잠들지 않게 하는 것입니다. 전원 설정은 바꾸지 않습니다.

**플레이 기록**

- 서비스는 물리 디스크의 누적 읽기 카운터를 1초 간격으로 표본 내고, 시작 뒤 30·60·120·300·600초와 종료 시점에 `play record:` 로그 줄과 `play_samples.json` 을 남깁니다.
- 같은 기록에 프레임 간격도 더합니다(`play.frame_times`, 기본 켬, [안티치트](ANTICHEAT.ko.md)의 게이트를 지난 게임만). 게임 프로세스의 Present 간격을 초 단위로 모아 검사점과 10분 구간마다 프레임 수, 가장 긴 간격, 50 ms·100 ms 를 넘은 간격 수를 남기고, 가장 긴 간격이 50 ms 이상이거나 디스크 쪽 느린 초(읽기 5건 이상, 평균 100 ms 이상)인 초는 `frameSeconds` 목록(최대 300개, 넘치면 가장 긴 간격이 큰 것을 남김)에 시작 뒤 초, 그 초의 디스크 읽기 횟수·평균 읽기 시간, 전체 CPU 사용률, 그래픽 메모리 전용 사용량과 함께 담습니다. 간격은 도착 순서가 아니라 이벤트 시각 순서로 셉니다(뒤바뀌어 도착한 수는 `frameEventsOutOfOrder`). 1초 이상 걸린 간격은 끊김이 아니라 멈춤(최소화, 창 가림, 로딩 화면, 응답 없음)으로 보고 `pauses` 로 따로 세며 50 ms·100 ms 초과 수와 가장 긴 간격에 넣지 않습니다. 그 초는 목록에 `pauses` 와 함께 남습니다. 목록은 10분 구간마다 50개, 전체 300개를 넘지 않으며 구간 안에서는 가장 긴 간격이 큰 것을 남깁니다. 프레임 값은 이벤트 전달 지연(이 PC 에서 최대 약 1.5초 실측) 때문에 측정 시각보다 약 5초 뒤까지만 확정된 값이고, 확정 뒤에 도착해 버린 이벤트 수는 `frameEventsLate` 와 로그의 `frame events late N` 에 남습니다(0 이 아니면 그 이벤트가 끝내는 간격이 빠졌을 수 있습니다). 디스크 표본이 없던 초는 `diskReads` 가 null 입니다. 등록 실행 파일이 런처인 게임은 런처 화면의 Present 가 불규칙해 간격이 의미 없는 값일 수 있습니다. `frameStatus` 는 `ok`, 못 쟀을 때의 이유(`off`, `blocked`, `unavailable`, `no_events`)이고 `frameEventsLost` 는 세션이 잃은 이벤트 수입니다. 로그의 `play record:` 와 `play record periods:` 줄에는 `frames N, longest M ms, over 50 ms K, over 100 ms L` 과 `, pauses P (longest X ms)`(1초 이상 걸린 간격의 수와 가장 긴 것, 없으면 괄호 생략)가 붙습니다. 가장 긴 멈춤은 검사점·구간·합계에도 남고(`maxPauseMs`), 목록이 넘칠 때는 `longest` 와 멈춤 길이 중 큰 쪽이 작은 칸부터 버립니다. 도중에 `blocked` 로 멈춘 플레이에서 멈춘 시각을 걸친 구간은 앞부분에 잰 값이 있어도 `frames blocked` 로만 표시되고, 값은 JSON 의 합계에 남습니다. DirectX 가 아닌 게임은 `no_events` 로 남습니다. 실제 게임에서의 값은 확인하지 않았습니다.

파일과 함께 지웁니다. `play_samples.json` 과 `frameSeconds` 는 그대로입니다. 열은 다음과 같습니다. `t_s`(플레이 시작 뒤 초). `frames`, `max_frame_ms`, `over50_n`, `over100_n`, `pauses_n`, `pause_max_ms`(그 초의 프레임 값이며 끊긴 초만이 아니라 모든 초). 하던 일을 `+` 로 이은 것: `touch` 게임 시작 때의 만지기, `keep` 캐시 유지 회차, `stream` 시작·단계 스트림, `trim` 배경 양보의 작업 집합 비우기, `supp` 보충 예열). `game_read_bytes`(서비스가 이미 아는 게임 프로세스들의 읽기 전송 바이트 증가분이며, 캐시에서 읽은 것과 다른 볼륨의 읽기를 포함하고, 첫 초는 비어 있습니다), `game_ws_mib`(같은 프로세스들의 작업 집합), `load_phase`(그 초의 로딩 판정이며 값은 `loading` 또는 `not_loading`, 판정이 없으면 빈 칸. 판정은 다음 항목에서 설명합니다), `other_ws_mib`(게임과 서비스를 뺀 프로세스의 작업 집합 합, MiB), `ws_grow_top_name`·`ws_grow_top_mib`(그 초에 작업 집합이 가장 많이 늘어난 프로그램의 이름(같은 이름은 합침)과 늘어난 양 MiB, 처음 보인 프로그램은 작업 집합 전체를 늘어난 양으로 세고, 늘어난 것이 없으면 둘 다 빈 칸), `yield_applied_n`(그 초에 배경 양보가 새로 우선순위를 적용한 프로그램 수). 이 네 칸은 프로세스를 열지 않는 같은 시스템 조회와 메모리 안의 카운터로 구하며, 줄마다 약 22바이트(2,500초 플레이에서 약 55,000바이트, 기존 파일 약 455,000바이트)를 더하고 분당 한 번 덧붙이는 쓰기에 함께 실립니다. 이 버전 이전에 기록한 파일에는 앞의 열만 같은 자리에 있고, 새 파일의 새 열은 항상 맨 끝에 있습니다. 읽지 못한 칸은 비어 있고, 첫 초의 CPU·재사용·쓰기 칸은 차이 값이라 비어 있습니다. 프로세스별 값은 `NtQuerySystemInformation(SystemProcessInformation)` 한 번의 조회(만지기가 자기 하드 폴트를 세는 데 이미 쓰는 조회)와 성능 카운터에서 얻으므로 게임·런처·안티치트 프로세스를 열지 않습니다. 같은 이름에 `.lists.csv` 가 붙은 두 번째 파일에는 30초마다 한 줄이 남습니다: `free_zero_mib`, 그다음 대기 우선순위 0~7 마다 크기(`standby_mib_p0`~`standby_mib_p7`)와 부팅 뒤 재사용 누계(`reused_mib_p0`~`reused_mib_p7`). 이 파일을 다시 읽는 곳은 없습니다: 캐시 유지·사다리·예열·배경 양보는 이 파일에 의존하지 않습니다. 비용은 게임이 없는 이 PC 에서 잰 값입니다(1초마다 한 번씩 180회): 시스템 값을 읽는 데 CPU 약 2.7~3.9 ms(거의 전부 프로세스 목록 조회 한 번)와 줄을 만들어 쌓는 데 약 0.1 ms 가 들어, 같은 1초 간격으로 기다리기만 한 기준선(시험 프로그램 자체와 타이머의 CPU)을 뺀 평균이 한 코어의 0.36%였습니다(빼기 전 0.52%). 관리되는 메모리는 늘지 않고(프로세스 목록 조회는 만지기가 이미 쥐는 약 2 MiB 버퍼를 씁니다), 파일은 1분에 약 10 KB 씩 1분마다 한 번 덧붙입니다. 실행 중인 게임 옆에서는 재지 않았습니다.
- **로딩 판정.** 서비스는 매초 게임이 로딩 중인지 가리며, 위 매초 기록의 `load_phase` 열이 그 결과를 적습니다. 로딩은 게임의 그래픽 메모리가 10초에 250 MiB 늘거나, 게임이 설치된 디스크의 읽기가(서비스가 그 디스크에서 직접 읽은 양을 뺀 값입니다: 서비스의 만지기·점검·붙들기가 디스크에서 읽은 바이트를 서비스가 따로 세며, 이 읽기는 매핑 뷰의 페이지 폴트라 프로세스의 읽기 전송 바이트에는 잡히지 않습니다) 5초에 80 MiB 이상이거나, 게임의 실행 파일이 뜰 때 시작하고, 읽기가 5초에 40 MiB 미만이고 그래픽 증가가 10초에 64 MiB 미만인 상태가 15초 이어지거나 시작 뒤 240초가 지나면 끝납니다(로딩 중에 실행 파일이 다시 뜨면 240초를 다시 세지만, 이어진 로딩 전체는 480초에 끝납니다). `loading` 이고 게임의 실행 파일이 시작해서 생긴 로딩이 아닐 때(경기 안 맵 전환처럼 그래픽 메모리나 디스크 읽기로만 알아챈 로딩) 서비스는 메모리에 이미 있는 범위를 다시 만지는 일은 그대로 하되 게임이 도는 중에 하는 디스크 읽기는 줄입니다. 캐시 유지 회차([SOLAR](SOLAR.ko.md) 참고)는 메모리에서 만질 것이 없을 때만 새 범위를 찾고 그때 디스크 읽기가 약 2 MiB 에서 멈추며, 보호 패스는 약 2 MiB 에서 멈추고, 순서 패스는 보호 패스가 방금 메모리에 있다고 확인한 범위만 만지다 디스크에서 읽어야 하는 첫 배치(16 MiB)에서, 또는 그 회차의 디스크 읽기가 32 MiB(로딩이 아닐 때와 같은 상한이며, 메모리에 없는 블록이 여러 배치에 흩어져 있을 때 걸립니다)를 넘으면 멈추며, 어떤 상한도 범위를 목록에서 빼지 않습니다. 붙든 범위의 점검은 게임이 바꾼 파일을 내놓는 일을 그대로 하고, 메모리 관리자가 줄여 간 구간을 약 2 MiB 에서 다시 읽기를 멈추며 그 상한에 닿아도 구간을 붙들기에서 빼지 않습니다. 상한은 읽기 수를 조회할 때만 보므로(느린 조각이 나오면 바로, 아니면 64 MiB 만질 때마다) 실제로는 회차가 보통 2~4 MiB, 점검이 약 8~10 MiB 를 읽고, 최악은 상한보다 최대 64 MiB 더 읽을 수 있습니다. 게임의 실행 파일이 시작해서 생긴 로딩에서는 서비스가 판정이 없을 때와 똑같이 움직이고, 게임을 시작할 때 서비스가 읽는 것은 그대로입니다. 판정은 초 단위 기록이 꺼졌거나 쓰지 않는 플레이에서도 돌며, 그래픽 메모리는 `gpu_game_mib` 를 읽는 곳에서만 쓰고 그 밖에서는 디스크 규칙만 돕니다. 로딩이 시작될 때 한 줄(`<게임>: loading phase started (<사유>)`), 끝날 때 한 줄(`<게임>: loading phase ended after <n> s (<사유>)`, 미룬 일 포함)을 로그에 남깁니다. 임계값은 한 게임의 기록된 플레이로 맞춘 값입니다.
- 만지기(게임 시작 때와 게임이 실행되는 동안)가 목록 끝 전에 메모리에 남은 부분의 경계를 찾으면 로그 줄 끝에 표본 확인이 붙습니다. 예: `probe 5/16 in memory (positions 0 211 422 MiB of 3386 MiB)`. 목록 전체에서 고르게 고른 16곳(각 64 KiB)을 하나씩 만져서, 만지는 동안 서비스의 하드 폴트가 2 미만으로 늘면 메모리에 있던 곳으로 셉니다(메모리에 없는 블록은 2~3회). positions 는 메모리에 있던 곳의 목록 위치이고, 하나도 없으면 `none of M MiB`, 열지 못한 곳(스파스 파일, 없는 파일)이 있으면 `, N not probed` 가 붙습니다. 앞부분만 잃었는지 목록 전체를 잃었는지를 가르는 용도입니다. 디스크에서 읽는 양은 최대 1 MiB 이고 어떤 판정·순서에도 쓰지 않습니다. 열기·매핑·읽기 오류가 있던 만지기는 수만 적지 않고 `, N errors (open A ranges in F files (win32 5 ×X (f files, r ranges, S requested), ...), beyond end B ranges in G files, map C ranges in H files (...), read D ranges in I files (...); most failures in <경로> ×K, ...)` 를 남깁니다: 종류별 범위 수와 서로 다른 파일 수(열지 못한 파일과 그 Win32 오류 번호, 파일 끝 밖의 범위, 매핑 실패, 읽기 실패)입니다. 열기 오류는 Win32 오류 번호마다 파일 수, 범위 수, 그 범위들이 요청한 바이트(MiB, KiB, B 중 하나로)도 적습니다. 세미콜론 뒤에는 종류에 상관없이 실패한 범위가 많은 파일을 최대 4개까지 각각의 횟수와 함께 적습니다.
- 게임 파일이나 프로세스는 읽지 않고 디스크 장치 카운터만 조회합니다. 로딩과 끊김을 비교하기 위한 계측입니다.
- 플레이의 종료 시각, 길이, 합계(읽은 양, 읽기 시간, 디스크 유휴 시간)는 서비스가 게임 프로세스가 사라진 것을 처음 본 시각까지만 셉니다. 그래서 60초 종료 확인 시간은 들어가지 않습니다. 이 확인 중에 게임이 다시 뜨면 플레이는 이어집니다.

</details>

### 7. 드라이브 회복 대기

- **언제.** SMR 디스크에서 재배치를 한 뒤, 그리고 게임 업데이트를 감지한 뒤.
- **무엇을.** 짧은 시험 읽기로 드라이브가 보통 속도로 돌아온 것을 확인할 때까지 기다린 뒤 다음 작업을 허용합니다.
- **하지 않는 것.** 예열은 막지 않습니다. 재배치를 막고, 게임 업데이트 뒤에는 그 게임의 재계획과 예열을 미룹니다.
- **설정.** `post_relocate_recovery`, `recovery_max_min`, `recovery_hard_max_min`, `post_update_delay_min`.
- **로그.** `drive D: recovering after relocation (...)`, `drive D: recovered after N min`

<details>
<summary>세부: `"probe"` 방식의 규칙, 상한, 다른 방식, 멈춤</summary>

**`"probe"`(기본)**

- 기준은 쓰기 직전에 표본이 도는 세 위치에서 재고 그 중앙값을 씁니다.
- 2분마다 짧게 읽어 기준의 90% 이상이 연속 2회면 회복으로 봅니다. 측정값이 흔들려도, 최근 6회(세 위치를 두 번씩) 가운데 4회 이상이 기준의 90% 이상이면 회복으로 봅니다.
- 미달이 이어지면 첫 6회 뒤부터 간격을 4분, 8분으로 늘립니다. 표본마다 위치, 속도와 기준, 판정과 사유를 로그에 남깁니다.
- 캐시 적중 상한을 넘는 표본이 돌아가며 고르는 세 위치에서 연속으로 나와도 회복으로 봅니다. 판정할 수 없는 표본은 최대 8분 간격으로 벌려 읽고, 버린 표본은 한 줄로 요약해 남깁니다.
- 최대 `recovery_max_min`분 기다립니다. 그래도 회복을 확인하지 못하면, 회복되거나 `recovery_hard_max_min`분이 지날 때까지 다음 재배치를 계속 보류합니다.
- `"fixed"`는 `post_update_delay_min`분을 고정으로 기다리고, `"off"`는 끕니다.

**게임 업데이트 뒤**

- 드라이브가 흩어진 쓰기를 아직 정리하는 중일 수 있어, 그 게임의 재계획·재배치·예열을 `post_update_delay_min`분 미룹니다(RESULTS_SUMMARY 실험 E9: 흩어진 쓰기 뒤 읽기 회복 시간).

**멈춤**

- 같은 디스크의 게임이 실행 중이면 대기를 멈추고, 게임이 끝난 뒤 남은 시간부터 이어갑니다. 그동안 회복 표본 읽기도 하지 않습니다.
- 서비스를 재시작해도 멈춘 상태와 남은 시간을 이어받습니다.
- 다른 로그 줄: `drive D: recovery clock paused (game running)`, `drive D: recovery discarded N cache-suspect samples ...`.

</details>

### 부팅 직후

서비스가 부팅 뒤 5분 안에 뜨면 스스로 시작하는 디스크 작업을 부팅 5분 경과와 게임 드라이브 60초 유휴 뒤까지 보류합니다. 보류 구간은 늦어도 부팅 15분 뒤에 끝납니다. 두 예열은 예외입니다. 서비스 시작 때의 예열과 런처가 시작한 예열은 읽기가 다른 읽기에 양보하므로, 부팅 60초 뒤 게임 드라이브가 20초 동안 한가해질 때까지만 기다립니다([예열](#4-예열) 참고).

<details>
<summary>세부: 무엇을 보류하나</summary>

- 보류하는 작업: 재배치, 새 트레이스 예열, 배치 검사와 재적용, HDD 깨워 두기. 그 뒤 기존 조건으로 실행합니다. 런처 트리거 예열은 위의 더 짧은 조건까지만 보류하며, 런처 예열을 보류한 동안에는 5초마다(그 밖에는 30초마다) 점검하고, 조건이 되면 그 점검에서 바로 풉니다(로그: `held prewarm triggers released: N (boot + idle disk)`, 그 앞에 `boot prewarm release: uptime U s, idle since S s, C checks (B not idle), last disk X MiB/s`). 다른 보류 작업은 구간이 끝날 때까지 그대로 보류합니다. 서비스 시작 예열은 `service start prewarm waits for 60 s after boot and 20 s of idle disk` 를 남깁니다.
- 부팅 15분 안에 시작한 예열 읽기는 첫 묶음 전에 디스크를 재고, 다른 읽기가 있으면 바로 낮은 I/O 우선순위로 양보합니다([예열](#4-예열) 참고).
- 재부팅하면 RAM 캐시는 비지만 쿨다운은 재부팅 전의 마지막 예열부터 셉니다. 표본이 캐시가 식었음을 보이면 그 게임의 쿨다운은 끝납니다(`cooldown ignored, the cache is cold [service start]`).
- 부팅 예열은 최근에 플레이한 게임만 대상으로 합니다. 재시작 전에 이미 예열한 트레이스는 새 트레이스로 다시 취급하지 않습니다.
- 디스크가 계속 바쁘거나 읽을 수 없어도 부팅 15분 뒤에는 구간을 끝냅니다.
- 로그: `<무엇> deferred: boot quiet period`, `boot quiet period ended: ...`.

**시험 PC 에서 잰 것 (2026-11-14)**

시험 도구와 HDD 의 시험 파일로 한 실험이며 서비스 자체나 실행 중인 게임이 아닙니다. 한 스레드가 1 GiB 시험 파일을 `PrefetchVirtualMemory` 로 읽는 동안, 다른 프로세스가 다른 파일의 64 KiB 조각을 쉬지 않고 무작위로, 캐시를 거치지 않고 읽었습니다.

- 읽는 스레드가 보통 I/O 우선순위일 때: 혼자 113 MB/s, 다른 읽기와 함께 99 MB/s, 다른 읽기는 평균 45.9 ms(p99 470.5 ms) 걸렸습니다.
- 읽는 스레드가 낮은 I/O 우선순위일 때: 혼자 51 MB/s, 다른 읽기와 함께 8 MB/s, 다른 읽기는 평균 26.1 ms(p99 84.9 ms) 걸렸습니다. 다른 읽기만 있을 때는 평균 25.0 ms(p99 124.9 ms)였습니다. 매우 낮은 우선순위도 비슷했습니다(혼자 49 MB/s, 함께 11 MB/s, 31.5 ms와 88.7 ms).
- 한가한 디스크에서 실제 예열 목록처럼 1.33 MiB 간격으로 128 KiB 조각을 읽으면 보통 우선순위에서 31.6~38.6 MB/s, 낮은 우선순위에서 13.0~14.2 MB/s 였습니다.
- 그래서 낮은 우선순위는 다른 읽기를 거의 방해하지 않지만, 디스크가 한가해도 예열을 약 2~3배 느리게 합니다. 예열이 다른 읽기가 있을 때만 이것을 쓰는 이유입니다. 이렇게 읽은 페이지도 대기 목록의 우선순위 5 로 들어갑니다. 실제 플레이에서 런처의 시작이 어떻게 달라지는지는 재지 않았습니다.

</details>

### 고정(선택)

`prewarm.pin` 을 켜면 예열한 페이지를 서비스가 읽기 전용 매핑으로 열어 두어 캐시에서 덜 밀려나게 합니다. 스파스 속성 파일은 고정하지 않으며(로그에 건너뛴 파일로 셉니다), 한 PC 의 시험에서 그런 파일은 매핑을 만들면 캐시된 페이지가 버려졌기 때문입니다. 효과 미확인(실험 필요).

<details>
<summary>세부: 언제 켜지고 언제 풀리나</summary>

- 설정에 적지 않으면 물리 RAM 24 GiB 이상에서 자동으로 켜짐, `false` 는 끔, 명시한 `true` 는 RAM 16 GiB 이상에서 동작합니다.
- 가용 RAM 이 여유 아래로 내려가거나 게임·런처가 시작되면 즉시 해제하므로, 런처 업데이트가 파일을 고칠 수 있습니다. 트리거 프로그램으로 뜬 예열은 고정하지 않습니다.

### 배경 메모리 양보

게임 세션 동안 게임과 무관한 프로그램이 메모리를 양보하게 해, Windows 가 예열 캐시부터 가져가지 않게 합니다. 기본으로 켜져 있고(`memory.background_yield`) 안티치트가 있는 게임을 포함해 등록된 모든 게임에 적용됩니다.

- **언제.** 등록 게임의 실행 파일이 시작될 때입니다. 런처나 다른 트리거 프로그램만으로는 시작하지 않습니다(그 프로그램이 시작하는 예열은 그대로입니다). 게임이 종료된 것으로 판정되고 실행 중인 다른 등록 게임이 없을 때, 서비스가 멈출 때(그 뒤에 온 시작 요청은 무시합니다), 설정을 껐을 때, 등록 게임이 마지막으로 실행 중인 것을 본 지 10분이 지났을 때(본 적이 없으면 시작한 때부터 셉니다) 끝납니다.
- **무엇을.** 제외 대상이 아니고(세부 참고) 최근 1분 동안 CPU 를 쓰거나 I/O 를 하지 않은(세부의 "쓰고 있는 프로그램" 참고) 사용자 세션의 프로그램마다 메모리 우선순위가 더 높으면 "매우 낮음"(1)으로 낮추고(Windows 기본값은 5), 가용 메모리에서 게임이 가져갈 것으로 보이는 양을 뺀 값이 하한보다 모자랄 때만(세부의 시점 참고) 그런 프로그램 가운데 큰 것부터 모자라는 만큼만 작업 집합을 비웁니다(32 MiB 이상인 것만). 끝나면 우선순위를 원래 값으로 되돌립니다. 계속 일하는 프로그램(방송, 음성 대화, 동영상을 재생하는 브라우저, 빌드)은 이 두 가지를 모두 받지 않으며, 메모리 우선순위만 "매우 낮음" 대신 "보통보다 낮음"(4)으로 낮춥니다(세부 참고). 고른 모든 프로그램(쓰고 있는 것 포함)의 디스크(I/O) 우선순위는 보통에서 낮음으로 낮춰 그 프로그램의 디스크 읽기가 게임의 읽기를 늦추지 않게 하고, 끝나면 되돌립니다(세부의 디스크 우선순위 참고). CPU 우선순위 등급을 보통에서 "보통보다 낮음"으로 낮추는 기능은 있지만 기본으로 꺼져 있습니다(세부의 CPU 우선순위 참고).
- **하지 않는 것.** 게임·런처·런처 보조·안티치트·Windows 구성요소 프로세스와 서비스 프로세스(세션 0)를 열지 않습니다(낮춘 값을 물려받은 Windows 폴더의 프로그램만 예외이며 세부의 "경로로 제외하는 것"에 있습니다). 다른 프로그램에 하는 일은 이 네 가지(메모리 우선순위, 작업 집합, 디스크 우선순위, CPU 우선순위 등급)뿐입니다. 종료, 일시 중지, 주입, 메모리 읽기는 없습니다. 메모리 예비량(`prewarm.min_free_ram_mib`)·캐시 예산·예열 판정은 그대로입니다.
- **새로 뜬 프로그램과 쓰고 있는 프로그램.** 등록 게임의 실행 파일이 떠 있는 동안 새로 뜬 프로그램은 약 3초 안에 알아채 같은 제외 규칙으로 같은 우선순위 변경을 합니다. 이 경로에서는 작업 집합을 비우지 않습니다(`memory.background_yield_fast`, 기본 `true`). 쓰고 있는 프로그램은 그대로 두지 않고 메모리 우선순위를 "보통보다 낮음"(4)으로 낮춥니다(`memory.background_in_use_memory_priority`, 기본 `true`). 메모리가 모자랄 때는 Windows 가 그 프로그램의 페이지를 우선순위 5 에 있는 예열한 게임 캐시보다 먼저 잘라내 재사용하므로 그 프로그램이 그 페이지를 다시 쓸 때 느려질 수 있습니다. 서비스는 그 프로그램의 작업 집합을 비우지 않으며, `memory.background_in_use_memory_priority` 를 `false` 로 두면 쓰고 있는 프로그램을 예전처럼 그대로 둡니다. 두 변경이 로딩 시간이나 끊김에 미치는 영향은 재지 않았습니다.
- **설정.** `memory.background_yield`(기본 `true`), `memory.background_io_priority`(기본 `true`), `memory.background_cpu_priority`(기본 `false`), `memory.background_yield_fast`(기본 `true`), `memory.background_in_use_memory_priority`(기본 `true`)입니다. 뒤의 넷은 `memory.background_yield` 가 `false` 면 아무것도 하지 않습니다.
- **로그.** `background yield (game started): trimmed N processes (...)` 또는 `... no trim needed (...)`, `background yield ended: ...`. 줄마다의 뜻은 [FAQ](FAQ.ko.md#문제-해결)에 있습니다.

<details>
<summary>세부: 이유, 건드리지 않는 것, 시점, 디스크 우선순위, 부작용, 복구, 끄는 법</summary>

**이유**

- 시험 PC 에서 게임이 10 GiB 안팎을 잡으면 Windows 는 캐시된 파일 페이지에서 메모리를 가져갔고, 예열 캐시가 바로 그 페이지입니다. 다른 프로그램의 파일 읽기도 예열 캐시를 밀어낼 수 있습니다.
- 무관한 프로그램의 작업 집합을 비우면 그 메모리가 Windows 가 캐시보다 먼저 재사용하는 형태로 풀립니다. 메모리 우선순위를 낮추면 그 프로그램이 이후에 읽는 페이지가 캐시를 밀어내지 못합니다.
- Windows 는 여유 페이지, 낮은 우선순위(0~4)의 대기 페이지, 그 뒤에야 파일 캐시가 있는 우선순위 5 의 순서로 메모리를 가져갑니다. 작업 집합에서 비운 페이지는 우선순위 0 목록으로 가며, 대부분 2초 안에 갑니다(시험 PC, 2026-11-14 에 잼). 여유 메모리와 우선순위 0~4 대기 메모리가 남아 있는 동안은 캐시가 재사용되지 않으므로, 비우기는 그것이 모자랄 때만 도움이 됩니다. 시험 PC 의 4시간 11분 세션에서, 캐시 상태를 보지 않던 첫 규칙은 배경 프로그램을 41번 다시 비웠습니다(매번 18~36개 프로그램, 1.6~4.1 GiB). 그다음 규칙은 우선순위 0~4 의 대기 메모리만 셌는데, 예열 캐시 자신이 우선순위 5 이상 목록을 채우므로, 2026-11-21 에는 가용 메모리가 15~22 GiB 인데도 여유분이 0.3~2 GiB 로 보여 한 번에 다른 프로그램 약 3~7 GiB 를 비웠습니다(런처만 떠 있을 때도 여러 번). 지금의 조건은 가용 메모리에서 게임이 가져갈 것으로 보이는 양을 뺀 값입니다(시점 참고).

**시험 PC 에서 잰 것**

2026-11-13 에 실험 도구, 시험 프로그램, 시험 파일로 한 실험이며 서비스 자체나 실행 중인 게임 안에서 잰 것이 아닙니다. 실제 플레이에서 로딩 시간이나 끊김이 얼마나 달라지는지는 재지 않았습니다.

- 배경 프로세스 29개(작업 집합 합 7,664 MiB)의 작업 집합을 비웠더니 가용 메모리가 15,587 MiB 에서 10초 뒤 19,324 MiB 가 됐습니다. 이후 2분 동안 Windows 가 재사용한 페이지 2,398 MiB 는 모두 가장 낮은 우선순위 목록에서 나왔고, 예열 캐시가 있는 우선순위 5 에서는 나오지 않았습니다. 그 프로세스들의 작업 집합 합은 861 MiB 로 줄었다가 2분 뒤 다시 1,900 MiB 가 됐습니다.
- 작업 집합 2 GiB 를 비운 시험 프로그램이 그 전체를 다시 접근하는 데 0.8초가 걸렸습니다.
- 가용 메모리 15.5 GiB 보다 많은 17 GiB 를 어떤 프로그램이 읽는 동안 512 MiB 시험 파일이 캐시에 있었습니다. 가장 낮은 메모리 우선순위로 읽으면 그 파일이 캐시에 남았고(4 KiB 표본 2,000개 중 38개가 느림, 중앙값 6.8 µs), 보통 우선순위(5)로 읽으면 밀려났습니다(2,000개 중 1,980개가 디스크로 감, 중앙값 134 µs).

**건드리지 않는 것**

- 이름으로 걸러 열지 않는 것: 시스템 프로세스와 AsterCache 자신(`AsterCache.*`), 게임이나 게임의 트리거 프로그램으로 등록된 실행 파일, 런처(`steam.exe`, `EpicGamesLauncher.exe`, `GalaxyClient.exe`, `Battle.net.exe`, `RiotClientServices.exe`, `EADesktop.exe`, `upc.exe`, `UbisoftConnect.exe`), 런처 보조(`steamwebhelper.exe`, `EpicWebHelper.exe`, `Agent.exe`, `explorer.exe`, `aster.exe`), [안티치트 호환](ANTICHEAT.ko.md#건너뛰거나-표시하는-파일)의 안티치트 구성요소(EasyAntiCheat, BattlEye, `vg*.exe` 를 포함한 Vanguard, 그 표의 나머지)와 이름이 `BlackCipher*`, `GameMon*`, `SGuard*`, `PnkBstr*`, `*_BE.exe` 인 보조 프로그램, Riot 자체 프로그램(`RiotClient*`, `LeagueClient*`, Riot 게임 실행 파일).
- 세션으로 걸러 열지 않는 것: 사용자 세션 밖의 프로그램, 곧 세션 0 의 서비스 전부.
- 경로로 제외하는 것: 이름 검사를 통과한 프로그램은 먼저 조회 전용 권한으로 열어 경로만 읽습니다. 경로가 Windows 폴더 아래, 등록 게임의 설치 폴더나 허용 폴더 아래, 런처 탐색이 이미 찾은 게임의 설치 폴더 아래(자동 모드가 켜져 있을 때만), 또는 `steamapps`, `Steam`, `Epic Games`, `Riot Games`, `Riot Vanguard`, `Battle.net`, `XboxGames`, `GOG Galaxy`, `EA Games`, `Origin Games`, `Ubisoft`, `EasyAntiCheat`, `BattlEye` 중 하나인 폴더 안이면 건드리지 않으며 쓰기 권한으로는 열지 않습니다. 한 가지 예외가 있습니다. Windows 폴더 아래라는 이유로만 빠진 프로그램(예: `cmd.exe`, `powershell.exe`, `conhost.exe`)이 낮춘 뒤에 AsterCache 가 낮춘 프로그램(또는 그런 자식, 몇 단계 아래든)에게서 시작됐고 물려받은 낮은 값이 그대로면, 세션이 끝날 때 원래 값으로 되돌리는 쓰기만 합니다. 그런 프로그램을 낮추거나 비우지는 않습니다. 그 밖의 이유로 건드리지 않는 프로그램은 여전히 열지 않습니다.

**시점**

- 순서는 대상 고르기, 우선순위 낮추기, 필요하면 작업 집합 비우기입니다. 비운 페이지가 가용 메모리로 잡히기까지 몇 초가 걸립니다. 세션 시작은 그것을 기다리지 않습니다.
- 앞 시작으로부터 60초가 지나지 않은 시작은 무시합니다. 예를 들어 첫 등록 게임 직후 다른 등록 게임이 시작되는 경우입니다. 세션이 끝난 뒤의 다음 시작은 막지 않습니다.
- **세션을 시작할 때** 가용 메모리에서 게임이 가져갈 것으로 보이는 양을 뺀 값이 하한보다 모자랄 때만, 모자라는 만큼(하한 + 게임 예상 사용량 - 가용 메모리)만 작업 집합을 비웁니다. 하한은 `max(4 GiB, 물리 RAM / 4)` 입니다(32 GiB PC 에서 8 GiB). 게임 예상 사용량은 실행 중인 등록 게임의 최근 플레이 기록의 중앙값이며, 예열이 메모리 예비를 정할 때 쓰는 값과 같습니다(시작 때의 가용 메모리에서 처음 10분 안의 최소 가용 메모리를 뺀 값). 쓸 수 있는 기록이 없는 게임은 하한과 같게 잡은 8 GiB 이며 실측한 값이 아닙니다. 쓰고 있지 않은 프로그램 가운데 큰 것부터 비우고, 모자라는 양에 이르면 멈춥니다. 충분하면 우선순위만 낮춥니다(로그: `background yield (game started): memory priority lowered for M, I/O priority lowered for L, CPU priority lowered for C, P in-use processes spared, no trim needed (available A MiB, expected game use G MiB, floor F MiB)`). Windows 의 메모리 통계(대기 목록)를 읽을 수 없으면 아래의 다시 비우기만 못 하며 `background yield: memory lists unavailable, trimming once per session` 을 남깁니다.
- **세션 중에는** 2분마다(30초 점검 때) 그사이 새로 뜬 프로그램(빠른 경로가 뜬 지 약 3초 뒤에 이미 처리한 것을 뺀 나머지)에 같은 우선순위 변경을 하며 쓰고 있는 프로그램을 가리는 규칙도 같습니다. 고른 프로그램은 마지막으로 비운 지 2분 이상 지났고, 캐시(우선순위 5 이상의 대기 페이지)가 실제로 재사용됐고(직전 2분 점검 이후 512 MiB 이상), 가용 메모리가 같은 규칙으로 여전히 모자랄 때만 다시 비웁니다. 모자란다는 것은 가용 메모리에서 게임이 앞으로 더 가져갈 양(예상 사용량에서 이미 가져간 양을 뺀 값)을 뺀 값이 하한보다 적다는 뜻입니다. 이미 가져간 양은 세션 시작 뒤 줄어든 가용 메모리와, 시스템 전체 프로세스 조회(프로세스를 열지 않음)로 읽은 등록 게임 실행 파일들의 현재 작업 집합 가운데 큰 쪽입니다. 그때도 모자라는 만큼만 큰 것부터 비웁니다. 비운 뒤 이전 작업 집합의 절반 이상을 되찾은 프로그램은 활발한 것이므로 그 세션에서 다시 비우지 않고, 비운 직후보다 2배 이상이고 256 MiB 이상 늘지 않은 프로그램도 다시 비우지 않습니다(`active processes skipped` 에 포함됩니다). 비운 직후의 첫 유지(2분 뒤) 한 번만, 비우기 직전보다 가용 메모리가 오른 양에 그사이 게임 프로세스 작업 집합이 늘어난 양을 더한 값이 비운 양의 절반에 못 미치면 비운 메모리가 가용으로도 게임으로도 가지 못한 것이므로 게임이 끝날 때까지 더 비우지 않고 `background yield: not trimmed again, the last trim of X MiB working set raised neither available memory (A -> B MiB) nor the game's working set (+G MiB) by half of it, no more trimming until the game ends` 를 한 번 남깁니다. 비우기 전 작업 집합이 약 552 MiB 이하인 프로그램은 위 두 규칙 때문에 한 세션에서 다시 비워지지 않습니다. 통계를 읽을 수 없으면 다시 비우지 않습니다. 로그: `background yield: trimmed again N processes (X MiB working set, shortfall Y MiB), cache repurposed R MiB in S s, K active processes skipped, P in-use processes spared, available A MiB, expected game use G MiB, floor F MiB`, 캐시는 재사용됐지만 메모리가 충분하면 `background yield: not trimmed again, memory is sufficient (...), cache repurposed R MiB in S s`.
- 메모리 통계를 읽는 데는 프로세스를 열지 않습니다. 시스템 전체 값이고, 서비스가 이를 위해 `SeProfileSingleProcessPrivilege` 권한을 켭니다.

**쓰고 있는 프로그램**

- 최근 1분 동안 CPU 를 쓰거나 I/O 를 한 프로그램은 쓰고 있는 것이며, 작업 집합을 그대로 두고 메모리 우선순위는 "매우 낮음"이 아니라 "보통보다 낮음"(4)까지만 낮춥니다(아래 "빠른 경로와 쓰고 있는 프로그램" 참고). 서비스는 30초 점검마다 한 번씩, 게임이 없을 때도 짧은 기록을 쌓습니다. 프로세스마다 시작한 뒤의 CPU 시간과 읽고 쓴 바이트 누계입니다(프로세스를 열지 않는 시스템 조회 한 번, 약 4 ms). 세션을 시작할 때 한 번 더 읽고, 가장 새 값을 60초 이상 지난 값 가운데 가장 새것과 비교합니다. CPU 사용이 한 코어의 0.5% 이상(100 ns 단위로 초당 50,000)이거나 읽고 쓴 양이 합쳐 초당 32 KiB 이상(디스크, 파이프 등 그 프로세스가 읽고 쓰는 것 전부이며 네트워크는 세지 않음)이면 쓰고 있는 프로그램입니다. 그러므로 처음 비우기 전에 판정하며, 비운 뒤에 판정하지 않습니다.
- 문턱 값의 근거: 2026-11-21 시험 PC 에서 사용자 세션의 프로세스 295개를 30초 간격으로 두 번 읽었습니다. CPU 0.5% 이상이 43개, 1% 이상이 31개였고, 읽고 쓴 양이 초당 16 KiB 이상이 19개, 64 KiB 이상이 16개였습니다. 계속 일하는 프로그램(방송 프로그램, 메신저, 게임 오버레이, 브라우저 프로세스)은 한 코어의 약 1~20% 였고, 대기 중인 터미널·셸·도구 서버는 0.5% 아래였습니다. 값은 그 사이에 잡았고 더 맞추지 않았습니다.
- 판정할 수 없으면 쓰고 있는 것으로 보아, 비우지 않고 메모리 우선순위를 "매우 낮음"이 아니라 "보통보다 낮음"(4)으로 낮춥니다. 기록에 읽은 값이 두 번 미만이거나 간격이 10초 미만일 때(서비스가 막 시작함), 읽지 못할 때, 가장 새 읽기에 그 프로세스가 없을 때입니다. 최근 1분 안에 뜬 프로세스는 시작한 뒤의 누계 전체로 판정합니다.
- 프로그램이 무엇을 하는지 보는 규칙은 이것뿐입니다. 서비스는 사용자 세션 밖에서 돌므로 맨 앞 창이 무엇인지, 어느 프로그램이 소리를 내는지 보지 않습니다. 그래서 곧 쓰려고 하지만 최근 1분은 쉬던 프로그램(곧 전환할 브라우저 탭)은 쉬는 프로그램과 구별하지 못합니다. `memory.background_in_use_memory_priority` 가 켜져 있으면 낮춘 프로그램(물려받은 것으로 기록한 항목은 제외)을 2분마다의 유지 때 다시 봅니다. 일을 시작한 프로그램(게임 중에 들어간 음성 통화)은 "보통보다 낮음"(4)을, 쉬게 된 프로그램은 "매우 낮음"을 받습니다. 바뀌는 것은 메모리 우선순위의 값뿐이며(상태 파일의 원래 값은 그대로), 원래 값이 4 이하였던 프로그램은 그 값보다 높이지 않습니다. 처음부터 꺼져 있으면 시작 때 설정한 값이 그대로 남고, 세션 중에 끄면 "보통보다 낮음"을 받았던 프로그램이 쉬게 될 때 "매우 낮음"으로 바뀝니다.
- 재지 않은 것: 이 프로그램들을 비우지 않고 "보통보다 낮음"까지만 낮추는 것이 실제 플레이에서 게임이나 다른 프로그램에 무엇을 바꾸는지입니다.

**빠른 경로와 쓰고 있는 프로그램**

- **왜 4 인가.** 서비스가 예열 캐시를 위해 만지거나 붙드는 페이지는 메모리 우선순위 5 로 셉니다(서비스는 자기 메모리 우선순위를 바꾸지 않고, Windows 는 우선순위 0~4 대기 목록을 5 보다 먼저 가져갑니다. 위 "이유" 참고). 쓰고 있는 프로그램을 5 로 두면 그 프로그램이 쓰다 놓은 페이지가 예열 캐시와 같은 목록에 섞입니다. 4 로 낮추면 그 페이지가 먼저 재사용됩니다. 서비스는 그 프로그램의 작업 집합을 비우지 않고, 원래 값이 4 이하인 프로그램은 건드리지 않습니다.
- **쓰고 있는 프로그램이 치르는 대가.** Microsoft 문서(`MEMORY_PRIORITY_INFORMATION`)에 따르면 메모리 관리자가 작업 집합에서 페이지를 자를 때 우선순위가 낮은 페이지를 먼저 자릅니다. 그래서 메모리가 모자란 동안에는 Windows 가 이 프로그램의 페이지를 우선순위 5 의 페이지(게임 포함)보다 먼저 자르고 먼저 재사용할 수 있습니다. 그 프로그램이 그 페이지를 다시 쓰면 디스크에서 다시 읽어야 해서 느려질 수 있습니다. 메모리가 넉넉하면 달라지는 것이 없습니다. 다른 프로그램도 평소처럼 돌아야 한다는 조건과 맞바꾸는 점이며 그 크기는 재지 않았습니다. `memory.background_in_use_memory_priority` 를 `false` 로 두면 쓰고 있는 프로그램을 예전처럼 그대로 둡니다.
- **효과는 재지 않았습니다.** 2026-11-23 Call of Duty 플레이에서 대기 목록 우선순위 5~7 의 재사용은 합계 23,831 MiB(약 23.3 GiB)였습니다. 어느 프로그램의 페이지가 예열 캐시의 어느 부분을 밀어냈는지는 기록하지 않았고, 이 변경이 그 값이나 로딩 시간, 끊김에 미치는 영향은 재지 않았습니다. 쓰고 있는 프로그램의 페이지가 우선순위 5 목록에서 4 목록으로 옮겨 가므로 우선순위 5 대기 양과 5~7 재사용 누계(`standby57_reused_mib` 와 이 값을 쓰는 문턱 값)가 예전과 다르게 움직일 수 있어, 이 버전 앞뒤의 기록은 같은 기준으로 비교할 수 없습니다.
- **빠른 경로.** 세션이 활성이고 등록 게임의 실행 파일이 떠 있는 것을 본 동안, 서비스는 1.5초마다 실행 중인 프로세스 번호만 읽습니다(프로세스를 열지 않는 호출 한 번, 약 0.05 ms). 한 번 새로 보이고 다음 점검에도 있는 번호만 대상으로 삼으므로 새 프로그램은 뜬 지 최대 약 3초 뒤에 골라집니다. 한 번만 보이고 다음 점검(1.5초 안팎) 전에 끝난 프로그램은 열지도 상태 파일에 쓰지도 않습니다. 고른 프로그램에는 2분 유지와 같은 선택과 낮추기를 같은 제외 규칙, 같은 순서(이름, 세션, 경로), 경로를 읽는 같은 조회 권한 열기, 같은 쓰기 권한으로 합니다. 그 밖에는 아무것도 열지 않으며, 이 경로에서 작업 집합은 비우지 않습니다. 새 프로그램은 아직 사용 기록에 없어 쓰고 있는 것으로 보고 "보통보다 낮음"(4)을 받으며, 2분 유지에서 다시 판정해 쉬는 것으로 나오면 "매우 낮음"으로 바뀝니다. `memory.background_in_use_memory_priority` 를 끄면 쓰고 있는 것으로 보인 새 프로그램은 빠른 경로에서 메모리 우선순위를 받지 않고, 2분 유지에서 쉬는 것으로 판정되면 예전처럼 "매우 낮음"을 받습니다. 세션이 없는 동안에는 아무것도 돌지 않습니다(세션이 시작될 때까지 잠듭니다).
- **쓰기 직전의 확인.** 유지가 값을 바꾸거나 빠른 경로가 미뤄 둔 프로그램의 값을 낮추기 전에, 그 번호의 프로그램이 고른 프로그램과 같은지 확인합니다. 지금 목록의 이름, 세션이 0 이 아님, 조회 전용으로 연 핸들에서 읽은 생성 시각입니다. 다른 프로그램이 번호를 이어받았으면 아무것도 쓰지 않고 그 기록을 버립니다.
- **한계.** 1.5초 간격의 두 점검 사이에 끝나고 같은 번호를 다른 프로그램이 이어받은 경우는 새 프로그램으로 알아채지 못합니다. 쓰기 직전의 확인이 옛 프로그램인 것처럼 쓰는 일은 막지만, 새 프로그램으로 고르는 것은 2분 유지에서만이고 그것도 이름이 다를 때뿐입니다(쓰기 직전의 확인에서 다른 프로그램으로 판정돼 빠진 번호는 이름이 같아도 다음 유지에서 새로 고릅니다).
- **비용.** 더해진 디스크 쓰기는 상태 파일뿐입니다. 새 프로그램을 하나라도 고른 점검마다 한 번 쓰므로 새 프로그램이 계속 나타나도 분당 최대 약 40회(쓰기에 실패가 있으면 한 번 더)이고, 새 프로그램이 없으면 쓰지 않습니다. 전과 같이 우선순위를 낮추기 전에 통째로 다시 씁니다. 재시작 뒤의 복구가 원래 값을 알아야 하므로 그 쓰기를 뒤로 미루지 않습니다. 빠른 경로가 일으키는 쓰기는 디스크 쓰기 캐시를 비우도록 강제하지 않습니다(비우기 없음). 서비스가 죽어도 운영체제가 살아 있으면 캐시의 내용은 디스크에 내려가고, 전원이 끊기면 PC 가 다시 시작되어 낮춘 우선순위 자체가 사라지므로 되돌릴 것이 없습니다. 세션 시작과 유지의 쓰기는 전과 같이 비웁니다. 스크립트가 짧은 프로그램을 자주 띄우는 PC 에서는 실제 빈도가 상한에 가까울 수 있습니다(게임이 없는 시험 PC 의 2분 표본에서 80번의 점검 가운데 55번에 새 프로그램이 있었습니다). 끝난 프로그램의 기록은 2분 유지 때 치우고 다음 쓰기에서 빠지므로 파일 크기는 살아 있는 항목 수(시험 PC 의 2026-11-23 로그에서 세션 시작 때 약 170개)를 따르며 세션 내내 커지지 않습니다. 메모리 안의 집계는 아무것도 쓰지 않습니다.
- **로그.** `background yield maintenance in S s: fast path saw N new processes (E not eligible), memory priority lowered for M, set below normal for U in-use, switched for W, I/O priority lowered for L, CPU priority lowered for C, F failed` 는 2분 유지와 세션 끝(이때는 `in S s` 가 없음)에, 값 중 하나라도 0 이 아닐 때만 한 줄 남습니다. E 는 평소의 제외 규칙으로 뺀 것과 읽기 전에 사라진 것을 합친 수입니다. 그사이 2분 유지가 먼저 고른 것은 N 에만 들어가고 E 에는 들어가지 않습니다. 세션 시작 줄에는 U 가 0 이 아니면 아낀 쓰고 있는 프로그램 수 뒤에 `(memory priority set below normal for U of them)` 가 붙습니다.
- **이것으로 알 수 없는 것.** 2026-11-23 Call of Duty 플레이에서 웹 브라우저의 쓰기가 가장 큰 초에 긴 프레임이 더 많았지만(510초 중 71초, 나머지는 1,980초 중 70초), 그 브라우저의 프로필·다운로드 폴더와 페이지 파일은 게임의 하드디스크가 아니라 시스템 SSD 에 있었습니다. 인과 방향은 확인되지 않았고(그 순간 게임과 브라우저 사이를 오간 것이 둘을 함께 움직였을 수 있음), 다른 프로그램의 CPU 합계와 긴 프레임의 상관은 다섯 플레이에서 -0.18~+0.10 으로 방향이 일정하지 않았습니다. 그래서 이 변경이 끊김을 없앤다고 말하지 않습니다. 이번 변경은 CPU 우선순위(기존 `memory.background_cpu_priority` 는 그대로 기본 꺼짐)·코어 제한·작업 개체 한도를 더하지 않았습니다.

**디스크 우선순위**

- 대상은 같은 프로그램이고 고르는 규칙(이름, 세션, 경로)도 같으며, 다른 프로세스를 더 열지 않습니다. I/O 우선순위가 보통(2)인 프로그램만 낮음(1)으로 낮춥니다. 이미 낮음이나 매우 낮음(0)이던 것과 보통보다 높은 것은 그대로 둡니다. 매우 낮음은 다른 작업이 거의 멈춰서 쓰지 않습니다.
- 프로그램은 자기 I/O 우선순위를 자기가 띄운 프로그램에 물려줍니다(실측: 낮은 프로그램이 띄운 자식은 낮음으로 시작했습니다). 세션 중에 뜬 프로그램이 낮은 채로 남지 않도록, 낮춘 프로그램이 낮춘 뒤에 만든 자식이 낮은 값 그대로이면 부모의 원래 값으로 기록하고, 메모리 우선순위와 같은 코드·같은 상태 파일로 부모와 함께 되돌립니다. 그 자식의 자식도 같은 방식으로 몇 단계 아래든 이어지며, Windows 폴더 아래의 자식도 포함합니다("경로로 제외하는 것" 참고). 마지막 2분 점검 뒤에 뜬 자식은 되돌리기 직전에 한 번 더 찾고, 비정상 종료 뒤에는 다음 시작 때 찾습니다(상태 파일에 낮춘 시각이 남습니다).
- 이것이 다루지 않는 것: 다른 이유로 건드리지 않는 자식은 물려받은 낮은 값이 그대로 남습니다. 특히 다른 게임 세션이 도는 중에 낮춘 프로그램이 게임을 띄우면 그 게임은 낮은 값으로 시작하고 되돌리지 못합니다. 게임 프로세스는 열지 않기 때문이며 알려진 한계입니다(게임 두 개를 동시에 돌릴 때만 생깁니다). 스스로 값을 바꾼 자식(낮은 값이 아닌 것)과 스스로 배경 모드에 들어간 자식은 건드리지 않습니다. 기록한 부모와 같은 프로세스일 때만 부모로 봅니다. 부모의 프로세스 번호를 지금 다른 프로세스(생성 시각이나 이름이 다르거나, 제외 대상이거나 세션 0 이라 목록에 없는 프로세스)가 쓰고 있으면 그 자식은 물려받은 것으로 보지 않으며, 이를 가리려고 프로세스를 열지는 않습니다. 재부팅 뒤에는 상태 파일의 항목을 부모로 쓰지 않습니다.
- 두 우선순위는 따로 적고 따로 되돌립니다. 한쪽만 낮추는 데 성공했으면 그쪽만 기록하고, 한쪽만 되돌렸으면 못 되돌린 쪽만 상태 파일에 남겨 다시 시도합니다.
- 게임이 읽는 동안에만 낮추지는 않고 세션 내내 낮춥니다. 게임을 열지 않고는 게임 자신의 읽기를 가려낼 수 없기 때문입니다. 쓰고 있는 프로그램("쓰고 있는 프로그램" 참고)도 낮춥니다. 작업 집합은 비우지 않고 메모리 우선순위는 "매우 낮음"이 아니라 "보통보다 낮음"까지만 낮추며, 디스크 우선순위는 효과를 잰 유일한 변경이기 때문입니다(아래 참고). 지금 쓰고 있지만 최근 1분은 쉬던 프로그램이나 CPU 는 쉬면서 소리를 내는 프로그램은 다른 프로그램과 똑같이 낮춥니다. 서비스는 사용자 세션 밖에서 돌며 맨 앞 창이 무엇인지 보지 않습니다. 디스크가 바쁠 때만 그 프로그램이 느려집니다.
- 2026-11-21 시험 PC 에서 실험 도구로 잰 것입니다(서비스가 아니고, 실행 중인 게임 안에서 잰 것도 아닙니다). 게임 대신 쓴 시험 프로그램으로 한 하드디스크에서 초당 30번 64 KiB 를 흩어진 자리에서 읽게 하고, 같은 디스크의 다른 파일을 흩어진 자리에서 읽는 프로그램 4개를 함께 돌렸습니다. 4개가 보통 우선순위이면 시험 프로그램은 초당 13번 읽고 99번째 백분위 지연이 427 ms(265번 중 70번이 100 ms 초과), 4개의 읽기는 합쳐 4.6 MiB/s 였습니다. 4개를 낮음으로 두면 시험 프로그램은 초당 30번 읽고 지연이 92 ms(598번 중 4번이 100 ms 초과), 4개는 합쳐 0.8 MiB/s 였습니다(혼자일 때 시험 프로그램의 지연은 31 ms, 45 ms). 곧 다른 작업이 멈추지는 않지만 게임이 읽는 동안 속도가 약 6분의 1로 떨어집니다. 큰 파일을 순서대로 읽는 프로그램 하나는 보통에서 38.3 MiB/s, 낮음에서 25.6 MiB/s 였습니다(20초씩 세 번, 그중 한 번은 20.2). 다른 읽기가 없어도 그렇게 떨어지므로, 게임이 읽지 않을 때도 그 프로그램은 느려집니다. 흩어진 자리를 혼자 읽는 프로그램은 어느 수준에서나 3.4~3.8 MiB/s 로 차이가 없었습니다. 실제 게임에서 로딩이나 끊김이 얼마나 달라지는지는 재지 않았습니다.

**CPU 우선순위**

- 대상은 같은 프로그램이며 같은 규칙(이름·세션·경로)으로 고르고, 다른 프로세스는 열지 않습니다. 등급은 조회 전용 권한으로 읽고 바꿀 때는 메모리·디스크 우선순위가 이미 쓰는 `PROCESS_SET_INFORMATION` 을 쓰므로 권한을 더하지 않습니다. 기본으로 꺼져 있습니다(`memory.background_cpu_priority`). 2026-11-21 에 초 단위로 기록한 Call of Duty 한 판(전체 CPU 사용률 약 74%)에서, 프레임이 길게 끊긴 초와 아닌 초의 다른 프로세스 CPU 사용에 차이가 없었기 때문입니다. 켜면 등록 게임의 실행 파일이 떠 있을 때만 합니다. 낮춘 프로그램이 띄운 프로그램은 "보통보다 낮음"을 물려받는데 게임 프로세스는 열지 않아 되돌릴 수 없기 때문입니다. 게임의 실행 파일이 프로세스 목록에 나타나기 전에 세션이 시작됐거나(시작 요청이 먼저 올 수 있음), 세션 중에 설정을 켰거나, 이미 우선순위를 낮춘 프로그램이 있는 채 같은 세션 안에서 다시 시작해 CPU 등급 없이 낮춘 경우에는 이미 고른 프로그램을 다음 30초 점검 때 낮춥니다(로그: `background yield: CPU priority lowered for N processes (game started)`). CPU 우선순위 등급이 보통인 프로그램만 "보통보다 낮음"으로 낮추고(유휴로는 내리지 않습니다), 보통보다 높음·높음·실시간·보통보다 낮음·유휴인 프로그램은 사용자나 그 프로그램이 정한 값이므로 그대로 둡니다.
- 끝날 때는 지금 등급이 여전히 "보통보다 낮음"인 프로그램만 보통으로 되돌립니다. 그 사이 사용자나 그 프로그램이 바꿨으면 건드리지 않습니다.
- Windows 는 "보통보다 낮음"을 프로그램이 띄우는 프로그램에 물려줍니다. 낮춘 프로그램이 낮춘 뒤에 띄웠고 지금도 "보통보다 낮음"인 자식은 메모리·디스크 우선순위를 물려받은 자식과 같은 코드·같은 상태 파일로 기록해 함께 되돌립니다(되돌리기 직전과 비정상 종료 뒤에 찾는 것도 같습니다). 부모를 낮춘 뒤 스스로 "보통보다 낮음"으로 시작한 자식은 물려받은 것과 구별할 수 없어 끝날 때 보통으로 돌아갑니다. 디스크 우선순위와 마찬가지로, 낮춘 프로그램이 다른 게임 세션이 돌아가는 중에 게임을 띄우면 그 게임은 "보통보다 낮음"으로 시작하고 되돌리지 않습니다(게임 프로세스는 열지 않기 때문입니다).
- 다른 작업에 주는 영향: CPU 가 모자랄 때만 배경 프로그램이 게임보다 CPU 를 덜 받으며, 코어가 남으면 전처럼 돕니다. 프로그램이 멀티미디어 클래스 스케줄러 서비스(MMCSS)에 등록한 소리·음성 스레드는 그 서비스가 스케줄링합니다. 프로세스 등급이 그 스레드에 영향을 주지 않는다는 것은 Microsoft 문서로 확인하지 못했고, 소리·음성은 재지 않았습니다.
- 확인하지 못한 것: CPU 경합이 실제 플레이의 끊김 원인인지입니다. 시험 PC 의 Call of Duty 한 판에서 프레임이 100 ms 를 넘은 43초 가운데 25초는 디스크 읽기가 5건 이하였고 그 초들의 시스템 CPU 사용률 중앙값은 86% 였지만, 그 플레이에는 어느 프로세스가 CPU 를 썼는지 기록되지 않았습니다(지금은 `play.series` 의 `cpu_other1_name`·`cpu_other2_name` 열에 남습니다). 이 설정이 끊김에 주는 효과는 재지 않았습니다.
- 세션 중에 이 부분만 끄면 디스크 우선순위와 같은 방식으로 다음 30초 점검 때 CPU 우선순위 등급을 되돌리고(로그: `background yield: CPU priority restored for N processes (setting turned off)`), 다시 켜면 다음 점검 때 다시 낮춥니다.

**부작용**

- 비운 프로그램은 다시 쓸 때 페이지를 다시 가져오느라 잠깐 느려질 수 있습니다.
- 게임 세션이 도는 동안 디스크가 바쁘면 배경 프로그램의 디스크 읽기가 느려질 수 있습니다. 의도된 동작이며 멈추지는 않습니다.
- 게임 세션 동안 쓰고 있지 않은 배경 프로그램이 약간 느려질 수 있습니다. 그 메모리를 먼저 재사용하기 때문이며 의도된 동작입니다. 쓰고 있는 프로그램은 비우지 않지만, 메모리가 모자란 동안에는 Windows 가 그 프로그램의 페이지(우선순위 4)를 우선순위 5 의 페이지보다 먼저 잘라내 먼저 재사용하므로 그 프로그램이 그 페이지를 다시 쓸 때 디스크에서 다시 읽느라 느려질 수 있습니다. 메모리가 넉넉하면 달라지는 것이 없습니다.
- 서비스가 관리자 권한이고 데이터 폴더를 믿을 수 있을 때만 동작합니다. 상태 파일을 쓰는 다른 기능과 같은 조건입니다.
- 세션 중에 설정이 바뀔 수 있습니다. 시작할 때마다와 2분마다의 유지 때, 이미 고른 프로그램을 현재 설정으로 이름과 경로를 다시 검사합니다. 새로 제외 대상이 된 것(예: 이제 등록 게임이 된 프로그램)은 목록에서 빼고 우선순위를 바로 되돌립니다.
- 로그에는 프로그램 이름이나 경로 없이 개수와 크기만 남습니다. 프로그램 이름(경로는 없음)은 세션이 도는 동안만 있는 아래의 상태 파일에만 적힙니다.

**상태 파일과 복구**

- 데이터 폴더(`%ProgramData%\AsterCache`)의 `background_yield.json` 에 우선순위를 낮춘 프로그램의 프로세스 번호, 프로그램 이름, 생성 시각, 원래 메모리 우선순위(`priority`), 원래 I/O 우선순위(`io_priority`), 원래 CPU 우선순위 등급(`cpu_priority`, 항상 32 = 보통), 낮춘 시각(`lowered_at`), 물려받은 항목으로 기록했는지(`inherited`), 설정해 둔 메모리 우선순위(`applied`, 1 이 아닐 때만 적으며 비정상 종료 뒤의 시작이 "보통보다 낮음"을 물려받은 자식을 찾는 데 씀)가 적힙니다. 낮추지 않은 쪽은 적지 않으며, I/O 나 시각 항목이 없는 이전 버전의 파일도 전처럼 읽습니다. 우선순위를 낮추기 전에 쓰고 세션이 끝나면 지웁니다. 쓰지 못하면 그때는 어느 우선순위도 낮추지 않습니다(작업 집합은 그래도 비웁니다).
- 서비스가 비정상 종료했으면 다음 시작 때 설정이 꺼져 있어도 그 우선순위를 먼저 되돌리고 `background yield: restored memory priority for N processes left by the previous run, I/O priority for M, CPU priority for K` 를 남깁니다. 프로세스 번호, 이름, 생성 시각이 모두 같은 프로세스만 되돌리므로, 번호를 이어받은 다른 프로세스는 건드리지 않습니다. 파일에 낮춘 시각이 있으면 같은 시작 때, 파일의 프로그램이 마지막 기록 뒤나 서비스가 내려가 있던 동안 띄운 프로그램도 찾아 낮은 값이 그대로인 것을 되돌립니다. 우선순위를 되돌려 쓰지 못한 프로그램은 파일에 남아 다음 종료나 시작 때 다시 시도합니다.

**끄는 법**

- `config.json` 에 다음을 넣습니다.

```json
"memory": { "background_yield": false }
```

- 게임 중에 새로 뜬 프로그램의 빠른 처리만, 또는 쓰고 있는 프로그램의 메모리 우선순위 낮추기만 끄려면 그 부분만 끕니다.

```json
"memory": { "background_yield_fast": false, "background_in_use_memory_priority": false }
```

- 세션 중에 `background_in_use_memory_priority` 만 끄면 이미 "보통보다 낮음"으로 낮춘 프로그램은 세션이 끝날 때까지 그 값을 유지합니다.
- 배경 양보는 두고 디스크 우선순위만 건드리지 않게 하려면 그 부분만 끕니다.

```json
"memory": { "background_io_priority": false }
```

- CPU 우선순위 부분은 기본으로 꺼져 있습니다. 켜려면 이렇게 합니다.

```json
"memory": { "background_cpu_priority": true }
```

- 설정 탭에는 스위치가 없습니다. 서비스가 파일을 다시 읽으며, 세션 중에 껐으면 다음 30초 점검 때 우선순위를 되돌립니다(`background_io_priority` 만 껐으면 디스크 우선순위만 되돌립니다. `background_cpu_priority` 만 껐으면 CPU 우선순위만 되돌립니다).
- `memory` 키는 1.0.3 부터 있습니다. 1.0.2 이하 버전은 이 키가 든 설정 파일을 거부하므로, 되돌리기 전에 지우십시오. `memory.background_yield_fast` 와 `memory.background_in_use_memory_priority` 는 1.0.6 다음 버전부터 있으며, 1.0.6 이하 버전은 이 중 하나라도 든 설정 파일을 거부합니다. `memory.background_io_priority` 와 `memory.background_cpu_priority` 는 1.0.5 부터 있으며, 1.0.4 이하 버전은 이 키가 든 설정 파일을 거부합니다([설정](CONFIGURATION.ko.md)). 되돌리기 전에 서비스를 정상 종료하십시오. 이전 버전은 I/O 또는 CPU 우선순위만 있는 항목을 읽지 못해 `background_yield.json` 에서 버립니다.

</details>

### SOLAR: 캐시 유지와 순서

게임의 예열 뒤 예열한 캐시를 메모리 안에서 다시 만져, 로딩이 가장 먼저 필요로 하는 데이터가 가장 나중에 밀려나게 하고, 다른 프로그램이 밀어내기 전에 다시 만집니다. 일부러 디스크에서 읽는 것은 없습니다. 기본으로 켜져 있습니다(`memory.standby_ladder`). 측정을 포함한 전체 설명은 [SOLAR](SOLAR.ko.md)에 있습니다.

- **언제.** 예열이 게임의 목록을 끝까지 읽은 직후. 그 뒤에는 Windows 의 대기 목록 통계가 이 게임의 페이지보다 먼저 재사용될 페이지가 다 쓰여 가고 있음을 보일 때(다시 쓴 캐시 페이지의 누계가 `max(512 MiB, 0.4 x 먼저 재사용될 양)` 늘었을 때) 약 30초마다 점검하고, 통계를 읽을 수 없으면 10분마다 합니다.
- **무엇을.** 그 게임이 캐시에 가진 것을 읽은 순서의 역순으로 만져, 공통 블록과 로딩 앞부분이 캐시에서 가장 나중에 나가게 합니다. 목록 일부가 캐시에 없음을 발견하면 멈추고, 다음 재예열 점검이 그 게임을 다시 예열합니다. 게임이 여럿이면 한 묶음으로 다룹니다. 한 게임을 새로 고칠 때, 그리고 다른 게임의 예열 스트림이 읽거나 끝나기 직전에, 이미 순서를 정해 둔 다른 게임을 순위가 낮은 것부터 먼저 만져서 한 게임의 읽기가 다른 게임의 캐시를 밀어내지 않게 합니다. 스파스 속성 파일의 페이지는 건너뜁니다. 시험 PC 한 대에서 스파스 파일을 새로 매핑하면 디스크가 그 파일을 다시 읽었기 때문입니다.
- **하지 않는 것.** 게임이 실행 중인 디스크에서 돌지 않습니다(그 게임 자신의 캐시를 게임이 시작될 때와 실행되는 동안 만지는 것은 예외). 게임의 데이터를 일부러 디스크에서 읽지 않고, 메모리를 잠그지 않고, 매핑을 열어 두지 않고(게임이 실행되는 동안 유지 목록을 붙드는 `memory.keep_hold` 는 예외이고 [SOLAR](SOLAR.ko.md#게임이-실행되는-동안의-붙들기-memorykeep_hold)에 설명합니다), 어떤 프로세스도 열지 않으며, 메모리 예비량·캐시 예산·예열 목록을 바꾸지 않습니다. 메모리가 정말 모자랄 때 캐시가 밀려나는 것을 막지는 않습니다.
- **설정.** `memory.standby_ladder`(기본 `true`). 빠진 부분 뒤의 재예열은 `rewarm_minutes` 를 따릅니다.
- **로그.** `<게임>: ladder ordered N MiB in S s`, `<게임>: cache refreshed in memory: N MiB in S s (R MiB repurposed of A MiB ahead)`, `<게임>: ladder found data missing from memory (...), left to the rewarm check`. 줄마다의 뜻은 [SOLAR](SOLAR.ko.md#켜졌는지-확인하는-법)에 있습니다.
- **끄는 법.** `config.json` 에 `"memory": { "standby_ladder": false }` 를 넣습니다. 설정 탭에는 스위치가 없고, 서비스가 파일을 다시 읽습니다. 1.0.3 이하 버전은 `memory.standby_ladder` 가 든 설정 파일을 거부하므로 되돌리기 전에 지우십시오([설정](CONFIGURATION.ko.md)).

## 한가함의 뜻

"한가하다"는 아래를 모두 만족하는 상태입니다.

- 옮길 게임과 같은 드라이브에 설치된 등록 게임이 돌지 않습니다(다른 드라이브의 게임은 보지 않습니다).
- 게임 드라이브 처리량이 30초 동안 연속으로 4 MiB/s 미만입니다.
- AC 전원이 연결됐거나 배터리가 50% 이상입니다.
- Windows 드라이브 최적화(`defrag.exe`, 예약 작업 "드라이브 최적화", `\Microsoft\Windows\Defrag\ScheduledDefrag`)가 돌지 않습니다. 서비스는 프로세스 이름만 보므로 최적화가 어느 드라이브를 처리하는지 알 수 없어 모든 드라이브의 재배치를 기다립니다. 이미 진행 중인 재배치는 낮은 I/O 우선순위(`auto.relocate_io_priority` 의 기본값)일 때만 조각 사이에서 쉬고, 보통 우선순위일 때는 끊지 않습니다. 한 번의 실행에 대해 기다리는 시간은 서비스가 그 실행을 처음 본 때부터 최대 30분이며, 그 뒤에는 다른 조건만으로 판단합니다. 실행이 끝난 직후에도 재배치는 앞당기지 않고 평소 시각에 합니다. 통째 계획이 있는 게임의 배치 검사만 앞당깁니다(재배치 절의 `auto.relocate_layout` 참고). 로그는 `drive optimization started at ...`, `drive optimization ended at ... after N s` 이고, 서비스가 시작될 때 이미 돌고 있었다면 `drive optimization already running when the service started ...` 가, 30분이 지나면 `drive optimization still running after 30 min, relocation no longer waits for it` 가 남습니다.

CPU 사용률은 보지 않습니다. 재배치는 낮은 I/O 우선순위로 대상 드라이브에만 영향을 줍니다. 6시간을 넘게 한가하지 않으면 `service.log` 에 이유(`game running`, `on battery`, `drive optimization running`, `disk busy`) 한 줄을 남깁니다. 게임마다 지금 어느 단계인지는 관리 창의 **상태** 탭과 **게임** 탭의 단계 열에서 볼 수 있습니다.

## 지원 런처

Steam, Epic Games Store, GOG Galaxy, Ubisoft Connect, Riot Client, Windows 제거 목록, Xbox 앱 폴더를 읽습니다. Battle.net 과 EA 앱의 라이브러리는 읽지 않으며, 그 게임은 제거 목록이나 휴리스틱으로 잡힙니다.

<details>
<summary>세부: 런처별 읽는 방법</summary>

**Steam** (예열 트리거 `steam.exe`)

- `libraryfolders.vdf` 와 `appmanifest` 파일. 실행 파일은 게임 폴더에서 가장 큰 `.exe` 이며, 설치 프로그램·재배포 파일·크래시 도구는 제외합니다.

**Epic Games Store** (트리거 `EpicGamesLauncher.exe`)

- `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests\*.item` 의 `LaunchExecutable`.

**GOG Galaxy** (트리거 `GalaxyClient.exe`)

- 레지스트리 `HKLM\SOFTWARE\WOW6432Node\GOG.com\Games`.

**Ubisoft Connect** (트리거 `upc.exe`, `UbisoftConnect.exe`)

- 레지스트리 `Launcher\Installs` 의 `InstallDir` 값.

**Riot Client** (트리거 `RiotClientServices.exe`)

- `%ProgramData%\Riot Games\Metadata\<제품>.live\*.product_settings.yaml` 의 `product_install_full_path`. Vanguard 안티치트로 표시합니다. `.live` 가 아닌 항목(예: PBE)은 제외합니다.
- 리그 오브 레전드(`LeagueClient.exe`, `League of Legends.exe`)와 전략적 팀 전투는 같은 실행 파일 이름을 쓰며, 같은 폴더면 합칩니다.
- 발로란트는 `VALORANT.exe`, `VALORANT-Win64-Shipping.exe` 를 씁니다. 그 밖의 제품은 폴더에서 가장 큰 `.exe` 입니다.

**Windows 제거 목록** (트리거 없음)

- HKLM·HKCU 의 `Uninstall` 레지스트리(32비트 포함). 설치 폴더가 HDD(시스템 드라이브가 아님)이고 1 GiB 이상이며, Microsoft·Intel·NVIDIA 등 일반 소프트웨어 게시자가 아니고, 런처 본체 폴더가 아닌 항목을 씁니다.
- exe 는 폴더에서 가장 큰 `.exe` 입니다. Battle.net·EA·넥슨·호요버스 등 독립 설치 게임이 여기로 잡힙니다.
- 런처 제외 단어에 걸려 건너뛴 항목은 서비스가 시작할 때 현재 규칙으로 exe 를 다시 고르며, 로그에 한 줄을 남깁니다.
- 한계: 런처형 폴더는 엉뚱한 exe 가 골라질 수 있고, 게임을 실제로 실행하면 휴리스틱이 실제 exe 를 더합니다.

**Xbox(Microsoft Store)** (트리거 없음)

- 각 HDD 의 `XboxGames\<게임>\Content` 폴더. exe 는 가장 큰 `.exe` 입니다. 읽을 수 없는 폴더는 건너뜁니다.

**확인한 것과 확인하지 못한 것**

- GOG 와 Ubisoft 읽기는 아직 실제 PC 에서 확인하지 않았습니다. Riot 읽기는 시험 PC 의 D: (HDD) 에 있는 리그 오브 레전드가 잡히는 것을 확인했습니다. Xbox 읽기는 시험 PC 에 해당 폴더가 없어 확인하지 못했습니다.
- `Battle.net.exe`, `EADesktop.exe` 는 예열 트리거 프로그램으로만 적혀 있으며, 서비스가 이 런처들의 라이브러리를 읽지는 않습니다.

</details>

## 휴리스틱 감지

등록되지 않은 프로세스가 HDD 볼륨의 exe 로 시작해 20초 안에 256 MiB 이상을 읽고, 폴더가 게임처럼 보이면 게임으로 보고 등록합니다. 트레이스는 다음 실행부터 기록합니다.

<details>
<summary>세부: 제외 대상과 폴더 검사</summary>

- **제외 대상.** Windows 폴더, AsterCache 자신, 런처와 도구 프로그램, `auto.ignore_exes` 의 exe.
- 경로에 `\bin\Debug\`, `\bin\Release\`, `\obj\`, `\.git\`, `\node_modules\`, `\AppData\Local\Temp\` 가 있는 exe 도 제외합니다.
- 내장 도구 exe(`testhost*`, `dotnet`, `msbuild`, `vstest*`, `python*`, `node`, `java*`, `powershell`, `pwsh`, `cmd`, `conhost`, `explorer`, `7z*`, `winrar`)도 제외합니다. 이 고정 목록은 `auto.ignore_exes` 와 별개입니다.
- **폴더도 게임처럼 보여야 합니다.** 256 MiB 이상 파일이 있거나 런처 흔적(`steam_appid.txt`, `.egstore`, `goggame-*.info`, Steam 매니페스트)이 있어야 합니다. 그래서 `AppData\Local\Temp` 아래 설치된 게임은 잡히지 않습니다.

</details>

## 설정

모든 `auto.*` 키의 뜻과 기본값은 [CONFIGURATION.ko.md](CONFIGURATION.ko.md)에 있습니다.

- `"auto": {"enabled": false}` 는 자동 모드 전체를 끕니다. `discover`, `trace`, `relocate` 는 각 단계만 끕니다.
- 상태는 `%ProgramData%\AsterCache\auto_status.json` 에 쓰입니다(서비스만 씁니다). `aster status` 출력에 `"auto"` 키가 있고, `aster discover [--json]` 은 런처 게임 목록을 읽기 전용으로 보여 줍니다.
- 수동 버튼(등록, 트레이스 수집, 계획 만들기, 재배치 실행, 지금 예열)은 자동 모드와 상관없이 그대로 동작합니다.

<details>
<summary>세부: 화면에 나오는 것</summary>

- 관리 창 상태 탭에는 게임마다 "자동: Frostpunk 발견 → 트레이스 수집 중 → 재배치 대기 → 재배치 중 → [완료]" 형태의 줄이 나오고, 게임 탭에는 출처·단계·안티치트 열이 있습니다.
- 학습 단계는 "첫 실행: 학습 중 (선행 읽기 n MiB)", 예열 뒤에는 "예열됨" 으로 표시됩니다.
- 게임별 상태 줄에는 `예열 직후 적중 N%`(예열이 끝난 직후에 잰 적중률)과 `SSD 보조 N GB`(게임의 SSD 사본 크기)도 나옵니다.
- 트레이 알림은 발견, 재배치 완료, 첫 실행 완료("첫 실행 기록을 마쳤습니다. 이 기록으로 계획을 세웁니다: <게임>") 때 보냅니다. 알림 창은 설정 탭의 **알림** 체크 상자(`tray.json` 의 `notifications.enabled`)로 끌 수 있으며, 내용은 트레이 로그에 그대로 남습니다.

</details>

## 효과

자동 모드가 게임 전체 로딩 시간을 얼마나 줄이는지는 재지 않았습니다. 시험 PC 의 서비스 로그(2026-11-02 ~ 2026-11-10)를 집계한 실사용 기록이 있으며, 통제된 벤치마크가 아니고 예열이 없을 때와 비교하지 않았습니다.

- League of Legends(Vanguard): 게임 시작 감지 10회, 트레이스 2회 수집 뒤 8회 건너뜀, 재배치 완료 4회, 예열 직후 적중률 100%(마지막 값 1개).
- Call of Duty(Ricochet): 게임 시작 감지 62회, 트레이스 수집 14회 시작, 재배치 완료 5회, 예열 직후 적중률 75%(마지막 값 1개).

집계 방법과 표본 수는 [실사용 기록](RESULTS_SUMMARY.ko.md#실사용-기록), 안티치트 게임에서의 정책은 [안티치트 호환](ANTICHEAT.ko.md)에 있습니다. 계정 제재 여부는 보증하지 않습니다.

## SSD 보조 저장 (선택)

기본으로 꺼져 있습니다(`auto.ssd_tier.enabled`). 꺼져 있으면 AsterCache 는 파일을 건드리지 않습니다. 다만 이전 실행이 남긴 링크는 되돌립니다. 켜면 HDD 게임의 파일 중 핫 바이트(트레이스가 읽은 바이트) 비율이 가장 높은 것을 예산 안에서 SSD 에 복사하고 그 자리에 심볼릭 링크를 둡니다.

<details>
<summary>세부: 고르기, 적용, 유지, 되돌리기</summary>

**고르기와 적용**

- 파일마다 핫 바이트(트레이스가 읽은 부분)를 파일 크기로 나눈 값을 매깁니다. 값이 높은 파일부터 예산(`budget_gib`, 게임당 기본 8 GiB, 1~4096) 안에 들어가는 만큼 고릅니다. 게임의 `.exe`·`.dll` 파일과 `allowed_roots` 밖의 파일은 고르지 않습니다.
- 파일을 SSD 에 복사하고 크기와 표본 SHA-256 을 확인합니다. 저널에 기록한 뒤 원본을 같은 폴더의 `<이름>.aster-orig` 로 이름을 바꾸고, 그 자리에 심볼릭 링크를 둡니다. 링크로 크기를 다시 확인합니다. 한 파일이 실패하면 그 파일만 되돌립니다.
- `root` 는 `"auto"`(시스템 드라이브가 SSD 면 그곳, 아니면 여유가 가장 큰 다른 SSD, 폴더는 `AsterCache\tier`) 또는 SSD 위의 절대 경로입니다.

**언제 하나**

- 한 번에 게임 하나씩, 게임이 꺼져 있고 HDD 이며 시스템 드라이브가 아니고 안티치트 흔적이 없으며 재배치가 끝난(또는 재배치가 꺼진) 게임에만 합니다.
- 재배치와 같이 한가함을 기다리며, 끝내지 못한 게임은 6시간 뒤에 다시 시도합니다.

**유지**

- 자동 모드가 재배치를 점검할 때마다(약 30초마다) 저널을 확인합니다. 사본이 없거나 크기가 다르면 바로 되돌립니다. 파일이 일반 파일로 바뀌었거나 사본이 링크를 통해 바뀌었으면 stale 로 표시하고 그대로 둡니다.
- SSD 여유가 1 GiB 아래면 새 사본을 만들지 않고, 가장 오래된 게임부터 되돌립니다. 예산이나 폴더 설정을 바꾸면 그 게임을 되돌린 뒤 새 설정으로 다시 적용합니다.

**되돌리기와 명령**

- `aster tier revert --game <이름>` 또는 `--all` 은 링크를 지우고 원본 이름을 복구합니다. 사본은 `aster tier clean` 이 쓰지 않는 것을 지울 때까지 tier 폴더에 남습니다. 제거할 때는 모든 게임을 먼저 되돌립니다.
- 저널은 `%ProgramData%\AsterCache\tier\<게임>.json` 입니다. 저널을 읽을 수 없으면 그 게임은 아무것도 건드리지 않고 건너뛰며, 로그에 한 줄을 남깁니다.
- 명령: `aster tier status`, `aster tier apply --game <이름>`, `aster tier revert --game <이름>` 또는 `--all`, `aster tier clean` (apply·revert·clean 은 관리자 권한 필요).
- 설정 탭의 자동 모드 항목에 체크박스와 예산이 있고, 게임별 상태 줄에 `SSD 보조 N GB` 가 나옵니다.
