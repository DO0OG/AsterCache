# Automatic mode

> Details that continue from [Getting started](../README.md#getting-started) in the README: the stages of what the service does by itself, the supported launchers, and the setting keys.

Automatic mode is on by default. In the usual case you do not need to register games or set anything. Each part can be turned off in the **Automatic mode** group of the Settings tab, or in `config.json`. Setting names are listed here; their meanings and defaults are in [CONFIGURATION.md](CONFIGURATION.md). Folded blocks (click to open) hold the conditions, exceptions, and numbers.

Each game can also be limited. Its **policy** (`games[].mode`: `inherit`, `prewarm_only`, `relocate_only`, or `off`) decides which stages may act on it, and **pause** (`games[].paused`) stops new work for it. A paused game, or one set to `off`, is not traced, prewarmed, or relocated. `prewarm_only` allows prewarming and planning but no relocation or periodic re-apply. `relocate_only` allows relocation but no prewarm, start-up stream, or pinning. Neither setting overrides the anti-cheat gate or the ban on pinning. A game that is no longer allowed to prewarm drops its waiting prewarm entries, and it resumes at the next check when allowed again.

## The stages at a glance

| Stage | One line |
|---|---|
| 1. Discovery | Finds HDD games in launcher libraries and registers them. |
| 2. Recording reads | Records what a game reads while it loads (the trace). |
| 3. Relocation | Moves the pieces the game reads into one zone (a contiguous area of the disk) while the PC is idle. |
| 4. Prewarm | Reads the zone into RAM before the game starts. |
| 5. Upkeep | Re-prewarms, tops up, retries, rechecks the layout, and keeps the prewarmed cache in order ([SOLAR](#solar-keeping-the-cache-in-order)). |
| 6. While a game runs | Yields the disk to the game, lets unrelated background programs give up memory, and records how the disk behaved. |
| 7. Drive recovery wait | Waits for an SMR drive to settle after bulk writes. |

"Idle" is defined in [What "idle" means](#what-idle-means).

## Sources before the first run

A game with no trace takes its first layout data from the first source below that applies: a shared profile, a Windows prefetch record, an engine profile, or the whole folder. The first real trace replaces it.

<details>
<summary>Details: the four sources</summary>

When the first real run records a trace, the plan made from it replaces the earlier one, trying the same zone position first (the old plan is kept as `.stale`).

- **Shared profile** (`auto.shared_profiles`, on by default). Once a week the service downloads one zip over HTTPS and looks each game up by Steam app ID and depot manifest IDs, Epic app name and version, or exe size and sample SHA-256.
- A profile is used only when the file size and sample hash on this PC match. Offline or 404 responses are skipped silently. The download is capped at 64 MiB. The shared repository is still being prepared.
- **Windows prefetch record** (`C:\Windows\Prefetch\*.pf`). Used when the SysMain service runs and the application bit of `EnablePrefetcher` is on. The service only reads the game's `.pf` files.
- It builds a boot trace from the files in the install folder, skipping files flagged "do not prefetch". The ranges the record refers to, plus 64 MiB before and after each (merged where they overlap, no file size limit), are moved into the zone in physical order.
- If the zone covers less than 30 % of what a play reads, the status detail shows `partial (N%)`. The management window shows this as "relocated (prefetch)".
- **Engine profile** (Unity, Unreal, or Source), prewarmed without a trace.
- **Whole folder**, prewarmed without a trace when the folder fits the RAM budget.

</details>

## Stages

### 1. Discovery

- **When.** Ten seconds after the service starts, then every hour.
- **What.** Reads the [supported launchers](#supported-launchers) and registers each HDD game with `"source": "auto"`. A process that reads a lot after it starts is caught by the [heuristic](#heuristic-detection).
- **Does not.** Register SSD games, resident utilities, or a game in the same folder as one you registered by hand. A game on the Windows system drive is only prewarmed.
- **Settings.** `auto.discover`, `auto.ignore_exes`.
- **Log.** `auto <launcher>: registered <name> (<exe>)`

<details>
<summary>Details: limits, skipped games, resident utilities</summary>

**Limits and skips**

- The list holds up to 32 games. When it is full, launcher discovery stops, and a game that is actually run and detected replaces the least recently used automatic entry.
- A game is skipped if its volume label is empty or longer than 32 characters (one log line), or its exe name or an overlapping folder is already registered.
- Games on an SSD are not registered, traced, or relocated. On an HDD that is the Windows system drive, a game is only discovered and prewarmed (status "prewarm only (system drive)").
- A game you remove in the management window has its exe added to `auto.ignore_exes`, so it is not registered again (up to 64 exes; the oldest are dropped).
- Other log lines: `auto <launcher>: skipped <name>: volume has no usable label`, `auto discovery: game list is full, skipping the rest`.

**Resident utilities**

- Desktop utilities that are not games and stay running once started (Wallpaper Engine, YoloMouse, Lossless Scaling, OBS Studio, SteamVR, and the like) are never registered.
- A fixed list of Steam app IDs and exe names excludes them from launcher discovery and the heuristic. This list is separate from `auto.ignore_exes`.
- One already registered automatically is unregistered once after the service starts, even if it is running, unless files are being relocated at that moment (then at the next discovery). Entries you registered yourself are not touched.
- Files already moved stay where they are. With the SSD assist storage (`auto.ssd_tier`), the links of a game that is no longer registered are reverted. A game that is no longer registered is not prewarmed or pinned.
- Log line: `auto: unregistered <game> (resident utility, not a game)`.

</details>

### 2. Recording reads (trace)

- **When.** The first time a registered game without a trace starts (the trace is recorded from the next run, since the detected start has already begun loading). It repeats for a few plays.
- **What.** Records the game's reads with a live ETW session and saves `plans\<name>.trace.json`, the same file as the manual **Capture trace** button.
- **Does not.** Trace a game whose anti-cheat forbids it ([ANTICHEAT.md](ANTICHEAT.md)), or open the game process. Reads are only observed through ETW.
- **Settings.** `auto.trace`, `auto.io_summary_enabled`, `trace_cap_seconds`, `trace_cap_mib`, `trace_runs`, `trace_merge_min_mib`, `trace_late_*`.
- **Log.** `<game>: auto trace started (run 2/3)`, `<game>: auto trace ended (<why>), N read events saved`

<details>
<summary>Details: caps, several plays, zone extension, first-run learning</summary>

**Recording**

- The session is named `AsterCacheAutoTrace`. The raw recording window closes at the first of: the game exiting, 1800 seconds (`trace_cap_seconds`), or the larger of 6144 MiB and twice the zone limit (`trace_cap_mib`).
- If a cap is reached while the game is still running, the raw recording window closes; cleanup, saving, and merging wait until it exits. With `auto.io_summary_enabled`, the same ETW session keeps observing through game exit. It continues tracking target processes and file names for read-mode attribution, but does not add to the frozen raw records.
- With `auto.io_summary_enabled`, the session also collects `DiskIORead` completions (the only keyword added) and target-process `FileIORead` request flags. While the game runs it sums disk completions per request (disk number, byte position, size): count, latency sum and maximum, first time, and paging count (IRP flag 0x2). The disk-read IRP is not the IRP of the file read, so linking by IRP at event time does not work (measured: 0 of 49,266 matched), and the file is not known at event time.
- File-read flags are classified by bits: paging when 0x02 (`IRP_PAGING_IO`) or 0x40 (`IRP_SYNCHRONOUS_PAGING_IO`) is set; no-cache when 0x01 (`IRP_NOCACHE`) is set without paging; otherwise cache. The session adds per-file request counts and bytes for all three classes, counts reads whose names remain unknown, and records the counts for up to 32 distinct flag values plus one overflow bucket. This continues while the raw window is frozen or a read window is closed.
- After the game exits, the service reads the layout of every file under the game's allowed roots with file-attribute queries (no file contents), converts each request to (file, 64 KiB block) rows, and writes them beside each run file as `.io.json`. A request that crosses an extent, block, or file boundary splits its bytes by overlap and its latency by bytes, so the totals are preserved; a block row's count is the number of requests that touched the block, and request-level totals are in the quality section. The conversion runs on a low-priority thread and logs the files scanned and the time it took. It is skipped if a game is already running on the disk, and it stops (only the summary is dropped, the raw trace is still saved) when the service stops, when any registered game starts, or after a 30-second budget; the log says which (`I/O summary not built (service shutdown / a game started / time budget / a game is running)`). Relocation, replanning, and extension wait `rewarm_after_exit_min` after the game exits, and the plan and journal state is compared before and after the conversion: if it changed, the summary is dropped. The conversion time has not been measured on a large game.
- Version 4 `.io.json` files also contain `read_modes` rows with each in-root file's cache, no-cache, and paging request counts and bytes. The quality section records files dropped at the 262,144-file cap, unnamed reads, flag-value counts, and the time read-mode observation ended. Version 3 files remain readable and mean read modes are unknown. The service keeps tracing until two distinct play session IDs have valid read-mode summaries; saving the same session again does not count as another play. The service and `aster trace --live --io-summary-root` log a `read modes:` line immediately after `I/O summary:`. Each row also has `open_options` (optional; 0 or absent when unknown): the options the target process gave when it opened the file, limited to sequential (0x4), no buffering (0x8), and random access (0x800), taken from the kernel file-create event, so a file that was already open when the observation began has 0. The `read modes:` line ends with `opened with sequential N, random access M, no buffering K files`. This follows the definition of the event and has not been checked in a live trace.
- Reads the service itself issued (the start stream and prewarm) are left out of the block rows. The disk-read event does not say which process asked: a mapped or cached read is issued as a paging read, often by a system thread, so process or thread IDs cannot separate the service from the game (the session does not even enable thread events). Instead, while a trace session observes, the service notes the file, byte range (widened to 4 KiB pages), and start and end time of each batch it read to the end (`SelfReadLog`; a batch that was stopped or had a file that could not be opened is not noted). Each observation keeps its own notes, up to 524,288 ranges; past that the later ones are dropped and the log says how many. When the summary is built a disk read is left out only if it was the only read of that disk range (count 1), it was a paging read, it began inside a raw recording window (outside the windows the game's own reads are not recorded, so they cannot be checked and the read stays), its whole range is covered by noted ranges of batches whose time (plus 10 seconds, because mapped reads can continue after the call returns) contains it, and the game's trace has no read of an overlapping range in that time. A read that is only partly covered stays. Reads the game made in the same range at the same time stay. The log line ends with how many reads and MiB were left out; `.io.json` stores them under `self_read`, and they are not part of `linked`. This applies to new summaries only; saved ones are not rewritten, and merging does not remove the earlier mixing. Limits: reads of the service's learning read-ahead are not noted; read-ahead that the cache manager adds beyond a noted range stays; a game that maps the same file (page-fault reads leave no file-read record) can still be taken for the service inside a window; paths are compared only ignoring case, so a different spelling of the same path (`\?\`, slashes, 8.3 names) is not matched. The rule has not been run against a real game yet.
- Reads are classified as: linked to a block; other disk (not the disk of the game folder); same disk but inside no file extent; not converted (NTFS-compressed or encrypted files, volumes that span several disks, volumes that are not NTFS or whose file system cannot be read, and game folders that are themselves or sit under a junction, symbolic link, or mount point, which are counted as skipped volumes); and dropped at the request-table limit (262,144 distinct requests; the dropped count, bytes, and latency are kept and `truncated` is set). Sparse holes are not in the layout, so nothing is attributed to them. A file written after the observation started is marked "changed during session" in the file table. Latency runs from when the request went down the disk stack to completion, so waiting in front of the device is included and it is not pure service time; with many overlapping requests the sum can be larger than the real stall time. If several files share the same disk range (hard links, block cloning), the range is attributed to one of them only or counted as "inside no file extent"; the totals stay exact but the per-file split is not. This summary does not change the trace or the plan input.
- A measurement-only follow-up that is too small to save as a run writes its summary to a capped `.io-only.NN.json` file beside the trace. Summaries include a session ID and the raw trace fingerprint so stale data cannot attach to different trace content. If a game update changes only a file that is not in a summary's file table, the summary stays and only its fingerprint is renewed.
- The trace records only reads that went to disk, so reads already served from the cache may be missed, and some of the first reads before the session starts may be missed too.

**Late windows**

- If the game is still running when the first window ends, the first late window opens right after it. It records for `auto.trace_late_window_seconds` seconds. Each later window opens `auto.trace_late_interval_min` minutes after the previous one ends, up to `auto.trace_late_windows` windows in total. The number of windows, the window length, and the gates that forbid tracing are unchanged. The interval is counted from the end of the first late window, not from the end of the first window.
- The session stays open from the first window until the game exits. The raw recording window closes after the last late window or a cap; when the summary is enabled the session keeps counting disk-read completions until the game exits. Reads outside open windows are left out of the raw trace, and files are written only after the game has exited. If the service shuts down after the raw recording ended, the raw trace is saved and the summary is not built. A new session per window could not tell which file a read belonged to if the game had opened that file before the window began, so those reads were dropped and a late window saved nothing; keeping one session lets the later windows save them. This was reproduced with a test program; it has not been confirmed with a real game yet.
- The raw read cap counts only the reads inside open windows. The disk summary includes the disk reads of the full session and records event loss, the request-table limit, and the block-table limit in its quality section.
- Keeping the session open means Windows delivers file events to the service for the whole play, outside the windows too. Its CPU cost has not been measured. Each window writes `<game>: trace window ended, N reads, P target processes, L events lost so far` to the service log; if the late windows save nothing, look at `N`. When the session stops, `trace session stopped: L events lost, M reads dropped (name unresolved), K file names, R records` gives the total; `M` should be small next to the total reads.
- A late window also opens when a registered executable of the same game starts while the trace session is alive (a map load that restarts the game program), so that load's read order is recorded even if it falls between the timed windows. The service already detects these starts; the next late window that is still left opens at that moment instead of waiting for its time. If a window is already open or no window is left, nothing happens, so the number of windows, the window length, the memory and event limits, the anti-cheat gate, and the running-game gate are unchanged. After a window opened this way ends, the next timed window opens one interval later as usual, so the two kinds never overlap. The log line is `<game>: late window k/N started at a target start (<exe>)`. Not yet confirmed with a real game.
- Games whose anti-cheat forbids tracing never get a session, so none of this applies to them ([ANTICHEAT.md](ANTICHEAT.md)).

**Several plays**

- The next plays are recorded the same way until `trace_runs` are collected, each saved as `plans\<name>.trace.runN.json`; the automatic disk-read summary is saved beside it as `.trace.runN.json.io.json`.
- `trace.json` becomes the union of their blocks (the first run's access order, then blocks first seen in later runs), replaced atomically. The status column shows `trace 2/3` meanwhile.
- When the run-file number limit is reached, the oldest run is replaced and the merged block list is kept.
- Once the merge gain is too small and collection stops, the game is traced once more if any of these holds since its last valid run: 5 plays, 7 days, or a detected game update.
- Next to the trace, the service also writes a stage index for the stage stream ([While a game runs](#6-while-a-game-runs)): the file `.stages.json` and an attempt counter `.stages.tried`. A game without an index is traced up to two more times. If no valid disk-read summary exists, the service can also trace up to two more times; one play can satisfy both needs. The same holds when the load-refill list was built from fewer than two plays with recorded start times: the next play is traced, at most three more times in total (two plays are missing at most, plus one spare for a play whose start time was not recorded), counted in `.loadrefill.tried`. When the service decides not to trace a started game it logs one line such as `auto trace not needed (valid 20/limit 8, relearn no (plays 3/5), stage index yes, io summaries 2, load list from 1 timed plays)`; the same line for the same game is logged once per service run.

**Zone extension**

- If the merged hot set (the blocks the traces read) is at least `trace_merge_min_mib` larger than the plan's, and the game is not running, the zone is extended in place.
- Blocks already in the zone stay and only new blocks are appended after them, within `max_zone_mib` (the earliest run's blocks win), through the same idle, daily-limit, and write-budget checks as any relocation.
- If the region after the zone is not free, the extension is skipped, the previous plan stays, and it is retried only when a newer play changes the trace. Log line: `<game>: zone extension blocked: ...`.
- When the zone has already reached its size limit, blocks that the merged trace holds but that no longer fit in it are not moved. Without moving anything (and so without writing to the game drive), they are added to the game's prewarm list instead, as long as the whole list stays inside the cache budget (`prewarm.max_cache_mib`, half of physical RAM by default). When the list is cut to fit memory, they rank after the zone's observed ranges (see [Order and budget](#4-prewarm)), and the start stream does not read them. Log line: `<game>: prewarm list gained N MiB of blocks outside the full zone`.

**First-run learning (experimental, off by default)**

- While the trace is recorded, the service can also read ahead. It is off (`auto.learn.enabled` is `false`; no gain in the E7 to E7f first-run read-ahead measurements, see [RESULTS_SUMMARY.md](RESULTS_SUMMARY.md#e7-first-run-read-ahead)).
- When on, it reads ahead only in files the game reads sequentially: 6 forward reads in a row, each at most 4 MiB past the end of the previous read, and at least 8 MiB of that file read.
- Such a file is read ahead in 16 MiB steps from the current position, up to `auto.learn.window_mib` further, without waiting for gaps in the game's reads (`auto.learn.mode` `"stream"`, the default). With `"gap"`, it reads only after 100 ms of quiet, in 1 MiB requests.
- Reads come from the service's own process, with one reader thread, low I/O priority, and the most recently read file first. Files the game has opened exclusively are skipped.
- The total is at most the game's reads × 1.5 + 64 MiB, and stays within `auto.learn.max_total_mib` and the free-RAM reserve (`min_free_ram_mib`). Only games on an HDD that is not the system drive are learned.
- The other modes `"bounded"` and `"adaptive"` are experimental variants; see [CONFIGURATION.md](CONFIGURATION.md).

</details>

### 3. Relocation

- **When.** After a trace exists, the game is not running, and the PC is idle, one game at a time.
- **What.** Plans a zone, moves the pieces into it (journal and SHA-256 sample check), confirms the layout, then prewarms the zone.
- **Does not.** Run while a game runs (a move in progress stops after the current fragment), move compressed or encrypted files, move a sparse file that also has another excluded attribute, fill the holes of a sparse file or change its attributes, or change file content. A failed check reverts from the journal.
- **Plans made before sparse files could be relocated.** A plan made by an earlier version does not record the allocated ranges of its sparse files, so applying it skips those files. Once per service run, for a game whose relocation is done and whose source files are unchanged, the service adds the current allocated ranges as the baseline and replaces the plan by planning only the remaining part again: pieces already in place stay, and the sparse pieces not yet in place are assigned one new contiguous free run that avoids the zones other plans reserve. The log line starts with `legacy plan replaced`. If no free run is large enough, it logs `legacy plan not replaced, no free run of N clusters` and tries again only on the next service start. The replacement moves nothing and does not change the game's state; the periodic re-apply moves the pieces within its usual limits (idle disk, no game running, daily budget). Because the targets change, the next layout check may log `layout degraded` and then apply again. A sparse file whose physical pieces do not fit the 16-cluster move unit is left out of a new plan as a whole: `<game>: N sparse file(s) left out of the plan, their pieces do not fit the 16-cluster move unit`.
- **Whole-file layout (`auto.relocate_layout`).** The default is `whole_file`. `ranges` is the layout described above. With `whole_file` the plan puts each chosen file in the zone as one whole piece, in the order of its first access, instead of only the pieces the play read. A file is chosen when it is at most twice the size of what the plan reads from it and it is not compressed or encrypted, not rewritten by the game, and has no holes (a sparse file with holes stays where it is). Files are taken in the order of first access until the zone is full (the zone is at most `max_zone_mib`); the files after that stay where they are (in this section, "left in place" means not moved), and so do a file larger than the whole daily budget (`max_relocate_gib_per_day`, when it is not 0). On one PC with Windows Scheduled Drive Optimization enabled on a hard disk, `ranges` placement was observed to be undone and put back again and again. Whole-file placement remained after the defragmentation stage on test files and one game; its state after the free-space consolidation stage was not checked, and the effect on load time has not been measured. If `config.json` has `ranges` written for `auto.relocate_layout`, that value is followed.
  - **Pause after repeated re-placement (both layouts).** The service counts a round when, with the source files unchanged, pieces it had already placed lost their place and it moved them again. What it had placed is the tasks the journal under that plan records as `done` and, when the earlier plan was made by a replan of the remaining part, also the part that plan left in place because it was already there (recorded as `in_place_bytes` and listed as tasks). When the service replans, it checks once where those pieces are now; if at least 64 MiB of them is no longer where the plan put them (the same minimum as the daily count of relocations), the first move after that replan is a round. A new plan candidate is not compared, so a change of layout, trace, or volatile marks does not count by itself. A round is counted in two cases: a periodic reapply that moved bytes (the layout check found the applied layout undone), including the first move after a reapply that was handed over because the zone was taken; and the first move after a replan of only the remaining part, or after a plan that was set aside because its zone was occupied while it was being applied, when the check above finds the loss. Not counted: a replan after which everything the service had placed is still in place, the first placement of a game (also when it takes several days), a replan after files that could not be read or the game rewrites were held out, and the move to a new plan. A round that the write cap or a cancel splits into several runs counts once, also across a service restart; if what is left to move at the start of a later run is larger than what the earlier run left, pieces already done were lost and that run counts as a new round. When three rounds fall within seven days, the service pauses automatic relocation and reapply for that game; the log has `<game>: reapply paused after N unchanged-source rounds in 7 days; ...` once, and the game's status in `auto_status.json` has `reapply paused after 3 unchanged-source rounds in 7 days` after its other marks, which the tray shows as a short explanation. Prewarming continues. The pause ends when the source files change (checked every 10 minutes) and the game is planned again, when a new plan replaces the old one (for example a zone extension or the move to a whole-file plan), when the game's layout setting changes, or when fewer than three rounds remain in the seven-day window. A replan of only the remaining part after the zone was taken does not end it. When the pause ends because the source files changed, the new plan is made with the layout setting (`whole_file` by default); when it ends because seven days passed, the game goes on with the layout of its current plan, and when the setting is `whole_file` a game with a range plan is moved to a whole-file plan after it has finished. The daily limits are not changed, and the manual `aster apply` and `aster revert` are not paused.
  - **What changes with `whole_file`.** New plans, plans made again after an update or a zone extension, use this layout. A replan of only the remaining part, made when a check before applying finds the zone taken, keeps the layout of the plan it replans, so a game that is still relocating with a range plan stays on ranges until its source files change or it has finished. When a plan is set aside because its zone was occupied while it was being applied, the plan made again in its place follows the layout setting; so does a plan made again for volatile files. The layout check judges each placed file as one piece inside the zone. A file is moved completely in one run even when it is larger than the write cap of one run (2 GiB, 1 GiB on an SMR disk), but never beyond what is left of the daily budget: a file larger than what is left today waits for the next day while the smaller files go on. With `max_relocate_gib_per_day` at 0 (unlimited) one run can write as much as its first file. A worker takes a file and finishes it, and a file is not started unless the budget for the whole rest of it is set aside, so no file is left half moved by the cap, also with `relocate_parallel` above 1. The prewarm budget is about the same as with `ranges`. Right after a drive optimization ends, the layout check of a game that has a whole-file plan is brought forward (the usual conditions, such as a running game or a busy disk, still apply); a game with a range plan is not brought forward, because the optimization is expected to undo that layout (see "Why 80 MiB" below) and the daily budget would be spent on the same files again.
  - **Large pieces.** A file that is not chosen as a whole file (it is more than twice the size of what the plan reads from it) can still put a part of itself in the zone. The file is cut from its start into stretches of 80 MiB (rounded up to a multiple of 16 clusters; the last stretch, which is shorter than that, is not used). A stretch in which at least half of the bytes are read by the plan is chosen, and chosen stretches that touch are joined into one piece, so every piece is at least 80 MiB. Each piece goes into the zone as one piece, mixed with the whole files in the order of first access; the rest of the file stays where it is, in however many pieces it has, and its size is not limited. Compressed, encrypted, rewritten, and sparse files are not cut this way, and neither is a piece larger than the whole daily budget. The layout check asks, for each piece, whether it lies as one piece inside the zone, and a piece is moved completely in one run like a whole file (a file with several pieces is finished as one unit). `ranges` does not use any of this.
    - **Why 80 MiB.** It comes from a test on this PC, not from a measured gain: a scheduled Windows drive optimization was left running for more than 46 minutes over test files that had pieces of different sizes. Of the pieces of 1 to 56 MiB, only 1 of 56 stayed where it was and the rest were gathered into one piece and moved; of the 64 MiB pieces, 6 of 9 stayed; of the 80 MiB pieces 9 of 9 stayed, and of the 128 MiB pieces 10 of 10. A file that was one piece from the start stayed as well. In a file with one large piece and many 1 MiB pieces, only the small pieces were gathered and the large piece stayed. 64 MiB is at the edge, so it is not used. What the optimization does to real game folders when it runs through to the end has not been seen, and the effect on load time has not been measured.
    - **A side effect.** Cutting a stretch out of a file that was one piece leaves that file in several pieces. The part that stays outside the zone may be gathered by the scheduled optimization; the large piece in the zone is expected to stay, as in the test.
  - **Per game (`games[].layout`).** A game can have its own `layout` (`whole_file` or `ranges`) in `config.json`. It wins over `auto.relocate_layout` for that game, and without it the game follows the global setting. The layout of the game is used when a plan is made, when a game that has a range plan is moved, and when it is decided to pause the re-apply of a game that has no file to place. Moving, checking, re-applying and re-planning a part of a plan that already exists follow the mark written in that plan, so removing the key does not turn an existing whole-file plan back. A game whose policy blocks relocation (Prewarm only, or paused) gets no whole-file plan even when its layout is `whole_file`; its plan is a range plan, so releasing the policy later does not start a whole-file move by itself (the game is then relocated like any range-plan game and may be moved to a whole-file plan afterwards). The global setting is `whole_file` by default.
  - **Moving a game that already has a range plan.** With `whole_file`, once per service run, for each game that has finished relocating with a range plan (the most recently played first), the service makes a whole-file plan from the same read list and puts it in a new zone. The old zone's pieces are not kept in place, because that would leave the files in pieces. The pieces of a file that stays in place remain where they are in the old zone and are not moved back; the scheduled drive optimization may gather them later. The game goes back to the relocation stage, and the usual relocation moves it, one game at a time, the most recently played first, within the same idle, daily-limit, and write-cap conditions. While it moves, the periodic layout check of that game rests. Prewarm and game start work as usual, and nothing is touched while the game runs. If no free run is as long as the zone, the limit is lowered to the longest free run and the later files stay in place; if no file is chosen, the plan already applied is left as it is and the game is not relocated or re-applied while `whole_file` is set (it is only prewarmed; a new plan in which no file is chosen likewise moves nothing, it is not replaced by a range plan). The earlier journal is kept beside the new one as a record that can be reverted.
  - **Going back to `ranges`.** New plans use ranges again. A whole-file plan that already exists is left as it is and is not turned back, so that nothing is moved at the moment the setting changes; it changes when an update, a zone extension, or a plan made again produces a new plan. To undo a game by hand: set the game to **Prewarm only** on the Games tab first, so that the service does not apply the layout again, then revert its journal (**Revert**, or `aster revert --journal <ProgramData>\AsterCache\journals\<game>.jsonl --allowed-root <game folder> --execute` in a command window opened as administrator). Revert puts each piece back where it was; a piece whose old place another file has taken since is skipped, so the file may end up in more pieces than before. The game then stays prewarm-only. Deleting `plans\<game>.plan.json` does not make the service lay the game out by ranges: a game that is marked done is not planned again. A range plan comes back only when a game update makes the service plan the game again while `auto.relocate_layout` is `ranges`. Do not set the policy back to inherit while the whole-file plan exists unless you want that layout applied again.
  - **Log.** `<game>: whole-file plan, N file(s) X MiB placed in the zone, M file(s) Y MiB hot left in place (<reasons>), zone Z MiB of L MiB, K file(s) left in place because of the zone limit, P large piece(s) Q MiB placed in the zone` (the reasons are counts of files by reason: `mostly_cold`, the file is more than twice the size of what the plan reads from it; `zone_full`, the zone was full; `unmovable`, a file that relocation does not move, such as a compressed or encrypted one; `volatile`, a file the game rewrites; `sparse_holes`, a sparse file with holes; `over_daily_limit`, larger than the whole daily budget); `<game>: plan rebuilt for whole-file placement, N file(s) X MiB whole, M left in place (<reasons>), Y MiB to move; old zone pieces of in-place files stay where they are, P large piece(s) Q MiB placed in the zone` when a range plan is moved; `<game>: whole-file placement in progress, A of B file(s) in one piece, P% of their clusters inside the zone, Y MiB left to move` when a run stops at a cap; `<game>: whole-file placement complete, A of B file(s) in one piece inside the zone` at the end (a large piece counts as one); `drive optimization ended at ..., layout check brought forward for N game(s)`; `<game>: no file qualifies for whole-file placement, the game is not relocated (prewarm only)` (with `; the plan already applied is left as it is` when a range plan was applied); `<game>: free space is shorter than the whole-file zone (X MiB), limit lowered to Y MiB, later files stay in place`; and in the `auto relocation moved ...` line `, N file(s) larger than the remaining daily write budget deferred`.
- **Hours.** If `auto.relocate_hours` is set, new relocations and periodic re-applies start only in those local hours. A relocation that already started and left a journal finishes outside them.
- **Settings.** `auto.relocate`, `idle_seconds`, `relocate_hours`, `max_relocations_per_day`, `max_zone_mib`, `max_relocate_gib_per_day`, `relocate_layout`. How much it writes: [Effect on the hard disk](GAME_GUIDE.md#effect-on-the-hard-disk).
- **Log.** `<game>: auto relocation done`, `[ERROR] <game>: auto relocation stopped: ...`

<details>
<summary>Details: limits, interrupted and split moves, game updates</summary>

**Limits**

- Zone size: hot data × 1.1, capped by `max_zone_mib`.
- At most `max_relocations_per_day` relocations run in 24 hours, counted from the start of each. Those under 64 MiB are not counted but still count toward the byte budget.
- Each game gets one automatic first relocation. Later upkeep uses the periodic check in [Upkeep](#5-upkeep).
- `auto.relocate` also applies to games you registered by hand. To prevent it, turn `auto.relocate` off, or pause the game or set its policy to **Prewarm only** or **Off** on the Games tab. Adding the exe to `auto.ignore_exes` only keeps it from being registered again; it does not stop a game that is already registered.

**Interrupted and split moves**

- If a game starts during a move, the move stops after the current fragment and resumes later from the journal.
- If another file takes the zone still to be moved, or the plan changes, the parts already moved are kept and only the remaining part is planned again into a new free area.
- A new zone (or the remaining part, when the space right after the moved part is not free) is not placed at the very start of the free run it picks. When the run is at least 1 GiB longer than needed, the zone starts after a margin of half of that extra length, up to 4 GiB, aligned to 4 clusters (16 KiB with 4 KiB clusters). Another program's new files tend to fill a big free run from its front, so the margin keeps the zone out of their way for a few hours of their writing (measured: about 0.8 GiB per hour from one program). A shorter run keeps the zone at its start. Log lines: `<game>: new zone placed N clusters after the free run start (run R, zone Z) ...` or, for the remaining part, `<game>: new place leaves N clusters after the free run start (run R, zone Z) ...`.
- If the zone is found occupied again and again, each held retry waits 30 minutes. From the third time in a row with the same kind of reason (`zone_not_free` or `zone region appears occupied`), even when each retry makes a new plan, the wait doubles each time (1 hour, 2 hours) up to 4 hours; it never stops for good. The count is cleared when a run moves at least 64 MiB, and a different reason counts separately. Reasons that are overlaps with another plan's reservation (`reserved by another plan`) are not counted. Log line: `<game>: zone occupied N times in a row, another program keeps writing to this drive, hold extended to M min`. Whenever the zone is found occupied, a line `<game>: zone rejected at LCN L: <place> (zone Z, moved up to P)` says where: in the margin before the zone, right after the last moved piece, elsewhere inside the zone, or outside it.
- A plan whose zone is already at its maximum size is not planned again, and the screen says the work resumes automatically.
- If the data check fails or an error occurs while the game is off, the journal is used to revert and the failure is recorded. Only that automatic change is reverted.

**Game updates**

- If a game's files change size or modification time after relocation, the old plan is set aside as `.stale` (checked every 10 minutes) and the stage goes back to discovery. After a small update only the ranges of the changed files are removed from the trace and the rest is kept; the update counts as small only when the changed files hold less than half of the planned data and also less than half of the bytes in the whole trace. After a larger change the whole trace is set aside too. A game whose anti-cheat forbids tracing keeps its usable trace.
- The 10-minute check compares every fingerprint of the plan, not only the game executable and the three largest files, so an update that touches only small files is caught. Files the game rewrites by itself are left out of the comparison: files whose names match the volatile rule and files the trace marked as changed between runs (`<game>.trace.volatile.json`). A file marked only after the plan was made does not count as an update. The cost: an update that changes only files the trace marked (real patch files can be marked too) is not detected as an update, and those files stay out of the plan (the zone hit rate can drop slightly).
- A finished plan that still holds a file the trace has since marked as volatile is planned again once, through the same path as the volatile-name check (`.extend`, same zone, same idle and daily gates), and the new plan leaves the marked files out. The plan records how many marks it already reflects (`volatile_marks`), so it is checked again only when the volatile mark list changes and holds more marks. Files left held because their layout could not be read (`held_files`) are not counted, since they stay in a new plan too. The re-plan is not done when automatic relocation is off. Log line: `<game>: plan holds N file(s) the trace marked as rewritten by the game (<reasons>), plan set aside as .extend, will plan again without them (same zone)`.
- The layout check and the check just before a reapply still compare by the volatile name rule only, so a plan holding a marked file that changed reports as changed until the one re-plan above removes the file from the plan.
- The game is traced and relocated again on its next run, trying its previous zone position first.

**Other**

- Moves carry a low I/O priority hint (`FileIoPriorityHintInfo` Low). The documentation does not guarantee that the kernel applies it to the copy I/O of a move, and this has not been measured yet.
- Right after a move finishes (or fails, if a trace exists), the zone is prewarmed.
- Other log line: `<game>: partially applied plan replanned, the parts already moved are kept`.

</details>

### 4. Prewarm

- **When.** At service start, when a supported launcher starts, and after a game exits.
- **What.** Reads the zones of the most recently played games into RAM, within a RAM budget, in 64 MiB batches.
- **Does not.** Keep reading after a game starts: it stops at the next batch boundary when any game starts, including the game being prewarmed.
- **Settings.** `auto.full_prewarm`, `auto.full_prewarm_max_mib`, `auto.engine_profiles`, `prewarm_recent`, `prewarm.max_cache_mib`, `prewarm.min_free_ram_mib`, `auto.startup_warm_max_mib`, `auto.rewarm_after_exit_min`.
- **Log.** `<game>: prewarm done (<reason>): N MiB requested, ... in S s = R hint MB/s, ...` (`hint MB/s` is the requested MiB divided by the elapsed seconds)

<details>
<summary>Details: when, order, budget, reading, games without a trace</summary>

**When exactly**

- A game counts as exited only when all of its registered exe files have been gone for 60 seconds, so a launcher-to-game handoff is not mistaken for an exit. Unregistered processes in the install folder do not delay it.
- After an exit, relocation, SSD tier apply, and prewarm or re-prewarm for a new trace on the same physical disk wait for the longer of 60 seconds and `auto.rewarm_after_exit_min` minutes.
- **Switching games.** While the 60-second exit check of a game that just closed is still running, a prewarm started by a launcher (a trigger prewarm) may read, if the games still registered on that disk are only ones waiting for that check. If one of them comes back, or another game starts, the prewarm is cancelled at once. Nothing changes while a game is actually running: no new reads on its disk. Re-prewarm checks, supplement prewarms, and relocation still wait as above.
- A trigger prewarm refused because a game was running is written down. The first time the service sees that game's processes gone (processes are checked every 30 seconds), it tries once more if the launcher is still running and the refusal is less than 30 minutes old (log line: `<game>: retrying the refused trigger prewarm (<exe>) now that the blocking game is gone`). If it is refused again, the usual waiting rules apply. How this behaves in real play has not been checked yet.
- **A launcher's prewarm goes first.** When a launcher starts a prewarm that will actually read, the background prewarm of another game on the same disk (a re-prewarm, a supplement prewarm, or a waiting retry) is stopped as soon as the read being issued is done, and the launcher's game is read first (log: `<game>: prewarm cancelled (...) after N MiB (preempted by trigger prewarm)`). A stopped supplement prewarm goes on later from where it stopped, and a stopped re-prewarm or retry goes back to its usual retry. If the launcher's prewarm still has to wait for a read that cannot be stopped, it writes `<game>: trigger prewarm waited N s for <game>` (only when it waited 1 second or more). A launcher prewarm of games that would all be skipped anyway (cooldown, a game running on the disk) does not wait for other reads and writes the skip line at once. A prewarm of a game without a record is not stopped this way. This was added because, in the service log of the test PC, a launcher prewarm once waited 2 minutes 6 seconds behind a 210-second supplement prewarm of another game; whether it now starts at once in real play has not been confirmed.
- **No calibration read for a launcher's prewarm.** A prewarm that a launcher starts no longer does the short disk-speed read that ORBIT takes before a prewarm. Any other prewarm limits that read to 5 seconds and drops the sample if it takes longer (log: `<game>: device calibration stopped at the 5 s limit, sample discarded`; the `prewarm phases` line shows `calibration N s`, with `(capped)` when the limit was reached).
- **Cooldown.** `prewarm.cooldown_min` (30 minutes by default) keeps a game from being prewarmed again too soon. Inside the cooldown the service first reads the same kind of sample as the re-prewarm check (only when no game is running on that disk, and a sample is reused for up to 5 minutes). If the sample shows that the cache has gone cold, which a reboot does, the cooldown is ignored and the game is prewarmed (log: `<game>: cooldown ignored, the cache is cold [service start]`, or `[trigger <exe>]`). If the cache is warm or the sample cannot be read, the cooldown applies as before (`<game>: prewarm skipped (cooldown (N min left)) [...]`). A game without a record has no sample and keeps the plain cooldown.

**Order and budget**

- The most recently played games first, with those played often at this time of day ahead. Games triggered recently (for example by a launcher) are prewarmed first for 6 hours.
- With `prewarm_recent` at 0, as many recent games as fit in the budget; a value from 1 to 32 caps the number of games instead.
- Budget: the smaller of half of physical RAM (or `prewarm.max_cache_mib`) and free RAM minus `min_free_ram_mib`.
- Free memory is measured again right before reading. If the list no longer fits, it reads the front part that fits and the rest is supplemented later. A 256 MiB margin is kept on top of the reserve (`prewarm.min_free_ram_mib`, 4,096 MiB by default) both in the last check before reading (whether the whole list still fits) and when it picks the front part, so a small change in free memory does not cancel the read. The reserve and the cache budget are unchanged.
- While a game is partly prewarmed, the budget is worked out again about every 30 seconds. The size figures it uses for each game (whole size and amount observed) are reused for up to 10 minutes as long as the input files (plan, list, prewarm-only list, volatile list (files the game also writes to), raw and boot traces) and the game's settings are unchanged, so the plan files are not read whole every time. The plans that decide what a prewarm reads are read fresh each time. When the sizes were not reused, on the test PC 450 seconds of idle time with a partly prewarmed game used 100.7 seconds of CPU and read 1,468 MiB in bursts every 30 seconds; the figure with the reuse has not been measured. A game update that changes file sizes in the list can show in the estimate up to 10 minutes late.
- The cache budget is divided between games by the size of each game's actual prewarm list. A partly relocated plan, which holds only the part still to be moved, used to be counted at its whole hot set, which gave that game a larger part of the budget than it read.
- What stays after the game starts. A game takes memory of its own after it starts (9 to 10 GiB in three recorded plays of one game), and that memory comes from the standby list, that is, from the cache the prewarm just filled. For each play the service now records the available RAM at the start and the lowest available RAM in the first 10 minutes (`minAvailableRamMib` in `play_samples.json`; the `play record:` log line shows `min RAM`); the difference is the memory the game takes. Only plays that were observed from the start through the first 10 minutes and in which memory did not run short (lowest available at least 1,024 MiB) count, and the value is cut at that play's start available. With three or more such plays the median of the latest three is used; with two, the smaller; with one, a value halfway between the old reserve and the footprint reserve, because a single play may include another program's memory or an overlapping game. For a game with such a record, the reserve of its prewarm is `max(min_free_ram_mib, the game's memory + 1,024 MiB)` instead of `max(min_free_ram_mib, 4,096 MiB)`, and the cache budget that all games share is also cut to the available RAM minus that reserve of the game most likely to be played next (the first in the order below), because a prewarm beyond that is pushed out when the game starts. Neither limit goes below half of what it would be without the footprint: the front part a game reads early in a load is used before it is pushed out, a wrongly learned footprint can then cut the prewarm by half at most, and a limit of 0 would keep the waiting retry going. The shared budget ignores the footprint while any registered game is running (its memory is already out of the available RAM) and keeps its value for 10 seconds so that small changes in free memory do not move it within one check. The prewarm log shows `<game>: game footprint F MiB (median of N plays), cap C MiB`. A game without a usable record keeps the old reserve and budget. The effect on loading has not been measured yet.
- Which game is touched last, and the prewarm after a relocation. To touch a range is to access its cached pages in memory so that Windows counts them as recently used; nothing is read from the disk on purpose. The ladder is the [SOLAR](SOLAR.md) pass that touches the cached ranges of the prewarmed games in a set order, so that the ones touched last are pushed out last. The order of the prewarmed games, which SOLAR uses to decide whose cache is touched last (see [SOLAR](SOLAR.md)) and which the re-prewarm check follows, is now the same rank that divides the cache budget (the prewarm score of recency and time-of-day habit), so the game that gets its budget first is also the game touched last (it used to be the last prewarm time; without the rank it is still the last prewarm time). After the prewarm stream of another game, the game first in that order is touched once more, so its cache is pushed out last; if its samples are found cold, the next re-prewarm check is brought forward (the same pull-in that a game exit uses; it is not done when `auto.rewarm_after_exit_min` is 0). The log line is `<game>: ladder ordered, <game> touched again after it as the first play priority`. The prewarm that runs after a relocation (and after a new trace) now gets the same share of the cache budget as the re-prewarm; before, it ran without a limit, so it could add to the total beyond the budget. A game that is not in the budget gets what is left of it. When the amount that fits is smaller than the list, the ranges in sparse-attribute files are left out of the memory prewarm first, because the ladder cannot touch them and they are the oldest pages of the game, so they are pushed out first; the ranges of the other files then get the amount, and the re-prewarm and ladder samples, the supplement, and the pin list skip the same ranges, so they are not judged cold for ranges that were never read. The log line is `<game>: N MiB in sparse files left out of the memory prewarm, the ladder cannot touch them`; the mark is judged again at each prewarm and the relocation plan is unchanged. The effect on loading has not been measured yet.
- When the list has to be cut, the ranges kept first are, in this order: (1) ranges in files the game also writes to (these are not moved with the zone and are kept in a separate prewarm-only list) that were first read early in the play, up to the loading boundary (the point where the load's heavy reading dies down) or 120 seconds when no boundary is known; (2) the front of the observed ranges, as many bytes as the loading head (tier0); (3) the blocks of the ranked block list (see "Ranked block list" below) if there is one, the part that overlaps an earlier step counted once; (4) the rest of the ranges observed in play; (5) the rest of the prewarm-only ranges, by the time they were first read; (6) guessed ranges. Ranges added from outside a full zone (see [Zone extension](#2-recording-reads-trace)) take part only at (5). Without a ranked list (3) is empty and the order is the previous one, and a list that fits whole is not cut, so the ranked list is not used. The early ranges of (1) are also read first. They used to sit at the end of the list, so a cut dropped them before anything else.

**Memory runs short while reading**

- If a prewarm that was reading only the front part loses memory (available memory falls below the reserve, or the remaining budget no longer fits), it no longer throws away what it has read. It ends there: it reads on only up to the amount that fits the memory available at that moment, then finishes, and the amount read is kept as a partial prewarm (`partial`, `warmed_mib`, and `hot_mib` in `prewarm_status.json`). It is still cancelled, as before, when nothing has been read yet and less than 256 MiB fits, and when the read had errors or ORBIT had changed the order (nothing is kept then). Log: `<game>: prewarm read the first N of M MiB, the rest does not fit in memory (available A MiB, reserve R MiB) [<reason>]`, followed by the usual `prewarm done (...): partial N/M MiB, the rest does not fit in memory: ...`.
- A supplement prewarm now starts only when the memory that fits exceeds the amount already read by at least `max(256 MiB, 5% of the amount read)`, or by what is left of the hot set when that is smaller. When the plan list of a window ended before the window was full, the size of that window is compared instead of the amount read, because the same window would give the same list again. Until then it reads nothing from the disk and writes `<game>: supplement waits for memory (read X MiB, room for Y MiB)`, once for each amount read (`read X MiB of a W MiB window whose plan list ended there` in that case). When it starts, it continues after the part already read, even if the window it remembers is larger than what fits now; the total is held to what fits. A supplement prewarm that reaches the limit ends there like a prewarm (`<game>: supplement prewarm read the first X MiB of Y MiB, the rest does not fit in memory (...)`), and the next one continues after it. This rule was added because of a cycle seen in the service log of the test PC (read on 2026-11-14): the supplement prewarm of a game whose list was close to the limit was cancelled again and again (86 times for Call of Duty, 79 of them without adding anything to what was recorded). The amounts those 79 attempts had been accepted for reading add up to 51,624 MiB, an upper bound on what was read from the HDD in vain. The effect on loading in real play has not been measured.
- If a prewarm that was reading the whole list (a supplement prewarm included) stops for memory, it reads again once in the same run, cut to the front part that fits the memory available at that moment. From there it is handled like a prewarm that was reading only the front part. What was already read is in the cache, so reading it again costs almost no disk time. It does not read again when it stopped for another reason, such as a game starting, and it is cancelled as before when less than 256 MiB fits. Log: `<game>: prewarm stopped by memory before the full list was read; reading the first N MiB of M MiB instead` (`supplement prewarm stopped by memory ...` for a supplement prewarm).
- After any stop caused by memory, including one that kept nothing, supplement prewarms and retries (the waiting-list retry and the re-prewarm check) leave that game alone for 2 minutes; a launcher trigger or a service start does not wait. If the stop had read something, a waiting retry is pulled forward to 2 minutes later instead of the usual period (`rewarm_minutes`, 10 minutes by default); a stop that read nothing keeps the usual period. A game with a kept partial prewarm stays on the waiting list instead of being dropped, and the rest is read once free memory exceeds the amount already read plus 256 MiB plus the reserve.
- Log lines for the cases that still cancel: `prewarm cancelled (...) after N MiB (memory reserve: ...)` (or `(memory budget: ...)`), followed by `<game>: prewarm stopped by memory; kept the N of M MiB read as partial`, and `<game>: prewarm skipped (stopped by memory less than 2 min ago) [<reason>]`. The `prewarm done` line ends with `room X MiB` (or `unlimited`) and `available Y MiB`, and a `rewarm check: cold (...)` line includes `available N MiB`, so the memory at that moment can be read from the log.
- A prewarm that read its whole list is no longer recorded as `partial`. For a game whose saved plan holds only the part still to be moved, the amount to read used to include whole-file reads added for files where 30% or more of the file was needed (1,306 MiB against 1,164 MiB allotted for one game), so a complete read of the list was recorded as `partial` and `rewarm check: the rest of the hot set is not read yet` repeated. The prewarm list is now counted on the same basis as the allotted amount, so those whole-file reads are not added and `partial` appears only when memory or the cache budget really fell short. A `partial` left in `prewarm_status.json` is cleared the next time a prewarm reads the whole list. The effect on loading has not been measured.

**Reading**

- Files with the sparse attribute are read with an ordinary buffered read, without the read-ahead hint, instead of a mapping, in the same order; the `prewarm done` line ends with `, K MiB of sparse files by buffered read` when there were any ([SOLAR](SOLAR.md)).
- In the disk's physical order. When a batch holds more than one game, the loading head (tier0, the blocks read first in a load) of each game is read first, in recent order, and then each game's whole zone.
- Each range is marked as observed in play or guessed from an engine profile. When the budget is short, the observed ranges of all games are filled first and the leftover goes to the guessed ranges.
- At service start only the head part is read, up to `auto.startup_warm_max_mib`. The rest is read later, once the disk is idle. A game that will be skipped anyway (for example during its cooldown, while it is running, or in the post-update delay) does not use any of that limit, so the next game gets it.
- The management window shows `prewarming x/y MiB`, and a tray notification is sent when a game's prewarm finishes (once per game per day).
- If another game starts, it stops at the next batch boundary. If the game being prewarmed starts, it also stops and yields (`auto.keep_stream_on_game_start`, default `false`; `true` reads to the end, for experiments).
- **Giving way to other reads.** The reading thread of a prewarm of a hot set (at service start, from a launcher, a re-prewarm, a supplement prewarm), of a game without a record, and of the loading head at service start lowers its own I/O priority to low while other programs read the same disk, and returns to normal when the disk is idle. About every 10 seconds it pauses for 1 second and measures the disk's throughput without its own reads: 4 MiB/s or more, or a figure that cannot be measured, counts as busy and means low priority. The rule for another game running on the disk is unchanged: that still cancels. A prewarm that a launcher starts, or that starts within 15 minutes of boot, measures the disk once before its first batch instead of waiting for the first 10-second interval, so it can step aside at once. Once the disk has been idle for 3 pauses in a row, the pause interval grows to 30 seconds; any pause that is not idle (busy, no sample, or a stale one) brings it back to 10 seconds. Log: `<game>: prewarm yields to other disk activity (low I/O priority)` (once per read), `<game>: prewarm back to normal I/O priority after N.N s at low` (the first return only), and, when low priority was used, `, read A MiB in S s at normal I/O priority and B MiB in T s at low (K switches)` after `, yielded N.N s` at the end of the `prewarm done` line of a hot-set prewarm. The same `, read ...` tail (without `yielded`) is at the end of its `prewarm cancelled (...) after N MiB (<reason>)` line and of the `load head prewarm done` and `cancelled` lines. A prewarm of a game without a record and a supplement prewarm (`supplement prewarm done`) do not carry it. Lowering the priority does not change the order, the amount, or the cancel rules.

**Games without a trace**

- A small game (folder within the RAM budget) gets its whole folder prewarmed, up to `auto.full_prewarm_max_mib`. A larger game gets its engine profile files.
- A game that is no longer registered is not prewarmed or pinned.
- Other log lines: `prewarm cancelled <reason>`, `<game>: prewarm skipped (...)`, and a `prewarm phases` line with the elapsed time per phase. Before the per-game reads, `prewarm prepared in N s before the per-game reads [<reason>]: cooldown and cold samples, order, lists and layout lookups, load head plans and layout lookups, load head reads, other waits in load heads` splits the preparation time into steps (only when it took 5 seconds or more; it is also written when the loading head read is cancelled), and the loading head read of a batch of several games writes `<game>: load head prewarm started`, then `done: N MiB in S s` or `cancelled (<reason>) after N MiB in S s` (or `interrupted (caller cancelled) after ...` when the service stops while it plans, or `skipped (<reason>)` when it was not read). A partial prewarm has `partial A/B MiB, the rest does not fit in memory:` in front.

</details>

### 5. Upkeep

- **When.** Re-prewarm check every `rewarm_minutes`; supplement prewarms and retries as the disk stays idle; layout check periodically.
- **What.** Samples 8 places in each zone and reads it again if it went cold; reads the part of a hot set that did not fit; retries a prewarm that was cut short; restores a drifted layout; keeps the prewarmed cache in order and refreshes it in memory ([SOLAR](#solar-keeping-the-cache-in-order)).
- **Does not.** Re-warm a game outside the prewarm budget, or touch the layout while the game runs.
- **Settings.** `rewarm_minutes`, `min_free_ram_mib`, `post_update_delay_min`, `memory.standby_ladder`, `auto.idle_read_gib_per_day`.
- **Log.** `<game>: rewarm check skipped (...)`, `<game>: layout degraded while source files are unchanged (...)` (when the service has seen a drive optimization end, the parentheses also say `the last drive optimization the service saw ended at <UTC time>`), `<game>: reapplied, moved N bytes, N failed` (the same tail is on `<game>: auto relocation moved N bytes, ...`; when a sparse file was moved or held it ends with `, sparse moved N bytes` and `, K sparse file(s) held (allocation changed)`), `<game>: K sparse file(s) changed allocation since the plan, held out of the layout check and reapply` (the allocated ranges of a sparse file differ from the plan, so the periodic layout check and the reapply leave that file out and treat the rest of the game as usual; logged only when the number changes) and `<game>: K sparse file(s) changed allocation since the plan, held, will plan again later` (the same finding after an automatic relocation: that file is not moved and is planned again after an hour), `<game>: held files remain, plan set aside as .stale, will plan again`, `<game>: ladder ordered N MiB in S s`

<details>
<summary>Details: re-prewarm, supplement prewarm, retry, layout recheck and reapply</summary>

**Re-prewarm (keeping the prewarm)**

- Reads 1 MiB from each of 8 places in the zone (the first 4 in read order and 4 evenly spaced). If at least 2 of them take more than 2 ms, the data has probably been evicted from the file cache, so it prewarms again while keeping `min_free_ram_mib` free. A place counts as slow only if the read took longer than the limit and, during that read, the system's page-read count grew in proportion to the sample size (at least a quarter of the pages read, 16 pages at the least). This keeps a cached sample that was read slowly while another program was using the CPU from being taken for a cold one. If the count cannot be read, time alone decides. Not yet checked on an installed build.
- Only games inside the prewarm budget are re-warmed, in prewarm-score order (recent play and time-of-day habits). A game outside the budget is not re-warmed after it cools, and the reason is logged.
- One running game does not stop the check for other games; each target is judged separately.
- If the [SOLAR](#solar-keeping-the-cache-in-order) ladder (its reverse-order pass) found part of the list missing from the cache, this check prewarms that game again even when its samples are warm (log: `<game>: rewarm check: part of the list is not in memory (found by the ladder), prewarming again (cooldown ignored)`). Parts still in the cache cost almost no disk time, so in effect only the missing parts are read. It happens at most once per `rewarm_minutes` for each game, counted from the last prewarm attempt, and not while a supplement prewarm is pending or a launcher's prewarm is waiting. It does nothing when automatic mode is off or `rewarm_minutes` is 0.
- While the cache of a game that was just read again goes cold again at the next check (another program keeps using the cache), the interval to that game's next check is doubled each time (the first cold re-read keeps `rewarm_minutes`, then 20, 40 minutes, at most 60 minutes, or `rewarm_minutes` itself when that is longer), and it goes back to `rewarm_minutes` after a check that finds that game warm (log: `<game>: rewarm check interval raised to N min: ...` and `<game>: rewarm check interval back to N min: ...`, only when the interval changes). Each game is counted by itself, so one game does not hold the others to its interval, and another game's warm result does not reset it. It counts the checks that really read again (a re-prewarm that was skipped for memory or because the disk read lease (the permission, granted per physical disk by the part that arbitrates background reads, see SOLAR) was refused does not count), both the cold sample checks and the re-prewarm that the ladder asks for. The prewarm that a game or launcher start triggers, the prewarm at service start and the one after a relocation do not use this interval, and a check pulled forward by a game exit still runs on time. The price is that a game's cache that went cold is read again later while another program keeps using the cache.
- While a supplement prewarm is still pending (the rest of the hot set is not read yet, including while it waits for memory or after its plan list ended before its window), a check that finds the part already read cold reads that part again, once the drive is idle and the other conditions of the check hold (log: `<game>: rewarm check: the part read into memory went cold (...), reading it again (cooldown ignored)`). It reads the same range as the first time: the same window, so the plan list is built the same way, and sparse files stay left out when the first prewarm left them out. The status file keeps what this needs, and a service restart restores it: `warmed_mib` is the amount actually read, `window_mib` is the window size when the plan list ended before its window, and `sparse_out` tells whether sparse files were left out. When the first range cannot be built again, this check does not read the part: that is the case when the prewarm was cut by memory or ended at the memory limit before its plan list ended (a supplement prewarm that was cut off or ended at the memory limit counts the same), and when the status file has no `sparse_out` (an older format). A game cut by memory is then prewarmed again as a whole, as before, and any other game is left to the supplement prewarm. When the read again is not cut by memory, the amount recorded as read does not shrink. When it is cut by memory, the amount read then is recorded, and the size of the whole hot set stays as it was. The supplement itself still reads the rest. A game is read again this way at most twice in 24 hours. If the part goes cold again within 2 × `rewarm_minutes` after such a read, the game is not read again this way for 24 hours from that read. While it waits, this check does not read the samples of that part from the disk. When no more memory fits than what was already read, the supplement prewarm does not sample the front part either. When more fits, the supplement prewarm goes on as usual: it samples what was read and, if that is cold, it may read the window again from the start, front part included, which the daily limit below covers. A log line is written when the state changes: `<game>: rewarm check: not reading the part read into memory again until <time> (...)`. The times of the reads and the end of the wait are kept in the game's entry in `prewarm_status.json` as wall-clock times, so a service restart does not clear them, and a clock set back is treated as now. A read of this kind also counts for the doubling of the interval in the line above. Reading the same range again therefore takes at most twice the window of each game per day (`window_mib`, or the amount read when there is none), and prewarming a game cut by memory as a whole takes at most twice the amount allotted to it. Over all the games that stay in the budget, both together stay within twice the prewarm budget (half of the physical RAM by default).

**Daily limit on automatic background reads**

- **What is limited.** On each drive, in any 24 hours, the reads that happen only because time has passed or because the service itself moved data: the re-prewarm check (its samples, the re-read of a cold list, and the re-read of the part already read), the supplement prewarm (including a window it reads again from the start), the retry from the waiting list of such a read that failed, and the prewarm after a relocation. These are the "idle reads" in the log. What the SOLAR ladder reads from the disk is counted with them but never held back.
- **What is not limited.** Reads that a game start or a launcher asks for (and the waiting-list retry of such a read; a request that failed first stays a request even if a periodic read of the same game fails later), the prewarm at service start, and the one check that follows a game exit. They are counted ("trigger reads" in the log) but never held back, so a prewarm that a game start or a launcher asks for reads as usual even when the limit is reached. The check after a game exit is done for each game once: a game that was blocked at that time (for example another game was using the disk, or it had just been prewarmed) keeps the mark until its check is done, at most 24 hours. The recovery samples after a relocation have their own limit ([drive recovery wait](#7-drive-recovery-wait)).
- **The limit and each game's share.** `auto.idle_read_gib_per_day`. At 0 (the default) it is the larger of 24 GiB and six times the size of the prewarm lists of the games on that drive whose prewarm is allowed; the setting replaces it. The default is not meant to reduce the usual reads: it stops periodic re-reads from growing without end on an unusually heavy day. To spare the hard disk more, lower the setting; the periodic refill then runs later and a game start can be slower. A prewarm that a launcher or a game start asks for is not limited by this setting. The limit is divided between those games in proportion to the size of each game's list, so with the default each game has at least six times its own list a day (six full refills of the list; how long that lasts depends on how often the cache goes cold, which was not measured). A read starts only if both the share of that game and the total of the drive have room, so one game that reads again and again cannot use up what the others are allowed. A game whose list size is not known gets the smaller of 1 GiB and what is left of the drive. What a game that was removed from the settings read stays in the drive total for 24 hours, but the shares are worked out again from the games that are in the settings: with the default and lists above the floor each share stays six times its list, and with the floor or a set value the shares of the games that are left grow.
- **What is counted.** For a prewarm stream, the smaller of the bytes it accepted (`MiB requested` in the `prewarm done` line) and the time the stream spent reading times a speed. The speed is the sequential read limit of the drive (250 MiB/s, or 1.25 times the recovery baseline of that drive when that is lower), or the speed of the read itself when that is no more than twice the limit (so a read that ran a little faster than the limit, as a faster disk can, is counted in full). A read more than twice as fast as the limit is taken to have pages that were already in memory in it and is counted at the limit times its time; a time that was measured as 0 counts as 0, and when the time or the limit is not known the accepted bytes are counted. The time is the one the streamer measured for the read itself (waiting and yielding between batches and the ladder are not in it). This is an estimate and it can be wrong in both directions: a read that is slower than the limit because the disk was shared is counted at its accepted bytes even when part of it came from memory (too many), and on a disk much faster than the speed the samples found, a read with memory in it can be counted at less than the disk read (too few). A physical disk counter is not used. The streams also count the re-read of the front part at their end (up to 64 MiB). For the check's samples, up to 1 MiB for each sample that was slow (read from the disk), also for the samples read before the check was cancelled. For the ladder, the bytes it counted as read from the disk, once (the stream does not count the ladder's time). Counted as reads started by a start: the stream of a prewarm at service start, the cache check samples before it, the load head prewarm of the service start batch, and the prewarm of a game without a record (by its accepted bytes and time). Not counted: the device calibration read, the common-block read ahead of a stream (it is part of the stream's range), the layout check, and fingerprints. Reads within a minute of the previous one for the same drive and game are merged under the first time, so they leave the 24-hour window up to about a minute early.
- **At the limit.** No idle read starts for that game until enough of its oldest reads are 24 hours old to bring both its total and the drive total under the limits, and the re-prewarm check does not read the samples of that game either. A read that starts below the limit gets what is left as the budget of its window, and a supplement prewarm checks the limit again before the second stream it starts after a memory stop; a read that does not fit in what is left is not started, so the total passes the limit by little. The ladder keeps touching pages that are in memory and keeps reading its own samples (it already stops once more than 32 MiB counts as read from the disk). Within one check the games are taken with the most recently played game first.
- **What this limit does not cover.** Games that have no play record yet and are prewarmed from their folder or from an engine profile. For such a game that has been played, the prewarm that the automatic mode starts is counted as a read started by a start and is not held by the limit; it works as it did before this limit existed. After that prewarm has succeeded the game is part of the periodic check, which stops at the limit, but a re-read of that game is not cut down to what is left of the limit. These reads are in the record of reads.
- **What can be later.** A cache that goes cold (for example because other programs used the memory) is read again by the periodic check only while the game's share and the drive have room. Until they have, a game start, a launcher, a game exit or a service start still prewarms it, and the start stream still runs; but a play that begins before then can find more of the list not yet in memory. A prewarm after a relocation that the limit held back is not retried: the next game start or launcher fills it.
- **Where it is kept.** In `prewarm_status.json` under `disk_reads`, per drive and per game, so a service restart does not free the limit, and a clock set back does not either. It is written with the writes the service already does, at service shutdown, and on its own only when at least 256 MiB were added since the last write and 10 minutes have passed; a write that fails leaves the record unsaved and it is written again at the next write; if the service dies suddenly, the last few minutes of the record can be lost. Log lines: `idle disk reads of <game> on drive D: paused: ... reading again from <time> (reads started by a game or launcher are not limited)` when a game's share is reached (`idle disk reads of drive D: paused` when the drive total is), `... resumed: ...` when it frees, and once a day `disk reads in the last 24 h: D: trigger reads X MiB, idle reads Y MiB of Z MiB limit, recovery reads W MiB in N samples`.

**Supplement prewarm**

- When a hot set does not fit the budget, a window that fits is read as the drive stays idle: the smaller of the remaining hot set, free RAM minus the 256 MiB margin and the reserve, and the prewarm budget, at least 256 MiB. It starts only when that window is larger than the amount already read (or than the window whose plan list ended before it was full, when that is larger) by at least `max(256 MiB, 5%)`; see [Memory runs short while reading](#4-prewarm).
- If a supplement prewarm stops midway, or ends at the memory limit, the position it reached is remembered while the service runs, and the next one continues from there. One that mixed in gap filling, or whose front has gone cold, starts again from the beginning.
- A failed read or a settings change discards the position, and a service restart loses it.
- Log lines: `<game>: rewarm check: the rest of the hot set is not read yet, supplementing once the drive has stayed idle`, `<game>: supplement prewarm skipped (...)`.

**Retrying an unfinished prewarm**

- A prewarm of a traced game that was cancelled before it finished, or skipped by the service-start cap, stays on a waiting list and is requested again once the disk has been idle for 60 seconds, no game is running on that disk, and the cache budget has room.
- Games without a trace are not retried this way.
- A cancelled prewarm is read again even while the drive recovers from a relocation. Further relocations still wait for recovery.

**Layout recheck and reapply**

- A periodic check (1440 minutes by default) finds that the layout has drifted while the source files are unchanged, and reapplies the plan.
- If a temporary condition blocks the check (a running game, a busy disk, drive recovery, battery power, not idle long enough, the post-update delay), it is repeated every 5 minutes instead. A reapply that stops at the per-round write cap keeps the 5-minute recheck.
- When reapply is rejected because another file occupies part of the zone (`zone_not_free`), the game is handed to automatic relocation, which keeps the moved parts and replans only the remaining part, under its existing holds and daily limits.
- It is handed over only when automatic relocation is on, the game has a trace, and it is not stopped by a failed data check. Otherwise it fails as before. A rejection before any move is recorded as 0 bytes.
- These checks (extent and fingerprint lookups) are rechecked about every second and stop when a game starts.
- Other log line: `<game>: reapply blocked by zone_not_free, handing over to auto relocation to replan the remaining part`.

</details>

### 6. While a game runs

- **When.** From a game's start to its exit (plus a short grace period).
- **What.** Blocks relocation, reapply, and tier writes on that disk, yields prewarm, lets unrelated background programs give up memory ([Background memory yield](#background-memory-yield)), and records how the disk behaved and the frame intervals (`play record:`, `play_series` folder). It also keeps the prewarmed cache of the running game in memory by touching it again or holding it (keeping read-only mappings of it open) ([SOLAR](SOLAR.md)). It also reads the blocks of each later program a game starts (stage stream), and skips its extra work for a run when a game keeps closing right after launch.
- **Does not.** Read or change a game process's memory, or open it with more than a query-only handle (the start and stage streams read its I/O counters through that handle). The play record uses only disk device counters, and it does not make the game faster by itself.
- **Settings.** `auto.start_stream_enabled` (when `false`, no start stream runs), `auto.stage_stream_enabled`, `auto.stream_idle_only`, `auto.start_stream_cap_seconds`, `auto.restream_cooldown_min`, `auto.quick_exit_seconds`, `auto.keep_awake`, `memory.background_yield`, `memory.background_io_priority`, `memory.background_cpu_priority`, `memory.background_yield_fast`, `memory.background_in_use_memory_priority`, `memory.standby_ladder`, `memory.keep_hold`, `memory.keep_hold_written_files`, `play.frame_times`, `play.series`.
- **Log.** `<game>: start stream skipped (<why>)`, `<game>: stage stream ...`, `<game>: exited quickly (Ns)`, `<game>: backing off for this run (...)`, `play record: ...`, `background yield ...`

<details>
<summary>Details: same-disk rules, start stream, stage stream, quick exit, play record</summary>

**Same disk**

- The running game's own prewarm, and any relocation, re-layout, reapply, or tier write, stay blocked.
- A prewarm of another game on that disk runs only if the running game reads under 1 MiB/s and the disk stays under its busy threshold for 60 seconds in a row.
- While reading, it checks that game's read growth between batches, and about every 10 seconds it pauses for 1 second to measure disk throughput again and yields if the disk is busy. A failed read-count query counts as busy.
- The log line for a prewarm skipped because a game is running names the process (name and pid) judged to be the running game. The elapsed run time is counted from when the service observed the start.
- If the disk-activity counter returns a sample without the drive letter in its instance name (seen around a game start), the service goes on reading the same disk number it remembered from when the letter was there. When no value can be read at all, the yield decisions use the last value for up to 10 seconds; the checks that need a clear "not busy" answer, such as the re-prewarm check, are unchanged and treat unknown as busy. The log has a pair of lines, `DiskActivity: D: disk activity unavailable; optimization paused (<reason>)` and `DiskActivity: D: disk activity available again after N s (<reason>)`, at most one pair per drive every 10 minutes; shorter outages in between are counted as `, N short outage(s) merged since the last report`. The cause was a real counter that lost the letter in three log cases on the test PC (2026-11-11 and 2026-11-15, twice); that shape was not reproduced with a real counter, and the remembered disk number has no time limit, so a disk number reused by another disk could be read for a while.

**Start stream**

- When a game starts, the service can read its hot set (the start stream). It stops at the loading boundary (the 10-second moving read rate falls below 10% of its peak, at most 60 seconds in) or at `auto.start_stream_cap_seconds`.
- When the game has a stage index, the first start stream reads only the head part and the first stage; see the stage stream below.
- It is not repeated within `auto.restream_cooldown_min`. Log line: `<game>: start stream stopped at load boundary after N bytes, S s (R MB/s); boundary at B ms, peak P MiB per 10 s, last window W MiB, observed T s`. The numbers after the semicolon show why it stopped there: the boundary time, the largest and the latest 10-second read amounts, and how long the start was watched.

**Stage stream (the programs a game starts after its first one)**

- A game can start several executables one after another, for example a launcher-like program and then the game itself. With the start stream alone, it runs only for the first one and stops at the loading boundary before the main program is up; when the main program starts, the start stream is skipped as `game already running`, so the blocks the main program reads first come straight from the disk. The stage stream treats the start of each registered executable as a stage boundary and reads the blocks that stage reads first, right after that executable starts. It is on by default and turned off with `auto.stage_stream_enabled` (with it off, no stage stream runs).
- Where the stages come from. While automatic tracing records a play, the service notes when each registered executable first appeared, and builds a stage index next to the merged trace file (the trace file name with `.stages.json` added; the per-play files get a marks file the same way, and `.stages.tried` counts the attempts). These files are safe to delete: they are made again, or the game is treated as having no stage information. A game with no stage index is traced up to two more times when the usual trace conditions hold (not when tracing is off or its anti-cheat forbids it). A manual trace, or a first-run learning that rewrites the trace, deletes the old index.
- First executable. With a stage index, the start stream reads only the head part and the first stage (and blocks assigned to no stage). Without one it reads the whole start list, not split into stages.
- Later executables. For a registered executable that is not a launcher, the blocks of its stage are read at low I/O priority, at most once per 60 seconds for each (game, executable). The priority is raised when the game's own reads have been quiet for 5 seconds, and lowered again from the next batch when they get busy. Read items are cut to at most 32 MiB and read in batches of about 64 MiB or more. Before each batch the stream checks memory and stops when available memory minus the reserve (`prewarm.min_free_ram_mib` or 4,096 MiB, whichever is larger) is smaller than the next batch (at most 96 MiB, or what is left to read); the first start stream follows this too while the stage stream is on. It also stops at the loading boundary measured on the new process's own reads, and at `auto.start_stream_cap_seconds`. With no stage index, it reads the start list only if, after it begins to wait, the new process's reads grow by 64 MiB or more while the process is less than 10 seconds old. If another game's start is waiting, it does not wait for that evidence.
- What it reads. The blocks are the intersection of the start list and the stage's blocks, so never more than the start list; volatile files and the background list are not read, and files with the sparse attribute use the buffered read path only. A run on which the service backs off (see below) gets no stage stream.
- Load history list. Each time a registered program of the game starts, the data the game reads in the first 120 seconds is read again, because the cache that was prewarmed is pushed out while the game runs and the second and later map loads then come from the disk. After each play, the service builds a list from the saved disk-read summaries (`.io.json`) of the earlier plays: for each start of a registered executable (recorded in the summary as `target_starts_us`; for older summaries, the later-start marks of that play's stage marks), the 64 KiB blocks first read within 120 seconds of it. Blocks that were read only without the file cache (no paging request) are left out, since reading them into memory does not help the game; files that changed during the play, files that are gone, volatile files, and files outside the allowed roots are left out too. The plays are merged; blocks are ordered by the number of plays they appeared in, then by their summed read delay, and cut at 4 GiB (the largest single load seen was about 4.1 GiB, the union of three loads about 2.9 GiB, and the memory available during a load about 11 GiB). The list is saved next to the trace as `<game>.trace.loadrefill.json` (written to a temporary file and moved into place; safe to delete, and removed when the trace is learned again). When a later program starts and the list exists, the stage stream reads this list instead of the stage blocks, in disk order, and the size is also cut to what the memory gate allows (available memory minus the reserve). It does not wait for the 64 MiB read evidence, does not stop at the first quiet moment of the loading boundary, and stops when the list is read, at `auto.start_stream_cap_seconds` (default 120 seconds, the same as the window), at the memory reserve, or when the game exits; low I/O priority, the memory gate, and the limit to one stream per 60 seconds are unchanged, and the 60 seconds are counted from the end of such a stream so an overlapping start of the same load does not read it twice. A start handled 120 seconds or more after it happened, or a game without a list, uses the stage blocks. The log line when the list is built is `<game>: load refill list built from P plays (Q without start times), L loads: N blocks/M MiB, K MiB left out as read only without the cache, J MiB over the 4096 MiB cap`. The effect in a real game has not been measured yet.
- Idle-only streaming (`auto.stream_idle_only`, on by default). With it on, the start stream and the stage stream above do not interleave with the game's reads at low I/O priority. They issue one batch at a time, and only while the game drive is idle: the disk queue is 0 and has stayed 0 for 300 ms (one judgment shared with the filling of the hold, see [SOLAR](SOLAR.md)), read straight from the disk performance counter; a queue that cannot be read counts as not idle. The read items are cut to 16 MiB and a batch is about 16 MiB, so the judgment is repeated before every batch and nothing new is issued while the drive is not idle. A prefetch request returns before the system has finished it, so after a batch the stream also waits until its own reads are gone from the queue. The cap of `auto.start_stream_cap_seconds`, the list and its order, the memory gate and the loading boundary do not change; time spent waiting counts against the cap. Because the stream now reads less while the game reads, the loading after it may be slower than with the interleaving. The end-of-stream line therefore ends with `; idle-only: N batches, M MiB; held back K times (queue a, measurement gap b, loading c) for S s, ended: <reason>, L MiB left unread`, so that the next play shows what it cost. Set `auto.stream_idle_only` to `false` for the old way. Whether it helps in real play has not been measured.
- The list is also built when the service starts: for each game whose list file is missing or older than the newest saved summary of that game, the list is built from the saved summaries (so a fresh install or a deleted list does not wait for the end of the next play). It follows the same wait as the service-start prewarm (after the boot delay and while the game drive is idle), runs in the background without delaying the start, holds the same game-folder lock, and skips a game that is running. A game with no saved summary is left alone. The log line is the usual `load refill list built from ...` with ` (service start)` appended.
- Files read only without the file cache. A file the game opens unbuffered is read from the disk every time, so reading it into memory does not help the game, takes memory from blocks that do go through the cache, and competes with the game for the disk while loading. After each play, the service judges such files from the per-file read modes (`read_modes`) of the saved disk-read summaries (`.io.json`): a file is judged when at least two distinct plays (by session ID) read it and every one of those reads was without the cache (no cache request and no paging request), and no play read it through the cache. A file is not judged when it is gone, is volatile or outside the allowed roots, or was written after the observation of the latest play that read it. The judged files are saved with their size and write time as `<game>.trace.json.unbuffered.json` (written to a temporary file and moved into place; safe to delete; an empty list is saved when no file is judged). It is also built when the service starts if it is missing or older than the newest summary, under the same wait, zone lock, and skip while the game runs as the load history list. When the read list is made, a file whose size or write time differs from the saved one (for example after a game update) is not left out, and the file is judged again after the next play. The files are left out of the memory prewarm list, the start stream, the stage streams (they are subsets of the start list), the refresh read, the probe samples, and the pinned files; the memory budget window is unchanged, so the bytes left out stay free for blocks that go through the cache. They are not left out of the relocation plan, because only their place on the disk can make them faster. The read modes record only reads by the game's process tree, so the service's own reads are not in them. The log line when the list is built is `<game>: unbuffered file list built from P plays: N files/M MiB read only without the cache`. One play is never enough, and no file name or extension is used. The effect in a real game has not been measured yet.
- Ranked block list. Most of the read delay in a match comes from blocks that other plays first read in a load or early in the play, so a list built from the match part alone is small. After each play, the service therefore ranks the 64 KiB blocks of the whole recorded range (start-up, loads, and match) of the saved disk-read summaries (`.io.json`) by the number of plays they appeared in, then by their summed read delay, and saves them as `<game>.trace.json.ranked.json`. The format, how it is saved, when it is built, the zone lock, and the rebuild at service start when it is missing or older are the same as for the load history list; it is removed when the trace is learned again, and a file whose size or write time differs from the saved one (for example after a game update) is not used. It is kept apart from `prefetch.json` and `warmonly.json`, which the plan and the additions outside the zone rewrite. As for the load history list, blocks read only without the cache (no paging request), files that changed during the play, files that are gone, volatile files, and files outside the allowed roots are left out; so are files read only without the cache (above), which the prewarm list leaves out anyway, sparse files (touching them does not keep them in the cache), and files outside the game's drive. The list is cut at 8 GiB, because the prewarm budget between games is about 5.8 GiB (8 to 11 GiB at most), so a larger list would not be read. It is used in two places: when the prewarm list has to be cut to fit memory it takes its place in the selection order (above), and it sets the order of the ranges that keeping the cache while a game runs touches ([SOLAR](SOLAR.md)). In both cases the summaries (`.io.json`) are not read again at game start, only this file; without the list nothing changes. With the list, the general prewarm stream, the partial prewarm stream, the ladder, the touch at the start, and the keeping while a game runs all choose the same set of ranges by the same rule (a list larger than the budget is cut in the order above for the general stream too, because a ladder that touches blocks the stream did not read would meet disk reads and the re-prewarm would repeat). The service keeps in memory the ranked list that the last prewarm read: when the ranked file is rewritten after a game ends, the ladder, the touch at the start, and the keeping follow the kept list until the next prewarm run sees the change. A service that has just started and keeps nothing reads the file as it is then and keeps that. The memory budget split between games does not count this list and stays as it was; only what goes into the budget changes. When the list changes, the reuse signature of the prewarm list and the generation of the prewarm samples change, so the list and the samples are computed again. The log line when it is built is `<game>: ranked block list built from P plays: N blocks/M MiB, K MiB left out as read only without the cache, S sparse files left out, J MiB over the 8192 MiB cap`, and the amount the prewarm selection took from it is shown at the end of the `prewarm phases` line as `N MiB selected from the ranked block list`. The effect in a real game has not been measured yet; only how much of another play's match delay the front of the ranking covers was computed from three saved recordings.
- This widens the rule that no new background read starts on a game's disk while the game runs: the exception is the moment a registered executable of the same game has just started, under the conditions above. To judge read evidence and the loading boundary it reads the I/O counters of the game's processes through the same query-only handle the start stream already uses, and it opens nothing else; a process that refuses even that is left out of the counters ([ANTICHEAT.md](ANTICHEAT.md)).
- Not included: reading the next stage ahead of time while the first stream runs. The effect in a real game has not been measured. The 5-second quiet time and the evidence limit (64 MiB in 10 seconds) are values set before any measurement, and the effect of cutting read items into 32 MiB pieces on throughput has not been measured; the `requests` count in the log is larger than before when a read item was cut.
- Log lines: `<game>: stage stream <exe> N MiB in S s (R MB/s, completed|stopped, <reason>), yielded Y s` (the reason is `load boundary`, `cap`, `memory reserve`, or `cancelled`; `; skipped volatile N MiB` is added when volatile files were left out, and the line ends with `; source trace stage`, `; source start list`, or `; source load history (P plays, L loads, N MiB planned)`) and `<game>: stage stream skipped (<exe>: <why>)` with a why such as `cooldown N s` (the same program started again within 60 seconds), `no blocks in the start list`, `no load evidence, ...`, `another game started`, or `disk yielded`.
- Prior art. Reading a program's data when it starts, and replaying a recorded read order, are old ideas: the Windows Prefetcher (one `.pf` file per executable, read when the process is created), FAST (USENIX FAST 2011), and Android iorap do something like it. What is different here is the combination: the start of each executable that one game starts in turn is taken as a stage boundary, the recorded blocks are split by the stage that first read them, and that stage's blocks are read when that program starts. In one recorded play of one game on the test PC, the blocks of the first stage and of the main program hardly overlapped (Jaccard index 0.023). No public source doing exactly this was found, which does not mean there is none, and whether the Windows Prefetcher also covers the data files that a second process reads was not settled.
- The play record keeps the result for each later executable. `play_samples.json` gets `stageStarts` (the stream result and the +30, +60, and +120 second windows from that executable's start, up to 20 per play) and `periods` (a summary for each 10 minutes after the first 600 seconds). The log lines are `play record stage <exe>: ...` and `play record periods: ...`, written separately from the `play record:` line.

**When a game closes right after launch**

- A game session that ends in less than `auto.quick_exit_seconds` (90 seconds by default, 10 to 600) is a quick exit. A session that is not a quick exit and lasts 5 minutes or more is a normal one and resets the count (with the default limit, any session of 5 minutes or more; a `quick_exit_seconds` above 300 makes a longer run still count as quick); one in between neither counts nor resets. A session runs from the first game process starting until all of them are gone. The length is taken when the service notices the processes gone (the check runs about every 30 seconds), so a run close to the limit may not be counted.
- The first quick exit writes `<game>: exited quickly (Ns)`.
- If the game is started again within 10 minutes of a quick exit, the service backs off for that one run. It does so at most once until a normal session resets the streak. A backed-off run that itself closes quickly is recorded; if it ends after the quick-exit limit and before 5 minutes, the `launched after the service backed off` log line and notice are written and the saved back-off mark is set to `launched`. Either way, the service does not back off again in that streak. A backed-off run gets no start stream, stage stream, automatic trace, loading-boundary reads, background memory yield, or trigger prewarm. The disk yield to the game stays on. Log lines: `<game>: backing off for this run (quick exit N in a row, last Ss, M min ago): no start stream, memory yield or trace`, `<game>: start stream skipped (quick exit guard: backing off)`, `<game>: auto trace skipped (quick exit guard: backing off)`.
- From the second quick exit in a row, the service lists the kernel drivers that have loaded since the last normal run (the last session of 5 minutes or more) and reports them in the log, in a tray pop-up (the Notifications switch applies), and on the game's card in the Status tab. Log line: `<game>: quick exit N in a row (runs 32s, 47s); backed-off run: exited too|launched|not backed off; new kernel drivers since the last normal run: <name (path), ...>|none|unavailable|unknown (no normal run recorded)`. `unavailable` means the driver list could not be read this time; `unknown (no normal run recorded)` means there is no normal run to compare with. If the backed-off run stayed open, the service writes `<game>: launched after the service backed off (Ns); the earlier quick exit(s) may involve the service, or the program may restart itself`: it does not claim the service was the cause, because a program that restarts itself shows the same pattern.
- The driver list is a read-only query of the loaded kernel drivers (file name and path as Windows gives them). It opens no process and touches no driver. The counts and the last normal run's driver list are kept in `quick_exit.json` in the data folder.
- What it is not. It does not stop a game from closing. It notices the pattern, skips its extra work for a run so that the service can be ruled out, and shows what changed since the last normal run. A kernel driver of another program can be the cause, and a new driver in the list is a clue, not a finding.
- Limits. When the same executable starts again, the service looks at how long the earlier run lasted: under 5 seconds, the new start is joined to the same session; 5 seconds or more with no other process of the game left, the session is split and the earlier run is judged by itself, so a program that restarts itself after a short run of 5 seconds or more counts as a quick exit. A game already running when the service started is not counted. If the PC is shut down right after a game closes, the last count may be lost. The driver list at the start is taken just after the game appears, so a driver that loads together with the game can be missing from the normal list and show up as new next time. If another game that uses the same launcher is prewarmed, the global background memory yield stays open during a backed-off run. Seen on one PC with a lightweight game closed by hand: the counting, the back-off, the Status tab card, and the driver list read as the service account. It has not been checked with a game that closes by itself.

**Small checks**

- The keep-awake read, pin creation, and boot checks check for a running game before they start.
- The keep-awake read (`auto.keep_awake`) is 4 KiB every 10 minutes while a launcher is open or at your usual play hour, so the HDD does not spin down. Power settings are never changed.

**Play record**

- The service samples the physical disk's cumulative read counters once per second and logs a `play record:` line and saves `play_samples.json` at 30, 60, 120, 300, and 600 seconds after the start and at exit.
- The same record also gets the frame interval (`play.frame_times`, on by default, only for a game that passes the gate in [Anti-cheat](ANTICHEAT.md)). It totals the Present intervals of the game's processes per second and keeps, for each checkpoint and 10-minute period, the frame count, the longest interval, and the number of intervals over 50 ms and over 100 ms. A second whose longest interval is 50 ms or more, or that is a slow disk second (5 or more reads with an average of 100 ms or more), goes into the `frameSeconds` list (at most 300; when it overflows, the ones with the longest interval stay) with the second since the start, the disk read count and average read time of that second, the total CPU use, and the dedicated graphics memory in use. Intervals are computed in event time order, not arrival order (the number that arrived out of order is `frameEventsOutOfOrder`). An interval of 1 second or more is not stutter but a pause (minimized window, covered window, loading screen, not responding): it is counted apart as `pauses` and is not part of the over-50 ms and over-100 ms counts or of the longest interval. The second stays in the list with `pauses`. The list holds at most 50 entries per 10-minute period and 300 in all, and within a period the ones with the longest interval stay. Because of event delivery delay (up to about 1.5 seconds measured on this PC), frame values are final only up to about 5 seconds before the measurement time, and the number of events that arrived after they were final and were dropped is kept in `frameEventsLate` and in the `frame events late N` part of the log (when it is not 0, an interval that such an event ends may be missing). A second with no disk sample has a null `diskReads`. For a game whose registered executable is a launcher, the Present calls of the launcher screen are irregular, so the intervals may be meaningless. `frameStatus` is `ok` or the reason it could not be measured (`off`, `blocked`, `unavailable`, `no_events`), and `frameEventsLost` is the number of events the session lost. The `play record:` and `play record periods:` log lines gain `frames N, longest M ms, over 50 ms K, over 100 ms L` and `, pauses P (longest X ms)` (the number of intervals of 1 second or more and the longest of them; the parentheses are left out when there is none). The longest pause is also kept in the checkpoints, periods, and total (`maxPauseMs`), and when the list overflows, the entries with the smaller of the longest interval and the pause length are dropped first. For a play that was stopped part-way as `blocked`, a period that spans the stop time is shown only as `frames blocked` in the log even if its first part was measured; the values stay in the totals in the JSON. A game that does not use DirectX stays `no_events`. The values in a real game have not been checked.
- While a game plays, the service also writes one line for every second to a file of its own (`play.series`, on by default; it is written only for a play whose frame times are measured, so the gate in [Anti-cheat](ANTICHEAT.md) applies in the same way). The file is a CSV with a header line, one per play, in the `play_series` folder of the data folder, named `<game key>_<start time>.csv` (the game name with every character other than letters, digits, `-`, and `.` replaced by `_`, and the local start time of the PC). The log line `<game>: play record series: <file name>` names it once. Lines are collected in memory, appended once a minute, and the file is closed when the play ends; only the newest 8 plays of each game are kept, and older ones are deleted together with their list files. `play_samples.json` and `frameSeconds` are unchanged. The columns are: `t_s` (seconds since the start of the play); `frames`, `max_frame_ms`, `over50_n`, `over100_n`, `pauses_n`, `pause_max_ms` (the frame values of that second, for every second and not only the stuttering ones); `cpu_sys_pct`, `cpu_game_pct`, `cpu_service_pct`, `cpu_other1_name`, `cpu_other1_pct`, `cpu_other2_name`, `cpu_other2_pct` (CPU use as a percentage of all logical processors, so that the game, the service, and the others add up to the system value: the whole system, the sum of the game processes the service already knows, the service itself, and the two other process names that used the most in that second, with processes of the same name added together); `avail_mib` (available memory), `standby57_reused_mib` (how much of standby priorities 5 to 7 was reused in that second), `page_reads_n` (the increase of the number of pages the whole system read from disk); `gpu_mib` (dedicated graphics memory in use, all adapters), `gpu_game_mib` (the amount used by the game processes, from the performance counter `GPU Process Memory`); `disk_read_n`, `disk_read_bytes`, `disk_read_mean_ms`, `disk_write_n`, `disk_write_bytes`, `disk_write_mean_ms`, `disk_queue` (the disk the game is installed on); `write_anyvol_top_name`, `write_anyvol_top_bytes` (the process that wrote the most in that second: its write transfer count covers every volume, the network, and pipes, not only the disk of the game); `service_ops` (what the service was doing in that second, joined by `+`: `touch` the touch at game start, `keep` a round of keeping the cache, `stream` a start or stage stream, `trim` a working set trim of background yield, `supp` a supplementary prewarm); `game_read_bytes` (the increase of the read transfer count of the game processes the service already knows, which includes reads served from the cache and reads of other volumes, and is empty for the first second); `game_ws_mib` (the working set of the same processes); `load_phase` (the loading judgment of that second, explained in the next item: `loading` or `not_loading`, empty when there is none); `other_ws_mib` (the sum of the working sets of the processes other than the game's and the service's, in MiB); `ws_grow_top_name` and `ws_grow_top_mib` (the program name, with the same names added together, whose working set grew the most in that second, and the growth in MiB; a program seen for the first time counts its whole working set as growth, and both are empty when nothing grew); `yield_applied_n` (how many programs the background yield newly applied a priority to in that second). These four come from the same system-wide query that opens no process and from a counter in memory. They add about 22 bytes to each line (about 55,000 bytes for a 2,500-second play, on a file of about 455,000 bytes), written in the same once-a-minute append. `service_read_bytes` is a fifth column added after them: the bytes the service itself read from the game's drive in that second (the disk reads counted by the keep rounds, the hold and its check, the same value the loading judgment subtracts from the drive's reads), taken from a counter in memory; the reads of the streams are not in it. A file recorded before this version has the earlier columns only, in the same places, and the new columns of a new file are always at the end. A cell that could not be read is empty, and the CPU, memory-reuse, and write columns of the first second are empty because they are differences. The per-process values come from one `NtQuerySystemInformation(SystemProcessInformation)` call (the call the touch already uses to count its own hard faults) and from performance counters, so no game, launcher, or anti-cheat process is opened. A second file with the same name and `.lists.csv` gets one line every 30 seconds: `free_zero_mib`, then for each standby priority 0 to 7 its size (`standby_mib_p0` to `standby_mib_p7`) and its reuse total since boot (`reused_mib_p0` to `reused_mib_p7`). Nothing reads these files back: keeping the cache, the ladder, prewarming, and background yield do not depend on them. Cost, measured on this PC with no game running (180 readings, one per second): reading the system values takes about 2.7 to 3.9 ms of CPU, almost all of it the one process-list call, and building and queuing a line about 0.1 ms, which was 0.36% of one core on average after subtracting a baseline in which the same test program only waited at the same 1-second interval (0.52% before subtracting); no managed memory is added (the process-list call uses the buffer of about 2 MiB the touch already keeps), and the file grows by roughly 10 KB per minute, written once a minute. It has not been measured next to a running game.
- **Loading judgment.** Once per second the service judges whether the game is loading; the `load_phase` column of the series above records the result. Loading starts when the graphics memory of the game grows by 250 MiB within 10 seconds, when the drive the game is installed on reads 80 MiB within 5 seconds (minus what the service itself read from that drive: it counts the bytes its touches, checks, and holds read from disk, because those reads are page faults of mapped views and do not appear in the read transfer count of its process), or when an executable of the game starts, and it ends when the reads stay below 40 MiB per 5 seconds and the graphics growth below 64 MiB per 10 seconds for 15 seconds, or 240 seconds after it started (an executable that starts again while loading restarts the 240 seconds, but loading as a whole ends after 480 seconds). While it is `loading` and no executable of the game started it (a loading seen only from the graphics memory or the drive reads, such as a map change in a match), the service keeps touching what is already in memory but limits the disk reads it makes while a game plays. A round of keeping the cache (see [SOLAR](SOLAR.md)) looks for new ranges only when it has nothing in memory to touch, and then stops at about 2 MiB of disk reads; its protect pass stops at about 2 MiB; its order pass touches only the ranges the protect pass just found in memory and stops at the first batch (16 MiB) that has to read from disk or when its disk reads in the round pass 32 MiB (the same cap as outside a loading, which matters when blocks that are not in memory are scattered over several batches); no cap takes a range off its list. The check of the held ranges still releases files the game changed, and stops reading back what the memory manager trimmed at about 2 MiB, without taking ranges off the hold when it reaches that cap. A cap is looked at only when the read count is looked up (at once after a slow piece, otherwise every 64 MiB touched), so a round usually reads 2 to 4 MiB and the check about 8 to 10 MiB, and a round or check reads at most 64 MiB more than its cap in the worst case. During a loading that an executable of the game started, the service does exactly what it does without the judgment, and what it reads when a game starts is unchanged. The judgment runs for every play, also when the series is off or not written; the graphics memory is used only where `gpu_game_mib` is read, and elsewhere only the disk rule runs. It logs one line when loading starts (`<game>: loading phase started (<reason>)`) and one when it ends (`<game>: loading phase ended after <n> s (<reason>)`, with what was postponed). The thresholds were fitted to the recorded plays of one game.
- When a touch (at game start or while the game runs) finds the edge of the part of the list that is still in memory before the end of the list, its log line ends with a probe such as `probe 5/16 in memory (positions 0 211 422 MiB of 3386 MiB)`: 16 spots spread evenly over the whole list (64 KiB each) are touched one by one, and a spot counts as in memory when the hard faults of the service grew by less than 2 while touching it (a block that is not in memory takes 2 to 3). The positions are those of the spots that were in memory, `none of M MiB` is written when there was none, and `, N not probed` is added for spots that could not be opened (sparse files, missing files). It tells whether only the front was lost or the whole list. The probe reads at most 1 MiB from the disk and is not used for any decision or order. A touch that had open, map, or read errors writes `, N errors (open A ranges in F files (win32 5 ×X (f files, r ranges, S requested), ...), beyond end B ranges in G files, map C ranges in H files (...), read D ranges in I files (...); most failures in <path> ×K, ...)` instead of the bare count: the number of ranges and of different files by kind (a file that could not be opened with its Win32 error numbers, a range past the end of the file, a failed mapping, a failed read). For open errors each Win32 error number also has its number of files, of ranges, and the bytes those ranges asked for (written in MiB, KiB, or B). After the semicolon come the files with the most failed ranges of any kind, at most 4, each with its count.
- It reads only the disk device counters, never the game's files or process. It is for comparing loading and stutter.
- The end time, the length, and the totals (bytes read, read time, disk idle time) of a play stop at the moment the service first saw the game's processes gone, so the 60-second exit check is not counted. If the game comes back during that check, the play continues.

</details>

### 7. Drive recovery wait

- **When.** After a relocation on an SMR drive, and after a game update is detected.
- **What.** Waits until short test reads show the drive back at its normal speed, then allows the next job.
- **Does not.** Block prewarm. It holds back relocation, and after a game update that game's re-planning and prewarm.
- **Settings.** `post_relocate_recovery`, `recovery_max_min`, `recovery_hard_max_min`, `post_update_delay_min`.
- **Log.** `drive D: recovering after relocation (...)`, `drive D: recovered after N min`

<details>
<summary>Details: rules of the `"probe"` mode, limits, other modes, pauses</summary>

**`"probe"` (default)**

- The baseline is measured right before the write at the three positions the samples rotate through, and their median is used.
- Every 4 minutes it reads a short sample (at most 192 MiB). The drive counts as recovered after 2 consecutive samples at 90% or more of the baseline. When the measurements fluctuate, it also counts as recovered once at least 4 of the last 6 samples (the three positions twice each) are at 90% or more.
- When samples keep falling short, the first 7 samples are 4 minutes apart and later ones 8 minutes apart. Each sample logs its position, speed and baseline, verdict, and reason.
- Samples above the cache-hit ceiling at all three rotating positions in a row also count as recovered. Samples that cannot be judged are spaced out up to 8 minutes apart, and the discarded ones are summarized in one log line.
- It waits at most `recovery_max_min` minutes. If recovery is still unconfirmed, further relocations stay on hold until the drive is recovered or `recovery_hard_max_min` minutes have passed.
- **Daily limit.** On one drive, in any 24 hours, at most 8 samples that were read to the end are counted, and at most 1.5 GiB (a sample cut short or failed counts its bytes but not one of the 8). A sample starts only if one whole sample (up to 192 MiB) still fits in the 1.5 GiB. When the limit is reached, no sample is read until both the number of samples and the bytes have room again (the oldest samples are 24 hours old). Recovery then stays unconfirmed, so relocation stays on hold, and the two time limits above end the wait as before: `recovery_max_min` and `recovery_hard_max_min` count the same whether or not samples are being read. This means a drive that has used up its samples can hold relocation until `recovery_hard_max_min`. Log lines: `drive D: recovery samples paused: N samples and M MiB read in the last 24 h (limit 8 samples, 1536 MiB), sampling again from <time>; ...` and `drive D: recovery samples resumed: ...`.
- `"fixed"` waits `post_update_delay_min` minutes; `"off"` turns it off.

**After a game update**

- Re-planning, relocation, and prewarm for that game wait `post_update_delay_min` minutes, because the drive may still be reorganizing scattered writes (RESULTS_SUMMARY experiment E9: replay time after scattered writes).

**Pauses**

- The wait stops while a game on the same disk is running, and continues from the remaining time after it exits. The recovery sample reads are skipped meanwhile.
- A service restart keeps the paused state and the remaining time.
- Other log lines: `drive D: recovery clock paused (game running)`, `drive D: recovery discarded N cache-suspect samples ...`.

</details>

### Right after boot

If the service starts within 5 minutes of boot, it holds the disk work it would start on its own until 5 minutes have passed and the game drive has been idle for 60 seconds. The quiet period ends 15 minutes after boot at the latest. Two prewarms are the exception: the prewarm at service start and a prewarm started by a launcher wait only until 60 seconds after boot and the game drive has been idle for 20 seconds, because their reads give way to other reads (see [Prewarm](#4-prewarm)).

<details>
<summary>Details: what is held</summary>

- Held work: relocation, new-trace prewarm, layout checks and reapply, and the keep-awake read. The held work then runs under the normal rules. A trigger prewarm such as a launcher starting is held only until the shorter condition above; while a launcher prewarm is held it is checked every 5 seconds (otherwise every 30 seconds), and it is released at the first check after that (log: `held prewarm triggers released: N (boot + idle disk)`, preceded by `boot prewarm release: uptime U s, idle since S s, C checks (B not idle), last disk X MiB/s`), while the other held work stays held until the quiet period ends. The prewarm at service start writes `service start prewarm waits for 60 s after boot and 20 s of idle disk`.
- A prewarm read that starts within 15 minutes of boot measures the disk before its first batch and, if other reads are there, steps aside at once with a low I/O priority (see [Prewarm](#4-prewarm)).
- After a reboot the RAM cache is empty, but the cooldown counts from the last prewarm before the reboot. A sample that finds the cache cold ends the cooldown for that game (`cooldown ignored, the cache is cold [service start]`).
- Boot-time prewarm covers only recently played games. A trace that was already prewarmed before the restart is not treated as new again.
- The period also ends 15 minutes after boot even if the disk is still busy or unreadable.
- Log lines: `<what> deferred: boot quiet period`, `boot quiet period ended: ...`.

**What was measured on the test PC (2026-11-14)**

These are experiments with a test tool and test files on the HDD, not the service itself and not a running game. A thread read a 1 GiB test file with `PrefetchVirtualMemory`, while another process read 64 KiB pieces of another file at random, without a pause and past the cache.

- Reading thread at normal I/O priority: 113 MB/s alone; beside the other reads, 99 MB/s, and the other reads took 45.9 ms on average (p99 470.5 ms).
- Reading thread at low I/O priority: 51 MB/s alone; beside the other reads, 8 MB/s, and the other reads took 26.1 ms on average (p99 84.9 ms). The other reads alone took 25.0 ms on average (p99 124.9 ms). Very low priority gave similar figures (49 MB/s alone, 11 MB/s beside, 31.5 ms and 88.7 ms).
- On an idle disk, a read of 128 KiB pieces spaced 1.33 MiB apart, like a real prewarm list, ran at 31.6 to 38.6 MB/s at normal priority and at 13.0 to 14.2 MB/s at low priority.
- So low priority hardly disturbs other reads, but it makes the prewarm about 2 to 3 times slower even on an idle disk. That is why the prewarm uses it only while other reads are there. The pages read this way still enter the standby list at priority 5. How this changes the start of a launcher in real play has not been measured.

</details>

### Pinning (optional)

With `prewarm.pin`, prewarmed pages stay open as read-only mappings in the service so they are less likely to be evicted. Files with the sparse attribute are not pinned (they are counted as skipped in the log), because creating a mapping for one discarded its cached pages in a test on one PC. Effect unverified (needs an experiment).

<details>
<summary>Details: when pinning is on and released</summary>

- When the key is not written, it turns on automatically with 24 GiB of RAM or more; `false` turns it off; an explicit `true` works with 16 GiB of RAM or more.
- The mappings are released at once when free RAM falls below the reserve or when a game or launcher starts, so launcher updates can change the files. A prewarm started by a trigger program is not pinned.

</details>

### Background memory yield

During a game session, programs that have nothing to do with the game give up memory, so that Windows does not take it from the prewarm cache first. It is on by default (`memory.background_yield`) and applies to every registered game, including games with anti-cheat.

- **When.** When a registered game's exe starts. A launcher or another trigger program alone does not start it (the prewarm that such a program starts is unchanged). It ends when the game counts as exited (and no other registered game is running), at service stop (a start request that arrives after that is ignored), when the setting is turned off, or 10 minutes after the last time a registered game was seen running (counted from the start when none was seen).
- **What.** For each program in your user session that is not excluded (see the details) and that has not been using the CPU or doing I/O in the last minute (see Programs in use in the details): lowers its memory priority to "very low" (1) when it is higher (the Windows default is 5), and, only when the available memory minus what the game is expected to take is below a floor (see Timing in the details), empties the working sets of the largest such programs, only as much as is missing (only those of 32 MiB or more). At the end it sets the priority back to the value it had. A program that has been working (streaming, voice chat, a browser playing video, a build) gets neither of these two; only its memory priority is lowered, to "below normal" (4) instead of "very low" (see the details). It also lowers the disk (I/O) priority of all the chosen programs from normal to low, including those in use, so that their disk reads do not delay the game's, and sets it back at the end (see Disk priority in the details). Lowering the CPU priority class (normal to "below normal") is available but off by default (see CPU priority in the details).
- **Does not.** Open a game, launcher, launcher helper, anti-cheat, or Windows component process, or any service process (session 0); the one exception, a Windows-folder program that inherited a lowered value, is described under Excluded by path in the details. It changes nothing in another program except these four things (memory priority, working set, disk priority, and CPU priority class): no ending, suspending, injecting, or reading memory. The memory reserve (`prewarm.min_free_ram_mib`), the cache budget, and the prewarm decisions are unchanged.
- **New programs and programs in use.** While a registered game's exe is running, a program that starts is noticed within about 3 seconds and gets the same priority change, under the same exclusions; the working set is not emptied on this path (`memory.background_yield_fast`, default `true`). A program in use gets its memory priority lowered to "below normal" (4) instead of being left alone (`memory.background_in_use_memory_priority`, default `true`): when memory is short, Windows then trims and reuses this program's pages before the game's prewarmed cache, which sits at priority 5, so the program can be slower when it needs those pages again. The service does not empty its working set, and `memory.background_in_use_memory_priority` set to `false` leaves programs in use alone. What either change does to loading time or stutter has not been measured.
- **Settings.** `memory.background_yield` (default `true`), `memory.background_io_priority` (default `true`), `memory.background_cpu_priority` (default `false`), `memory.background_yield_fast` (default `true`), and `memory.background_in_use_memory_priority` (default `true`); the last four do nothing while `memory.background_yield` is `false`.
- **Log.** `background yield (game started): trimmed N processes (...)` or `... no trim needed (...)`, `background yield ended: ...`. The meaning of each line is in the [FAQ](FAQ.md#troubleshooting).

<summary>Details: why, what is left alone, timing, disk priority, side effects, recovery, turning it off</summary>

**Why**

- On the test PC, when a game took about 10 GiB, Windows took the memory from cached file pages, and the prewarm cache is made of those pages. Reads by other programs can also push the prewarm cache out.
- Emptying the working set of an unrelated program frees its memory in a form Windows reuses before the cache. A lowered memory priority keeps the pages that program reads afterwards from pushing the cache out.
- Windows takes memory from free pages first, then from standby pages of lower priority (0 to 4), and only then from priority 5, where the file cache sits. A page emptied from a working set goes to the priority 0 list, most of it within 2 seconds (measured on the test PC, 2026-11-14). While free memory and priority 0 to 4 standby memory last, the cache is not reused, so emptying helps only when they run short. In a 4 hour 11 minute session on the test PC, the first rule, which did not look at the state of the cache, emptied the background programs again 41 times (18 to 36 programs and 1.6 to 4.1 GiB each time). The next rule used the standby memory of priority 0 to 4 only, and the prewarm cache itself fills the lists of priority 5 and above, so on 2026-11-21 it showed 0.3 to 2 GiB of spare memory while 15 to 22 GiB were available, and emptied about 3 to 7 GiB of other programs at a time (more than once from a launcher alone). The present condition is the available memory minus what the game is expected to take (see Timing).

**What was measured on the test PC**

These are experiments with an experiment tool, test programs, and test files on 2026-11-13, not the service itself and not measurements inside a running game. How much this changes loading time or stutter in real play has not been measured.

- Emptying the working sets of 29 background processes (7,664 MiB of working set in total): available memory went from 15,587 MiB to 19,324 MiB after 10 seconds. In the next 2 minutes, all 2,398 MiB of pages that Windows reused came from the lowest-priority list and none from priority 5, where the prewarm cache sits. Their working sets together fell to 861 MiB and were 1,900 MiB again 2 minutes later.
- A test program with an emptied working set of 2 GiB took 0.8 seconds to touch all of it again.
- A program read 17 GiB, more than the 15.5 GiB of available memory, while a 512 MiB test file sat in the cache. At the lowest memory priority the file stayed in the cache (38 of 2,000 sampled 4 KiB reads were slow, median 6.8 µs). At normal priority (5) it was pushed out (1,980 of 2,000 went to the disk, median 134 µs).

**What is left alone**

- Never opened, by name: system processes and AsterCache itself (`AsterCache.*`); any exe registered as a game or as a trigger program of a game; the launchers `steam.exe`, `EpicGamesLauncher.exe`, `GalaxyClient.exe`, `Battle.net.exe`, `RiotClientServices.exe`, `EADesktop.exe`, `upc.exe`, `UbisoftConnect.exe`; the helpers `steamwebhelper.exe`, `EpicWebHelper.exe`, `Agent.exe`, `explorer.exe`, `aster.exe`; the anti-cheat components in [Anti-cheat compatibility](ANTICHEAT.md#skipped-and-marked-files) (EasyAntiCheat, BattlEye, Vanguard including `vg*.exe`, and the others in that table) plus helpers named `BlackCipher*`, `GameMon*`, `SGuard*`, `PnkBstr*`, or `*_BE.exe`; and Riot's own programs (`RiotClient*`, `LeagueClient*`, the Riot game exes).
- Never opened, by session: any program outside a user session, which includes the services in session 0.
- Excluded by path: a program that passes the name check is first opened with query-only rights to read its path. If the path is under the Windows folder, under a registered game's install or allowed folder, under the install folder of a game the launcher scan has already found (only while automatic mode is on), or inside a folder named `steamapps`, `Steam`, `Epic Games`, `Riot Games`, `Riot Vanguard`, `Battle.net`, `XboxGames`, `GOG Galaxy`, `EA Games`, `Origin Games`, `Ubisoft`, `EasyAntiCheat`, or `BattlEye`, it is left alone and never opened with write rights. The one exception is a program that is excluded only because it is under the Windows folder (for example `cmd.exe`, `powershell.exe`, `conhost.exe`) and was started, after the lowering, by a program that AsterCache lowered (or by such a child, down to any depth) and still has the low value it inherited: AsterCache only sets it back to the original value at the end of the session. It never lowers or empties such a program. A program with any other reason to be left alone is still never opened.

**Timing**

- Order: choose the programs, lower the priorities, then, if needed, empty the working sets. The freed pages take a few seconds to show up as available memory. The start of a session does not wait for them.
- A start less than 60 seconds after the previous one is ignored, for example a second registered game starting just after the first. After a session has ended, the next start is not held back.
- **At the start of a session,** the working sets are emptied only when the available memory minus what the game is expected to take is below a floor, and then only by the amount that is missing: floor + expected game use - available memory. The floor is `max(4 GiB, physical RAM / 4)` (8 GiB on a 32 GiB PC). The expected game use is the median of the recent play records of the registered game that is running, the same figure the prewarm uses for its memory reserve (the available memory at the start minus the lowest available memory in the first 10 minutes); for a game without a usable record it is 8 GiB, a value set equal to the floor and not measured. The largest programs that are not in use are emptied first, and it stops once the missing amount is reached. If there is enough, only the priorities are lowered (log: `background yield (game started): memory priority lowered for M, I/O priority lowered for L, CPU priority lowered for C, P in-use processes spared, no trim needed (available A MiB, expected game use G MiB, floor F MiB)`). If Windows' memory statistics (the standby lists) cannot be read, only the re-emptying below is lost, and `background yield: memory lists unavailable, trimming once per session` is written.
- **During the session,** every 2 minutes (on the 30-second check) programs that started since then (those the fast path has not already taken about 3 seconds after they started) get the same priority change, with the same in-use rule. The chosen programs are emptied again only when at least 2 minutes have passed since the last emptying, the cache (standby pages of priority 5 and above) was really reused (512 MiB or more since the previous 2-minute check), and the available memory is still short by the same rule: the available memory minus what the game is still expected to take (the expected use minus what the game already took) is below the floor. What the game already took is the larger of the available memory lost since the session started and the current working set of the registered game executables, read from the system-wide process query without opening any process. Then only the missing amount is emptied, largest first. A program that got back at least half of its previous working set after being emptied is active, and it is not emptied again in that session. A program whose working set has not grown to at least twice its size right after the last emptying and by at least 256 MiB is not emptied again either (counted in the skipped programs). At the first check after an emptying (2 minutes later), only once, if the rise in available memory since just before it plus the growth of the game processes' working set is less than half of the emptied amount, that memory reached neither the available pool nor the game, so nothing more is emptied until the game ends, and `background yield: not trimmed again, the last trim of X MiB working set raised neither available memory (A -> B MiB) nor the game's working set (+G MiB) by half of it, no more trimming until the game ends` is logged once. A program whose working set before the emptying was about 552 MiB or less is never emptied again in a session because of the two rules above. If the statistics cannot be read, nothing is emptied again. Log: `background yield: trimmed again N processes (X MiB working set, shortfall Y MiB), cache repurposed R MiB in S s, K active processes skipped, P in-use processes spared, available A MiB, expected game use G MiB, floor F MiB`, or `background yield: not trimmed again, memory is sufficient (...), cache repurposed R MiB in S s` when the cache was reused but the memory is enough.
- Reading the memory statistics opens no process: it is a system-wide figure, and the service turns on the `SeProfileSingleProcessPrivilege` right for it.

**Programs in use**

- A program that used the CPU or did I/O in the last minute is in use, and it keeps its working set; its memory priority is lowered only to "below normal" (4) and not to "very low" (see Fast path and programs in use below). The service keeps a short history with one reading per 30-second check, also when no game is running: for every process, the CPU time and the bytes read and written since it started (one system query that opens no process, about 4 ms). At the start of a session it adds one more reading and compares the newest reading with the newest one that is at least 60 seconds old. A program is in use when its CPU use is 0.5% of one core or more (50,000 units of 100 ns per second), or when it read and wrote 32 KiB per second or more in total (disk, pipes, and anything else the process reads and writes; network traffic is not counted). So the judgement is made before the first emptying, not after it.
- Where the thresholds come from: on the test PC on 2026-11-21, 295 processes in the user session were read twice, 30 seconds apart. 43 were at 0.5% CPU or more, 31 at 1% or more, 19 had read and written 16 KiB/s or more, and 16 had 64 KiB/s or more. The programs that work continuously (a streaming program, a messenger, a game overlay, browser processes) were at about 1 to 20% of a core; waiting terminals, shells, and tool servers were below 0.5%. The values are between those and are not tuned further.
- When it cannot be judged, the program counts as in use (it is not emptied and gets "below normal" (4), not "very low"): when the history has fewer than two readings or less than 10 seconds between them (the service has just started), when the readings cannot be taken, or when the process is not in the newest reading. A process that started inside the last minute is judged by its whole total since it started.
- This is the only rule that looks at what a program is doing. The service runs outside the user session and does not see which window is in front or which program is playing sound, so a program you are about to use but that was idle in the last minute (a browser tab you switch to) is not told apart from an idle one. While `memory.background_in_use_memory_priority` is on, a program that was lowered is looked at again at each 2-minute upkeep (except children recorded as inherited): one that has started working (a voice call joined during the game) gets "below normal" (4), and one that has gone idle gets "very low"; only the memory priority value is switched (the original value in the state file does not change, and a program whose original value was 4 or lower is never raised above it). If it was off from the start, the value set at the start stays; if it is turned off during a session, a program that had got "below normal" gets "very low" when it goes idle.
- Not measured: what not emptying these programs and lowering them only to "below normal" changes for the game or for the other programs in real play.

**Fast path and programs in use**

- **Why 4.** The pages the service touches or holds for the prewarm cache are counted at memory priority 5 (the service does not change its own memory priority, and Windows takes memory from standby priorities 0 to 4 before 5; see Why above). A program in use that was left alone at 5 leaves the pages it has finished with in the same list as the prewarm cache. At 4 they are reused first. The service does not empty the working set of such a program, and a program whose original value is 4 or lower is not touched.
- **What it costs the program in use.** According to Microsoft's documentation of `MEMORY_PRIORITY_INFORMATION`, when the memory manager trims pages from a working set it trims lower-priority pages first. So while memory is short, Windows can trim this program's pages before pages at priority 5 (the game's included) and reuse them first. If the program needs those pages again it has to read them back from the disk, which can make it slower. While memory is plentiful nothing changes. This trades against the aim that other programs keep running as usual, and the size of the cost has not been measured. `memory.background_in_use_memory_priority` set to `false` leaves programs in use alone, as before.
- **Effect not measured.** In the 2026-11-23 Call of Duty play, standby pages of priority 5 to 7 were reused for 23,831 MiB (about 23.3 GiB) in total. Which program's pages pushed out which part of the prewarm cache was not recorded, and what this change does to that figure, to loading time, or to stutter has not been measured. Because pages of programs in use move from the priority 5 list to the priority 4 list, the amount of priority 5 standby memory and the reuse count of priorities 5 to 7 (`standby57_reused_mib`, and the thresholds that use them) can move differently from before: recordings from before and after this version are not on the same footing.
- **Fast path.** While the session is active and a registered game's exe was seen running, the service lists the running process ids every 1.5 seconds (one call that opens no process, about 0.05 ms). An id that is new at one look and still there at the next is taken, so a new program is chosen at most about 3 seconds after it started. A program seen at only one look and gone before the next one (about 1.5 seconds) is never opened and never written to the state file. For the taken programs the same selection and lowering as at the 2-minute upkeep run, with the same exclusions in the same order (name, session, path), the same query-only open to read the path, and the same write rights; nothing else is opened. The working set is never emptied on this path. A new program is not yet in the usage history, so it counts as in use and gets "below normal" (4); at the 2-minute upkeep it is judged again and switched to "very low" when it turns out to be idle. With `memory.background_in_use_memory_priority` off, a new program that counts as in use gets no memory priority from the fast path, and the 2-minute upkeep gives it "very low" once it is judged idle, as before. Nothing runs between sessions (the loop sleeps until a session starts).
- **Before every write.** Before the upkeep switches a value or lowers one that the fast path put off, it checks that the program behind the id is the one that was chosen: its name in the current list, a session other than 0, and its creation time read from a query-only open. If another program took over the id, nothing is written and the record is dropped.
- **Limit.** A process id that ended and was taken by another program between two looks 1.5 seconds apart is not noticed as new. The check before writing keeps it from being written to as if it were the old program, but it is picked up as a new program only at the 2-minute upkeep, and only when its name differs (a number dropped because the check before a write found another program behind it is chosen again at the next upkeep even when the name is the same).
- **Cost.** The only disk write added is the state file. It is written once for each look that takes at least one new program, so at most about 40 times a minute while new programs keep appearing (once more when a write failed), and not at all while none appears. As before it is rewritten as a whole before priorities are lowered, because a restart must know the original values; for that reason the write is not put off to a later time. Writes caused by the fast path are not forced through the disk's write cache (no flush): after a crash of the service the operating system still writes the cached content to the disk, and after a power loss the PC restarts and the lowered priorities are gone, so nothing is left to restore. The writes at the start of a session and at the upkeep are flushed as before. On a PC where scripts keep starting short programs the real rate can be close to the limit (in a 2-minute sample on the test PC without a game, new programs showed up at 55 of 80 looks). Records of programs that have ended are dropped at the 2-minute upkeep and are left out of the next write, so the file follows the number of programs alive (about 170 at the start of a session in the 2026-11-23 log of the test PC) and does not keep growing for the whole session. The counters in memory write nothing.
- **Log.** `background yield maintenance in S s: fast path saw N new processes (E not eligible), memory priority lowered for M, set below normal for U in-use, switched for W, I/O priority lowered for L, CPU priority lowered for C, F failed` is written at the 2-minute upkeep and at the end of a session (then without `in S s`), only when at least one of the values is not 0. E counts the programs left alone by the usual exclusions and those that were gone before they could be read; programs the 2-minute upkeep had already chosen are counted in N only. The line at the start of a session adds `(memory priority set below normal for U of them)` after the number of in-use programs spared when U is not 0.
- **What this does not show.** In the 2026-11-23 Call of Duty play, the seconds in which a web browser wrote the most had more long frames (71 of 510 seconds, against 70 of 1,980 for the others), but that browser's profile, downloads, and the page file were on the system SSD, not the game's hard disk. The direction of the cause was not established (switching between the game and the browser at those moments moves both), and the other programs' total CPU use had a correlation of -0.18 to +0.10 with long frames over five plays, with no consistent sign. So this change is not claimed to remove stutter. It adds no CPU priority (the existing `memory.background_cpu_priority` stays off by default), core limit, or job-object limit.

**Disk priority**

- The programs are the same ones, chosen by the same rules (name, session, and path), and no other process is opened. Only a program whose I/O priority is normal (2) is lowered, to low (1). A program already at low or very low (0), or above normal, is left as it is. Very low is not used, because it slows the other work almost to a halt.
- A program passes its I/O priority to the programs it starts (measured: a child of a low program started as low). So that a program started during the session does not stay low, a child of a lowered program that was created after the lowering and still has the low value is recorded with the parent's original value, by the same code and in the same state file as the memory priority, and is restored together with it; its own children are followed the same way, down to any depth, and this includes children under the Windows folder (see "Excluded by path"). Children started after the last 2-minute check are looked up once more right before the restore, and after a crash at the next start (the state file keeps the time each program was lowered).
- What this does not cover: a child that is left alone for another reason keeps the low value it inherited. In particular, if a lowered program starts a game while another game session is running, that game starts low and is not restored, because a game process is never opened (a known limit; it happens only when two games run at once). A child that has set its own value (not the low one), or that put itself in background mode, is not changed. A process counts as the parent only if it is the same recorded process: if the parent's process id is now used by another process (a different creation time or name, or one that is not on the list because it is excluded or in session 0), its children are not taken as inherited, and nothing is opened to decide that. After a reboot, the entries in the state file are not used as parents.
- The two priorities are written and restored separately. If only one of them could be lowered, only that one is recorded; if only one could be restored, only that one stays in the state file and is tried again.
- The service does not lower it only while the game is reading. It lowers it for the whole session, because the game's own reads cannot be told apart without opening the game. A program in use (see Programs in use) is lowered too: its working set is not emptied and its memory priority goes only to "below normal", not "very low", because the disk priority is the one change whose effect was measured (see below). A program you are using at that moment but that was idle in the last minute, or one that plays sound while idle on the CPU, is lowered like the others: the service runs outside the user session and does not look at which window is in front. It is slower only when the disk is busy.
- Measured on the test PC on 2026-11-21 with an experiment tool (not the service, and not inside a running game): a test program, used instead of a game, reading 64 KiB at random places 30 times a second from one hard disk, while four programs read random places of another file on the same disk. At normal priority the test program managed 13 reads a second with a 99th-percentile delay of 427 ms (70 of 265 reads over 100 ms) and the four programs read 4.6 MiB/s together; with the four at low priority it managed 30 reads a second with a 99th-percentile delay of 92 ms (4 of 598 over 100 ms) and the four read 0.8 MiB/s together (alone, the test program's delay was 31 and 45 ms). So the other work is not stopped, but it runs at about one sixth of its speed while the game reads. One program reading a large file in order ran at 38.3 MiB/s at normal priority and 25.6 MiB/s at low (three runs of 20 seconds each, one of them at 20.2), even with nothing else reading, so lowering costs that program speed even when the game is not reading. Programs reading random places alone were not affected (3.4 to 3.8 MiB/s at every level). How much this changes load time or stutter in a real game has not been measured.

**CPU priority**

- The programs are the same ones, chosen by the same rules (name, session, and path), and no other process is opened. Reading the class needs the query-only right and setting it needs `PROCESS_SET_INFORMATION`, the right the memory and disk priorities already use; no right is added. It is off by default (`memory.background_cpu_priority`): in a Call of Duty session recorded second by second on 2026-11-21 (about 74% total CPU use), the other processes' CPU use did not differ between the seconds with a long frame and the seconds without. When it is on, it is done only while a registered game's exe is running: a program started by a lowered program inherits "below normal", and a game process is never opened, so it could not be set back. If the session started before the game's exe showed up in the process list (a start request can arrive first), if the setting is turned on during a session, or if the session is started again inside a running session after programs were lowered without the CPU class, the programs already chosen are lowered at the next 30-second check (log: `background yield: CPU priority lowered for N processes (game started)`). Only a program whose CPU priority class is normal is lowered, to "below normal" (not to idle). A program at above normal, high, real-time, below normal, or idle was set that way by you or by the program, so it is left as it is.
- At the end, a program is set back to normal only if its class is still "below normal". If it has been changed since (by you, or by the program itself), it is not touched.
- Windows passes "below normal" to the programs a program starts. A child of a lowered program that was created after the lowering and still has the "below normal" class is recorded and restored the same way as the inherited memory and disk priorities, by the same code and in the same state file, including the children found right before the restore and after a crash. A child that was started with "below normal" on its own, after the parent was lowered, cannot be told apart from an inherited one and is set to normal at the end. As with the disk priority, a game started by a lowered program while another game session runs starts below normal and is not restored, because a game process is never opened.
- What it does to other work: only while the CPU is short, the background programs get less of it than the game; with free cores they run as before. Sound and voice threads that a program has registered with the Multimedia Class Scheduler Service (MMCSS) are scheduled by that service; this document did not confirm from Microsoft documentation that the process class has no effect on them, and no sound or voice was measured.
- Not confirmed: that CPU contention is the cause of stutter in real play. On the test PC, 25 of the 43 seconds with a frame over 100 ms in one Call of Duty session had 5 or fewer disk reads and the median system CPU use in those seconds was 86%, but which process used the CPU was not recorded in that session (the `cpu_other1_name` and `cpu_other2_name` columns of `play.series` record it now). The effect of this setting on stutter has not been measured.
- Turning only this part off during a session restores the CPU priority class at the next 30-second check, the same way as the disk priority (log: `background yield: CPU priority restored for N processes (setting turned off)`); turning it on again lowers it again at the next check.

**Side effects**

- A program that was emptied can be slower for a moment when you use it again, because its pages are brought back.
- Background programs can read the disk more slowly while a game session is running and the disk is busy. This is intended; they are not stopped.
- Background programs that are not in use can be slightly slower during a game session, because their memory is now reused first. This is intended. A program in use is not emptied, but while memory is short Windows trims its pages (priority 4) before pages at priority 5 and reuses them first, so the program reads them back from the disk when it needs them again and can be slower; when memory is plentiful nothing changes.
- It works only when the service has administrator rights and a trusted data folder, the same condition as the other features that write state files.
- Settings can change during a session. At each start and each 2-minute upkeep, the programs already chosen are checked again against the current settings by name and path. One that has become excluded, for example a program that is now a registered game, is dropped from the list and its priority is put back at once.
- The log has counts and sizes only, no program names or paths. Program names (no paths) are written only to the state file below, which exists while a session runs.

**State file and recovery**

- `background_yield.json` in the data folder (`%ProgramData%\AsterCache`) lists the programs whose priority was lowered: process id, program name, creation time, the original memory priority (`priority`), the original I/O priority (`io_priority`), the original CPU priority class (`cpu_priority`, always 32 = normal; each of the three is left out when that one was not lowered), the time it was lowered (`lowered_at`), whether it was recorded as inherited (`inherited`), and the memory priority that was set (`applied`, written only when it is not 1: after a crash the restart uses it to find a child that inherited "below normal"). A file from an earlier version without the I/O or time entries is read as before. It is written before the priorities are lowered and deleted when the session ends. If it cannot be written, neither priority is lowered that time (the working sets are still emptied).
- If the service stopped abnormally, the next start restores those priorities first, even when the setting is off, and writes `background yield: restored memory priority for N processes left by the previous run, I/O priority for M, CPU priority for K`. A process is restored only if its id, name, and creation time still match, so a process that reused the id is not touched. If the file has the lowering times, the same start also looks for programs started after the last record, or while the service was down, by a program in the file, and restores those that still have the low value. A program whose priority could not be written back stays in the file and is tried again at the next end or start.

**Turning it off**

- Add this to `config.json`:

```json
"memory": { "background_yield": false }
```

- To turn off only the quick handling of programs that start during the game, or only the lowering of the memory priority of programs in use:

```json
"memory": { "background_yield_fast": false, "background_in_use_memory_priority": false }
```

- If `background_in_use_memory_priority` is turned off during a session, a program already set to "below normal" keeps that value until the session ends.
- To keep the yield but leave the disk priority alone, turn off only that part:

```json
"memory": { "background_io_priority": false }
```

- The CPU priority part is off by default. To turn it on:

```json
"memory": { "background_cpu_priority": true }
```

- There is no switch in the Settings tab. The service re-reads the file; when a setting is turned off during a session, the priorities are restored at the next 30-second check (only the disk priority when only `background_io_priority` was turned off; only the CPU priority when only `background_cpu_priority` was turned off).
- The `memory` key is new in 1.0.3. Versions 1.0.2 and earlier reject a settings file that contains it, so remove it before rolling back. `memory.background_yield_fast` and `memory.background_in_use_memory_priority` are new after 1.0.6, and 1.0.6 and earlier reject a settings file that contains either. `memory.background_io_priority` and `memory.background_cpu_priority` are new in 1.0.5; versions 1.0.4 and earlier reject a settings file that contains either ([Configuration](CONFIGURATION.md)). Stop the service normally before rolling back: an earlier version cannot read an entry that has only an I/O or CPU priority and would drop it from `background_yield.json`.

</details>

### SOLAR: keeping the cache in order

After a game's prewarm, the prewarmed cache is touched again in memory, so that the data a load needs first is the last to be pushed out, and it is touched again before other programs push it out. Nothing is read from the disk on purpose. It is on by default (`memory.standby_ladder`). The full explanation, with the measurements, is in [SOLAR](SOLAR.md).

- **When.** Right after a prewarm has read a game's list to the end. After that, about every 30 seconds, when Windows' standby-list statistics show that the pages that would be reused before the game's pages are being used up (the count of reused cache pages has grown by `max(512 MiB, 0.4 x the amount reused first)`); every 10 minutes when the statistics cannot be read.
- **What.** Touches the cache the game has in the reverse of the read order, so the common blocks and the loading head leave the cache last. If it finds part of the list missing from the cache, it stops, and the next re-prewarm check prewarms the game again. With several games it works on them as one group: when one game is refreshed, and right before another game's prewarm stream reads or ends, the other games that have been ordered are touched first, the lowest-ranked first, so that the reads of one game do not push out another's cache. Pages of files with the sparse attribute are skipped, because a new mapping of one made the disk read them again in a test on one PC.
- **Does not.** Run on a disk where a game is running, except for the touch of that game's own cache at its start and while it runs; read the game's data from the disk on purpose (the holding while a game runs reads within caps, see [SOLAR](SOLAR.md#holding-the-cache-while-the-game-runs-memorykeep_hold)); lock memory; keep a mapping open (except the holding of the keep list while a game runs, `memory.keep_hold`, described in [SOLAR](SOLAR.md#holding-the-cache-while-the-game-runs-memorykeep_hold)); open any process; or change the memory reserve, the cache budget, or the prewarm list. It does not stop the cache from being pushed out when memory is truly short.
- **Settings.** `memory.standby_ladder` (default `true`). The re-prewarm that follows a missing part uses `rewarm_minutes`.
- **Log.** `<game>: ladder ordered N MiB in S s`, `<game>: cache refreshed in memory: N MiB in S s (R MiB repurposed of A MiB ahead)`, `<game>: ladder found data missing from memory (...), left to the rewarm check`. The meaning of each line is in [SOLAR](SOLAR.md#checking-that-it-runs).
- **Turning it off.** `"memory": { "standby_ladder": false }` in `config.json`. There is no switch in the Settings tab; the service re-reads the file. Versions 1.0.3 and earlier reject a settings file that contains `memory.standby_ladder`, so remove it before rolling back ([Configuration](CONFIGURATION.md)).

## What "idle" means

"Idle" means all of these:

- No registered game installed on the same drive as the games waiting to move is running (games on other drives are ignored).
- The game's drive stays under 4 MiB/s for 30 seconds in a row.
- The PC is on AC power, or on a battery at 50 % or more.
- The Windows drive optimization (`defrag.exe`, the scheduled "Optimize Drives" task, `\Microsoft\Windows\Defrag\ScheduledDefrag`) is not running. The service sees it by process name only, so it cannot tell which drive the optimization is working on and waits for all drives. A relocation already under way rests between its pieces only at low I/O priority (the default of `auto.relocate_io_priority`); at normal I/O priority it is not interrupted. The wait for one run is at most 30 minutes from when the service first saw it; after that the other conditions alone decide. Right after a run ends relocation is not brought forward: it comes at its usual time. Only the layout check of a game that has a whole-file plan is brought forward (see `auto.relocate_layout` under Relocation). The log has `drive optimization started at ...`, `drive optimization ended at ... after N s`, if the service started while it was running, `drive optimization already running when the service started ...`, and, when the 30 minutes are over, `drive optimization still running after 30 min, relocation no longer waits for it`.

CPU use is not part of the test: relocation uses low I/O priority and only affects the target drive. If the PC has not been idle for 6 hours, `service.log` records one line with the reason (`game running`, `on battery`, `drive optimization running`, or `disk busy`). To see which stage each game is in, open the management window and look at the **Status** tab and the stage column of the **Games** tab.

## Supported launchers

Steam, Epic Games Store, GOG Galaxy, Ubisoft Connect, Riot Client, the Windows uninstall list, and the Xbox app folders are read. Battle.net and EA app libraries are not read; their games are found by the uninstall list or the heuristic.

<details>
<summary>Details: how each launcher is read</summary>

**Steam** (prewarm trigger `steam.exe`)

- `libraryfolders.vdf` and `appmanifest` files. The executable is the largest `.exe` in the game folder, excluding installers, redistributables, and crash tools.

**Epic Games Store** (trigger `EpicGamesLauncher.exe`)

- `LaunchExecutable` in `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests\*.item`.

**GOG Galaxy** (trigger `GalaxyClient.exe`)

- Registry `HKLM\SOFTWARE\WOW6432Node\GOG.com\Games`.

**Ubisoft Connect** (triggers `upc.exe`, `UbisoftConnect.exe`)

- Registry `Launcher\Installs`, value `InstallDir`.

**Riot Client** (trigger `RiotClientServices.exe`)

- `product_install_full_path` in `%ProgramData%\Riot Games\Metadata\<product>.live\*.product_settings.yaml`. Marked as Vanguard anti-cheat. Entries that are not `.live` (for example PBE) are skipped.
- League of Legends (`LeagueClient.exe`, `League of Legends.exe`) and Teamfight Tactics use the same exe names, and their entries are merged when they share a folder.
- VALORANT uses `VALORANT.exe` and `VALORANT-Win64-Shipping.exe`. Other products use the largest `.exe` in the folder.

**Windows uninstall list** (no trigger)

- `Uninstall` keys of HKLM and HKCU (32-bit too). Kept when the install folder is on an HDD (not the system drive), is at least 1 GiB, is not from a common publisher (Microsoft, Intel, NVIDIA, and others), and is not a launcher's own folder.
- The exe is the largest `.exe` in the folder. Catches standalone games such as Battle.net, EA, Nexon, and HoYoverse titles.
- An entry skipped because its name matched a launcher exclusion word has its exe chosen again at service start under the current rules (one log line).
- Limits: a launcher-style folder can give the wrong exe; after the game runs, the heuristic adds the real exe.

**Xbox (Microsoft Store)** (no trigger)

- `XboxGames\<game>\Content` folder on each HDD. The exe is the largest `.exe`. Folders that cannot be read are skipped.

**Checked and not checked**

- The GOG and Ubisoft readers have not been checked on a real PC yet. The Riot reader was checked on the test PC with League of Legends on D: (an HDD). The Xbox reader has not been checked, because the test PC has no such folder.
- `Battle.net.exe` and `EADesktop.exe` are listed only as prewarm trigger programs; the service does not read their libraries.

</details>

## Heuristic detection

A process that is not registered, starts from an exe on an HDD volume, and reads 256 MiB or more within 20 seconds is treated as a game and registered, if its folder looks like a game. The first trace is recorded from the next run.

<details>
<summary>Details: exclusions and the folder test</summary>

- **Excluded.** The Windows folder, AsterCache itself, launchers and tool programs, and the exes in `auto.ignore_exes`.
- Also excluded: exes whose path contains `\bin\Debug\`, `\bin\Release\`, `\obj\`, `\.git\`, `\node_modules\`, or `\AppData\Local\Temp\`.
- Also excluded: the built-in tool exes `testhost*`, `dotnet`, `msbuild`, `vstest*`, `python*`, `node`, `java*`, `powershell`, `pwsh`, `cmd`, `conhost`, `explorer`, `7z*`, and `winrar`. This fixed list is separate from `auto.ignore_exes`.
- **The folder must look like a game.** It holds a file of 256 MiB or more, or a launcher mark (`steam_appid.txt`, `.egstore`, `goggame-*.info`, or a Steam manifest). Games installed under `AppData\Local\Temp` are therefore not found.

</details>

## Settings

All `auto.*` keys, their meanings, and their defaults are in [CONFIGURATION.md](CONFIGURATION.md).

- `"auto": {"enabled": false}` turns off the whole automatic mode. `discover`, `trace`, and `relocate` turn off one stage each.
- The state is written to `%ProgramData%\AsterCache\auto_status.json` (only the service writes it). `aster status` has an `"auto"` key, and `aster discover [--json]` lists the launcher games read-only.
- The manual buttons (register, capture trace, create plan, run relocation, prewarm now) work regardless of the automatic mode.

<details>
<summary>Details: what the screens show</summary>

- The Status tab shows one line per game, such as "Auto: Frostpunk discovered → collecting trace → waiting to relocate → relocating → [done]". The Games tab shows the source, stage, and anti-cheat columns.
- The learning stage shows "First run: learning (read-ahead n MiB)", and "Prewarmed" appears after prewarm.
- The per-game status line also shows `hit right after prewarm N%` (the hit rate measured right after a prewarm ends) and `SSD assist N GB` (the size of the game's SSD copies).
- Tray notifications are sent for discovery, for a finished relocation, and when a first run ends ("First run recorded; planning from this recording: <game>"). The pop-up can be turned off in the Settings tab's Notifications card (`notifications.enabled` in `tray.json`); the notice is still written to the tray log.

</details>

## SSD assist storage (optional)

Off by default (`auto.ssd_tier.enabled`). While it is off, AsterCache does not touch any file, except that it reverts links left by an earlier run. When on, it copies the files of an HDD game with the highest share of hot bytes (bytes the trace read) to an SSD within a budget and puts a symbolic link in their place.

<details>
<summary>Details: choosing, applying, keeping, reverting</summary>

**Choosing and applying**

- Each file is scored by its hot bytes (the parts the trace read) divided by its size. Files are taken from the highest score down while they fit the budget (`budget_gib`, default 8 GiB per game, 1 to 4096). Game `.exe` and `.dll` files and files outside `allowed_roots` are never chosen.
- The file is copied to the SSD, and the size and a sampled SHA-256 are checked. The copy is recorded in the journal, the original is renamed to `<name>.aster-orig` in the same folder, a symbolic link takes its place, and the link is checked by size. If one file fails, only that file is reverted.
- `root` is `"auto"` (the system drive if it is an SSD, otherwise the SSD with the most free space, under `AsterCache\tier`) or an absolute path on an SSD.

**When it runs**

- One game at a time, only for an HDD game that is not running, is not on the system drive, has no anti-cheat folder, and has finished relocation (or has relocation turned off).
- It waits for idle like relocation does, and retries a game it could not finish after 6 hours.

**Keeping**

- Each time the automatic mode runs its relocation check (about every 30 seconds), the journal is checked. A missing or wrong-size copy is reverted at once. A file that became a normal file, or whose copy changed through the link, is marked stale and left alone.
- If the SSD has less than 1 GiB free, no new copies are added and the oldest game is reverted first. A change to the budget or the folder makes the game revert and apply again with the new setting.

**Reverting and commands**

- `aster tier revert --game <name>` or `--all` removes the links and restores the originals. The copies stay in the tier folder until `aster tier clean` deletes the unused ones. Uninstalling reverts all games first.
- The journal is `%ProgramData%\AsterCache\tier\<game>.json`. If a journal cannot be read, that game is skipped, nothing is touched, and a log line is written.
- Commands: `aster tier status`, `aster tier apply --game <name>`, `aster tier revert --game <name>` or `--all`, and `aster tier clean` (apply, revert, and clean need administrator rights).
- The checkbox and the budget are in the Settings tab, under Automatic mode. The per-game status line shows `SSD assist N GB`.

</details>
