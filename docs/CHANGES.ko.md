# 변경 내역

> 버전별 주요 변경입니다. 자세한 내용은 각 버전의 GitHub 릴리스와 커밋 기록을 보십시오.

## 0.9.0-beta.25 ~ 0.9.0-beta.38

- **0.9.0-beta.38, 진전 없는 보충 예열을 되풀이하지 않음.** 가용 메모리가 빠듯하면 보충 예열이 매번 다른 양을 계획하고, 같은 앞부분을 다시 읽고, 더 읽지 못한 채 끝났습니다. 관찰된 사례에서는 같은 1,305 MiB 를 10분 동안 여섯 번, 약 90초마다 읽었습니다. 이제 읽은 바이트가 늘지 않은 보충은 재시도 간격(`rewarm_minutes`)을 기다린 뒤에 다시 읽습니다. 정상 종료, 읽을 목록이 계획 상한보다 짧게 끝난 경우, 메모리 재판정으로 진전 없이 끊긴 경우에 모두 적용됩니다(게임 시작으로 끊긴 읽기는 전처럼 이어 읽습니다). 메모리로 정한 상한이 256 MiB 이상 커지면 한 번 앞당겨 다시 시도하고, 메모리가 핫셋 전체를 읽을 만큼 늘면 바로 다시 판정합니다. 전체 경로에서는 읽을 목록을 오류 없이 다 처리했으면 핫셋보다 작아도 완료로 봅니다. 대기는 실제 진전, 읽을 목록이나 게임 설정 변경, 게임 제거, 게임 시작 때 풀립니다. 보충 로그 줄에는 받아들여진 양, 요청량, 오류 수가 함께 남습니다.
- **0.9.0-beta.37, 남은 캐시 예산 사용.** 예열 예산은 게임의 관찰된 범위 전체가 들어갈 때만 배정했고, 들어가지 않는 게임은 남은 예산 배정에서도 빠졌습니다. 관찰된 사례에서는 한 게임이 16,347 MiB 예산 가운데 10,026 MiB 를 받은 뒤, 서비스 시작 상한에 밀렸던 다른 게임이 0 MiB 인 채로 남았고 같은 "건너뜀" 줄이 매분 기록됐습니다. 이제 기존 배정이 끝난 뒤 남은 예산이 256 MiB 이상이면 빠졌던 게임에 순위대로 배정해 앞부분을 예열합니다. 다른 게임의 배정분, 메모리 예비량, 캐시 예산은 그대로입니다. 보충 예열과 재예열 검사도 같은 배정표를 씁니다. 예산으로 거절되면 유지 점검마다 다시 판정하지 않고 재시도 시각을 재시도 간격만큼 뒤로 미룹니다. 거절 줄은 상태가 바뀔 때만 기록하고, 문구도 예산이 "사용됨"이 아니라 "배정됨"이라고 적습니다.
- **0.9.0-beta.36, 상주 유틸리티 제외, 메모리에 맞춰 줄여 읽는 예열.** Wallpaper Engine 처럼 한 번 띄우면 계속 켜져 있고 다시 읽지 않는 데스크톱 유틸리티가 게임으로 등록되어, 얻는 것 없이 재배치·예열·재검사 대상이 됐고 그 재배치 뒤의 드라이브 회복 대기가 실제 게임을 미뤘습니다. 이제 그런 유틸리티의 고정 목록(Steam 앱 번호와 그 제품 고유의 실행 파일 이름)을 발견에서 제외하고, 자동 등록된 항목이 목록에 해당하면 서비스 시작 뒤 실행 중이어도 등록을 해제합니다. 직접 등록한 항목은 건드리지 않고 `auto.ignore_exes` 도 바꾸지 않습니다. 등록이 사라진 게임은 예열하거나 고정하지 않습니다. 예열은 읽기 직전에 가용 메모리를 다시 잽니다. 그때 목록이 들어가지 않으면 0 MiB 에서 취소했는데(관찰된 사례는 39 MiB 부족), 이제 256 MiB 여유를 두고 들어가는 앞부분만 읽고 나머지는 나중에 보충합니다. 메모리 예비량과 캐시 예산은 그대로입니다. 취소된 예열은 드라이브가 재배치 뒤 회복 중이어도 다른 예열과 같이 다시 읽습니다. 추가 재배치는 계속 회복을 기다립니다. 보충 예열의 "더 읽을 것 없음" 줄은 상태가 바뀔 때만 기록합니다. 재배치 뒤 드라이브 회복 확인은 기준을 0번 칸에서 한 번 재고 표본은 다른 세 칸을 돌며 재서, 위치에 따른 속도 차이가 그대로 미달로 잡혔습니다. 43 MB 를 옮긴 뒤 149분 동안 확인되지 않아 같은 디스크의 재배치가 모두 보류된 일이 있었습니다. 이제 기준을 표본과 같은 세 칸에서 재서 중앙값을 쓰고, 2회 연속 통과에 더해 최근 6회 중 4회 이상 통과도 회복으로 봅니다. 미달이 이어지면 측정 간격을 8분까지 늘리고, 표본마다 판정에 쓴 값과 사유를 로그에 남깁니다.
- **0.9.0-beta.35, 막힌 재적용을 자동 재배치로 넘김.** 재적용은 원본 파일이 그대로인데 흐트러진 배치를 다시 맞춥니다. 존 일부를 다른 파일이 차지해 거절되면(`zone_not_free`) 오류로 끝나고 하루 뒤 같은 시도를 되풀이했습니다. 업데이트도 새 읽기 기록도 없는 게임은 영영 다시 맞춰지지 않았습니다. 아무것도 옮기지 않았는데도 예정 바이트가 하루 예산에 잡히고 드라이브 회복 대기가 시작되어, 같은 디스크의 다른 게임까지 미뤄졌습니다. 이제 그런 게임은 자동 재배치로 되돌립니다. 자동 재배치는 옮긴 부분을 지키고 남은 부분만 다시 계획하며, 기존 보류와 하루 상한을 그대로 따릅니다. 자동 재배치가 켜져 있고, 읽기 기록이 있고, 무결성 검사 실패로 멈춘 상태가 아닐 때만 넘기고, 그 밖에는 전처럼 실패로 남깁니다. 이동 전에 거절된 경우는 0 바이트로 기록합니다. 회당 쓰기 상한에서 멈춘 재적용은 5분 재검사를 유지합니다. 남은 부분을 일반 간격(기본 1440분) 뒤가 아니라 드라이브가 회복되는 대로 이어 옮깁니다.
- **0.9.0-beta.34, 끝내지 못한 예열 재시도, 드라이브 회복 확인 단축, 막힌 배치 재검사.** 읽기 기록이 있는 게임의 예열이 끝나기 전에 취소됐거나 서비스 시작 상한에 밀려 건너뛰면, 대기 목록에 남겨 두었다가 디스크가 60초 동안 한가하고, 그 디스크에서 게임이 실행 중이 아니고, 드라이브가 재배치 뒤 회복 중이 아니고, 캐시 예산에 여유가 있을 때 다시 요청합니다. 전에는 다음 런처 트리거가 올 때까지 차가운 채로 남았습니다. `prewarm cancelled` 로그 줄에 취소 사유가 붙습니다. 읽기 기록이 없는 게임은 이 방식으로 다시 시도하지 않습니다. 재배치 뒤 드라이브 회복 확인은 기준 속도의 1.25배보다 빠른 표본을 드라이브 캐시 적중으로 보고 모두 버렸습니다. 그래서 기준 속도가 낮게 잡히면 회복을 확인할 수 없어 절대 상한(관찰된 사례에서 178분)까지 2분마다 192 MiB 를 읽으며 기다렸습니다. 이제 순환하는 세 위치에서 연달아 그 상한을 넘으면 회복으로 보고(그 사례에서 약 6분), 판정할 수 없는 표본은 간격을 8분까지 늘리며, 버린 표본을 로그 한 줄로 요약합니다. 배치 검사에서 배치가 미완료로 확인됐는데 일시적인 이유(게임 실행, 디스크 바쁨, 드라이브 회복, 배터리 전원, 유휴 부족, 업데이트 뒤 지연)로 막히면 일반 간격(기본 1440분)이 아니라 5분마다 다시 검사합니다. 흐트러진 배치를 하루 기다리지 않고 다시 맞춥니다. 경고 문구도 서비스가 자동으로 다시 시도한다고 알립니다.
- **0.9.0-beta.33, 로그온 때 트레이 관리자 권한 시작, 플레이 기록, 관찰된 읽기 우선 예열.** Program Files 아래에 설치하면 설치 프로그램이 로그온 예약 작업 `AsterCache` 를 등록해 트레이를 관리자 권한으로 시작합니다. 확인 창(UAC)이 뜨지 않으므로 관리자 권한으로 다시 실행할 필요가 없습니다. 그 밖의 폴더에 설치하면 기존처럼 시작프로그램 바로가기를 씁니다. 관리 창은 게임 목록을 먼저 그리고 배치 확인은 뒤에서 채우며, 게임이 실행 중일 때는 트레이가 디스크 배치를 조회하지 않습니다. 게임이 실행되는 동안 서비스는 물리 디스크의 누적 읽기 카운터(읽은 양, 횟수, 읽기 대기 시간)를 1초 간격으로 표본 내고, 시작 뒤 30·60·120·300·600초와 종료 시점의 요약을 `play record:` 서비스 로그 줄과 `play_samples.json` 에 남깁니다. 게임 파일이나 게임 프로세스는 읽지 않고 디스크 장치의 카운터만 조회하므로, 로딩과 끊김을 수치로 비교하기 위한 계측이며 그 자체로 게임을 빠르게 하지는 않습니다. 예열 목록의 각 범위에는 실제 플레이에서 읽힌 범위인지 엔진 프로필로 추측한 범위인지 표식을 둡니다. 예산이 모자라면 모든 게임의 관찰된 범위를 먼저 채우고 남는 예산을 추측 범위에 씁니다. 표식이 없는 예전 목록은 기존 트레이스와 대조해 출처를 복원합니다. 예산이 충분하면 읽는 범위와 순서는 전과 같습니다.
- **0.9.0-beta.32, 재배치 건너뛰기와 예열 캐시 예산.** 재배치가 옮기지 않고 건너뛰는 파일(스파스·압축·암호화 파일)을 배치 판정에서 뺐습니다. 이런 파일 때문에 "이어 옮기기 필요"가 계속 표시되고 재배치가 끝나지 않던 문제가 없어졌습니다. 존이 이미 최대 크기인 계획은 다시 계획하지 않으며, 화면 문구가 "자동으로 이어서 진행한다"는 점을 알려 줍니다. 예열이 쓰는 캐시 예산은 기본으로 물리 RAM 의 절반이며(`prewarm.max_cache_mib` 로 지정), 런처 실행 등으로 최근에 트리거된 게임은 6시간 동안 먼저 예열합니다.
- **0.9.0-beta.31, 트레이 화면 개편.** 창·탭·대화상자·알림을 하나의 디자인 체계로 맞췄습니다. 밝은 테마와 어두운 테마를 모두 지원합니다(`--theme light|dark` 로 고정할 수 있고, 지정하지 않으면 Windows 설정을 따릅니다). 상태 탭은 상태 배지·숫자 타일·게임별 카드로, 게임 탭은 색 배지 상태 열과 작업 순서대로 묶은 버튼으로, 설정 탭은 구역 카드와 정렬된 양식으로 바꿨습니다. 색·글자 크기·간격은 `csharp/src/AsterCache.Tray/Look.cs` 한 곳에 있습니다.
- **0.9.0-beta.30, 예열 한 회의 중복 계산 제거.** 예열 한 회 안에서 같은 예열 목록을 세 번 계산하던 것을 한 번으로 줄였습니다(계획·트레이스·예열 전용 목록·가변 표지 파일이 바뀌면 다시 계산). 예열 완료 로그 뒤에 단계별 경과 시간 한 줄이 남습니다.
- **0.9.0-beta.29, 게임 시작 스트림과 트레이스.** 시작 스트림이 로딩이 끝난 뒤에도 디스크를 읽어 플레이 중 끊김을 일으키던 문제를, 게임 프로세스 읽기량으로 판정한 로딩 경계와 `auto.start_stream_cap_seconds`(기본 120) 상한에서 멈추도록 고쳤습니다. 트레이스는 첫 창 뒤에도 `auto.trace_late_*` 설정으로 플레이 후반을 짧게 수집하고, 저장은 게임이 끝난 뒤에 합니다. 게임 종료 뒤 같은 디스크의 재배치·계층 적용·보충·재예열은 `auto.rewarm_after_exit_min` 유예 뒤에 시작합니다.
- **0.9.0-beta.28, ORBIT 보강과 서비스 안정화.** ORBIT 결정 규칙에 에피소드별 지연 허용치 `max(5%, 200 ms)` 를 넣고 결정 경로·보정·결과 판정을 개선했습니다. 디스크 읽기 중재가 판정하지 못한 볼륨을 다시 조회하고, 디스크 활동 표본 스레드가 서비스 종료 때 멈추며, 로딩 경계 감시가 중재 대여와 안티치트 정책표를 거치게 했습니다. 트레이 메뉴와 작업표시줄 아이콘이 상태 4종(정지·주의·작업 중·정상)을 보여 줍니다.
- **0.9.0-beta.27, 트레이 안내 수정.** 게임 업데이트 뒤 학습을 유지한 채 다시 계획하는 게임이 트레이에 "다음 실행에서 다시 수집"으로 잘못 표시되던 것을 고쳤습니다.
- **0.9.0-beta.26, ORBIT 실기 검증.** ORBIT 예열 순서 조정을 실제 HDD 에서 측정하고 결정 경로 성능을 개선했습니다. `aster orbit mode|calibrate|model`, `aster orbit-bench run|summarize|rescore`, `orbit_mode.json` 이 추가됐습니다.
- **0.9.0-beta.25, 디스크 읽기 중재와 학습 보존.** 물리 디스크 단위 읽기 중재(대여·양보), 게임 업데이트 때 바뀐 파일 범위만 빼고 다시 계획하는 학습 보존, 런처 표시 이름, 기능별 정책 결정표, 로딩 시간 표본 기록이 들어왔습니다.

## beta.8 이후

beta.8 이후 `main` 에 들어온 변경입니다(외부 검토 반영 포함).

- **ORBIT 예열 순서 조정.** 기록이 있는 게임의 예열 순서를 64 MiB 안팎 구간 단위로 바꿀 때, 최악 조건의 이득이 양수이고 모든 에피소드가 허용 지연 안에 들도록 설계했습니다. 2026-11-09 사용자 PC Call of Duty ABBA 벤치(WD20EZAZ 2 TB SMR HDD)에서 가치 가중 준비 시간 중앙값은 18.8% 줄었고(10/10쌍이 10% 이상 개선, 부호 검정 p=0.001), 총 읽기 시간은 0.1% 줄었습니다. 최악 에피소드 p95는 13.1초 늘어 플래그 4에 실패했습니다. 새 규칙 재채점은 B 후보를 `episode_regression`으로 거부했고 모형 추정 최악 지연은 55.5초였습니다. 게임 1종·드라이브 1대·한 세션 측정이라 일반화는 이릅니다([ORBIT: 예열 순서 조정](ORBIT.ko.md) 참고).
- **병렬 재배치.** 시험 HDD에서 병렬 8 읽기로 재배치 작업이 186 s 에서 41 s 로 줄었습니다(4.5배). [docs/RESULTS_SUMMARY.ko.md](RESULTS_SUMMARY.ko.md) 참고.
- **드라이브 회복 판정.** 게임 업데이트 뒤, 또는 SMR 드라이브에서 재배치한 뒤 서비스가 드라이브 회복을 판정하고 다음 작업을 시작합니다(`auto.post_relocate_recovery`).
- **설치 뒤 자동 진행.** `aster status` 와 관리 창 요약에 "발견 → 부트스트랩 계획 → 재배치 완료 → 예열 완료 → 적중률 평균" 한 줄을 보여 줍니다. 게임을 할 것 같은 시간(런처 실행 중이거나 평소 플레이하던 시간대)에는 HDD 가 꺼지지 않게 10 분마다 4 KiB 를 읽습니다(`auto.keep_awake`, 기본 켜짐, 전원 설정은 바꾸지 않음). 같은 디스크에서 게임이 실행 중이면 이 읽기는 하지 않습니다.
- **게임 시작 시 예열 양보.** 같은 물리 디스크에서 게임이 시작되면 예열은 다음 64 MiB 묶음 경계에서 멈춥니다. 같은 디스크인지는 드라이브 문자가 아니라 물리 디스크 번호로 판정하므로, HDD 한 대를 여러 볼륨으로 나눈 PC 에서도 함께 멈춥니다. 그 디스크에서 초당 1 MiB 미만으로 읽는 게임이 있어도, 디스크가 60초 동안 한가하면 같은 디스크의 다른 게임 예열을 막지 않습니다(단계 4번 참고). `auto.keep_stream_on_game_start`(기본 `false`, 실험용. `true` 면 옛 동작)로 바꿉니다. 게임 시작 직후 핫셋을 읽는 시작 스트림도 로딩 경계에서 멈춥니다. 게임 프로세스의 읽기 카운터를 1초 간격으로 보고(디스크 I/O 없음), 10초 이동 창 읽기량이 최고치의 10% 아래로 떨어지면 멈추며, 최대 60초까지입니다. `auto.start_stream_cap_seconds`(기본 120, 0이면 상한 없음)도 넘기지 않습니다. 멈춘 나머지는 게임이 실행 중일 때 다시 읽지 않습니다. 게임 시작 시 디스크가 양보 상태라 상주 표본을 읽을 수 없으면, 최근 `rewarm_minutes` 안에 실제 표본이 따뜻했고 계획이 바뀌지 않은 경우 시작 스트림을 건너뜁니다(로그 `start stream skipped (recent probe warm ...)`). 표본이 거절된 것을 식은 것으로 보지 않습니다.
- **시스템 드라이브가 HDD 인 게임.** Windows 가 있는 드라이브가 HDD 면 게임은 발견과 예열만 합니다. 재배치하거나 티어를 두지 않습니다(상태 "prewarm only (system drive)").
- **지표 이름.** `tier0_probe_ready_ms`(옛 이름 `load_boundary_ms`, 계속 읽음)는 tier0 예열 표본이 RAM 에 적중한 시각입니다. 게임 로딩이 끝난 시간이 아닙니다.
