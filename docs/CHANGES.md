# Changes

> Main changes by version. For details, see each version's GitHub release and the commit history.

## 0.9.0-beta.25 to 0.9.0-beta.38

- **0.9.0-beta.38, supplement prewarm no longer rereads without progress.** When available memory was tight, the supplement prewarm planned a different amount each time, read the same front part again, and ended without reading more; in the observed case it read the same 1,305 MiB six times in ten minutes, about every 90 seconds. A supplement that does not increase the bytes read now waits for the retry interval (`rewarm_minutes`) before it reads again. This covers a normal end, a read list that ends below the planned cap, and a read that a memory check cut off without progress (a read cut off by a game start is continued as before). It retries once earlier when the memory-based cap grows by 256 MiB or more, and is judged again as soon as memory allows the whole hot set. On the full path, a read list processed without errors now counts as complete even when it is smaller than the hot set. The wait is released by real progress, a changed read list or game settings, a removed game, or a game start. The supplement log lines now show the accepted amount, the requested amount, and the error count.
- **0.9.0-beta.37, leftover cache budget used.** The prewarm budget was given to a game only when its whole observed part fit; a game that did not fit was left out of the remaining budget as well. In the observed case one game held 10,026 MiB of a 16,347 MiB budget, and the game that had been skipped by the service-start cap stayed at 0 MiB while the same "skipped" line was logged every minute. After the regular allocation, games that were left out now receive the remaining budget in rank order when at least 256 MiB is left, and prewarm their front part; the allocations of other games, the memory reserve, and the cache budget are unchanged. Supplement prewarm and the rewarm check use the same table. A budget refusal now moves the retry time forward by the normal retry interval instead of being judged again at every maintenance tick, the refusal line is logged only when its state changes, and its wording says the budget is assigned rather than used.
- **0.9.0-beta.36, resident utilities excluded, prewarm shrinks to fit memory.** A desktop utility that stays running and does not load again, such as Wallpaper Engine, used to be registered as a game, so it was relocated, prewarmed, and rechecked for nothing, and the drive-recovery wait after its relocation held back real games. A fixed list of such utilities (Steam app IDs and their own executable names) is now left out of discovery, and an auto-registered entry on the list is unregistered after service start, even while it is running; entries you registered yourself are not touched and `auto.ignore_exes` is not changed. A game that is no longer registered is not prewarmed or pinned. Prewarm measures free memory again right before reading. If the list no longer fit, it was cancelled at 0 MiB (39 MiB short in the observed case); it now reads the front part that fits, with a 256 MiB margin, and the rest is supplemented later. The memory reserve and the cache budget are unchanged. A prewarm that was cancelled is read again even while the drive recovers from a relocation, like any other prewarm; further relocations still wait for recovery. The "nothing new to read" supplement line is logged only when its state changes. The drive-recovery check after relocation measured its baseline once at position 0 while the samples rotated through three other positions, so the speed difference between positions was counted as a shortfall. After a 43 MB move it stayed unconfirmed for 149 minutes and held back every relocation on that disk. The baseline is now the median of the same three positions, and besides 2 consecutive passes, at least 4 passes in the last 6 samples also count as recovered. When samples keep falling short the interval grows up to 8 minutes, and each sample logs the values and the reason behind its verdict.
- **0.9.0-beta.35, blocked reapply handed to auto relocation.** Reapply restores a layout that has drifted while the source files are unchanged. When it was rejected because another file occupied part of the zone (`zone_not_free`), it ended as an error and tried the same thing a day later; a game with no update and no new trace was never restored. Nothing had been moved, yet the planned bytes were charged to the daily budget and a drive-recovery wait started, which also held back other games on the same disk. Such a game now goes back to auto relocation, which keeps the moved parts and replans only the remaining part, under its existing holds and daily limits. It is handed over only when auto relocation is on, the game has a trace, and it is not stopped by a failed data check; otherwise it fails as before. A rejection before any move is recorded as 0 bytes. A reapply that stops at the per-round write cap keeps the 5-minute recheck, so the remaining part continues once the drive has recovered instead of at the normal interval (1440 minutes by default).
- **0.9.0-beta.34, unfinished prewarms retried, quicker drive-recovery check, blocked layout rechecked.** A prewarm of a traced game that was cancelled before it finished, or skipped by the service-start cap, now stays on a waiting list and is requested again once the disk has been idle for 60 seconds, no game is running on that disk, the drive is not recovering from a relocation, and the cache budget has room. Before, the game stayed cold until the next launcher trigger. The `prewarm cancelled` log line now carries the reason. Games without a trace are not retried this way. The drive-recovery check after relocation used to discard every sample faster than 1.25 times the baseline as a drive-cache hit, so a baseline that was measured low made recovery impossible to confirm and the wait ran to the hard limit (178 minutes in the observed case) while reading 192 MiB every 2 minutes. Samples above that ceiling at all three rotating positions in a row now count as recovered (about 6 minutes in that case), samples that cannot be judged are spaced out up to 8 minutes apart, and the discarded samples are summarized in one log line. A layout check that finds the layout unfinished but is blocked by a temporary condition (a running game, a busy disk, drive recovery, battery power, not idle long enough, the post-update delay) is repeated every 5 minutes instead of at the normal interval (1440 minutes by default), so a degraded layout is restored without waiting a day. The warning now says the service retries automatically.
- **0.9.0-beta.33, tray at logon, play records, observed-read prewarm.** When the tray is installed under Program Files, the installer registers a logon task named `AsterCache` that starts it with administrator rights, so no UAC prompt appears and you do not need to relaunch it as administrator. Other install folders keep the Start-folder shortcut. The management window draws the game list first and fills in the placement checks in the background, and the tray does not query disk placement while a game is running. While a game runs, the service samples the physical disk's cumulative read bytes, read count, and read latency once per second, and records summaries at 30, 60, 120, 300, and 600 seconds after the start and at exit, in `play record:` service log lines and in `play_samples.json`. It reads only the disk device counters, not the game's files or process, so it is measurement for comparing loading and stutter and does not make the game faster by itself. Each prewarm range is marked as observed in play or guessed from an engine profile. When the budget is short, the observed ranges of all games are filled first and the leftover goes to the guessed ranges. Lists written before this change get their source restored from the existing trace. With enough budget, the ranges read and their order do not change.
- **0.9.0-beta.32, relocation skips and prewarm cache budget.** Relocation leaves out sparse, compressed, and encrypted files, which it skips rather than moves. These files used to keep the "needs relocation to continue" status on screen, and relocation never finished. A plan whose zone is already at its maximum size is no longer planned again, and the screen says that the work resumes automatically. Prewarm's cache budget is half of physical RAM by default (`prewarm.max_cache_mib` sets it). Games triggered recently, such as by a launcher, are prewarmed first for 6 hours.
- **0.9.0-beta.31, tray redesign.** The windows, tabs, dialogs, and notifications now share one design system. Light and dark themes are both supported (`--theme light|dark` forces one; otherwise the Windows setting is followed). The Status tab became a status badge, number tiles, and per-game cards; the Games tab got colored status badges and buttons grouped in working order; the Settings tab got section cards and an aligned form. Colors, type sizes, and spacing are defined in one place, `csharp/src/AsterCache.Tray/Look.cs`.
- **0.9.0-beta.30, no duplicate work in one prewarm round.** The same prewarm list was computed three times inside one round; it is now computed once (and again when the plan, trace, prewarm-only list, or volatile-marker file changes). One line with per-phase elapsed times follows the prewarm completion log.
- **0.9.0-beta.29, game start stream and trace.** The start stream kept reading the disk after loading ended and caused stutter during play. It now stops at a loading boundary judged from the game process's read volume, and at the `auto.start_stream_cap_seconds` cap (default 120). After the first window, the trace also collects short late-play windows through the `auto.trace_late_*` settings, and saving happens after the game ends. Relocation, tier apply, top-up, and rewarm on the same disk start after the `auto.rewarm_after_exit_min` grace once a game exits.
- **0.9.0-beta.28, ORBIT refinements and service hardening.** The ORBIT decision rule gained a per-episode delay allowance of `max(5%, 200 ms)`, and the decision path, calibration, and result judgment were improved. Disk read arbitration re-queries volumes it could not resolve, the disk activity sampling thread stops on service shutdown, and the load boundary watch now goes through the arbitration lease and the anti-cheat policy table. The tray menu and taskbar icon show four states (stopped, attention, working, healthy).
- **0.9.0-beta.27, tray message fix.** A game replanned after an update while keeping its learning was wrongly shown in the tray as "will be collected again on the next run".
- **0.9.0-beta.26, ORBIT field validation.** ORBIT prewarm order adjustment was measured on a real HDD and the decision path was sped up. `aster orbit mode|calibrate|model`, `aster orbit-bench run|summarize|rescore`, and `orbit_mode.json` were added.
- **0.9.0-beta.25, disk read arbitration and learning preservation.** Added per-physical-disk read arbitration (lease and yield), learning preservation that drops only the changed file ranges when a game updates, launcher display names, a per-feature policy decision table, and loading-time sample recording.

## Since beta.8

These changes landed on `main` since beta.8, including follow-ups from an external review.

- **ORBIT prewarm order adjustment.** For games with recorded traces, ORBIT changes the prewarm order in chunks of about 64 MiB only when the worst-case gain is positive and no episode exceeds the per-episode delay limit. The 2026-11-09 Call of Duty ABBA bench on the user's WD20EZAZ 2 TB SMR HDD cut median value-weighted prep time by 18.8% (10/10 pairs improved by at least 10%; sign-test p=0.001) and total read time by 0.1%, but increased the worst episode p95 by 13.1 s (flag 4 failed). Rescoring with the new rule rejected the B candidate as `episode_regression`; its modeled worst delay was 55.5 s versus the measured 13.1 s. This is one game, one drive, and one session, so generalization is premature ([ORBIT: prewarm order adjustment](ORBIT.md)).
- **Parallel relocation.** Eight parallel reads cut relocation work on the test HDD from 186 s to 41 s (4.5×). See [docs/RESULTS_SUMMARY.md](RESULTS_SUMMARY.md).
- **Drive recovery check.** After a game update, or after a relocation on an SMR drive, the service judges whether the drive has recovered before it starts the next job (`auto.post_relocate_recovery`).
- **Hands-off after install.** `aster status` and the manager window summary show one line: "found → bootstrap planned → relocated → prewarmed → average hit rate". While you are likely to play (a launcher is running or it is your usual play hour), the service reads 4 KiB every 10 minutes so the HDD does not spin down (`auto.keep_awake`, on by default; power settings are never changed). The read is skipped while a game on the same disk is running.
- **Prewarm yields to a running game.** On the same physical disk, a prewarm stops at the next 64 MiB batch boundary when a game starts. Disks are compared by physical disk number, not drive letter, so one HDD split into several volumes also counts as the same disk. On that disk, a game that reads under 1 MiB/s does not block prewarm of other games if the disk stays idle for 60 seconds (step 4 under Stages). `auto.keep_stream_on_game_start` (default `false`, experimental) restores the old behavior. The start-up stream, which reads the hot set right after a game starts, also stops at the loading boundary (the 10-second moving read rate falls below 10% of its peak, at most 60 seconds in, judged from the game's read counter at 1-second intervals with no disk I/O) and at `auto.start_stream_cap_seconds` (default 120; 0 means no cap). It does not read the rest again while the game runs. If the disk is yielding at game start and the resident sample cannot be read, the start stream is skipped when a real sample was warm within `rewarm_minutes` and the plan has not changed (log `start stream skipped (recent probe warm ...)`). A rejected sample is not treated as cold.
- **System drive on an HDD.** Games on an HDD that is the Windows system drive are discovered and prewarmed only, not relocated or tiered (status "prewarm only (system drive)").
- **Metric name.** `tier0_probe_ready_ms` (formerly `load_boundary_ms`, still read) is the time a tier0 prewarm sample was found in RAM. It is not the time a game finishes loading.
