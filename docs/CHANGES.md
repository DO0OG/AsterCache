# Changes

> Main changes by version. For details, see each version's GitHub release and the commit history.

## After 1.0.6 (not released yet)

The changes merged into `main` after the 1.0.6 release. They are in no release yet. The terms prewarm, zone, relocation, and holding are explained in the 1.0.6 section below. This list changes the default zone layout, adds limits on repeated work (placing the same pieces again, background disk reads), re-reads a cooled front part while a supplement prewarm waits, changes how a game's prewarmed cache is held and in which order it is kept, lets a refresh use a larger time share when a cache is about to be pushed out, and adds two switches to the yield of background programs. None of these was measured in real play, so their effect on loading time and stutter is unknown. They were checked with unit tests, code review, and, for the relocation pause, a test with a simulated volume and clock.

- **The whole-file layout is the default (`auto.relocate_layout`).** New plans use `whole_file`, which places each chosen file in the zone as one piece. A `ranges` written in `config.json` for the key is followed, and so is a game's own `layout`; the tray of 1.0.6 wrote `ranges` into `config.json` when it saved settings, and that file keeps `ranges` until the key is deleted. A game that already finished relocating with a range plan is moved to a whole-file plan once per service run, within the daily relocation limits (`max_relocations_per_day`, `max_relocate_gib_per_day`) and the write cap of one round. The state after the free-space consolidation step of a drive optimization and the effect on loading time were not checked.
- **Relocation pauses when the same pieces keep being placed again.** When a game's source files did not change but pieces the service had already placed lost their place (at least 64 MiB of them) and were moved again, the service counts a round. Three rounds within seven days pause automatic relocation and re-applying for that game, with either layout; prewarm goes on. The log has `reapply paused after N unchanged-source rounds in 7 days`, and the tray shows the reason. The pause ends when the source files change and the game is planned again, when a new plan replaces the old one, when the game's layout setting changes, or when fewer than three rounds remain in the seven days. The counts are kept in `auto_status.json` (`reapply_limits`). The manual `aster apply` and `aster revert` are not paused. The cycle this stops (a drive optimization undoes a range placement, the service places it again, and the daily write budget is spent each time) was reproduced with a simulated volume and clock, not seen in a real game log.
- **The move to the whole-file layout is no longer skipped silently.** A game was left out of the move whenever an older plan backup (`<game>.plan.json.stale`) existed, and that file stays after a replan. That condition is gone. When the move waits for another reason (the plan was restored after a failed replan, the zone is being extended, a plan switch is unfinished, or the game has no trace), the log has `<game>: whole-file placement waits, <reason>` once per game and service run.
- **Keeping sparse blocks gives its reasons.** Each round of `memory.keep_sparse` that is skipped or reads nothing now logs why (once per change of reason in a play), and the end line counts the skipped rounds by reason and the failed block reads. When the prewarm budget was too small to include the sparse ranges, the log says `sparse files left out of the memory prewarm, nothing to keep`, and there is nothing to keep in that play. What is read and prewarmed did not change.
- **Holding starts first and continues where it stopped.** For a game that can be held, the first holding runs before the touch at game start, which then skips the held ranges; the check of the holding floor runs on its own thread and does not wait for the touch. What a stopped first holding left (skipped or not yet visited ranges) is remembered and continued about every second in 4 MiB batches, up to 16 batches (64 MiB) per check, under the conditions of holding again (the game is not loading, the drive queue is 0). Holding again and continuing share 1 GiB of disk reads per play. The ranges that are not held get keep rounds on a separate thread, after the touch at start and only while the game is not loading. If the hard-fault count of a batch cannot be read, holding adds no more disk reads in that play. The first target also leaves room above the floor for what the game is known to take (learned from its play records); when nothing has been learned, it uses a quarter of the available memory instead of half. The log has the time since detection and the amount left in the start line, and the continued total in the end line. The values 1 second, 4 MiB, and 16 batches were not chosen by measurement. The game's start stream is not delayed for the holding, so both read the same drive at the same time (not measured). A round of holding again can read one 16 MiB batch beyond the 1 GiB limit (open issue #355).
- **A cooled front part is read again while a supplement prewarm is pending.** The supplement prewarm reads the rest of a game's list that did not fit in memory. When the part it had read earlier has gone cold, that part is now read again even while the supplement is held back, from the same ranges as the first read, and the recorded amount read (`warmed_mib`) is not lowered. The usual conditions still apply (idle disk, check interval, no game running on the drive, budget, memory floor). Limits: at most 2 times a day for a game, and if the part goes cold again within `2 × rewarm_minutes`, 24 hours of rest from that read. The count and the rest survive a service restart and setting the clock back. A game that stopped for memory, or whose first read cannot be rebuilt, is left to the full re-prewarm or to the supplement. `prewarm_status.json` now keeps the amount actually read (`warmed_mib`), the window size (`window_mib`), and whether the first prewarm left out sparse files (`sparse_out`). The log of file-open errors during a touch or prewarm now totals them by error code (files, ranges, requested bytes) and names up to 4 failed files; a file that failed to open is not opened again in the same call.
- **Automatic disk reads have a daily limit (`auto.idle_read_gib_per_day`, new).** The service counts the bytes it reads from a game drive by purpose (`trigger`: asked for by a game start, a launcher, a game exit, or a service start; `idle`: no such trigger; `recovery`: samples after a relocation) in a moving 24-hour window per drive (and per game for `idle`). The count is kept in `prewarm_status.json` (`disk_reads`) and survives a restart, and one log line a day, `disk reads in the last 24 h`, shows it. The reads without a trigger (the re-prewarm check, the supplement prewarm, retrying such a read from the waiting list, the prewarm after a relocation) stop when the share of the drive or of the game is used up (log `idle disk reads of ... paused`). The limit is `auto.idle_read_gib_per_day` per drive; 0 means the larger of 24 GiB and six times the prewarm lists of the games on that drive, divided among the games in proportion to their lists. Reads that a game start, a launcher, a game exit, or a service start asks for, and what the SOLAR ladder reads, are counted but not limited. The automatic prewarm of a played game that has no play record yet is not limited either (open issue #356). The recovery samples after a relocation are now taken every 4 minutes (2 before), at most 8 samples read to the end and 1.5 GiB per drive in 24 hours; a drive that used them up can hold back selective relocation until the hard limit (`recovery_hard_max_min`). The amount is estimated from the read time and a speed limit, so it can be too high or too low. The default is meant to cap an unusually heavy day, not to cut ordinary reading; a lower value delays the periodic refill, and a game start can then be slower (the start prewarm is not limited). On the development PC, replaying its log gave about 65 GiB a day of counted reads without a trigger under the default, against about 82 GiB without a limit; this is an estimate from the log, not a measurement of the installed build.
- **Background yield: new programs sooner, and programs in use get a lower memory priority.** `memory.background_yield_fast` (on by default): while a registered game runs, the list of process ids is compared every 1.5 seconds (nothing is opened), and a new program seen twice in a row, so within about 3 seconds, gets the same priority changes as the 2-minute check, under the same exclusions; its working set is not emptied. `memory.background_in_use_memory_priority` (on by default): a program in use gets the memory priority "below normal" (4) instead of being left alone, so Windows reuses its pages before the prewarmed cache (priority 5); an idle program still gets "very low" (1), and a program whose own value is 4 or lower is left alone. The original value is restored at the end of the session. The cost is that while memory is short, Windows trims the pages of a program at priority 4 before the cache, so a program in use can be slower when it needs them again. Both do nothing when `memory.background_yield` is off. The per-second record (`play.series`) has four more columns at the end (`other_ws_mib`, `ws_grow_top_name`, `ws_grow_top_mib`, `yield_applied_n`), and a log line with counts is written when a value is not 0. The effect on loading time and stutter was not measured, and whether Windows hands a child process the parent's memory priority 4 was checked only with a simulated one.
- **A second order for the keep list, from reads during the match.** Each ranked block gets a score from the plays: 1 point for each play with a paging read of it, and 3 points when that read was a single request made at least 120 seconds after the executable started (so not in the loading right after start). The scores and the order by score are worked out once when the ranking list is written (while no game runs) and saved in `ranked.json` (`play_scores`, `play_order`, `play_sparse`); earlier versions read the file and ignore them. Only the keep list uses the new order (keep rounds, holding, keeping sparse blocks): its first 2 GiB, counted only over blocks that passed the file check and lie inside the prewarmed read ranges (not sparse blocks), are put in score order, and the rest stays in ranking order. The touch at game start, the ladder outside games, and the choice of what to prewarm are unchanged, so a block with a high score that is outside the prewarm list is not kept. The estimate comes from earlier Call of Duty records on the development PC: of the blocks with a paging read during a match (blocks of general files, each play predicted from the plays before it), the first 2 GiB covered 22.8% with the new order against 16.9% with the old one. How long the blocks stay in memory and the frame intervals were not measured.
- **A cache about to be pushed out may be refreshed with 5% of wall time instead of 2%.** While no registered game runs and the 2% cap holds a refresh back, a game whose reuse count since its recorded state has reached `max(512 MiB, 0.5 x the amount reused first)` is refreshed within a separate 5% cap (at most 12 seconds can build up; for a game whose refresh time is not known yet, its ladder size at 512 MiB/s). Only the games at risk are chosen, in rank order, and when one does not fit yet the games below it wait for the next 30-second check. The time of these touches is not added to the 2% account. The log has `cache refresh brought forward past the 2% cap, within 5% of wall time: ...`, and `cache refresh deferred: the eviction risk of ... is near but touching time is capped at 5% of wall time too` when the 5% share is used up as well. The cause was seen on 2026-11-24: refreshes were deferred from 12:23 to 12:27, and at 12:28 the reuse (6,866 MiB) had passed the amount reused first (4,973 MiB) and the samples were cold. The effect in real play was not measured.
- **Settings keys.** `auto.idle_read_gib_per_day`, `memory.background_yield_fast`, and `memory.background_in_use_memory_priority` are new; versions 1.0.6 and earlier reject a settings file that contains them, so remove them before rolling back. Defaults: 0, on, on. The default of `auto.relocate_layout` changed from `ranges` to `whole_file`.

## 1.0.6

The changes merged since 1.0.5. The service reads a game's files ahead into the in-memory file cache (prewarm), moves a game's files together into a continuous area of the disk (the zone; relocation), and, while a game runs, keeps the prewarmed cache open as read-only mapped views so that it is not pushed out of memory (holding). This version adds: deferring relocation while the drive optimization that Windows schedules is running and recording that run; judging whether a game is loading right now and reading less from the disk in the service while it loads; holding again what was released because memory ran short; the whole-file layout, a new way of laying files out that a drive optimization does not move (a feature you turn on by a setting; the default stays the old way); mixing the blocks of sparse files (files that allocate no disk space for their empty stretches) into the prewarm ranking and keeping them while a game runs; and a wording fix in one screen notification. The effect of these changes on load time and stutter was not measured. Detecting a drive optimization run and deferring moves were checked in real runs; the touch again at start, the loading judgment raised by an executable start, holding, and the release at exit were checked with a fake-game test (a test program started under a registered executable name). Holding again, the in-game loading judgment from graphics and disk signals, and keeping sparse blocks were checked only with unit tests and code review, and their behavior and effect in a real game were not measured.

- **Screen notification wording.** The notification shown when the first-run recording ends (`Toast_FirstRun`) said "Faster from the next launch", an effect that was not measured. It now says only what was done: "First run recorded; planning from this recording" (the Korean text was changed the same way).
- **Relocation deferred while the scheduled drive optimization runs.** The service notices the start and end of `defrag.exe` from the process names only (no process is opened) and defers moving files while it runs. It waits at most 30 minutes from the first sight of one run, and a move in progress rests between pieces. The start, the end, and the length are logged, and the warning that a layout came undone carries the end time of the last run the service saw. Because only the name is seen, it cannot tell which drive is processed, so relocation on every drive is deferred, and whether an optimization the user starts from the window shows the same name was not checked. Windows scheduled tasks and system settings are neither read nor changed. In a real run the logs of the start, the 30-minute limit, and the end appeared, and file moves were deferred meanwhile.
- **Loading judgment inside a game.** While a game runs, the state is judged as loading, not loading, or unknown. The inputs are the read amount of the drive the game is on (the service's own reads subtracted), the growth of the game process's dedicated graphics memory, and a newly started executable. During a loading caught only by the read amount and the graphics memory signal, without an executable start, the service reads less from the disk while a game runs (the re-read amount of the touching-again rounds and of the checks of held ranges). Touching again references the pages again in memory without reading the disk so that they are pushed out last. The judgment ends 240 seconds after it started, so a wrongly raised judgment does not block the service's work for long (when an executable starts again during a loading, the whole continued loading ends at 480 seconds). The columns `game_read_bytes`, `game_ws_mib`, and `load_phase` were added at the end of the per-second record (`play.series`).
- **Holding again what was released.** When the available memory fell under the floor (2 GiB) and everything held was released, the holding of that play ended and the touching again stopped with it; this is fixed. The existing 2-minute retry now holds again and the touching again goes on meanwhile. If only part was released, the 2-minute check holds the released ranges again in importance order. The conditions for holding again are: the loading judgment is not loading, the disk queue of the game's drive is 0 (unknown counts as not 0), and the target `min(5 GiB, available x 0.5, available - floor - 1,024 MiB)` is at least 64 MiB. What it reads from the disk while holding again is 32 MiB per round at 256 MiB/s and at most 1 GiB per play. The 1 GiB is not a measured value but one fifth of the first holding target (5 GiB). What was held again is released again if the available memory falls under the floor during a later loading.
- **Whole-file layout (`auto.relocate_layout`, per-game `layout`, new, off by default).** A way of placing files so that a drive optimization does not move them. The current way (`ranges`) joins the ranges in the plan to the zone in the order of first read, so one file becomes several pieces, and a drive optimization can move those pieces again. The new way (`whole_file`) puts only two shapes in the zone. One is a file whose size is at most twice the bytes in the plan, placed whole as one piece; the other is, in a larger file, a stretch of 80 MiB blocks in which at least 0.5 of the bytes are in the plan (neighboring stretches are joined; a stretch under 80 MiB at the end of the file is left out), placed as one piece. The rest of such a file, files the game writes, and sparse files with holes stay in place, and when the zone limit is exceeded the files read later stay in place first. The settings are the global `auto.relocate_layout` (`ranges` by default, or `whole_file`) and a `layout` in a game entry of `config.json`; the game's `layout` wins. The default is `ranges`; `whole_file` is turned on by these settings. Once on, games laid out the old way are moved to the new layout once per service run, the most recently played game first (deferred while the game runs), over several days within the daily relocation limit (`max_relocate_gib_per_day`). Right after a drive optimization ends, the layout check of the games on the new layout is brought forward. The command `aster plan` also got the option `--zone-cap-mib`.
- **Mixing sparse-file blocks into the ranking and keeping them during a game (`memory.keep_sparse`, new, on by default).** The blocks of sparse files are no longer left out of the block ranking list but are ranked with the same score as the other blocks (blocks read in more plays first, then by total delay) and prewarmed by score within the prewarm budget (when the budget is small, the blocks with the lowest score drop out first). A sparse file is not held because mapping it makes it read from the disk again even when it is in the cache; instead, while a game runs, the sparse ranges that were prewarmed are re-read every 20 to 30 seconds with an ordinary read through the file cache (buffered read) so that they are not pushed out. A block in the cache is a memory copy and does not read the disk. A block that was pushed out is read from the disk again only under the conditions of holding again (not loading, game drive disk queue 0, 32 MiB per round), up to 512 MiB per play (counted apart from the 1 GiB of holding again). It follows the same anti-cheat gate as holding. A ranking list made before this version has no sparse blocks, so until the next play ends and the list is rebuilt, only the sparse ranges the plan reads are kept.
- **Good to know.**
  - The default of the whole-file layout stays the old way (`ranges`). `whole_file` is a feature you turn on with the global `auto.relocate_layout` or a per-game `layout`.
  - Reason: the state after a Windows drive optimization that ran to the end was not checked. On the test PC (an SMR hard disk) the optimization's free space consolidation step could not be run to the end within a few hours, so whether that step moves a file placed as one piece was not seen.
  - What was checked, first: test files with different piece sizes were compared after the defragmentation step of the optimization reached 100%. The 9 pieces of 80 MiB and the 10 pieces of 128 MiB all stayed in place, and a 128 MiB file that was one piece from the start stayed as it was. All 56 pieces of 1 to 56 MiB were gathered into one piece and moved, and of the 9 pieces of 64 MiB only 5 stayed. In a file with small pieces mixed into a large piece, only the small pieces were gathered and the large piece stayed. The 80 MiB limit of a large piece was chosen from these observations.
  - What was checked, second: the whole-file layout was turned on by a per-game setting for one game (Lobotomy Corporation), about 250 MiB were moved (0 failures), and the service's layout check confirmed that all 254 whole files and 1 large piece were each one piece inside the zone. Whether they stay after a scheduled optimization runs later was not seen yet.
  - On this PC the largest free continuous stretch fell from 8.04 GB to 4.79 GB after the defragmentation step. When the free continuous stretch is too short, the whole-file layout leaves the files read later in place first. The prewarm time and the in-game read delay after the new layout were not measured.
  - What was checked with the fake-game test (a test program started under a registered executable name, about 3 minutes, twice on development builds): the touch again at start of the ranges in memory (0 disk reads), the loading judgment raised by an executable start and ending about 16 to 17 seconds later, holding (298 MiB) and the 2-minute check, the release at exit, and the restoring of other processes' priorities. What did not happen in this test and so was not checked: holding again after a release because of memory, the in-game loading judgment from graphics and disk signals, and keeping sparse blocks. These three were checked only with unit tests and code review, and their behavior and effect in a real game were not measured. The effect of holding again on the load between matches was not measured either.
  - Basis experiment for keeping sparse blocks: a 512 MiB file re-read with buffered reads every 10 seconds on an SSD stayed 99.9 to 100% in the cache after memory pressure (3 runs), and a sparse file that was not re-read stayed 0%. The service's real interval (20 to 30 seconds) and a hard disk were not measured. The rule that tells a read that came from the disk was measured on a hard disk and told 100% of the read batches that came from the disk (measured while a drive optimization was running).
  - The thresholds of the loading judgment were fitted to four play records (12 transitions) of one game, Call of Duty, and evaluated on the same records, so the accuracy on other games is unknown. The only thing done with the judgment is deferring the service's disk reads.
  - Anti-cheat scope: for a game where holding is forbidden, holding again and keeping sparse blocks do not run. For a game whose anti-cheat forbids tracing, the loading judgment does not read the graphics memory value and uses only the disk-read rule. No new path opens a game, launcher, or anti-cheat process.
  - The new settings keys `auto.relocate_layout`, `games[].layout`, and `memory.keep_sparse` are rejected by versions 1.0.5 and earlier, so remove them before rolling back (this matters when a game was set to `whole_file` or the keys were written by hand; see the matching paragraph of `docs/CONFIGURATION.md`). Defaults: `ranges`, none, on. The three columns added to the per-second record did not move the existing columns.

## 1.0.5

The changes made since 1.0.4: keeping the prewarmed cache while a game runs, giving the disk to the game by lowering the priority of background programs, a per-second play record with frame intervals, and a number of fixes to prewarm selection, trace collection, relocation, and the resources the service and the tray use. The measurements below come from one PC, one game (Call of Duty), and four plays, each with a second-by-second frame record. In the two plays before holding (the first item below) was introduced, 8.0% and 9.7% of the seconds during a match had a frame interval over 100 ms; in the two plays after it, 4.0% and 1.4%. In the play with 1.4%, most of the held data was released right after the match began, so that play's low share cannot be credited to holding. Several other changes went in between these plays besides holding, the plays differed in free memory, in the programs running alongside, and in match length, and the sample is small, so this is not a measured effect of holding; effects on load time and stutter in other games have not been measured. A replay measurement found that when a game reads a file without the file cache, that read took about 2 times as long while the service held the file, so such files are not held.

- **Holding the cache while a game runs (`memory.keep_hold`, new, on by default).** Touching the pages on the standby list every 2 minutes (referencing them again in memory without reading the disk, so that they are pushed out last) could not stop a page that was pushed out between two touches. While a game runs, the service now holds the keep list (the front of the prewarmed cache in importance order, up to 5 GiB or what the available memory allows) as read-only mapped views in its own process, so those pages stay out of the standby list. The pages are not locked: when the available memory falls under 2 GiB (`HoldMinFloorMib`), the less important part is released first, and everything is closed when the game exits. Not held: files marked volatile, sparse files, files that changed after the ranking list was made, anti-cheat component files, executable images (files that start with `MZ`), files under 16 MiB, and files for which holding costs more than it gains (judged from the read-mode records of earlier plays). No game, launcher, or anti-cheat process is opened. The gate is the same range as for tracing: nothing is held for a game whose anti-cheat forbids tracing (EasyAntiCheat, BattlEye, Vanguard, kernel-level, or an unknown kind). A Ricochet game is held, and pinning stays forbidden for it. Task Manager shows the service's memory larger by the held amount and the available memory smaller by it while a game runs. A write by the game that shrinks a held file fails (error 1224) until the view is closed. How the game and an anti-cheat react to a file kept mapped by another process was not checked, and no vendor statement was found. See [SOLAR](SOLAR.md) and [Anti-cheat compatibility](ANTICHEAT.md).
- **Files the game writes are held too (`memory.keep_hold_written_files`, new, on by default).** Part of the cached read delay in a match came from files the game itself writes (for example the `xpak_cache` of Call of Duty). Such a file is now held when the NTFS change journal shows no truncation in at least 3 plays (without journal data, when its size never shrank in 3 recorded plays), the game was not updated since the last finished play, and the file does not change during this play; it is compared every 5 seconds, and the view of a file that changed is closed at once. These files also enter the block ranking list when they were read from the disk in at least 2 plays, and the I/O summary records the writes (`write_files`). A shrink inside the 5-second window could still fail the game's write.
- **Touching again while a game runs, for a game that cannot be held.** When the keep list is not held (anti-cheat, no trace yet, or the setting off), the prewarmed ranges are touched again in memory while the game runs. The touch now covers, at game start, the ranges that game prewarmed, so the game that actually started is pushed out last; it follows one importance order everywhere (ranked blocks first, then the other prewarmed blocks); judges a miss by the hard-fault count of the service process instead of the time a touch took; skips a missing piece and goes on to the end of the list instead of ending the round at the first one; and remembers within a play which ranges are in memory and which are missing, touches only the ones in memory, least important first, and rechecks the others within a read limit of 8 MiB per round and 64 MiB per play, with no rate limit or pause. A round that reads the disk stops at 32 MiB of disk reads when holding or when skipping missing pieces.
- **Background yield gives the disk to the game and spares programs in use.** During a game session the service now also lowers the disk (I/O) priority of the background programs it already selects from normal to low, so that their disk reads do not delay the game's (`memory.background_io_priority`, on by default). In a test with an experiment tool on the test PC (not the service, not a running game), a test program that reads random places 30 times a second like a game had a 99th-percentile delay of 427 ms while four programs read the same disk at normal priority, and 92 ms with the four at low priority; the four programs then ran at about one sixth of their speed (4.6 MiB/s to 0.8 MiB/s together). Lowering the CPU priority class from normal to below normal was added as `memory.background_cpu_priority` and is off by default: in a second-by-second play record the other processes' CPU use did not differ between the seconds with a long frame and the seconds without. A program that used the CPU (0.5% of one core or more) or did I/O (32 KiB per second or more) in the last minute keeps its memory priority and its working set. A working set is emptied only when the available memory minus what the game is expected to take is below a floor, only by the missing amount, largest first; programs started by a lowered program give back the low memory priority they inherited; yield does not start from a launcher alone; and a program is not emptied again when the last emptying raised the available memory by less than half of the emptied amount, nor repeatedly because of a shortfall that emptying cannot fill.
- **Prewarm and relocation yield to small scattered reads from other programs.** A hard disk that another program read in many small places had a low throughput and was judged idle, so the prewarm and relocation did not yield to it. A disk whose idle-time share (`% Idle Time`) is under 75% now counts as busy even when the throughput is low, and a relocation looks at other programs' disk activity between write pieces, rests while there is some, and ends the round after resting more than 10 minutes. On the test PC, while another process read 64 KiB 30 times a second, a supplement prewarm of 7.8 GiB went back to normal I/O priority after 16 seconds and raised that process's average read delay from 22.9 to 33.4 ms; the new rule was checked only with a test program, and on an idle disk the relocation is about 3% slower because of the observation.
- **Play record (`play.frame_times`, `play.series`, new, on by default).** While a game runs, the play record keeps the frame interval: an ordinary ETW session receives only the `Microsoft-Windows-DXGI` Present start event and the service totals the intervals of the game's processes per second (frame count, longest interval, intervals over 50 ms and over 100 ms, pauses of 1 second or more). It passes the same gate as automatic tracing and opens no game process; only DirectX games are measured. `play.series` writes one line per second (frame values, CPU, available memory, graphics memory, disk values, and what the service was doing) to a file per play in the `play_series` folder of the data folder, keeps the newest 8 plays of each game, and writes the standby list sizes by priority every 30 seconds to a `.lists.csv` file beside it. The record also counts touch errors by kind, and the check of 16 positions on the whole list (`probe N/16 in memory`) is written only to the log. The cost measured without a game: about 0.36% of one core for the per-second record and 0.23% for the frame session. The cost next to a running game and the behavior next to a real anti-cheat game were not measured. The end-of-play tally is now kept and made later when another game is running on the same disk, instead of being dropped, and the size record of game-written files is written at the end of every play.
- **Read tallies, ranking, and prewarm selection.** The automatic trace now totals the real disk reads and their delays until the game exits (`auto.io_summary_enabled`, on by default; disk-read completions only) and keeps the number of reads per file by read mode (with the file cache, without it, paging). From all the intervals of these tallies a block ranking list is built (blocks read in more plays first, then by delay), and prewarm, supplement prewarm, the touching, and the holding use the same selection: prewarm-only ranges, the first load section, ranked blocks, then the rest. Files a game reads only without the file cache are left out of prewarm, the start and stage streams, pinning, and the sample list. The prewarm reserve of a game whose memory use is known is `max(prewarm.min_free_ram_mib, the game's memory use + 1024 MiB)`, with the memory use (the amount of memory the game takes once it runs) learned from the play records. A supplement prewarm no longer repeats every 10 minutes when the prewarm list is shorter than the window it can read. A tally that included the service's own reads, and a first extra trace window that opened late, were corrected.
- **Load-section refill.** The service builds, for each game, a list of the blocks read first in the 120 seconds after each registered executable started (`<game>.trace.loadrefill.json`), and reads it again when the executable of the same game starts later in the play, because the prewarmed cache is pushed out while the game runs and the later map loads then came from the disk. The list is also rebuilt at service start when it is missing or older than the newest tally, a late trace window opens when a registered executable starts during a late window, and a game whose list was built from fewer than 2 plays with start times is traced for the next play (up to 3 times, not for a game on which anti-cheat forbids tracing). Blocks that were only read without the file cache are left out of the list, and the list is read in disk-position order.
- **Trace collection.** A trace that was being saved when a game started was dropped as a whole, and a game that was started again immediately gave up the trace start; both are fixed. The prewarm that waited after a reboot is released correctly and the reason for the preparation section appears in the log.
- **Relocation of sparse files and the estimate command.** The allocated ranges of a file with only the sparse attribute are relocated like those of any other file (this also covers plans written in the older format, which move without being planned again), and a relocation estimated by physical reads can be calculated before anything is moved: `aster plan estimate --io-summary <file> --origin-root <game folder>` reads only the summary, the optional plan, and file layout, selects blocks by the gain of joining pieces, and can evaluate a kept play. The estimate no longer classifies sparse files as unmovable. The layout check reported a change but never replanned; a new file of another program took the place of the zone margin and kept the move from finishing; and a game that closed in an intermediate time kept the next run backing off. All three are fixed.
- **Less CPU, memory, and disk use.** (1) The tray kept animating its progress bar and refreshing its status when the window was hidden; they now run only while working or while the window is shown (a copied data folder with the window hidden for 90 seconds: process CPU 2.39 and 2.67 s before, 1.59 and 1.16 s after, with a large difference between runs). (2) The checks while a game runs now share one process-list snapshot when the list of process ids has not changed and 1 second has not passed (one budget calculation called the check 51 times, about 0.58 s of snapshots); the CPU saving on the installed build was not measured. (3) A trace file is no longer parsed as a whole; the service memory had exceeded 500 MiB. (4) While no game runs, the periodic refresh of the cache of all games is done only when the time spent touching stays within 2% of the elapsed time, a re-prewarm that is small enough not to push out another game's cache skips the protection of the other games, and the re-prewarm interval of a game whose re-read cache goes cold again lengthens to 10, 20, 40, and 60 minutes. In the installed build, while another program read about 1 GiB a minute for 10 minutes, the service had used 39.9 s of CPU (6.6% of one core) and refreshed 9 times; the values after the fix were not measured in a real session.
- **Cache keeping and prewarm reserve fixes.** Keeping the cache stopped at the first range missing from memory and so left most of the list unprotected; it now goes on past a missing piece. The memory a game takes after it starts pushed the prewarmed cache out during loading; the reserve now counts that memory use. Blocks pushed out when a map is loaded again inside a game are read again by the load-section refill above.
- **Games already running, and size history.** The size history of game-written files is now kept for every play, whether or not a trace was collected. When a game is already running, the touch at its start no longer reads the disk.
- **Settings keys and documents.** `auto.io_summary_enabled`, `memory.background_io_priority`, `memory.background_cpu_priority`, `memory.keep_hold`, `memory.keep_hold_written_files`, `play.frame_times`, and `play.series` are new keys; versions 1.0.4 and earlier reject a settings file that contains them (and the `play` object), so remove them before rolling back. Defaults: on, on, off, on, on, on, on. Invented names and filler wording in the documents were replaced with the terms in use or plain descriptions, and the descriptions of holding, the play record, and background yield were added or corrected.

## 1.0.4

The changes made since 1.0.3: keeping the prewarmed cache without reading the disk and setting the order in which it is pushed out (SOLAR) with its follow-ups, prewarm right after boot, sparse-file handling, a stage-aware start stream (reading the game's recorded start-up data in order right after it starts), and quick-exit detection. The effect on load time and stutter in real games has not been measured yet, and neither has the effect of the stage-aware start stream in real games.

- **Keeping the prewarmed cache and its eviction order (SOLAR, new, on by default).** The prewarmed files are ordinary file cache, so when memory runs short they are pushed out in the order they entered the standby list, and the data a game reads first goes first. After a prewarm AsterCache now touches the ranges it has in the cache again, in the reverse of the read order and without reading the disk, so the most important data is pushed out last, and touches them again in memory once cache reuse reaches 0.4 times the amount reused first at the time they were touched (at least 512 MiB). When it reaches a part that would need a disk read it stops and leaves the decision to the re-prewarm check. It does not run on a disk where a game is running, and the memory reserve and the cache budget are unchanged. Measured with test files on the test PC: a file touched again every 5 minutes stayed in the cache to the end, while a file read once was pushed out between 7.0 and 9.2 GiB of cache reuse; the page-read counter rose by 258 MiB when touching 256 MiB that was not in the cache, and by only 65 to 128 pages when it was. It does not guarantee that nothing is pushed out; under heavy memory pressure data is still pushed out eventually. Turn it off with `"memory": {"standby_ladder": false}`. See [SOLAR](SOLAR.md).
- **SOLAR keeps the order for large games and for several games.** When the ladder (the reverse-order pass) finds a part missing from the cache, the next re-prewarm check now fills it. For a large game, the most important front part was pushed out even after the prewarm read to the end, so re-prewarms repeated; the prewarm stream now touches each batch again as it reads it (about 0.5 s per GiB of cache, measured on the same PC). Refreshing or prewarming one game pushed out another game's cache first; games with a recorded state (the time and the standby-list figures SOLAR keeps in memory after it builds a ladder) are now handled as one group, refreshed from the lowest rank, and a prewarm stream touches the other games with a recorded state before, during, and at the end of the stream. This delays a service-start, rewarm, or supplement stream by the size of those games (about 0.5 s per GiB); a launcher-triggered prewarm is not delayed. A cache refresh only touches in memory, so it does not follow the drive-usage gate (when the drive is busy and it meets a part missing from the cache, an 8 MiB sample and up to about 100 MiB before it stops can be read). The basis is the installed build's log and a 61-minute trace of four test files on the same PC (the three files that were not touched again disappeared together, and the file touched once more stayed 39 minutes longer).
- **SOLAR false stops and cold misjudgments fixed.** A burst of page reads by another process (30,000 to 80,000 pages in 0.25 s) was counted by the touch as disk reads and stopped it; the amount seen as disk reads in one view is now capped at what the disk can read during the time the view took (256 MiB per second). The cache sample check judged samples that were slow because of load as cold; it now counts a sample as slow only if, besides the read time, the system's page-read counter rose by at least a quarter of the sample's pages (at least 16 pages) during the read. Whether the false stops and misjudgments decreased on the installed build has not been checked yet.
- **A large game's prewarm no longer repeats cancelling near the memory limit.** For a game with a large list, a prewarm read near the memory limit and cancelled again and again (in the installed build's log, 93 cancelled supplement prewarms, 79 of which added nothing to the record). When the limit is hit it now keeps what was read, shrinks to the range that fits now, and finishes, and it reads no disk when there is nothing new to read. The memory reserve (4,096 MiB) and the cache budget are not lowered.
- **Sparse files.** For a file with the sparse attribute, creating and closing a mapping was enough to drop the ranges that had been loaded earlier from the cache (all 3 runs on a test file), and reading in batches with a new mapping each time kept only the last range (all 6 runs), so touching the cache again read the disk every time and re-prewarms repeated. The prewarm stream now reads the ranges of sparse-attribute files with buffered reads and no mapping (the cache then carried over, 27 of 28 runs), and touching again and pinning skip sparse files. A buffered read of a scattered sparse list ran at 91.3 MiB per second against 116.0 MiB per second for a mapped read of a regular file, so the first prewarm of a sparse file can be that much slower. The judgment uses the file attribute only and looks at no game name or extension. The effect in real games has not been measured yet.
- **Prewarm right after a reboot.** After a reboot emptied the file cache, the service-start prewarm and the launcher-triggered prewarm were still skipped because of the cooldown from the pre-boot prewarm time. The cache is now checked with a sample only at the moment the cooldown would skip, and the cooldown is not applied when it is cold. Prewarm reads yield to other reads on the same disk: when there are other reads it does not cancel but keeps reading at a low I/O priority (on the test PC's HDD, a read like the prewarm's at normal priority slowed another concurrent read from 25.0 to 45.9 ms on average, and at low priority it was 26.1 ms), and the boot wait of the held launcher trigger and the service-start prewarm was shortened to "60 seconds of uptime + 20 seconds of game-drive idle". The pauses for observing can reduce prewarm throughput by up to 10%. A launcher-triggered prewarm used to wait until another game's background prewarm finished; it now stops the other game's background stream on the same disk and reads first (on the installed build a trigger once waited 2 minutes 6 seconds). Behavior after a reboot on the installed build has not been checked yet.
- **Stage-aware start stream (new, on by default).** When a game launched its executables one after another, the start stream ran only for the first one and stopped before the main process came up. Each time a registered executable starts, AsterCache now streams the blocks that stage reads first; the stream for a later executable starts at a low I/O priority and is raised while the game's reads are quiet. Auto trace records each executable's start time, and a game without stage information is traced up to two more times when the trace conditions are met. The effect in real games has not been measured yet. Streaming the next stage ahead of time after the first executable's stream ended is not included. The blocks read never exceed the start list, and without stage information the stream runs only after a new process has read more than 64 MiB within 10 seconds of its start. The read unit is cut to 32 MiB or less so priority switching and the memory check happen per batch (the effect of cutting on throughput has not been measured). Turn it off with `"auto": {"stage_stream_enabled": false}`.
- **Quick-exit detection (new).** This is not a feature that keeps a game from exiting right after launch. A game that exits within the threshold (`auto.quick_exit_seconds`, default 90 seconds) counts as a quick exit, and when it is launched again within 10 minutes the service skips its extra work for that run (no start stream, auto trace, loading-boundary reads, background memory yield, or trigger prewarm; the disk yield stays as it is). When quick exits come in a row, the kernel drivers that appeared after the last normal run (5 minutes or more) are reported in the log and the tray. It is a read-only enumeration, and "unknown" is shown when it cannot be read. The notice is a clue, not a confirmed cause. The same rules apply to every game with no branching on names. A normal self-restart that takes 5 seconds or more counts as a quick exit. The behavior was checked on the installed build with a light game.
- **Background memory yield no longer empties again and again with plenty of memory.** With a busy process around, it emptied all working sets about every 6 minutes even with plenty of memory (41 times in 4 hours in a real session). It now empties at session start only when the standby-list headroom is below max(4 GiB, RAM/4), during the session only when the cache was reused by 512 MiB or more, and a process that regained half or more of its working set after being emptied is not emptied again in that session. The exclusion rules and the memory-priority lowering are unchanged. When the standby list cannot be read, it empties only once at session start.
- **Less background CPU.** The tray used 0.3 to 0.6 cores even with nothing to do; fixing the window composition mode to the ordinary window surface took it from 0.33 to 0.38 cores down to 0.008 to 0.016 with the window closed, and from 0.41 to 0.49 down to 0.017 to 0.037 with the window open (10-second samples, before and after measured side by side on the test PC). The plan files were re-read in full every 30 seconds when a game had a partial prewarm; per-game estimates are now reused (before the fix, on the installed build, 100.7 s of CPU in 450 idle seconds; the value after the fix has not been measured yet).
- **Disk activity lookup.** Right after a game started, the yield decision switched off when the drive letter was missing from the performance counter's instance name; it now remembers the disk number that had the letter and keeps reading the instance with the same number. This form could not be reproduced on a real counter; the basis is three log entries.
- **Settings keys and documents.** `auto.stage_stream_enabled`, `auto.quick_exit_seconds`, and `memory.standby_ladder` are new keys; versions 1.0.3 and earlier reject a settings file that contains them, so remove them before rolling back. A SOLAR document is new.

## 1.0.3

Makes the prewarmed game files less likely to be pushed out of memory while a game runs. The effect on load time and stutter in real games has not been measured yet.

- **Background memory yield (new, on by default).** A game that takes memory gets it from the standby list, and the prewarmed game files are on that list, so they were the first to go. Other programs reading files kept replacing the entries of the same list. Measured on the test PC: emptying a process's working set sends its pages to standby priority 0, which is reused before the prewarmed files at priority 5; a process reading 17 GiB at normal memory priority pushed a cached test file out completely, while the same read at very low memory priority left it in place; emptying 29 background processes raised available memory from 15,587 to 19,324 MiB. During a game session (a launcher starting a prewarm, or a registered game starting) AsterCache now empties the working sets of background programs (32 MiB or larger) and lowers their memory priority, applies the priority to programs that start later, and empties again only after five minutes and 1 GiB of regrowth. When the session ends (the game exits, ten minutes without activity, the setting is turned off, or the service stops) the priority is restored; a state file lets the next start restore it after a crash. Registered games and their trigger programs, launchers and their helpers, anti-cheat and Riot components, session 0, and AsterCache itself are never opened; programs under a game folder, a game library, a launcher or anti-cheat folder, or the Windows folder are left alone. Nothing else is done to other processes. The memory reserve, the cache budget, and the prewarm checks are unchanged. A program that was emptied can be slow for a moment when you return to it. Turn it off with `"memory": {"background_yield": false}`.
- **A prewarm that read the whole list is no longer recorded as partial.** The read order widened a file to its full size when 30% or more of it was read, using a budget taken from the plan rather than from the list, so for a game whose plan total was larger than its list the widened list exceeded the amount it was allowed and the prewarm was recorded as `partial` with plenty of memory free. The order now uses the same list-based budget as the allowance.
- **Tray update text shows the version.** "Up to date" was shown and logged with an empty placeholder.
- **Champion select read-ahead stays off.** Riot's developer relations notice of 2019-01-24 says players in Korea may not use applications that use the League Client API, and no retraction was found. The documentation now says so instead of "unconfirmed".

## 1.0.2

A fix found in the service log right after 1.0.1 was installed.

- **A full prewarm that fails the memory check now shrinks.** A prewarm that judged the whole list to fit and started reading it was cancelled when the check just before or during the read found less memory, and kept nothing, unlike a prewarm that had started with only the front part. Available memory dips for a moment while a prewarm reads, so a list near the edge of available memory was cancelled again on each attempt. The blocks that 1.0.1 adds to the list moved a large game onto that edge. A full prewarm or supplement prewarm that stops for memory now reads the front part that fits the memory available at that moment, once, in the same run, and is handled like any front-part prewarm from there (log: `prewarm stopped by memory before the full list was read; reading the first N MiB of M MiB instead`). It does not read again when it stopped for another reason, such as a game starting. The reserve (`prewarm.min_free_ram_mib`), the 256 MiB margin, the cache budget, and the checks themselves are unchanged.
- **Supplement prewarm follows the current list size.** The list size remembered for a partial prewarm stayed at the old value after the list grew, which capped the front part at the old size. It is now raised to the current list size when that is larger.

## 1.0.1

Changes since 1.0.0. They fix cases, found in real play records, where the prewarm read less than it could or ran late. The effect on load time and stutter in real games has not been measured yet.

- **Prewarm list order and additions.** When the list has to be cut to fit memory, it now keeps, in this order: the ranges of files the game also writes that were first read early in play (up to the load boundary, or 120 seconds when the boundary is unknown), the ranges observed in play, the remaining prewarm-only ranges in first-read order, and guessed ranges. The early ranges are also read first; they used to sit at the end of the list and were cut first. The cache budget is divided between games by the real size of each prewarm list, so a partly relocated game no longer takes a larger part of the budget than it reads. Once the zone (the area the recorded blocks were moved to) has reached its size limit, blocks that are in the merged trace but no longer fit are added to the prewarm list instead, within the cache budget and without moving anything (log: `prewarm list gained N MiB of blocks outside the full zone`). The start stream log now also shows why it stopped at the load boundary.
- **Later trace windows.** The trace session of a game that may be traced now stays open from the first window until the game exits, the last extra window ends, or the limit is reached, instead of being opened again for each window. A new session could not tell which file a read belonged to when the game had opened the file earlier, so the extra windows saved nothing. Reads between windows are dropped at once and are not kept in memory, the read limit counts only reads inside a window, and files are written only after the game exits. Each window logs `trace window ended, N reads, P target processes, L events lost so far`. Games whose anti-cheat forbids tracing still get no session at all. The CPU cost of keeping the session open was not measured.
- **Memory checks.** The last check before reading and the choice of the front part both leave 256 MiB above the reserve, so a small change in available memory no longer cancels the whole prewarm. A front-part prewarm that loses memory while reading keeps what it read in list order as a partial prewarm, and the rest is read when available memory exceeds the amount already read plus 256 MiB plus the reserve. After a memory stop, supplement and retry leave the game alone for 2 minutes; when something was read, the waiting retry moves up to 2 minutes instead of the normal interval. Games that would be skipped anyway (in cooldown, running, or delayed after an update) no longer use any of the service-start limit. The reserve (`prewarm.min_free_ram_mib`) and the cache budget are unchanged.
- **Switching games.** While the 60-second exit check of a game that was just closed is still running, a prewarm started by a launcher may now read if the only registered game left on that disk is the one being checked; it is cancelled at once if that game comes back or another game starts. A trigger prewarm that was refused because a game was running is remembered and retried once when that game's process is first seen gone, if the launcher is still running and the refusal is less than 30 minutes old. Nothing is read from a disk while a game on it is actually running, as before.
- **Play record.** The end time, length, and totals of a play now stop at the time the service first saw the game process gone, so the 60-second exit check is not included.
- **Code layout.** The two largest service source files were split into files by role. Behavior is unchanged.

## 1.0.0

The first stable release. Changes since 0.9.0-beta.38:

- **Automatic updates.** The tray checks the official releases 5 minutes after it starts and every 24 hours. It downloads only an installer with a higher version, verifies its SHA-256 against the release asset digest or `SHA256SUMS.txt`, and installs quietly when the installed tray runs as administrator, no registered game is running, and no relocation is in progress. Otherwise it only notifies. `update.mode` (`auto`, `notify`, `off`; default `auto`) and `update.prerelease` control it, and the Update card on the Settings tab sets them. Downloads use HTTPS, an allowed host list, and a URL fixed to the release path of the official repository, with a size limit and a time limit. If the download folder or file is writable by a non-administrator, nothing is downloaded or run. After two install attempts of the same version that leave the version unchanged, the tray only notifies. A failed check is retried after 15 minutes, 1 hour, and 6 hours. The service does not download updates; its only network use is the shared-profile download (`ProfileFeed.cs`). Releases now include `SHA256SUMS.txt`, and the installer starts the tray again after a silent install. The earlier update code, which was not connected to the real distribution, was removed.
- **Per-game policy and pause.** `games[].mode` (`inherit`, `prewarm_only`, `relocate_only`, `off`) and `games[].paused` limit what the service does for a game. Prewarm work (prewarm, rewarm, supplement, start stream, service-start prewarm, SSD tier, first-run learning read-ahead) covers only games that allow prewarm, and the cache budget of an excluded game goes to the other games. Relocation work (automatic relocation, replanning, periodic reapply) covers only games that allow relocation; a game that does not allow it still gets a plan and prewarm, without moving files. A game that is off or paused is not traced. The anti-cheat gate and the no-pin rule apply regardless of the policy.
- **Relocation hours and the start stream switch.** With `auto.relocate_hours`, a new relocation and a periodic reapply start only in those local hours; a round that already started and left a journal is finished outside them. `auto.start_stream_enabled` set to `false` skips the start stream.
- **Settings in the tray.** The Games tab has a Game settings window for pause, policy, and the display names. The Settings tab has the start stream checkbox, the relocation hours (any time, or one start-to-end range that may cross midnight; other values in the file are kept and shown as custom), and a collapsed Advanced section with the cache budget, service-start prewarm count and limit, rewarm delay after exit, relocations per day, idle seconds, and the start stream time limit. All inputs are validated first and saved in one write, and a value set back to its default is removed from the file.
- **Last-play summary, diagnostics export, notification switch.** Each game on the Status tab shows when it was last played, the prewarm state at start, and the disk read statistics for the first 30 seconds, the first 120 seconds, and the whole session. These are disk read counters, not a load time or frame measurement. Export diagnostics on the Logs tab writes a ZIP with versions, settings, status files, and the last 2,000 lines of the logs, masks user names and credential-like values, stays under 20 MiB, and sends nothing over the network. `notifications.enabled` in `tray.json` and a checkbox on the Settings tab turn the notification pop-ups off. An empty game list explains what to do next.
- **Memory and tray refresh.** The service drops the trace cache, model snapshot, and temporary state of games removed from the settings, stops and waits for a trace session before releasing it, and keys its log suppression by fixed reason codes instead of creating a new key each time available memory changes. The supplement prewarm keeps the same 256 MiB margin as a normal prewarm. The tray rereads settings and status files on its 5-second refresh only when their size or modification time changed, and reads the last 200 log lines without loading the whole file. The before and after memory figures were not measured.
- **New icon.** A teal star and a tilted orbit ring on a navy rounded square, drawn separately for each size.

## 0.9.0-beta.25 to 0.9.0-beta.38

- **0.9.0-beta.38, supplement prewarm no longer rereads without progress.** When available memory was tight, the supplement prewarm planned a different amount each time, read the same front part again, and ended without reading more; in the observed case it read the same 1,305 MiB six times in ten minutes, about every 90 seconds. A supplement that does not increase the bytes read now waits for the retry interval (`rewarm_minutes`) before it reads again. This covers a normal end, a read list that ends below the planned cap, and a read that a memory check cut off without progress (a read cut off by a game start is continued as before). It retries once earlier when the memory-based cap grows by 256 MiB or more, and is judged again as soon as memory allows the whole hot set. On the full path, a read list processed without errors now counts as complete even when it is smaller than the hot set. The wait is released by real progress, a changed read list or game settings, a removed game, or a game start. The supplement log lines now show the accepted amount, the requested amount, and the error count.
- **0.9.0-beta.37, leftover cache budget used.** The prewarm budget was given to a game only when its whole observed part fit; a game that did not fit was left out of the remaining budget as well. In the observed case one game held 10,026 MiB of a 16,347 MiB budget, and the game that had been skipped by the service-start cap stayed at 0 MiB while the same "skipped" line was logged every minute. After the regular allocation, games that were left out now receive the remaining budget in rank order when at least 256 MiB is left, and prewarm their front part; the allocations of other games, the memory reserve, and the cache budget are unchanged. Supplement prewarm and the rewarm check use the same table. A budget refusal now moves the retry time forward by the normal retry interval instead of being judged again at every check, the refusal line is logged only when its state changes, and its wording says the budget is assigned rather than used.
- **0.9.0-beta.36, resident utilities excluded, prewarm shrinks to fit memory.** A desktop utility that stays running and does not load again, such as Wallpaper Engine, used to be registered as a game, so it was relocated, prewarmed, and rechecked for nothing, and the drive-recovery wait after its relocation held back real games. A fixed list of such utilities (Steam app IDs and their own executable names) is now left out of discovery, and an auto-registered entry on the list is unregistered after service start, even while it is running; entries you registered yourself are not touched and `auto.ignore_exes` is not changed. A game that is no longer registered is not prewarmed or pinned. Prewarm measures free memory again right before reading. If the list no longer fit, it was cancelled at 0 MiB (39 MiB short in the observed case); it now reads the front part that fits, with a 256 MiB margin, and the rest is supplemented later. The memory reserve and the cache budget are unchanged. A prewarm that was cancelled is read again even while the drive recovers from a relocation, like any other prewarm; further relocations still wait for recovery. The "nothing new to read" supplement line is logged only when its state changes. The drive-recovery check after relocation measured its baseline once at position 0 while the samples rotated through three other positions, so the speed difference between positions was counted as a shortfall. After a 43 MB move it stayed unconfirmed for 149 minutes and held back every relocation on that disk. The baseline is now the median of the same three positions, and besides 2 consecutive passes, at least 4 passes in the last 6 samples also count as recovered. When samples keep falling short the interval grows up to 8 minutes, and each sample logs the values and the reason behind its verdict.
- **0.9.0-beta.35, blocked reapply handed to auto relocation.** Reapply restores a layout that has drifted while the source files are unchanged. When it was rejected because another file occupied part of the zone (`zone_not_free`), it ended as an error and tried the same thing a day later; a game with no update and no new trace was never restored. Nothing had been moved, yet the planned bytes were charged to the daily budget and a drive-recovery wait started, which also held back other games on the same disk. Such a game now goes back to auto relocation, which keeps the moved parts and replans only the remaining part, under its existing holds and daily limits. It is handed over only when auto relocation is on, the game has a trace, and it is not stopped by a failed data check; otherwise it fails as before. A rejection before any move is recorded as 0 bytes. A reapply that stops at the per-round write cap keeps the 5-minute recheck, so the remaining part continues once the drive has recovered instead of at the normal interval (1440 minutes by default).
- **0.9.0-beta.34, unfinished prewarms retried, quicker drive-recovery check, blocked layout rechecked.** A prewarm of a traced game that was cancelled before it finished, or skipped by the service-start cap, now stays on a waiting list and is requested again once the disk has been idle for 60 seconds, no game is running on that disk, the drive is not recovering from a relocation, and the cache budget has room. Before, the game stayed cold until the next launcher trigger. The `prewarm cancelled` log line now carries the reason. Games without a trace are not retried this way. The drive-recovery check after relocation used to discard every sample faster than 1.25 times the baseline as a drive-cache hit, so a baseline that was measured low made recovery impossible to confirm and the wait ran to the hard limit (178 minutes in the observed case) while reading 192 MiB every 2 minutes. Samples above that ceiling at all three rotating positions in a row now count as recovered (about 6 minutes in that case), samples that cannot be judged are spaced out up to 8 minutes apart, and the discarded samples are summarized in one log line. A layout check that finds the layout unfinished but is blocked by a temporary condition (a running game, a busy disk, drive recovery, battery power, not idle long enough, the post-update delay) is repeated every 5 minutes instead of at the normal interval (1440 minutes by default), so a degraded layout is restored without waiting a day. The warning now says the service retries automatically.
- **0.9.0-beta.33, tray at logon, play records, observed-read prewarm.** When the tray is installed under Program Files, the installer registers a logon task named `AsterCache` that starts it with administrator rights, so no UAC prompt appears and you do not need to relaunch it as administrator. Other install folders keep the Start-folder shortcut. The management window draws the game list first and fills in the placement checks in the background, and the tray does not query disk placement while a game is running. While a game runs, the service samples the physical disk's cumulative read bytes, read count, and read latency once per second, and records summaries at 30, 60, 120, 300, and 600 seconds after the start and at exit, in `play record:` service log lines and in `play_samples.json`. It reads only the disk device counters, not the game's files or process, so it is measurement for comparing loading and stutter and does not make the game faster by itself. Each prewarm range is marked as observed in play or guessed from an engine profile. When the budget is short, the observed ranges of all games are filled first and the leftover goes to the guessed ranges. Lists written before this change get their source restored from the existing trace. With enough budget, the ranges read and their order do not change.
- **0.9.0-beta.32, relocation skips and prewarm cache budget.** Relocation leaves out sparse, compressed, and encrypted files, which it skips rather than moves. These files used to keep the "needs relocation to continue" status on screen, and relocation never finished. A plan whose zone is already at its maximum size is no longer planned again, and the screen says that the work resumes automatically. Prewarm's cache budget is half of physical RAM by default (`prewarm.max_cache_mib` sets it). Games triggered recently, such as by a launcher, are prewarmed first for 6 hours.
- **0.9.0-beta.31, tray redesign.** The windows, tabs, dialogs, and notifications now share one design system. Light and dark themes are both supported (`--theme light|dark` forces one; otherwise the Windows setting is followed). The Status tab became a status badge, number tiles, and per-game cards; the Games tab got colored status badges and buttons grouped in working order; the Settings tab got section cards and an aligned form. Colors, type sizes, and spacing are defined in one place, `csharp/src/AsterCache.Tray/Look.cs`.
- **0.9.0-beta.30, no duplicate work in one prewarm round.** The same prewarm list was computed three times inside one round; it is now computed once (and again when the plan, trace, prewarm-only list, or volatile-marker file changes). One line with per-phase elapsed times follows the prewarm completion log.
- **0.9.0-beta.29, game start stream and trace.** The start stream kept reading the disk after loading ended and caused stutter during play. It now stops at a loading boundary judged from the game process's read volume, and at the `auto.start_stream_cap_seconds` cap (default 120). After the first window, the trace also collects short late-play windows through the `auto.trace_late_*` settings, and saving happens after the game ends. Relocation, tier apply, supplement prewarm, and rewarm on the same disk start after the `auto.rewarm_after_exit_min` grace once a game exits.
- **0.9.0-beta.28, ORBIT refinements and service hardening.** The ORBIT decision rule gained a per-episode (per load scenario) delay allowance of `max(5%, 200 ms)`, and the decision path, calibration, and result judgment were improved. Disk read arbitration re-queries volumes it could not resolve, the disk activity sampling thread stops on service shutdown, and the load boundary watch now goes through the arbitration lease and the anti-cheat policy table. The tray menu and taskbar icon show four states (stopped, attention, working, healthy).
- **0.9.0-beta.27, tray message fix.** A game replanned after an update while keeping its learning was wrongly shown in the tray as "will be collected again on the next run".
- **0.9.0-beta.26, ORBIT field validation.** ORBIT prewarm order adjustment was measured on a real HDD and the decision path was sped up. `aster orbit mode|calibrate|model`, `aster orbit-bench run|summarize|rescore`, and `orbit_mode.json` were added.
- **0.9.0-beta.25, disk read arbitration and learning preservation.** Added per-physical-disk read arbitration (lease and yield), learning preservation that drops only the changed file ranges when a game updates, launcher display names, a per-feature policy decision table, and loading-time sample recording.

## Since beta.8

These changes landed on `main` since beta.8, including follow-ups from an external review.

- **ORBIT prewarm order adjustment.** For games with recorded traces, ORBIT changes the prewarm order in chunks of about 64 MiB only when the worst-case gain is positive and no episode exceeds the per-episode delay limit. The 2026-11-09 Call of Duty ABBA bench on the test PC's WD20EZAZ 2 TB SMR HDD cut median value-weighted prep time by 18.8% (10/10 pairs improved by at least 10%; sign-test p=0.001) and total read time by 0.1%, but increased the worst episode p95 by 13.1 s (the no-late-episode check, flag 4, failed). Rescoring with the new rule rejected the B candidate as `episode_regression`; its modeled worst delay was 55.5 s versus the measured 13.1 s. This is one game, one drive, and one session, so generalization is premature ([ORBIT: prewarm order adjustment](ORBIT.md)).
- **Parallel relocation.** On the test HDD, fewer samples, batched journal writes, and a sample right before the job cut relocation work from 186 s to 88 s, and eight parallel reads cut it to 41 s (4.5× against the 186 s). See [docs/RESULTS_SUMMARY.md](RESULTS_SUMMARY.md).
- **Drive recovery check.** After a game update, or after a relocation on an SMR drive, the service judges whether the drive has recovered before it starts the next job (`auto.post_relocate_recovery`).
- **Hands-off after install.** `aster status` and the manager window summary show one line: "found → bootstrap planned → relocated → prewarmed → average hit rate". While you are likely to play (a launcher is running or it is your usual play hour), the service reads 4 KiB every 10 minutes so the HDD does not spin down (`auto.keep_awake`, on by default; power settings are never changed). The read is skipped while a game on the same disk is running.
- **Prewarm yields to a running game.** On the same physical disk, a prewarm stops at the next 64 MiB batch boundary when a game starts. Disks are compared by physical disk number, not drive letter, so one HDD split into several volumes also counts as the same disk. On that disk, a game that reads under 1 MiB/s does not block prewarm of other games if the disk stays idle for 60 seconds (step 4 of [Stages](AUTO_MODE.md#stages) in Automatic mode). `auto.keep_stream_on_game_start` (default `false`, experimental) restores the old behavior. The start-up stream, which reads the hot set right after a game starts, also stops at the loading boundary (the 10-second moving read rate falls below 10% of its peak, at most 60 seconds in, judged from the game's read counter at 1-second intervals with no disk I/O) and at `auto.start_stream_cap_seconds` (default 120; 0 means no cap). It does not read the rest again while the game runs. If the disk is yielding at game start and the resident sample cannot be read, the start stream is skipped when a real sample was warm within `rewarm_minutes` and the plan has not changed (log `start stream skipped (recent probe warm ...)`). A rejected sample is not treated as cold.
- **System drive on an HDD.** Games on an HDD that is the Windows system drive are discovered and prewarmed only, not relocated or tiered (status "prewarm only (system drive)").
- **Metric name.** `tier0_probe_ready_ms` (formerly `load_boundary_ms`, still read) is the time a tier0 prewarm sample was found in RAM. It is not the time a game finishes loading.
