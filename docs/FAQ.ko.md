# 자주 묻는 질문과 문제 해결

> 짧게 답하고, 자세한 설명은 해당 문서로 안내합니다. 먼저 README 의 [시작하기](../README.ko.md#시작하기)를 보십시오.

## 자주 묻는 질문

**SSD 에 설치한 게임도 되나요?**
아니요. HDD 에 있는 게임만 대상입니다. SSD 에 있는 게임은 필요가 없으므로 건너뜁니다. Windows 가 있는 드라이브가 HDD 이면 그 게임은 발견과 예열만 하고(상태 "prewarm only (system drive)") 재배치하지 않습니다.

**하드디스크 수명에 나쁜가요?**
재배치는 게임 드라이브에 쓰지만 상한이 있습니다. 한 번에 SMR 드라이브는 최대 1 GiB(그 밖에는 2 GiB), 하루에 SMR 은 2 GiB(그 밖에는 8 GiB)이고, PC 가 한가할 때만 합니다. 그 뒤에는 주로 읽습니다. 드라이브 수명, 온도, 소음에 미치는 영향은 측정하지 않았습니다. [하드디스크에 미치는 영향과 주의사항](../README.ko.md#하드디스크에-미치는-영향과-주의사항)과 [게임 적용 안내](GAME_GUIDE.ko.md)를 보십시오.

**게임을 하는 동안 무엇을 하나요?**
게임이 시작되면 그 게임의 기록된 데이터를 최대 120초 동안 순서대로 읽고(로딩 경계에서 더 일찍 멈춥니다), 같은 디스크의 배경 작업(재배치, 예열, 다른 읽기)은 기다리거나 멈춥니다. 플레이 기록을 위해 게임 파일이나 프로세스가 아니라 디스크의 읽기 카운터를 표본으로 읽습니다. 트레이스가 허용된 게임에서는 기록 세션이 플레이 내내 열려 있지만, 읽기는 기록 창 안에서만 저장합니다. 게임과 무관한 프로그램도 그 세션 동안 메모리를 양보합니다([배경 메모리 양보](AUTO_MODE.ko.md#배경-메모리-양보)). 단계는 [자동 모드](AUTO_MODE.ko.md), 설정은 [설정](CONFIGURATION.ko.md)에 있습니다.

**지우면 어떻게 되나요? 게임을 목록에서 빼면요?**
프로그램을 제거하면 먼저 SSD 보조 저장의 링크를 되돌린 뒤 프로그램과 서비스를 지웁니다. 데이터 폴더 `%ProgramData%\AsterCache` 는 남습니다. 이미 옮긴 조각은 되돌려지지 않으며 어느 쪽이든 파일 내용은 그대로입니다. 예전 배치로 복원하려면 먼저 게임 탭에서 **되돌리기**를 누르십시오. 게임을 목록에서 빼도 파일은 그대로입니다. [사용법](USAGE.ko.md#자주-하는-작업)을 보십시오.

**RAM 을 얼마나 쓰나요?**
예열한 데이터는 일반 파일 캐시입니다. 모든 게임을 합쳐 기본으로 물리 RAM 의 절반 이하이며(`prewarm.max_cache_mib`), 예열 뒤에도 가용 RAM 이 4 GB 이상 남을 때만 실행합니다. 다른 프로그램이 메모리를 필요로 하면 Windows 가 캐시를 회수합니다. 가용 메모리에 예열 목록 전체가 들어가지 않으면 들어가는 앞부분만 읽되 4 GB 예비량보다 256 MiB 를 더 비워 두고, 나머지는 메모리가 다시 날 때 읽습니다. 예비량과 캐시 예산을 낮추지는 않습니다. [설정](CONFIGURATION.ko.md)을 보십시오. 트레이와 서비스도 예전에 붙들고 있던 메모리를 풀어 줄였습니다(트레이는 로그 전체를 읽지 않고, 서비스는 등록 해제된 게임의 남은 데이터를 정리합니다). 전후 수치는 재지 않았습니다.

**게임을 켠 뒤 열어 두었던 프로그램이 잠깐 느려졌습니다. 왜 그런가요?**
배경 메모리 양보 때문입니다. 게임 세션이 시작되면 AsterCache 가 게임과 무관한 프로그램의 작업 집합을 비우고 메모리 우선순위를 낮춰, Windows 가 예열 캐시보다 그 프로그램의 메모리를 먼저 가져가게 합니다. 비워진 프로그램은 다시 쓸 때 페이지를 다시 가져와야 해서 잠깐 느려질 수 있습니다. 시험에서는 2 GiB 를 다시 만지는 데 0.8초가 걸렸습니다. 그 메모리를 먼저 재사용하므로 세션 동안 배경 프로그램이 약간 느려질 수도 있습니다. 의도된 동작이며 게임이 끝나면 우선순위를 되돌립니다. 게임·런처·안티치트 프로그램은 건드리지 않습니다. 실제 플레이에서 얼마나 달라지는지는 재지 않았습니다. [배경 메모리 양보](AUTO_MODE.ko.md#배경-메모리-양보)를 보십시오.

**배경 메모리 양보를 끄려면 어떻게 하나요?**
`config.json` 에 `"memory": {"background_yield": false}` 를 넣으십시오. 설정 탭에는 스위치가 없습니다. 서비스가 5초 안에 파일을 다시 읽으며, 게임 세션 중에 껐으면 다음 30초 점검 때 우선순위를 되돌립니다. 이전 버전으로 되돌릴 때는 1.0.2 이하 버전이 `memory` 키를 거부하므로 먼저 지우십시오([설정](CONFIGURATION.ko.md)).

**안티치트 게임에서 안전한가요?**
AsterCache 는 게임 프로세스에 손대지 않습니다. 자기 프로세스에서 파일을 읽고, Windows 이벤트 추적으로 파일 읽기를 관찰하며, 게임이 종료된 뒤에만 파일을 옮깁니다. 다른 프로그램에 하는 일은 게임 세션 동안 게임과 무관한 프로그램의 작업 집합을 비우고 메모리 우선순위를 낮추는 것뿐이며, 게임·런처·안티치트 프로세스는 열지 않습니다([안티치트 호환](ANTICHEAT.ko.md)). 다만 통제된 검증은 하지 않았고 한 PC 의 사용 기록만 있으며, 계정 제재 여부는 보증하지 않습니다. 안티치트 게임은 플레이 전에 자동 모드를 끄거나 `auto.ignore_exes` 에 넣으십시오. [안티치트 호환](ANTICHEAT.ko.md)을 보십시오.

**게임 업데이트 뒤에는 어떻게 되나요?**
패치로 파일이 바뀌면 저장해 둔 계획과 맞지 않을 수 있습니다. AsterCache 는 옮기기 전에 계획을 확인해 바뀐 파일은 건너뛰고, 게임이 꺼져 있는 동안 5분마다 배치가 흐트러졌는지 보고 흐트러졌으면 계획을 다시 적용합니다. 자동 모드에서는 바뀐 파일을 다시 학습하며, 계획 데이터의 절반 이상이 바뀌었으면 트레이스와 계획 전체를 `.stale` 로 치웁니다. 실제 게임 업데이트로는 아직 시험하지 않았습니다. [자동 모드](AUTO_MODE.ko.md)를 보십시오.

**게임을 끄고 곧바로 다른 게임을 켰는데 두 번째 게임이 느리게 로딩됩니다. 예열은 됐나요?**
이제는 되어야 하지만 실제 플레이에서는 아직 확인하지 않았습니다. 게임은 프로세스가 사라지고 60초가 지나야 꺼진 것으로 보는데, 그동안 런처가 시작한 예열이 거절되어 뒤로 밀리곤 했습니다. 이제 그 디스크에 남은 게임이 이 확인을 기다리는 게임뿐이면 런처가 시작한 예열이 읽을 수 있습니다. 게임이 실제로 실행 중일 때는 읽지 않습니다. 첫 번째 게임이 아직 실행 중이라 런처의 예열이 거절됐다면, 런처가 아직 열려 있는 한 그 게임이 사라진 것을 처음 본 때 한 번 다시 시도합니다. `service.log` 의 `prewarm triggered by` 와 `retrying the refused trigger prewarm` 줄을 보십시오([자동 모드](AUTO_MODE.ko.md#4-예열)).

**SMR 인지 CMR 인지가 중요한가요?**
SMR 드라이브(WD20EZAZ) 1대만 측정했고 CMR 은 측정하지 않았습니다. 헤드 이동을 줄이는 것이므로 둘 다 도움이 될 것으로 보지만 검증하지 않았습니다. SMR 은 처음 한 번 옮길 때 쓰기가 느려질 수 있습니다.

**첫 실행이 꼭 필요한가요?**
재배치에는 게임이 실제로 읽는 기록(트레이스)이 필요합니다. 첫 실행 전에는 맞는 공유 프로필(저장소가 준비 중이라 지금은 건너뜁니다)을 먼저 찾고, 그다음 게임의 Windows 프리페치 기록을 봅니다. 둘 다 부트 트레이스가 되어 재배치를 일찍 시작할 수 있습니다. 예열은 기록이 없어도 합니다. 설치 폴더 전체가 RAM 예산 안인 게임은 폴더 전체를, 더 큰 게임은 엔진의 파일만 예열하며, 효과는 아직 측정하지 않았습니다. 다른 PC 에서 만든 기록은 `aster profile import` 로 가져올 수 있습니다([사용법](USAGE.ko.md#aster-명령)).

**처음 실행도 빨라지나요?**
아니요. 첫 실행은 읽기 기록만 하고, 최대 효과는 재배치와 예열이 끝난 두 번째 실행부터입니다. 첫 실행 선행 읽기는 실험 기능이며, E7~E7f 측정에서 이득이 없어 기본 꺼짐입니다(`auto.learn.enabled`, [RESULTS_SUMMARY](RESULTS_SUMMARY.ko.md) 참고).

**자동 업데이트를 끌 수 있나요?**
네. 설정 탭의 **업데이트** 카드에서 **끄기**를 고르거나, 설치하지 않고 알림만 받으려면 **알림만**을 고르십시오. 같은 설정이 `config.json` 의 `update.mode`(`auto`, `notify`, `off`)입니다. `update.prerelease` 가 `true` 가 아니면 프리릴리스는 제안하지 않습니다.

**자동 업데이트는 무엇을 내려받고, 언제 설치하나요?**
트레이는 시작 5분 뒤와 그 뒤 24시간마다 공식 GitHub 릴리스를 확인합니다. 현재보다 새로운 버전의 `AsterCache-v<버전>-win-x64-setup.exe` 만 GitHub 에서 받고, 설치 프로그램의 SHA-256 을 릴리스의 digest 나 `SHA256SUMS.txt` 와 대조합니다. 둘 다 없으면 설치하지 않습니다. 조용한 설치는 설치된 트레이를 관리자 권한으로 실행 중이고, 등록된 게임이 실행 중이 아니며, 재배치가 진행 중이 아닐 때만 합니다. 설치 프로그램은 `/SILENT` 로 실행되고 끝나면 트레이가 다시 뜹니다. 그 밖의 경우에는 새 버전을 알리기만 하거나, zip 으로 실행했거나 관리자 권한이 없으면 릴리스 페이지를 엽니다. 같은 버전의 설치를 두 번 시도해도 설치된 버전이 바뀌지 않으면 그 뒤로는 알리기만 합니다. 확인이나 받기가 실패하면 15분, 1시간, 6시간 뒤에 다시 시도합니다. 서비스는 네트워크를 쓰지 않습니다. 이 조용한 설치는 아직 실기기에서 확인하지 않았습니다.

**진단 ZIP 에는 무엇이 들어가나요?**
관리 창의 **로그** 탭에서 **진단 내보내기**를 누르면 고른 위치에 ZIP 파일 하나를 만듭니다. `info.txt`(트레이·서비스·OS 버전, .NET 런타임), `config.json`, `tray.json`, `auto_status.json`, `prewarm_status.json`, `play_samples.json`, `logs/service.log` 와 `logs/tray.log` 의 마지막 2,000줄, 그리고 무엇을 넣고 무엇을 뺐는지 이유와 함께 적은 `manifest.txt` 가 들어갑니다. 합계는 20 MiB 이하입니다. 게임 폴더는 읽지 않습니다. 경로와 본문의 사용자 이름, URL 의 사용자 정보, 토큰 모양의 문자열, token·secret·password 등이 이름에 든 JSON 값은 자리 표시로 가립니다. 가림은 규칙 기반이라 완전하지 않으므로 공유하기 전에 내용을 확인하십시오. 네트워크로는 아무것도 보내지 않습니다.

**게임 하나만 제외할 수 있나요?**
네. **게임** 탭에서 게임을 고르고 **게임 설정**을 누른 뒤, **일시 중지**를 켜거나 정책을 **사용 안 함**으로 바꾸십시오. 둘 다 그 게임에 새 작업을 시작하지 않습니다. 다시 등록되지 않게 하려면 **제거**를 누르거나 그 exe 를 `auto.ignore_exes` 에 넣으십시오. 게임을 목록에서 빼도 파일은 그대로 남습니다.

**Wallpaper Engine 처럼 계속 켜져 있는 프로그램도 최적화하나요?**
아니요. 게임이 아니고 한 번 띄우면 계속 켜져 있는 데스크톱 유틸리티(Wallpaper Engine, YoloMouse, Lossless Scaling, OBS Studio, SteamVR 등)는 자동 등록에서 제외하며, 이미 등록된 항목은 서비스가 시작된 뒤 한 번 등록 해제합니다. 그 밖의 프로그램은 게임 탭에서 제거하면 다시 등록되지 않습니다.

**파일이 망가질 수 있나요?**
옮길 때마다 SHA-256 으로 검증하고, 되돌릴 수 있는 저널에 기록합니다. 그래도 AsterCache 는 실제 데이터를 옮기므로 중요한 드라이브는 먼저 백업하십시오. [안전 장치](DEVELOPMENT.ko.md#안전-장치)를 보십시오.

## 문제 해결

**설정을 저장할 권한이 없다고 나옵니다.**
데이터 폴더는 관리자만 쓸 수 있습니다. 관리 창을 관리자 권한으로 다시 실행하십시오.

**게임을 추가하거나 제거했는데 반영되지 않습니다.**
서비스는 `config.json` 을 5초마다 다시 읽으므로 보통 다시 시작하지 않아도 반영됩니다. 새 설정이 검증에 실패하면 옛 설정을 유지하고 이유를 `service.log` 에 남깁니다.

**트레이에 "서비스 재설치 필요"가 표시됩니다.**
트레이 갱신은 서비스 실행 파일을 바꾸지 않습니다. 설치 프로그램으로 서비스를 다시 설치하십시오.

**재배치 명령이 `not_admin` 으로 끝납니다.**
재배치, 되돌리기, 볼륨 명령은 관리자 PowerShell 에서 실행하십시오.

**예열이 실행되지 않았습니다.**
건너뛴 이유는 `service.log` 에 남습니다. 가용 RAM 이 부족하거나, 게임이 실행 중이거나, 쿨다운 중이거나, 계획 파일이 없는 경우입니다. 게임 실행 여부는 그 게임에 등록된 실행 파일 이름으로만 봅니다. `aster status` 의 `prewarm` 항목에서도 확인할 수 있습니다.

**예열이 `partial` 로 끝나거나 로그에 메모리 때문에 멈췄다고 나옵니다.**
가용 메모리에 예열 목록 전체가 들어가지 않아 앞부분만 읽은 것입니다. 읽는 도중 메모리가 예비량 아래로 내려가면 예열이 멈추고, 앞부분을 목록 순서대로 읽던 중이었다면 그때까지 읽은 만큼은 부분 예열로 남습니다. 나머지는 가용 메모리가 읽은 양 + 256 MiB + 예비량(`prewarm.min_free_ram_mib`, 기본 4,096 MiB)을 넘으면 읽으며, 멈춘 뒤 2분 안에는 읽지 않습니다. 예비량과 캐시 예산은 이 때문에 낮추지 않습니다. 목록 전체를 읽은 예열은 `partial` 로 기록되지 않습니다. 저장된 계획이 아직 옮기지 못한 부분만 담고 있는 게임에서는 예전 버전이 그렇게 기록하기도 했습니다(예: `partial 1164/1306 MiB`). `service.log` 에서 볼 줄은 다음과 같습니다.
- `<게임>: prewarm stopped by memory; kept the N of M MiB read as partial`
- `<게임>: prewarm skipped (stopped by memory less than 2 min ago) [<사유>]`
- `<게임>: prewarm done (...): ..., room X MiB, available Y MiB` 와 `rewarm check: cold (..., available N MiB)`. 그 시점의 메모리를 보여 줍니다.
- `<게임>: prewarm list gained N MiB of blocks outside the full zone`. 가득 찬 존에 더는 들어가지 않는 블록을 아무것도 옮기지 않고 예열 목록에 더했다는 뜻입니다.

**로그의 `background yield` 줄은 무슨 뜻인가요?**
[배경 메모리 양보](AUTO_MODE.ko.md#배경-메모리-양보)가 남기는 줄이며 프로그램 이름이나 경로 없이 개수와 크기만 담습니다(프로그램 이름은 경로 없이, 세션이 도는 동안의 `background_yield.json` 에만 적힙니다).
- `background yield (trigger): trimmed N processes (X MiB working set), memory priority lowered for M, available B -> A MiB`: 런처나 다른 트리거 프로그램이 예열을 시작할 때 남습니다. N개 프로그램의 작업 집합을 비웠고(합계 X MiB, 32 MiB 이상인 프로그램만 비움), M개 프로그램의 메모리 우선순위를 낮췄으며, 가용 메모리는 B MiB 에서 최대 3초 기다린 뒤 A MiB 가 됐다는 뜻입니다. `trimmed 0` 은 대상이 없었거나 하나도 열지 못했다는 뜻입니다.
- `background yield (game started): trimmed N processes (X MiB working set), memory priority lowered for M, available B MiB`: 등록 게임의 실행 파일이 시작될 때 같은 일을 기다리지 않고 해서 앞의 값만 있습니다. 60초 안에 세션이 이미 시작됐으면 남지 않습니다.
- `background yield: trimmed again N processes (X MiB working set regrown by D MiB)`: 게임 중에 고른 프로그램들의 작업 집합 합이 1,024 MiB 이상 다시 늘어서 한 번 더 비웠다는 뜻입니다.
- `background yield ended: memory priority restored for N processes`: 세션이 끝났고 N개 프로그램의 우선순위를 원래대로 되돌렸다는 뜻입니다.
- `background yield: restored memory priority for N processes left by the previous run`: 서비스가 시작될 때, 직전 실행이 비정상 종료했던 경우입니다.
- `background yield state file not written: <예외 형식>`: `background_yield.json` 을 쓰지 못해서 그때는 우선순위를 낮추지 않았다는 뜻입니다(작업 집합은 그래도 비웁니다). 오류와 함께 남는 `background yield failed` 는 그 밖의 실패이며 서비스의 나머지에는 영향이 없습니다.

**로그의 `trace window ended` 줄은 무슨 뜻인가요?**
`<게임>: trace window ended, N reads, P target processes, L events lost so far` 는 기록 창이 닫힐 때마다 남습니다. `N` 은 그 창에서 저장한 읽기 수, `P` 는 창이 닫힐 때 살아 있던 게임 프로세스 수이며, `N` 이 0 인 추가 창은 아무것도 저장하지 못한 것입니다. `L` 은 트레이스 세션이 시작된 뒤 놓친 이벤트의 누적 수입니다. 세션이 멈출 때 남는 `trace session stopped: ... M reads dropped (name unresolved)` 는 어느 파일인지 알아내지 못한 읽기 수입니다. [자동 모드](AUTO_MODE.ko.md#2-읽기-기록트레이스)를 보십시오.
