# ORBIT: 예열 순서 조정

> README 의 [작동 원리](../README.ko.md#작동-원리)에서 이어지는 상세 설명입니다.

ORBIT 은 게임의 예열이 데이터를 어떤 순서로 읽을지 정하는 계산입니다. 바뀌는 것은 순서뿐입니다. 읽는 데이터와 읽는 양은 그대로입니다.

## 왜 있나

예열은 게임의 핫 데이터를 정해진 순서로 RAM 에 읽어 둡니다. 예열이 아직 도는 중에 게임이 시작되면 예열이 끊기고, 그때까지 읽은 것만 도움이 됩니다. 로딩마다 필요한 데이터(공통 블록과 로딩 앞부분 tier0)는 이미 먼저 읽습니다. 남는 것은 뒤쪽, 예를 들어 예열 도중 중단이 잦은 게임의 맵 구간입니다. ORBIT 은 이 64 MiB 안팎 구간들을 다른 순서로 읽으면 실제 플레이에 필요한 데이터가 더 일찍 준비되는지를 따집니다.

## 어떻게 판단하나

1. **같이 읽히는 것을 익힙니다.** 플레이 기록에서 같이 읽히는 데이터 묶음(에피소드, 예를 들어 맵 하나의 로딩)을 뽑고, 각 에피소드가 얼마나 자주 나오는지 셉니다.
2. **중단 횟수를 셉니다.** 예열 도중 게임이 시작돼 예열이 끊기는 빈도를 셉니다.
3. **디스크를 잽니다.** 서비스가 자기 예열 직전에 디스크를 조금 읽어 탐색 지연과 전송률의 범위를 알아냅니다.
4. **다른 순서를 따져 봅니다.** 64 MiB 안팎 구간 단위로 후보 순서를 계산하고, 각각을 지금 순서와 비교합니다. 앞쪽 tier0 구간은 고정합니다.
5. **안전할 때만 바꿉니다.** 잰 범위 안에서 가장 나쁜 경우에도 이득이 있고, 각 에피소드의 준비 시각이 기준 순서보다 `max(5%, 200 ms)` 넘게 늦어지지 않을 때만 후보를 씁니다. 아니면 전과 똑같이 예열하고, 계획 파일에 사유(`episode_regression`)를 기록합니다. 결정 전체의 예산은 500 ms 입니다.

<details>
<summary>세부: 디스크 측정, 방법, 이득이 나올 수 있는 곳</summary>

- **디스크 측정.** 스트림당 12 MiB 남짓, 캐시를 거치지 않는 읽기입니다(탐색 지연용 작은 읽기 12회와 전송률용 4 MiB 읽기 3회).
- **방법.** 표준 기법(빔 탐색, 구간 하한, 분할 conformal 구간, 이항 정확 구간)을 이 문제에 맞게 엮은 것입니다.
- **이득이 나올 수 있는 곳.** 공통 블록과 tier0 는 이미 먼저 읽으므로, 이득은 예열 도중 중단이 잦은 게임의 맵 구간에 한정될 수 있습니다. 중단이 관측되지 않은 게임에서는 항상 지금 순서를 씁니다(설계 의도).

</details>

## 언제 켜지나

아래가 모두 맞아야 합니다. 맞지 않는 동안은 지금 순서를 씁니다.

| 조건 | 내용 |
|---|---|
| 모드 | `active`(기본). [모드와 안전](#모드와-안전)을 보십시오. |
| 기록이 있는 게임 | 게임에 트레이스와 예열 목록이 있습니다. |
| 디스크 보정 | 그 디스크의 예열 스트림 38회분(지표마다 적합 19회 + 보정 19회). |
| 에피소드 모형 | 유효 플레이 기록 3회 이상과 중단 사건 1회 이상. |

보정을 빨리 얻으려면 서비스를 멈추고 등록 게임을 모두 끈 상태에서 `aster orbit calibrate --disk <문자> [--samples N]`를 씁니다. 장치 구간이 생기면 멈추며, 보통 40개 전후, 약 7분입니다.

<details>
<summary>세부: calibrate 명령이 표본을 뽑는 방식</summary>

- 10초 간격으로 최대 N개(기본 60)를 잽니다.
- 예열 목록이 아직 없는 게임은 건너뛰고, 그 디스크의 허용 게임 파일을 합친 풀에서 표본을 뽑습니다.
- 최근 읽은 위치에서 64 MiB 안쪽은 피해 드라이브 캐시 적중을 막습니다.
- 이 부트스트랩 표본은 같은 시간대에 모은 것이라 커버리지 주장이 약합니다. 운영 중 표본이 38개 쌓이면 대체됩니다.
- 기존 플레이 기록으로 에피소드 모형을 만들려면 서비스를 멈추고 등록 게임을 모두 끈 상태에서 `aster orbit model --game <이름>` 을 실행합니다.

</details>

## 켜졌는지 확인하는 법

- **로그.** 결정마다 `service.log` 에 한 줄이 남습니다. 예:

  ```
  <게임>: orbit active, applied False, reason no_episode_model, blocks <n>, segments <n>, <ms> ms
  <게임>: orbit shadow, applied False, reason no_device_calibration, blocks <n>, segments <n>, <ms> ms
  ```

  `applied True` 는 순서를 바꿨다는 뜻입니다. 모드가 자동으로 `shadow` 로 내려가면 `orbit mode changed to shadow: <사유>` 줄이 남습니다.
- **상태 파일.** `auto_status.json` 의 `shadow_orbit` 에 `mode`, `applied`, `device_n`, `value_runs`, `lambda`, `d_low`, `orbit_reason` 키가 있습니다.
- **계획 파일.** `<plans>\<게임>.orbit.json` 에 에피소드, 중단 위험, 거부 사유를 포함한 최근 결정이 남습니다.

<details>
<summary>세부: reason 의 뜻</summary>

- `no_device_calibration`: 디스크 보정이 아직 없음.
- `no_episode_model`: 쓸 만한 에피소드 모형이 아직 없음.
- `no_hazard_model`: 중단 비율이 아직 없음.
- `episode_regression`: 어떤 에피소드가 늦어져 후보를 거부함.
- `timeout`: 500 ms 예산 초과.
- `calculation_error`: 계산 실패. 2회 연속이면 모드가 `shadow` 로 내려갑니다.

</details>

## 모드와 안전

`aster orbit mode off|shadow|active` 로 모드를 바꿉니다.

| 모드 | 동작 |
|---|---|
| `off` | 계산도 하지 않습니다. |
| `shadow` | 계산과 기록만 하고 순서는 그대로 둡니다. |
| `active` | 기본. 위 규칙이 허용하면 새 순서를 씁니다. |

유의한 악화, 보정 이탈 2회 연속, 계산 예외 2회 연속이면 자동으로 `shadow` 로 내려가며, 자동으로 다시 올라가지 않습니다. 보정 읽기는 게임이 없고 디스크가 한가할 때만 합니다. `config.json` 에 새 키가 없습니다.

<details>
<summary>세부: 자동 강등, 안전 규칙</summary>

- 설정 파일이 없으면 `active`, 깨졌으면 `shadow` 입니다.
- 강등 조건: 기존 `ProbeReadyMs` 대리 지표에서 부트스트랩으로 유의한 악화가 확인됨, 보정 이탈(커버리지 감시 실패) 2회 연속, 계산 예외 2회 연속.
- 보정 읽기는 디스크 읽기 중재 대여 안에서, 게임 미실행과 디스크 유휴일 때만 합니다. 안티치트 정책이 새 예열을 허용하는 게임(안티치트 없음 또는 Vanguard)에만 합니다.

</details>

## 파일

| 파일 | 내용 |
|---|---|
| `<데이터 폴더>\orbit_mode.json` | 모드 |
| `<데이터 폴더>\disk_model.json` | 디스크별 보정 표본 |
| `<plans>\<게임>.orbit.json` | 에피소드, 중단 위험, 최근 결정 |

이 파일들을 지우면 이전 판과 같게 동작합니다. 이전 판은 이 파일과 `auto_status.json` 의 새 키를 무시합니다.

<details>
<summary>세부: orbit.json 버전 2</summary>

- `<게임>.orbit.json` 은 버전 2 부터 파일 경로 사전과 에피소드별 블록 구간(시작 블록, 개수)으로 저장합니다. 같은 입력에서 39 MB → 2.7 MB 로 줄었고 읽기는 수십 ms 입니다.
- 버전 1 파일은 읽을 때 자동 변환합니다. 결정 예산(500 ms)은 그대로입니다.

</details>

## 한계와 주의

- 측정된 이득은 게임 1종·드라이브 1대·한 세션에 한정됩니다(아래 참고). 다른 게임이나 드라이브로 일반화하기는 이릅니다.
- 자동 강등에 쓰는 `ProbeReadyMs` 대리 지표는 실제 준비 시각이 아닙니다. 강등은 시드를 고정한 1,000회 재표본 부트스트랩을 쓰며, 후보를 자동으로 채택하지는 않습니다.
- 실제 서비스에서의 결정 결과는 아직 확인되지 않았습니다.
- 순서만 바꿉니다. 읽는 데이터가 줄지는 않습니다.

## 측정 기록

벤치는 기준 순서와 ORBIT 순서에서 에피소드 데이터가 얼마나 일찍 준비되는지 비교합니다(서비스 정지, 게임 종료, 회마다 standby 비우기, ABBA 교차).

2026-11-09 시험 PC(Call of Duty, ABBA 10쌍 20회) 결과입니다.

| 확인 항목 | 기준 | 결과 |
|---|---|---|
| 준비 시각 단축(플래그 2) | 가치 가중 준비 시간 10% 이상 단축, p<0.05 | 중앙값 18.8% 단축. 10/10쌍이 10% 이상 개선, 부호 검정 p=0.001. 통과 |
| 총 읽기 시간(플래그 3) | 5% 이상 악화 없음 | 0.1% 단축. 통과 |
| 늦어지는 에피소드 없음(플래그 4) | 어떤 에피소드도 p95 기준 max(기준선의 5%, 200 ms) 이상 늦어지지 않음 | 최악 에피소드 p95가 13,096 ms 늘어남. 실패 |

준비 시간은 줄었지만 일부 에피소드는 늦어졌습니다. 같은 날 앞서 돌린 실행의 값(21.3% 단축, 최대 지연 18.2초)과 전체 표는 [결과 요약](RESULTS_SUMMARY.ko.md#orbit-예열-순서-벤치-2026-11-09)에 있습니다. 새 규칙 재채점은 B 후보를 `episode_regression`으로 거부했습니다. 모형 추정 최악 에피소드 지연은 55.5초로 실측 p95(13.1초)의 약 4.2배였고, 이는 보수 방향입니다.

<details>
<summary>개발자용: 다시 측정하는 방법</summary>

`aster orbit-bench run|summarize`와 `csharp\scripts\cs_orbit_bench.ps1`(관리자 권한)로 벤치를 돌립니다.

**순서**

1. 입력을 먼저 만듭니다. 새로 설치한 직후라면 서비스를 멈추고 모든 등록 게임을 끈 상태에서 `aster orbit model --game <이름>` 으로 기존 플레이 기록에서 `<plans>\<게임>.orbit.json` 을 만든 뒤, `aster orbit calibrate --disk <문자>` 를 실행합니다.
2. 예열 중단 기록이 없으면 B 팔 후보에만 `--lambda-per-min`(기본 1.0, 분당 1회 중단 가정)을 씁니다. 이 값은 실제 서비스 결정에는 쓰지 않습니다. 결과 파일에는 `lambda_source`(`model` 또는 `bench_override`)가 기록됩니다.
3. 기존 측정 파일을 새 에피소드 모형으로 다시 채점하고(원본은 보존), 요약 명령으로 플래그 2~4를 확인합니다.

   ```powershell
   aster orbit-bench rescore --orbit <orbit.json> --in <run.json>... --out-dir <rescored>
   aster orbit-bench summarize --in <rescored\run.json>...
   ```

**재채점에 대한 참고**

- 저장된 op 완료 시각으로 에피소드 지표를 다시 계산하며 디스크를 다시 읽지 않습니다.
- 현재 `Decide` 규칙으로 후보를 다시 판정해 B 후보 채택 여부, 사유, 모형 추정 최악 에피소드 지연도 출력합니다.
- ABBA 묶음이 완전하면 실측 플래그 4의 p95 지연과 통과 여부를 모형 추정치와 함께 보여 줍니다.
- 모형(에피소드)은 `--orbit` 파일에서 읽고, 장치 보정(`disk_model.json`)과 게임 설정만 데이터 폴더에서 읽습니다. 데이터 폴더 밖 파일만으로는 판정이 `game_settings_unavailable` 로 끝나며, `--data-dir <폴더>` 는 재채점이 읽을 데이터 폴더 사본을 지정합니다.
- `--budget-ms <ms>` 는 재채점에만 쓰는 결정 예산을 지정합니다(기본 500 ms, 서비스는 항상 500 ms).

</details>
