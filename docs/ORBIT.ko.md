# ORBIT: 예열 순서 조정

> README 의 [작동 원리](../README.ko.md#작동-원리)에서 이어지는 상세 설명입니다.

기록이 있는 게임의 핫 집합 예열에서, 지금 예열 순서를 기준으로 두고 64 MiB 안팎 구간 단위로 순서를 바꿨을 때 이득이 있는지 계산합니다. 앞쪽 tier0 구간은 고정합니다. 읽는 데이터 양과 집합은 바뀌지 않고 순서만 바뀝니다.

- 플레이 기록에서 같이 읽히는 묶음(에피소드)과 그 발생 비율을 뽑습니다. 예열 도중 게임이 시작돼 예열이 끊기는 빈도도 셉니다.
- 서비스가 자기 예열 직전에 디스크를 조금(스트림당 12 MiB 남짓, 캐시를 거치지 않는 읽기) 재서 탐색 지연과 전송률의 범위를 보정합니다. 이 범위 안 가장 나쁜 경우에도 이득이 있고, 각 에피소드의 준비 시각 악화가 기준 순서 대비 `max(5%, 200 ms)` 이내일 때만 순서를 바꿉니다. 결정 예산은 500 ms로 유지합니다. 후보가 탈락하면 계획 파일에 `episode_regression` 사유와 최악 에피소드 지연을 기록합니다.
- 방법은 표준 기법(빔 탐색, 구간 하한, 분할 conformal 구간, 이항 정확 구간)을 이 문제에 맞게 엮은 것입니다. 공통 블록과 tier0 는 이미 먼저 읽으므로, 이득은 예열 도중 중단이 잦은 게임의 맵 구간에 한정될 수 있습니다. 중단이 관측되지 않은 게임에서는 항상 지금 순서를 씁니다(설계 의도).

**언제 켜지나.** 보정에는 예열 스트림 38회분(지표마다 적합 19회 + 보정 19회)이 쌓여야 합니다. 빨리 켜려면 `aster orbit calibrate --disk <문자> [--samples N]`를 씁니다. 서비스 정지와 등록 게임 모두 종료 상태에서 10초 간격으로 최대 N개(기본 60)를 재고, 장치 구간이 생기면 멈춥니다(보통 40개 전후, 약 7분). 예열 목록이 아직 없는 게임은 건너뛰고, 그 디스크의 허용 게임 파일을 합친 풀에서 표본을 뽑습니다. 최근 읽은 위치에서 64 MiB 안쪽은 피해 드라이브 캐시 적중을 막으며, 장치 구간이 생길 때까지 계속 잽니다(기본 상한 60개). 이 부트스트랩 표본은 같은 시간대에 모은 것이라 커버리지 주장이 약합니다. 운영 중 표본이 38개 쌓이면 대체됩니다. 에피소드는 유효 플레이 기록 3회 이상과 중단 사건 1회 이상이 필요합니다.

**모드.** 기본은 `active`입니다. `aster orbit mode off|shadow|active`로 바꿉니다. `off`는 계산도 하지 않습니다. `shadow`는 계산과 기록만 하고 순서는 그대로 둡니다. 설정 파일이 없으면 `active`, 깨졌으면 `shadow`입니다. 기존 `ProbeReadyMs` 대리 지표에서 부트스트랩으로 유의한 악화가 확인되거나, 보정 이탈(커버리지 감시 실패) 또는 계산 예외가 2회 연속이면 자동으로 `shadow`로 내려가며, 자동으로 다시 올라가지 않습니다.

**안전.** 보정 읽기는 디스크 읽기 중재 대여 안에서, 게임 미실행과 디스크 유휴일 때만 합니다. 안티치트 정책이 새 예열을 허용하는 게임(안티치트 없음 또는 Vanguard)에만 합니다. `config.json` 에 새 키가 없습니다.

**새 파일 3개.** `<데이터 폴더>\orbit_mode.json`(모드), `<데이터 폴더>\disk_model.json`(디스크별 보정 표본), `<plans>\<게임>.orbit.json`(에피소드·중단 위험·최근 결정). `<게임>.orbit.json` 은 버전 2 부터 파일 경로 사전과 에피소드별 블록 구간(시작 블록, 개수)으로 저장합니다. 같은 입력에서 39 MB → 2.7 MB 로 줄었고 읽기는 수십 ms 입니다. 버전 1 파일은 읽을 때 자동 변환합니다. 결정 예산(500 ms)은 그대로입니다. 지우면 이전 판과 같게 동작합니다. 이전 판은 이 파일과 `auto_status.json` 의 새 키를 무시합니다.

**측정.** `aster orbit-bench run|summarize`와 `csharp\scripts\cs_orbit_bench.ps1`(서비스 정지, 게임 종료, 관리자 권한, 회마다 standby 비우기, ABBA 교차)로 기준 순서와 ORBIT 순서의 에피소드 준비 시각을 비교합니다. 2026-11-09 사용자 PC(Call of Duty, ABBA 10쌍 20회)에서 가치 가중 준비 시간 중앙값은 18.8% 줄었고(10/10쌍이 10% 이상 개선, 부호 검정 p=0.001), 총 읽기 시간은 0.1% 줄어 플래그 2·3은 통과했습니다. 최악 에피소드 p95는 13,096 ms 늘어 플래그 4는 실패했습니다. 새 규칙 재채점은 B 후보를 `episode_regression`으로 거부했고 모형 추정 최악 지연은 55.5초여서 실측 회귀 방향을 예측했습니다. 플래그 2는 가치 가중 준비 시간 10% 이상 단축이고 p<0.05, 플래그 3은 총 읽기 시간 5% 이상 악화 없음, 플래그 4는 어떤 에피소드도 p95 기준 max(기준선의 5%, 200 ms) 이상 늦어지지 않음입니다. 기존 측정 파일을 새 에피소드 모형으로 다시 채점하고 원본은 보존한 뒤, 요약 명령으로 플래그 2~4를 확인할 수 있습니다. 재채점은 모형(에피소드)을 `--orbit` 파일에서 읽고, 장치 보정(`disk_model.json`)과 게임 설정만 데이터 폴더에서 읽으므로, 데이터 폴더 밖 파일만으로는 판정이 `game_settings_unavailable`로 끝납니다. `--data-dir <폴더>`는 재채점이 읽을 데이터 폴더 사본을 지정합니다. `--budget-ms <ms>`는 재채점에만 쓰는 결정 예산을 지정합니다(기본 500 ms, 서비스는 항상 500 ms):

```powershell
aster orbit-bench rescore --orbit <orbit.json> --in <run.json>... --out-dir <rescored>
aster orbit-bench summarize --in <rescored\run.json>...
```

재채점은 저장된 op 완료 시각으로 에피소드 지표를 다시 계산하며 디스크를 다시 읽지 않습니다. 현재 `Decide` 규칙으로 후보를 다시 판정해 B 후보 채택 여부, 사유, 모형 추정 최악 에피소드 지연도 출력합니다. ABBA 묶음이 완전하면 실측 플래그 4의 p95 지연과 통과 여부를 모형 추정치와 함께 보여 줍니다. 벤치 전에 장치 보정과 에피소드 모형이 필요합니다. 새로 설치한 직후라면 서비스를 멈추고 모든 등록 게임을 끈 상태에서 `aster orbit model --game <이름>` 을 실행해 기존 플레이 기록으로 `<plans>\<게임>.orbit.json` 을 만든 뒤, `aster orbit calibrate --disk <문자>` 를 실행합니다. 예열 중단 기록이 없으면 B 팔 후보에만 `--lambda-per-min`(기본 1.0, 분당 1회 중단 가정)을 쓰며, 이 값은 실제 서비스 결정에는 쓰지 않습니다. 결과 파일에는 `lambda_source`(model 또는 bench_override)가 기록됩니다. 2026-11-09 재채점에서 모형의 최악 에피소드 지연 추정(55.5초)은 실측 p95(13.1초)보다 약 4.2배 컸습니다(보수 방향). 실제 서비스에서의 결정 결과는 아직 확인되지 않았습니다.

**상태.** `auto_status.json` 의 `shadow_orbit` 에 `mode`, `applied`, `device_n`, `value_runs`, `lambda`, `d_low`, `orbit_reason` 키가 있습니다.
