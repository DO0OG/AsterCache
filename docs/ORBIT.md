# ORBIT: prewarm order adjustment

> Details that continue from [How it works](../README.md#how-it-works) in the README.

For the hot-set prewarm of games with recorded traces, ORBIT calculates whether reordering the prewarm in chunks of about 64 MiB, relative to the current prewarm order, gains anything. The first tier0 chunks stay fixed. The data read and the set read do not change; only the order does.

- It extracts episodes (groups of data read together) and how often each occurs from play records. It also counts how often a game starts during a prewarm and interrupts it.
- Before its own prewarm, the service measures the disk briefly (about 12 MiB per stream, uncached reads) to calibrate the range of seek latency and transfer rate. It changes the order only when the calculation shows a gain even in the worst case of that range and every episode stays within `max(5% of its baseline ready time, 200 ms)`. The same 500 ms decision budget applies. Otherwise it prewarms exactly as it does now; rejected candidates record `episode_regression` and the worst episode delay in the plan file.
- The method combines standard techniques (beam search, lower confidence bounds, split conformal intervals, exact binomial intervals) for this specific problem. The common blocks and tier0 are already read first, so any gain may be limited to map chunks of games that are often interrupted during prewarm. For games where no interruption has been observed, the current order is always used (by design).

**When it turns on.** Calibration needs 38 prewarm streams (19 for fitting and 19 for calibration, per metric). To turn it on sooner, run `aster orbit calibrate --disk <letter> [--samples N]`. With the service stopped and all registered games closed, it takes up to N samples (default 60) at 10-second intervals and stops as soon as the device envelope exists (usually around 40, about 7 minutes). Calibration skips games that do not yet have a prewarm list and draws samples from the pool of allowed game files on that disk. It stays more than 64 MiB away from the most recent read position to avoid drive cache hits, and keeps sampling until the device envelope exists (default cap 60 samples). These bootstrap samples were collected in one time window, so the coverage claim is weak. They are replaced once 38 samples have accumulated during operation. Episodes need at least 3 valid play records and at least 1 interruption event.

**Modes.** The default is `active`. Change it with `aster orbit mode off|shadow|active`. `off` does no calculation at all. `shadow` calculates and records but keeps the current order. If the settings file is missing, the mode is `active`; if it is corrupt, `shadow`. A significant bootstrap-confirmed deterioration in the existing `ProbeReadyMs` proxy, two consecutive calibration drift (coverage monitor failure), or two consecutive calculation exceptions drops it to `shadow` automatically. It never goes back up automatically.

**Safety.** Calibration reads run only inside a disk read-arbitration lease, and only when no game is running and the disk is idle. They run only for games whose anti-cheat policy allows new prewarm (no anti-cheat, or Vanguard). `config.json` has no new keys.

**Three new files.** `<data folder>\orbit_mode.json` (mode), `<data folder>\disk_model.json` (per-disk calibration samples), and `<plans>\<game>.orbit.json` (episodes, interruption risk, recent decisions). From version 2, `<game>.orbit.json` stores a dictionary of file paths and block ranges per episode (start block, count). On the same input the file dropped from 39 MB to 2.7 MB, and reading takes tens of milliseconds. Version 1 files are converted automatically when read. The decision budget (500 ms) is unchanged. Deleting them makes the build behave as before. The previous build ignores these files and the new keys in `auto_status.json`.

**Measurement.** `aster orbit-bench run|summarize` and `csharp\scripts\cs_orbit_bench.ps1` (service stopped, games closed, administrator rights, standby list cleared before each round, ABBA crossover) compare episode ready times between the baseline order and the ORBIT order. On 2026-11-09, on the user's PC with Call of Duty (ABBA, 10 pairs, 20 runs), median value-weighted prep time dropped 18.8% (10/10 pairs improved by at least 10%; sign-test p=0.001) and total read time dropped 0.1% (flags 2 and 3 passed), but the worst episode p95 increased by 13,096 ms, so flag 4 failed. The values of an earlier run on the same day (21.3% reduction, maximum delay 18.2 s) are in the [results summary](RESULTS_SUMMARY.md#orbit-prewarm-order-bench-2026-11-09). Rescoring with the new rule rejected the B candidate as `episode_regression` (modeled worst delay 55.5 s), so it predicted the direction of the measured regression. Flag 2 is a value-weighted prep time reduction of 10% or more with p<0.05, flag 3 is no total read time worsening of 5% or more, and flag 4 is no episode delayed by more than max(5% of the baseline, 200 ms) at p95. Rescore existing runs against the updated episode model without overwriting them, then summarize the rescored files to report flags 2–4. The rescore reads the episode model from the file passed with `--orbit`, and reads only the device calibration (`disk_model.json`) and the game settings from the data folder, so run files outside the data folder end with `game_settings_unavailable`. `--data-dir <folder>` points the rescore at a copy of the data folder. `--budget-ms <ms>` sets the decision budget used only by rescore (default 500; the service always uses 500 ms):

```powershell
aster orbit-bench rescore --orbit <orbit.json> --in <run.json>... --out-dir <rescored>
aster orbit-bench summarize --in <rescored\run.json>...
```

This recalculates episode timings from each recorded op completion time; it does not repeat disk reads. It also reevaluates the candidate with the current `Decide` rule and reports whether B would be adopted, the reason, and the modeled worst episode delay. When the inputs contain complete ABBA groups, the same output includes measured flag 4 p95 delay and its result beside the modeled delay. The bench needs device calibration and an episode model first. On a fresh install, stop the service and turn off all registered games, then run `aster orbit model --game <name>` to build `<plans>\<game>.orbit.json` from existing play records, and then run `aster orbit calibrate --disk <letter>`. If no prewarm-interruption record exists yet, use `--lambda-per-min` (default 1.0, assuming one interruption per minute) only for the B-arm candidates; it is never used for real service decisions. The result file records `lambda_source` (model or bench_override). In the 2026-11-09 rescoring, the modeled worst episode delay (55.5 s) was about 4.2 times the measured p95 (13.1 s), which is the conservative direction. The decision result in the actual service has not been confirmed yet.

**Status.** `auto_status.json` has a `shadow_orbit` block with the keys `mode`, `applied`, `device_n`, `value_runs`, `lambda`, `d_low`, and `orbit_reason`.
