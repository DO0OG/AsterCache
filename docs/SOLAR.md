# SOLAR: keeping the cache and its eviction order

> Details that continue from [How it works](../README.md#how-it-works) in the README. SOLAR stands for Standby Order LAdder & Refresh.

SOLAR works on data that a game's prewarm has already read into RAM. It does not read from the disk on purpose. It touches that data again in memory (re-references the cached pages), so that the data a load needs first is the last to be pushed out of the cache, and so that the cache is kept up without going back to the HDD. It is on by default (`memory.standby_ladder`).

## Why it exists

Prewarmed data is ordinary file cache. Windows keeps cache pages that no program is using in its standby list and reuses them when memory is needed. On the test PC the file cache, prewarm cache included, sat at priority 5 of the list's priorities 0 to 7, and pages at the same priority were reused in the order they entered the list (see [the measurement record](#measurement-record)). Two things follow.

- **The cache cools.** Reads and memory use of other programs push cache pages out. In the service log of the test PC, the median time from a complete prewarm to the first re-prewarm check that found the cache cold was 29.0 minutes for League of Legends and 71.5 minutes for Call of Duty. Checks run about every 10 minutes, so these are upper bounds on when the cache cooled. Since 2026-11-11, 47% (League of Legends) and 71% (Call of Duty) of the re-prewarm checks found the cache at least partly cold. A cold cache is read from the HDD again.
- **The most important data goes first.** Prewarm reads the data every load needs (the common blocks and the loading head, the blocks read first in a load) first. Pages read first enter the list first, so the most important data is also the first to be reused when memory runs short.

SOLAR answers both without reading the disk on purpose. It touches the cache again in the reverse of the read order, so the most important data enters the list last and leaves it last, and it does this again before the pages that Windows reuses before them have been used up.

## How it decides

1. **Make the ladder.** When a prewarm of a game has read its list to the end, SOLAR touches what that game has in the cache in the reverse of the read order: the later part of the list first, and the loading head and the common blocks last. A touched page goes to the back of the standby list, so the order of eviction becomes the reverse of the order of importance. The importance order is the one the prewarm already uses, which comes from the game's own recorded reads. While the prewarm is still reading, each batch it has just read is touched again right away, in read order. A prewarm read skips pages that are already cached and does not move them in the list, so without this the rest of the game's pages would keep the old order of an earlier prewarm; touching the batch sends those skipped pages to the back as well. A supplement prewarm that continues an interrupted read skips the front part an earlier pass already read, so it touches that skipped front part once, in list order, before it reads the rest. It costs about 0.5 s per GiB of cached data, and the prewarm done line shows it as `, requeued N MiB in S s`.
2. **Record the state.** After a ladder it records the time, Windows' running count of cache pages that have been reused, and the amount reused first (the standby pages that Windows would reuse before this game's pages): the cache in the standby list minus what this game touched. The amount reused first is not always the same value: when another game touches its cache again, the pages that were reused before this game's pages are now reused after them. So when that game had an earlier recorded state and the recorded state is older than this game's, the amount reused first is lowered by the smaller of what that earlier recorded state touched and what the game touched now (never below zero). The rest of a touch was read from the disk and is already in the reuse count, and a game with no earlier recorded state has no known position, so neither lowers it (the ladder at the end of a prewarm stream is the exception; see the details). The recorded state lives in memory only.
3. **Watch one statistic.** About every 30 seconds, when a game has a recorded state, SOLAR reads Windows' standby-list statistics once. It is a system-wide figure and no process is opened. Windows reuses the pages that come before the game's pages first, so when the count of reused cache pages has grown since the recorded state by `max(512 MiB, 0.4 x the amount reused first)`, or when what is left of that amount (the amount reused first minus that growth) is under 2 GiB, the game's pages are getting close to the front. The second rule does not apply to a game whose amount reused first was already under 4 GiB when its recorded state was made.
4. **Refresh the whole group without the disk.** When a game with a recorded state that can be touched right now (its gates are open) is due, all the games with a recorded state are refreshed, the lowest-ranked one first and the most recently prewarmed one last (a game that is not due yet is refreshed too, because the pages touched for the others have moved behind it). Before each game's refresh, the usual sample check runs (1 MiB at each of 8 places). If the samples are warm, SOLAR touches the same ladder again, which moves the pages to the back of the list. If they are cold or cannot be read, the recorded state is dropped and the [re-prewarm check](AUTO_MODE.md#5-upkeep) takes over. One exception: when the game drive is busy (4 MiB/s or more, or its load is unknown) and the samples come out cold, they may have been slow because of another program's reads, so, once per recorded state, the recorded state is kept and only that round is skipped (no log line). If the samples come out cold a second time for the same recorded state, it is handled as when the drive is not busy: the recorded state is dropped and the game is left to the re-prewarm check. The memory of having let one go is cleared when the recorded state is dropped or made anew, or when a warm sample is seen. A game that a gate blocks is skipped and the rest go on; a blocked game that is due does not start a group, so it cannot make the others be touched again and again. Afterwards the recorded states of the games that were touched are written again from one point in time: the amount reused first for a game is the cache in the standby list minus what that game and the games touched after it touched, and the count of reused pages is the one of that moment. A skipped game keeps its recorded state, but its amount reused first is lowered by the rule of step 2. A group refresh is not repeated within 60 seconds of the last one, and a re-reference of other games' cache before a stream, during one and right before its ladder (see the details) counts as one: each of them that touches a game sets the time of the last group refresh (the one right before a ladder does not wait for the 60 seconds itself).
5. **Stop when the disk is read.** A page that is no longer in the cache would be read from the disk by the touch. After each view, SOLAR compares how many pages the whole system has read from the disk meanwhile and stops once more than 32 MiB is counted. Then the recorded state is dropped and the game is flagged for the next re-prewarm check, which re-prewarms it even if its samples look warm. Parts still in the cache cost almost no disk time, so in effect only the missing parts are read. At most one such re-prewarm per game is made each `auto.rewarm_minutes`, counted from the last prewarm attempt.

If Windows' statistics cannot be read (for example because the privilege is missing), step 3 falls back to a refresh every 10 minutes after the last ladder, with no other change.

<summary>Details: the numbers, how a touch is made, how disk reads are told</summary>

- **How a touch is made.** Each range is mapped as its own read-only view of at most 64 MiB, read 1 MiB at a time from inside the service's own process, and unmapped at once. Nothing is locked and no mapping is kept. Up to 64 files are open at a time. The result is the same as if a program had read the pages normally.
- **Why a view per range.** On the test PC, a file's ranges left the cache in the order they were touched only when each range had its own view that was released right after. With one view for all ranges they left in address order (SOLAR experiments E10 and E11).
- **Where 0.4 and 512 MiB come from.** In the eviction experiment (SOLAR experiment E9) the first untouched file left the cache when the reuse count had grown by 0.61 to 0.81 times the amount reused first. Some of the pages reused first are used again and drop out of the way, so the real moment comes earlier than a plain count suggests, and a margin was added. The lower bound of 512 MiB keeps a small amount reused first from triggering refreshes too often. Both values come from that one experiment and have not been tuned further. The 2 GiB of room comes from a reuse burst of about 1.9 GiB within 30 seconds that was seen twice in one measurement on the installed PC (see the measurement record); it is a value of that PC and time of day, not a general one.
- **How disk reads are told.** The system's page-read count is read before and after each view. The increase, minus an allowance for other programs (2 pages and about 8 MiB per second), counts as read from the disk, at most the size of the view and at most what a disk could read in the time the view took (256 MiB per second). The count is for the whole system, so reads by other programs are mixed in; on the test PC another process read 30,000 to 80,000 pages within 0.25 s about once every 90 seconds, and a touch that happens to overlap such a burst would otherwise count a whole view as read from the disk. Touching 64 MiB from memory took about 20 ms and reading it from an HDD 0.4 to 1 s, so a view that took 20 ms counts at most about 5 MiB, while a view that really came from an HDD is counted as before. More than 32 MiB counted ends the touch, so in the worst case about 100 MiB is read from the disk before it stops (the 32 MiB counted, plus the view being touched). If the count cannot be read, a view that takes more than about 256 ms per 64 MiB counts as read from the disk. A looser safety net also stops the touch when pieces that took more than 20 ms per MiB add up to more than 2 seconds.
- **What is touched.** The list is the common blocks that the prewarm reads first followed by the whole list that was read, in read order; the ladder is its reverse. For a prewarm that read only the front part, it is the part that was read. A range that continues the previous one in the same file is joined to it.
- **Touching while reading.** After each batch of a prewarm stream (about 64 MiB of reads) and after the common blocks, the range just read is touched again in the same thread, under the same disk read lease and the same stop signal as the stream, and after the stream's own per-batch checks (memory, outside load, game running), whose order and meaning are unchanged. If a game starts or the lease ends, no later batch is touched. If the touch finds data missing, throws, or is cancelled, the stream goes on and its result (the amount read, success) is the same; an exception is logged once as `requeue of the read batches skipped`. When the touch of a batch stops on disk reads, the later batches of that stream are not touched (so the disk reads are not repeated for each batch), and the done line says `requeue stopped by disk reads`. The same stop of the skipped front part ends only that touch. The time spent touching is left out of the `yielded` time and of the stream's exposure time, because a touch is not a disk read. It follows the same conditions as the ladder (see below), and with `memory.standby_ladder` off the stream is exactly as before.
- **Re-referencing other games' cache before a stream (the log calls this `protected`).** Right before a prewarm stream (service start, re-prewarm, supplement prewarm) reads from the disk, the other games that have a recorded state are touched once, the lowest-ranked first, by the same function as the group refresh (the stream's own game is left out). The pages the stream then reads push out the plain cache, and the stream's own old pages, before they push out another game. It runs under the stream's disk read lease and stop signal and only while no game start or launcher preemption flag stands. The sample check and the gates are the same as for a refresh. A launcher prewarm does not do this, because a game start is close and its prewarm must not be delayed; after that stream the ladder only lowers the amount reused first for the other games. The time it takes is left out of the `yielded` time and of the stream's exposure time, and the done line gets `, protected K games (N MiB in S s)` (left out when none was touched). If it fails or is cancelled, the stream goes on and its result is the same.
- **Re-referencing other games' cache during a stream.** While a prewarm stream that is not a launcher's runs, after each batch has been read, checked and touched again, SOLAR looks at whether another game with a recorded state is due. It is the same decision as the maintenance tick (the criterion of step 3 above: a game that can be touched is due and 60 seconds have passed since the last group refresh) by the same function. The decision reads the standby-list statistics once, so it is made only when 10 seconds have passed since the previous decision. When it is due, the other games are touched again by the same function as the re-reference before a stream. It runs in the stream's thread, under the stream's disk read lease and stop signal, and only while no game start or launcher preemption flag stands; the stream's own game is not a target (its ladder at the end makes it). A launcher prewarm does not do it. The time it takes is left out of the `yielded` time and of the stream's exposure time and is added into the `protected` tail of the done line (the number of different games, the totals of amount and time, and the number of times when it was more than once). When it writes the new recorded states, the cache in the standby list is reduced by what the stream has touched so far minus the share the ladder at the end of the stream lowers anyway (what the stream game's earlier recorded state touched; with no earlier recorded state nothing is subtracted, because the ladder then lowers the amount reused first by everything it touched), because the pages the stream read are touched again by that ladder and then lie behind these games; this keeps the amount reused first for a game that the end of the stream then skips from being lowered twice (when the re-reference right before the ladder at the end of the stream, below, runs, the recorded states of those games drop this value and are written again in their real order). If it fails or is cancelled, the stream goes on and its result is the same.
- **Re-referencing other games' cache right before the ladder, and one group of recorded states.** Right before a prewarm stream that is not a launcher's has finished and makes its game's ladder (a ladder after a memory-limit finish included), the other games that have a recorded state are touched once, the lowest-ranked first. It is the same function, gates, sample check, disk read lease and stop signal as the re-reference before a stream, and the stream's own game is left out. The end of a stream happens once and the order has to be set then for the amount reused first to be right, so it does not look at "is it due" or at the 60-second minimum between group refreshes. Then the ladder is made, and the recorded states of the other games touched and of this game are written again as one group, in the order they were touched (the calculation of step 4). So whether or not this game had an earlier recorded state, the amount reused first matches the real order right after the ladder, and a recorded state written again as a group is not lowered a second time by the rule of step 2. This does not use the "subtract what the stream has touched so far" of the re-reference during a stream. When the re-reference could not run (a launcher prewarm, no other game with a recorded state, a group refresh in progress so it was skipped) and for a game the re-reference skipped (blocked by a gate, for example), the ladder lowers the amount reused first by everything the ladder touched if this game had no earlier recorded state; the recorded state of the stream's game can already be dropped (after a cold sample or missing data was found, for example), which would give 0 under the rule of step 2. How much of it really went from before the game's pages to after them is not known, so it takes the larger amount, which at worst brings a refresh one round early. With an earlier recorded state, the rule of step 2 stands as it was. The time it takes is left out of the `yielded` time and of the exposure time and is added into the `protected` tail of the done line.
- **A ladder right after a service start.** A game that the service-start prewarm skipped as `prewarm skipped (already warm) [service start]` gets its first ladder on the spot, using the sample verdict of that skip (the samples are not read again), under the same conditions and by the same function as the first ladder of the re-prewarm check. With several games the lowest-ranked is made first and the recorded states are then tidied by the group rule. A game in a partial state (a supplement prewarm waiting) follows the conditions of the first ladder for a supplement prewarm that waits for memory. The launcher path does not do it. It fills the gap in which, after a restart, there is no recorded state and no refresh until the first re-prewarm check (after `auto.rewarm_minutes`).
- **Where the first ladder comes from.** After a prewarm stream of the game has finished to the end (service start, launcher, re-prewarm, supplement prewarm). When the ladder of a game is made, the amount reused first for the other games' recorded states is lowered by the rule of step 2 (a first ladder, of a game with no earlier recorded state, lowers nothing; the ladder at the end of a prewarm stream follows "Re-referencing other games' cache right before the ladder, and one group of recorded states" above). A stream that ended at the memory limit makes a ladder over the range it read, right after it ends, in the same lease. The target is the front of the same window the stream read, cut at the amount read, so the part that was not read is not touched. This holds only for a window read or a continued read, which have no gap-filling budget, so the list the stream read is the one planned for the same window. A supplement prewarm that read a full list with such a budget and stopped at the limit makes none; it is left to the re-prewarm check, whose first ladder covers a game that waits for memory. After a service restart the recorded states are gone, so a game that the start prewarm skipped as already warm gets a new ladder right after that, and any other game at the first re-prewarm check with warm samples.

- **A touch when a game's executable starts.** When a registered executable of a game starts (the first one, and each later one of the same game), the game's prewarmed list is touched again in memory in ladder order, in a lease of the start stream's kind, apart from the start stream and the stage stream, which it neither blocks nor delays. The point is that the game then takes 9-10 GiB for itself and the oldest pages of the standby list go first: when the guess of which game is played next is wrong, the cache of the game that was actually started would go first. The range is the one the ladder uses (what the prewarm read, with sparse files and unbuffered files left out), the recorded state and the amounts reused first of the other games are updated as for a ladder, and the disk is not read beyond the usual limit: the touch stops at the first range that is not in memory (a slow piece). When part of the list is already known to be missing, or the ladder-order touch stops at a missing range, the touch first goes through the list in the order of importance (the order the prewarm read it) to find the end of the front part that is still in memory, then touches only that front part in ladder order, so that the most important block that is left goes last. The reason is that the standby list gives up the older, less important pages first, so the missing range is usually at the start of the ladder order and a ladder-order touch would stop before it touches the most important part. In that case no "all of it is in memory" recorded state is made and the missing flag stays, so the re-prewarm check reads the rest after the game ends; the amounts reused first of the other games are lowered by the size of the front part, as for the end of a prewarm stream (this game has no recorded state, so the whole touched amount counts). It runs only for a game whose start stream is allowed (game policy, `auto.start_stream_enabled`, the quick-exit back-off), only for a game whose list is in memory by the same conditions as the service-start ladder (prewarmed since the boot, skipped as already warm at the service start, or with a recorded state), and not during a relocation. The lease ends it when the game ends, when another game starts on the same disk, or when the service stops. The start stream and the stage stream always come first: the leases do not block each other (the coordinator does not count active leases), and the touch reads at low I/O priority on its own thread. A second touch of the same game waits 60 seconds after the end of the first (the same length as the start stream cooldown and the stage stream cooldown); the executables of one launch come within seconds of each other, before the game has taken its memory, so a second touch would change the order very little. It opens no process and does not write.

## When it runs

All of these must hold. Otherwise nothing is touched.

| Requirement | Detail |
|---|---|
| Setting | `memory.standby_ladder` is `true` (the default). |
| Service rights | The service has administrator rights and a trusted data folder, the same condition as [background memory yield](AUTO_MODE.md#background-memory-yield). |
| No game running on that disk | A touch that misses the cache is a disk read, so it follows the rule that no new background reads go to a disk where a game runs. It stops when a game starts. The one exception is the touch of the game that has just started, which reads only its own pages from memory and stops at the first one that is not there (see "A touch when a game's executable starts"). |
| Not while a launcher prewarm waits | A launcher's prewarm has priority. SOLAR also skips a stream that was stopped for it, and the group refresh stops when a launcher prewarm starts to wait. |
| Refresh gates | The same gates as the re-prewarm check except the drive load: no relocation in progress, the exit grace period over, the game inside the prewarm budget, and the disk read lease granted. A refresh only touches pages that are in the cache, in memory, so it runs while another program uses the same drive. The gates of the re-prewarm check, which can read the disk again (including the game drive under 4 MiB/s), are unchanged. The lease is refused only while a game on that disk is running and yielding; a refused lease only skips the game and its recorded state stays. |
| Not with `auto.keep_stream_on_game_start` | With this experimental setting a stream is not stopped when the game starts, so SOLAR does not follow it. |

## What it does not do

- It does not keep data in memory by force: no lock, no kept mapping (unlike the optional [Pinning](AUTO_MODE.md#pinning-optional)), and no change of page priority. Windows can still reuse these pages when memory is short; SOLAR only changes which ones go first.
- It does not run on a disk where a game is running, except for the touch of the game that has just started on its own prewarmed list.
- It does not lower the memory reserve (`prewarm.min_free_ram_mib`) or the cache budget (`prewarm.max_cache_mib`), and it changes neither the prewarm list nor the amount read.
- It does not open any game, launcher, or anti-cheat process, and it opens no process at all. See [Anti-cheat compatibility](ANTICHEAT.md).

## Turning it off

Add this to `config.json`:

```json
"memory": { "standby_ladder": false }
```

There is no switch in the Settings tab. The service re-reads the file and then stops touching the cache. Nothing else changes: the prewarm, the re-prewarm check, and [background memory yield](AUTO_MODE.md#background-memory-yield) work as before and have their own settings. The `memory.standby_ladder` key is newer than 1.0.3, and versions 1.0.3 and earlier reject a settings file that contains it, so remove it before rolling back ([Configuration](CONFIGURATION.md)).

## Checking that it runs

Each line goes to `service.log`. `<game>` is the game's name, and a tail such as `, N MiB read from disk`, `, N errors` or `, K MiB in sparse files not touched` is added only when it is not zero (a figure in MiB is left out when it would show 0 MiB).

- `<game>: ladder ordered N MiB in S s`: a ladder was made after a prewarm or a re-prewarm check. `<game>: ladder has nothing to touch (K MiB in sparse files not touched)` means every range of the list is in sparse files, so no ladder was made; it is logged when that finding is new (again after a service restart or a new prewarm), not at every check.
- `<game>: cache refreshed in memory: N MiB in S s (R MiB repurposed of A MiB ahead)`: a refresh. `R` is the growth of the reuse count and `A` the amount reused first. A game that was not due itself but was refreshed with the group gets the same line, with its own values.
- `<game>: prewarm done (...) ..., protected K games (N MiB in S s)` (at the end of the done lines, after `requeued` when both are there): right before the stream read, while it read and right before its ladder, K different other games with a recorded state were touched, N MiB and S seconds in all. When it re-referenced other games more than once, `, R times` is added at the very end (not for one time). It is left out when none was touched, and a `cache refreshed in memory` line stays for each of those games. It is never on the line of a launcher prewarm.
- `<game>: prewarm done (...) ..., requeued N MiB in S s` (and the same at the end of `supplement prewarm done`): the batches the stream touched while reading; left out when nothing was touched or skipped. `requeued N MiB in S s (K MiB in sparse files not touched)` shows the part of the batches that sat in sparse files (see Limits and cautions) and was skipped; the parentheses are left out when it is zero. `, requeue stopped by disk reads` is added when a touch saw disk reads and stopped. A supplement prewarm that read only a window ends with `supplement prewarm read the first …` instead of `done`, and that line carries the same `requeued` text. `, K MiB of sparse files by buffered read` (before `requeued`, on the same lines) shows how much of the stream was read that way instead of through a mapping; it is left out when zero.
- `<game>: cache touched at game start (<exe>): N MiB in S s, D MiB read from disk`: the touch when the executable `<exe>` started (see "A touch when a game's executable starts"); `D` is the amount the touch saw read from disk and is shown even when it is 0. `<game>: cache touched at game start (<exe>): N MiB of M MiB still in memory, in S s, D MiB read from disk, left to the rewarm check`: only the front part of the list was still in memory and only that part was touched; `<game>: cache touch at game start (<exe>) found none of the M MiB list in memory (...)`: none was. When the touch stopped, the lines have the same words as the ladder with `cache touch at game start (<exe>)` in place of `ladder`: `... found data missing from memory after T of N MiB (...), left to the rewarm check`, `... stopped after N MiB`, `... was too slow without disk reads seen (...), skipped`. `<game>: cache touch at game start skipped (<exe>: <reason>)` says why none was made: `last touch S s ago, within 60 s` or `disk yielded` (the lease was refused, for example because another game runs on the same disk).
- `<game>: ladder found data missing from memory after T of N MiB (K slow pieces, M MiB read from disk), left to the rewarm check`, and the same for `cache refresh found data missing from memory after T of N MiB (...)`: part of the list was not in the cache. For a game that had a recorded state, `, since the ladder M min ago: R MiB repurposed of A MiB ahead` is added at the end of the line (M is minutes since that recorded state was made, R the reuse since then, A the amount reused first now (at the moment the recorded state was dropped, if it was); when the standby-list statistics cannot be read, only the time and no `: R MiB … ahead`). It is left out when there was no recorded state. It helps tell whether the cooling came from a refresh that was late, one that was blocked, or an eviction out of order. The ladder touches in reverse order, so when `T` is close to `N` the missing part is at the front of the list, the most important part. `N` is the whole ladder including sparse ranges that were skipped, so when the line ends with `K MiB in sparse files not touched`, check whether `T` plus `K` is close to `N`.
- `<game>: rewarm check: part of the list is not in memory (found by the ladder), prewarming again (cooldown ignored)`: the next re-prewarm check re-prewarms the game. `..., waiting until N min after the last prewarm attempt` means it waits for the period to pass.
- `<game>: cache refresh skipped, the samples are cold (X/Y over Z ms), left to the rewarm check`, or `the samples could not be read` or `there are no readable samples`: the sample check came before the refresh. These three lines (cold, `could not be read`, `there are no readable samples`) and the `<game>: rewarm check: cold (...), prewarming again (cooldown ignored)` line also get the same `, since the ladder M min ago: ...` tail for a game that had a recorded state (when a refresh dropped the recorded state first, the values from before are kept and added once to the cold line of the re-prewarm check, then discarded; a new recorded state discards them too). A cold sample read while the game drive is busy is skipped without a log line once per recorded state, so that line does not appear then.
- `<game>: ladder stopped after N MiB`, `cache refresh stopped after N MiB`: stopped because a game started or the lease ended; the recorded state stays and a refresh is tried again.
- `<game>: ladder was too slow without disk reads seen (K slow pieces), skipped`, `cache refresh was too slow without disk reads seen (...)`: the touch took long but no disk read was seen, for example under heavy CPU load.
- `<game>: ladder skipped: <exception type>` and `<game>: cache refresh failed: <exception type>` (or `cache ladder failed`): a failure that did not affect the prewarm.

## Limits and cautions

- **The effect in real play has not been measured.** The experiments show that the order can be set and that refreshing cache that is still in memory needs no disk read. They do not show how much load time or stutter changes in a running game. Whether the share of cold re-prewarm checks has fallen has not been checked either.
- **A program that uses again the pages Windows would reuse before the game's pages moves them behind the game's pages, and that cannot be counted.** So the criterion can be late; the re-prewarm check is the backstop for that case.
- **The effect of the group refresh, the re-reference before a stream and the ladder after a memory-limit finish has not been checked on an installed build yet.**
- **The refresh runs while the drive is busy too, because it does not read the disk.** When a sample or a touch meets a part that is not in the cache, it does read then: the sample 8 MiB, and a touch up to about 100 MiB before it stops. A cold sample read on a busy drive is let go once per recorded state (the recorded state is kept, that round's 8 MiB sample read is spent); the second one drops the recorded state and leaves the game to the re-prewarm check, also on a system where the drive load cannot be read. Whether to read from the disk again is still decided only by the re-prewarm check.
- **The effect of re-referencing right before the ladder, of writing the recorded states again as one group, and of lowering the amount reused first by everything the ladder touched when the stream game had no earlier recorded state has not been checked on an installed build yet.** Lowering by everything is a cautious value chosen because the real amount is not known, so it can lower more than the real amount and bring a refresh early (the decision to re-prewarm from the disk is still made only by the re-prewarm check; an early refresh may still read the 8 MiB sample and, when a touch meets a part that is not in the cache, up to about 100 MiB before it stops).
- **The re-reference during a stream, the ladder right after a service start, the log tails and this whole change have not been checked on an installed build yet.** How much the ladder right after a service start delays the start prewarm has not been measured either (it runs first, for the `S` seconds of its `ladder ordered N MiB in S s` line).
- **It does not stop eviction.** When memory is truly short, Windows still reuses these pages. SOLAR changes only which ones go first and how soon they come back.
- **Files with the sparse attribute are not touched.** Measured on one PC (an HDD, test files): right after a prewarm read, an ordinary file touched through a new mapping (a section) caused no disk read (47 runs), while a sparse file was read again from the disk every time (64 MiB in about 1.1 s). So before it opens a section SOLAR reads the file's attributes (metadata only, once per file in a run) and skips a sparse file. The log shows the skipped amount (`K MiB in sparse files not touched`); it is not counted as touched, as errors or as data missing. The data of such files is not part of SOLAR's order or upkeep and depends only on the prewarm and the re-prewarm check (a buffered-read sample). This is what was measured on that PC, not a statement about how Windows behaves in general. SOLAR only reads the attribute and never changes a file. The prewarm reads such files differently from ordinary ones as well: it does not map them but reads them with an ordinary buffered read of the same ranges in the same order, because on that PC creating a mapping for a sparse test file discarded the cache pages read earlier from that whole file, while buffered reads alone kept them. These reads turn the cache manager's read-ahead off: with it on, a list of scattered 64 to 256 KiB pieces (256 MiB requested) read 13 to 23% more than requested from the disk on that PC, and with it off the disk read stayed within about 1% of the request in the measured runs. How much this helps in a real game has not been measured yet. If every range of a game's list is in sparse files, the log says `ladder has nothing to touch (K MiB in sparse files not touched)` once, and the re-prewarm check does not try the ladder again until the next prewarm stream has judged it again.
- **A very long prewarm can lose its own start.** Once, a prewarm of 11,388 MiB for Call of Duty took 322 seconds, and the ladder made right after it already found data missing. The list was close to the capacity of the standby list, so the part read first may have been pushed out while the rest was being read; other programs' reads may have added to it. Separately, in the installed build 1.0.4-dev.7 the batch touch for Call of Duty stopped with `requeue stopped by disk reads` at the same position (3,379 MiB) in different streams, and the ladder also found data missing, so the re-prewarm repeated. A count of file attributes (metadata only, 2026-11-14) found 78 of the 210 `.xsub` files in that game's folder (50.6 GiB) sparse, and no sparse files in the folder of another game whose ladder ended without disk reads. From these three the repetition was judged to come from sparse files; that the file at the stopping position is sparse was not checked, and how much of the first case was pushing out has not been separated. A re-prewarm that reads only the missing part also leaves the rest of the game's pages in the old order of the earlier prewarm, which Windows reuses first; touching each batch right after it is read is meant to prevent that. **Whether the repetition stops after this change has not been checked on an installed build yet.** If the list is larger than what the standby list can hold, the part read first can still be pushed out while the rest is read; the `after T of N MiB` in the log shows how far the ladder got.
- **The 8-place sample check can miss a partly cold cache.** The ladder looks at the whole list, which is why a ladder that finds missing parts leads to a re-prewarm even when the samples look warm.
- **A slow sample counts only when the system's page-read count grew too.** A place is counted as slow only if its read took longer than the limit and, during that read, the system's page-read count grew in proportion to the sample size (at least a quarter of the pages read, 16 pages at the least). Before this, a sample that was in the cache could read slowly while another program was using the CPU and be taken for a cold one. If the count cannot be read, time alone decides. A rare burst of other programs' reads that overlaps a sample can still cause a wrong call. Not yet checked on an installed build.
- **Other programs' reads can still add to the disk read count, up to a limit.** The page-read count is system-wide, so the time cap only keeps a short burst from counting as a whole view; a burst that overlaps a view that really took long (on a slow or busy disk) can still add up to what that time allows. Whether the false stops (`requeue stopped by disk reads`, `ladder found data missing`) have stopped on an installed build has not been checked yet.
- **The statistic is an undocumented Windows interface.** It was checked on Windows 11 10.0.26200 only. If it cannot be read, the 10-minute fallback is used.
- **The eviction order was checked with test files on one HDD,** for pages of priority 5 only. Raising the page priority to 6 or 7 was refused by Windows (`STATUS_INVALID_PARAMETER`), so it is not used.
- Games on an SSD are skipped by the prewarm, so SOLAR has nothing to do for them.

### Test files while the service was running (2026-11-14)

Four 512 MiB test files on the HDD were put in the cache and watched for 61 minutes while the installed service was running and the PC was in ordinary use. ## Prior art

Each technique in SOLAR has an earlier precedent. Putting a cache's replacement bookkeeping into a chosen state by reading data in a set pattern from user level was done by Dust ([Burnett et al., USENIX 2002](https://static.usenix.org/event/usenix02/full_papers/burnett/burnett_html/index.html)), there to identify the replacement policy. Touching files periodically to keep them cached is what [vmtouch](https://linux.die.net/man/8/vmtouch) with a scheduled job does. Releasing the memory of background programs only under memory pressure is close to [SmartTrim in Process Lasso](https://bitsum.com/apps/process-lasso/docs/algorithms/smarttrim/), and Windows itself ranks standby pages by value ([SuperFetch](https://learn.microsoft.com/en-us/previous-versions/technet-magazine/cc162480(v=msdn.10))).

What is specific to this program is the combination: one control loop that uses a Windows statistic of the standby list per priority as its signal to decide the eviction order, the timing of the keeping, and the yielding of background memory ([background memory yield](AUTO_MODE.md#background-memory-yield) uses the same statistics), and an importance order that comes from each game's own recorded reads. A search on 2026-11-14 did not find a product, paper, patent, or public code that does the same combination. That is a statement about the search, not proof that none exists. The comparison and the sources are in [prior_art_and_windows_api.md](prior_art_and_windows_api.md#f-solar-선행-기술-캐시-유지-순서-배경-양보).
