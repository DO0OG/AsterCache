# SOLAR: keeping the cache and its eviction order

> Details that continue from [How it works](../README.md#how-it-works) in the README. SOLAR stands for Standby Order LAdder & Refresh.

SOLAR works on data that a game's prewarm has already read into RAM. It does not read from the disk on purpose. It touches that data again in memory (a touch is a read-only read of pages that are already in the cache, which sends them to the back of the standby list), so that the data a load needs first is the last to be pushed out of the cache, and so that the cache is kept up without going back to the HDD. It is on by default (`memory.standby_ladder`).

## Why it exists

Prewarmed data is ordinary file cache. Windows keeps cache pages that no program is using in its standby list and reuses them when memory is needed. On the test PC the file cache, prewarm cache included, sat at priority 5 of the list's priorities 0 to 7, and pages at the same priority were reused in the order they entered the list (see [the measurement record](#measurement-record)). Two things follow.

- **The cache cools.** Reads and memory use of other programs push cache pages out. A prewarmed page that has been pushed out of memory in this way, in part or whole, is called cold in this document and in the logs, and a page still in memory is called warm. In the service log of the test PC, the median time from a complete prewarm to the first re-prewarm check that found the cache cold was 29.0 minutes for League of Legends and 71.5 minutes for Call of Duty. Checks run about every 10 minutes, so these are upper bounds on when the cache cooled. Since 2026-11-11, 47% (League of Legends) and 71% (Call of Duty) of the re-prewarm checks found the cache at least partly cold. A cold cache is read from the HDD again.
- **The most important data goes first.** Prewarm reads the data every load needs (the common blocks and the loading head, the blocks read first in a load) first. Pages read first enter the list first, so the most important data is also the first to be reused when memory runs short.

SOLAR answers both without reading the disk on purpose. It touches the cache again in the reverse of the read order, so the most important data enters the list last and leaves it last, and it does this again before the pages that Windows reuses before them have been used up.

## How it decides

1. **Make the ladder.** When a prewarm of a game has read its list to the end, SOLAR touches what that game has in the cache in the reverse of the read order: the later part of the list first, and the loading head and the common blocks last. This pass, or the order it follows, is what this document calls the ladder. A touched page goes to the back of the standby list, so the order of eviction becomes the reverse of the order of importance. The importance order is the one the prewarm already uses, which comes from the game's own recorded reads, and when the ranked block list exists its blocks come first in rank order ("What is touched" below). While the prewarm is still reading, each batch it has just read is touched again right away, in read order. A prewarm read skips pages that are already cached and does not move them in the list, so without this the rest of the game's pages would keep the old order of an earlier prewarm; touching the batch sends those skipped pages to the back as well. A supplement prewarm that continues an interrupted read skips the front part an earlier pass already read, so it touches that skipped front part once, in list order, before it reads the rest. It costs about 0.5 s per GiB of cached data, and the prewarm done line shows it as `, requeued N MiB in S s`.
2. **Record the state.** After a ladder it records the time, Windows' running count of cache pages that have been reused, and the amount reused first (the standby pages that Windows would reuse before this game's pages): the cache in the standby list minus what this game touched. The amount reused first is not always the same value: when another game touches its cache again, the pages that were reused before this game's pages are now reused after them. So when that game had an earlier recorded state and the recorded state is older than this game's, the amount reused first is lowered by the smaller of what that earlier recorded state touched and what the game touched now (never below zero). The rest of a touch was read from the disk and is already in the reuse count, and a game with no earlier recorded state has no known position, so neither lowers it (the ladder at the end of a prewarm stream is the exception; see the details). The recorded state lives in memory only.
3. **Watch one statistic.** About every 30 seconds, when a game has a recorded state, SOLAR reads Windows' standby-list statistics once (this periodic check is called the 30-second check below). It is a system-wide figure and no process is opened. Windows reuses the pages that come before the game's pages first, so when the count of reused cache pages has grown since the recorded state by `max(512 MiB, 0.4 x the amount reused first)`, or when what is left of that amount (the amount reused first minus that growth) is under 2 GiB, the game's pages are getting close to the front. The second rule does not apply to a game whose amount reused first was already under 4 GiB when its recorded state was made.
4. **Refresh the whole group without the disk.** When a game with a recorded state that can be touched right now (its gates are open) is due, all the games with a recorded state are refreshed, the lowest-ranked one first and the most recently prewarmed one last (a game that is not due yet is refreshed too, because the pages touched for the others have moved behind it). Before each game's refresh, the usual sample check runs (1 MiB at each of 8 places). If the samples are warm, SOLAR touches the same ladder again, which moves the pages to the back of the list. If they are cold or cannot be read, the recorded state is dropped and the [re-prewarm check](AUTO_MODE.md#5-upkeep) takes over. One exception: when the game drive is busy (4 MiB/s or more, or its load is unknown) and the samples come out cold, they may have been slow because of another program's reads, so, once per recorded state, the recorded state is kept and only that round is skipped (no log line). If the samples come out cold a second time for the same recorded state, it is handled as when the drive is not busy: the recorded state is dropped and the game is left to the re-prewarm check. The mark that one round was skipped is cleared when the recorded state is dropped or made anew, or when a warm sample is seen. A game that a gate blocks is skipped and the rest go on; a blocked game that is due does not start a group, so it cannot make the others be touched again and again. Afterwards the recorded states of the games that were touched are written again from one point in time: the amount reused first for a game is the cache in the standby list minus what that game and the games touched after it touched, and the count of reused pages is the one of that moment. A skipped game keeps its recorded state, but its amount reused first is lowered by the rule of step 2. A group refresh is not repeated within 60 seconds of the last one, and a re-reference of other games' cache before a stream, during one and right before its ladder (see the details) counts as one: each of them that touches a game sets the time of the last group refresh (the one right before a ladder does not wait for the 60 seconds itself). The time spent touching while no game is running is also capped: the time used by group refreshes, the re-references before and during a stream, and the ladder after a stream is counted together, and a group refresh is made only while that total stays within 2% of wall time. After a touch that took 7 seconds, for example, the next group refresh waits until 350 seconds have passed; the 60 seconds above stay the minimum. Only the group refresh that the 30-second check starts is held back by the cap: the re-reference before a stream, the one during a stream, the one right before its ladder and the ladder itself are not, but their time counts toward it. The touches at game start and while the game runs (see the details) are not part of this, and neither is the time the stream spends touching each batch it has just read. When a refresh that is due is put off by the cap, one line `cache refresh deferred: ...` is logged, and no further line until the cap has passed.
5. **Stop when the disk is read.** A page that is no longer in the cache would be read from the disk by the touch. After each view, SOLAR compares how many pages the whole system has read from the disk meanwhile and stops once more than 32 MiB is counted. Then the recorded state is dropped and the game is flagged for the next re-prewarm check, which re-prewarms it even if its samples look warm. Parts still in the cache cost almost no disk time, so in effect only the missing parts are read. At most one such re-prewarm per game is made each `auto.rewarm_minutes`, counted from the last prewarm attempt.

If Windows' statistics cannot be read (for example because the privilege is missing), step 3 falls back to a refresh every 10 minutes after the last ladder, with no other change.

<summary>Details: the numbers, how a touch is made, how disk reads are told</summary>

- **How a touch is made.** Each range is mapped as its own read-only view of at most 64 MiB, read 1 MiB at a time from inside the service's own process, and unmapped at once. Nothing is locked and no mapping is kept. Up to 64 files are open at a time. The result is the same as if a program had read the pages normally.
- **Why a view per range.** On the test PC, a file's ranges left the cache in the order they were touched only when each range had its own view that was released right after. With one view for all ranges they left in address order (SOLAR experiments E10 and E11).
- **Where 0.4 and 512 MiB come from.** In the eviction experiment (SOLAR experiment E9) the first untouched file left the cache when the reuse count had grown by 0.61 to 0.81 times the amount reused first. Some of the pages reused first are used again and drop out of the way, so the real moment comes earlier than a plain count suggests, and a margin was added. The lower bound of 512 MiB keeps a small amount reused first from triggering refreshes too often. Both values come from that one experiment and have not been tuned further. The 2 GiB of room comes from a reuse burst of about 1.9 GiB within 30 seconds that was seen twice in one measurement on the installed PC (see the measurement record); it is a value of that PC and time of day, not a general one.
- **How disk reads are told.** The number of disk reads of the service process itself (its hard fault count) is read about every 64 MiB touched and, when a piece takes long, sooner (after at least 8 MiB and 100 ms); the first reading of a round is thrown away, and within a round the count carries over from one group of ranges to the next. A touch ends when the count has risen by more than 32 between two readings (about 1.7 MiB of missing data), or when more than 32 MiB counted as read from the disk (the smaller of the pages the system read and the readings times 64 KiB). Touching ranges that are in memory raises the count by 0 to 1 even while other processes read the disk and every core is busy, so reads by other programs do not mix in; reads of the service itself through file mappings and the paging of its own memory would ("Keeping the cache while the game runs"). If the count cannot be read, the sum of the times of slow pieces (more than 20 ms per MiB, 2 seconds) is the only stop; with the count, only slow pieces in a stretch where the count rose by at least 4 are added.
- **What is touched.** The list is the common blocks that the prewarm reads first followed by the whole list that was read, in read order. It is put in the order of importance: the 64 KiB blocks of the ranked block list (`<game>.trace.json.ranked.json`, "Ranked block list" in [Automatic mode](AUTO_MODE.md)) that lie inside the range that was read come first in rank order, and the other prewarmed blocks follow in the read order; without the list it is the read order. The ladder is the reverse of that order (the least important first, the most important last). The ladder, the refresh, the touch at the start of the game and the keeping while it runs all use this one order, so when the game takes about 10 GiB of memory for itself and the oldest pages of the standby list go first, the less important blocks leave first and what survives is the front of the importance list, which the keeping then touches again up to the point where it ends. For a prewarm that read only the front part, it is the part that was read. A range that continues the previous one in the same file is joined to it.
- **Touching while reading.** After each batch of a prewarm stream (about 64 MiB of reads) and after the common blocks, the range just read is touched again in the same thread, under the same disk read lease (a permission granted per physical disk by the part of the service that arbitrates its background reads; it is cancelled when a game starts on that disk) and the same stop signal as the stream, and after the stream's own per-batch checks (memory, outside load, game running), whose order and meaning it does not change. If a game starts or the lease ends, no later batch is touched. If the touch finds data missing, throws, or is cancelled, the stream goes on and its result (the amount read, success) is the same; an exception is logged once as `requeue of the read batches skipped`. When the touch of a batch stops on disk reads, the later batches of that stream are not touched (so the disk reads are not repeated for each batch), and the done line says `requeue stopped by disk reads`. The same stop of the skipped front part ends only that touch. The time spent touching is left out of the `yielded` time and of the stream's exposure time (the time the stream spent reading the disk; ORBIT uses it to estimate how often a prewarm is interrupted by a game start), because a touch is not a disk read. It follows the same conditions as the ladder (see below), and with `memory.standby_ladder` off the stream does not touch what it has read.
- **Re-referencing other games' cache before a stream (the log calls this `protected`).** Right before a prewarm stream (service start, re-prewarm, supplement prewarm) reads from the disk, the other games that have a recorded state are touched once, the lowest-ranked first, by the same function as the group refresh (the stream's own game is left out). The pages the stream then reads push out the plain cache, and the stream's own old pages, before they push out another game. It runs under the stream's disk read lease and stop signal and only while no game start or launcher preemption flag stands. The sample check and the gates are the same as for a refresh. A launcher prewarm does not do this, because a game start is close and its prewarm must not be delayed; after that stream the ladder only lowers the amount reused first for the other games. The time it takes is left out of the `yielded` time and of the stream's exposure time, and the done line gets `, protected K games (N MiB in S s)` (left out when none was touched). If it fails or is cancelled, the stream goes on and its result is the same. It is skipped when the stream is small: when the amount the stream will read (its planned list, estimated as described below) would not make any game with a recorded state due even if the reuse grew by that amount (the criterion of step 3), the others cannot be pushed out by this stream, and this re-reference is not made. The amount the stream will read is its planned list (minus the part an interrupted supplement skips) plus the gap-filling budget. If the reuse then grows during the stream so that a game becomes due, the re-reference during the stream protects it. At the end of the stream the decision is made again with the reuse at that moment, and the re-reference right before the ladder is skipped only if still no game is due. The extra touch of the first-priority game after the ladder is always made, because the ladder just made would otherwise lie behind it.
- **Re-referencing other games' cache during a stream.** While a prewarm stream that is not a launcher's runs, after each batch has been read, checked and touched again, SOLAR looks at whether another game with a recorded state is due. It is the same decision as the 30-second check (the criterion of step 3 above: a game that can be touched is due and 60 seconds have passed since the last group refresh) by the same function. The decision reads the standby-list statistics once, so it is made only when 10 seconds have passed since the previous decision. When it is due, the other games are touched again by the same function as the re-reference before a stream. It runs in the stream's thread, under the stream's disk read lease and stop signal, and only while no game start or launcher preemption flag stands; the stream's own game is not a target (its ladder at the end makes it). A launcher prewarm does not do it. The time it takes is left out of the `yielded` time and of the stream's exposure time and is added into the `protected` tail of the done line (the number of different games, the totals of amount and time, and the number of times when it was more than once). When it writes the new recorded states, the cache in the standby list is reduced by what the stream has touched so far minus the amount the ladder at the end of the stream lowers anyway (what the stream game's earlier recorded state touched; with no earlier recorded state nothing is subtracted, because the ladder then lowers the amount reused first by everything it touched), because the pages the stream read are touched again by that ladder and then lie behind these games; this keeps the amount reused first for a game that the end of the stream then skips from being lowered twice (when the re-reference right before the ladder at the end of the stream, below, runs, the recorded states of those games drop this value and are written again in their real order). If it fails or is cancelled, the stream goes on and its result is the same.
- **Re-referencing other games' cache right before the ladder, and one group of recorded states.** Right before a prewarm stream that is not a launcher's has finished and makes its game's ladder (a ladder after a memory-limit finish included), the other games that have a recorded state are touched once, the lowest-ranked first. It is the same function, gates, sample check, disk read lease and stop signal as the re-reference before a stream, and the stream's own game is left out. The end of a stream happens once and the order has to be set then for the amount reused first to be right, so it does not look at "is it due" or at the 60-second minimum between group refreshes. Then the ladder is made, and the recorded states of the other games touched and of this game are written again as one group, in the order they were touched (the calculation of step 4). So whether or not this game had an earlier recorded state, the amount reused first matches the real order right after the ladder, and a recorded state written again as a group is not lowered a second time by the rule of step 2. This does not use the "subtract what the stream has touched so far" of the re-reference during a stream. When the re-reference could not run (a launcher prewarm, no other game with a recorded state, a group refresh in progress so it was skipped) and for a game the re-reference skipped (blocked by a gate, for example), the ladder lowers the amount reused first by everything the ladder touched if this game had no earlier recorded state; the recorded state of the stream's game can already be dropped (after a cold sample or missing data was found, for example), which would give 0 under the rule of step 2. How much of it really went from before the game's pages to after them is not known, so it takes the larger amount, which at worst brings a refresh one round early. With an earlier recorded state, the rule of step 2 stands as it was. The time it takes is left out of the `yielded` time and of the exposure time and is added into the `protected` tail of the done line.
- **A ladder right after a service start.** A game that the service-start prewarm skipped as `prewarm skipped (already warm) [service start]` gets its first ladder on the spot, using the sample verdict of that skip (the samples are not read again), under the same conditions and by the same function as the first ladder of the re-prewarm check. With several games the lowest-ranked is made first and the recorded states are then tidied by the group rule. A game in a partial state (a supplement prewarm waiting) follows the conditions of the first ladder for a supplement prewarm that waits for memory. The launcher path does not do it. It fills the gap in which, after a restart, there is no recorded state and no refresh until the first re-prewarm check (after `auto.rewarm_minutes`).
- **Where the first ladder comes from.** After a prewarm stream of the game has finished to the end (service start, launcher, re-prewarm, supplement prewarm). When the ladder of a game is made, the amount reused first for the other games' recorded states is lowered by the rule of step 2 (a first ladder, of a game with no earlier recorded state, lowers nothing; the ladder at the end of a prewarm stream follows "Re-referencing other games' cache right before the ladder, and one group of recorded states" above). A stream that ended at the memory limit makes a ladder over the range it read, right after it ends, in the same lease. The target is the front of the same window the stream read, cut at the amount read, so the part that was not read is not touched. This holds only for a window read or a continued read, which have no gap-filling budget, so the list the stream read is the one planned for the same window. A supplement prewarm that read a full list with such a budget and stopped at the limit makes none; it is left to the re-prewarm check, whose first ladder covers a game that waits for memory. After a service restart the recorded states are gone, so a game that the start prewarm skipped as already warm gets a new ladder right after that, and any other game at the first re-prewarm check with warm samples.

- **A touch when a game's executable starts.** When a registered executable of a game starts (the first one, and each later one of the same game), the game's prewarmed list is touched again in memory in ladder order (after the first hold of a game that is held, the part the hold already holds is left out; the touch at the start of a later executable of a game whose keeping already runs does not leave the held ranges out separately; see "Holding the cache while the game runs"), in a lease of the start stream's kind, apart from the start stream and the stage stream, which it neither blocks nor delays. The point is that the game then takes 9-10 GiB for itself and the oldest pages of the standby list go first: when the guess of which game is played next is wrong, the cache of the game that was actually started would go first. The range is the one the ladder uses (what the prewarm read, with sparse files and unbuffered files left out), the recorded state and the amounts reused first of the other games are updated as for a ladder, and the disk is not read beyond the usual limit: the touch stops at the first range that is not in memory. That point is found from the number of disk reads of the service process itself (the hard fault count of the process, read about every 64 MiB touched and sooner when a piece takes long): when it has risen by more than 32 since the last reading (about 1.7 MiB of missing data) the touch has reached the boundary of what is still in memory. Measured on this PC, touching ranges that are in memory raises the count by 0 with noise of +1 now and then (the first reading after a pause pulls the reading buffer and the code back in, so the first reading of a round is thrown away), even while another process reads the same disk and every core is busy, and a missing range raises it by about 19 per MiB. Reads that the service itself issues with `PrefetchVirtualMemory` or with cached `ReadFile` did not raise the count either (+0 for 64 MiB each), so the service's own streams do not mix in; the paging of the service's own memory, or reads of other threads of the service through file mappings, would. Time alone does not stop the touch, because a busy CPU also stretches the time of ranges that are in memory (all cores busy stopped a time-only rule in 5 of 6 runs while the count stayed at 0); the sum of the times of slow pieces stays as a last fallback limit (2 seconds), but only for the stretch between two readings in which the count rose by at least 4 (the noise is +1, a missing 64 KiB block is 2 to 3), and the line of a stopped touch says which of the two ended it. A reading that a slow piece brings forward waits until the touching took at least 100 ms since the last reading, so a busy CPU does not make the readings frequent, and the round line shows how many readings were made (`checks`). When part of the list is already known to be missing, or the ladder-order touch stops at a missing range, the touch first goes through the list in the order of importance (the order the prewarm read it) to find the end of the front part that is still in memory, then touches only that front part in ladder order, so that the most important block that is left goes last. The reason is that the standby list gives up the older, less important pages first, so the missing range is usually at the start of the ladder order and a ladder-order touch would stop before it touches the most important part. In that case no "all of it is in memory" recorded state is made and the missing flag stays, so the re-prewarm check reads the rest after the game ends; the amounts reused first of the other games are lowered by the size of the front part, as for the end of a prewarm stream (this game has no recorded state, so the whole touched amount counts). When another registered process of the same game is already running (a mode switch, or the game body after a launcher), the touch does not read the disk to fill anything: it skips the ladder-order touch and the search for new ranges and touches only the ranges that this play has already found in memory, because the game's own loading is reading the same disk; the line ends with `, disk reads skipped (the game is already running)`. The 60-second wait below is checked first. It runs only for a game whose start stream is allowed (game policy, `auto.start_stream_enabled`, the quick-exit back-off), only for a game whose list is in memory by the same conditions as the service-start ladder (prewarmed since the boot, skipped as already warm at the service start, or with a recorded state), and not during a relocation. The lease ends it when the game ends, when another game starts on the same disk, or when the service stops. The start stream and the stage stream always come first: the leases do not block each other (the part that grants leases does not count the leases already out), and the touch reads at low I/O priority on its own thread. A second touch of the same game waits 60 seconds after the end of the first (the same length as the start stream cooldown and the stage stream cooldown); the executables of one launch come within seconds of each other, before the game has taken its memory, so a second touch would change the order very little. It opens no process and does not write.

## Keeping the cache while the game runs

The touch at the start happens once, and the game keeps reading afterward. During play it reads 0.8 to 1.7 GiB per minute of data that was not prewarmed (in the 2026-11-21 Call of Duty play the reuse total of the priority-5 standby list grew by 8.5 GiB in the 180 seconds after the start), and pages that the prewarm put in memory leave the standby list within minutes to a dozen minutes. Measured in matches, 71 to 88% of the disk read latency during the match came from blocks that were already in the prewarm list. So the same work continues after the touch at the start for as long as any registered executable of the game runs. What it keeps, the keep list, is the prewarmed list in the order of importance, the same order that the ladder and the touch at the start use.
There are two ways. A game that has volatile-file information (the marks of files the game writes) and that the anti-cheat gate for holding does not block is kept by **holding** (keeping the keep list mapped in the service and in its working set; see "Holding the cache while the game runs" below, and the re-touching of this section still runs for the part that the hold did not take); every other case (a game whose anti-cheat forbids tracing, a game without volatile file information, or `memory.keep_hold` turned off) is kept by the **re-touching** of this section (touching the keep list in the standby list again in memory each time the reuse has grown enough). The holding gate has the same range as the trace gate (EasyAntiCheat, BattlEye, Vanguard, kernel-level and unknown kinds are blocked; Ricochet and no anti-cheat are allowed), so for example holding does not run for League of Legends (Vanguard) and runs for Call of Duty (Ricochet).

- **When it runs.** When the standby-list reuse total (`MemoryLists.CacheRepurposedBytes`) has grown by a threshold since the last round (or the touch at the start). The total is checked every 5 seconds (one system statistic, no process is opened). The threshold is `min(1 GiB, (priority 5 standby size - keep list size) / 2)` with a floor of 64 MiB (touched pages go to priority 5 and 6 and 7 are reused only after 5 is used up, so only priority 5 counts as the room in front; the first round too is calculated with the real size of the keep list, which is computed before the loop starts): the standby list reuses the oldest pages first, so the list has to be touched again before the other cache in front of it is used up. Halving is room for the reuse that grows between rounds, and it is not a value chosen by an experiment. Rounds are at least 10 seconds apart. Nothing runs while the reuse does not grow. If the total cannot be read, it runs every 2 minutes.
- **A confirmed set, and finding a missing piece.** During the play the service keeps a **set P of ranges confirmed to be in memory** (in importance order). When P is not empty a round has three steps, always in this order: (1) the **protect pass** walks P **from the most important** and touches it, so the most important part is touched again right at the start of the round; (2) the **order pass** touches what is left of P again from the least important to the most important, so that the most important comes to the newest place of the standby list; (3) the **look outside the set** (last, optional) checks ranges that are not in P a little at a time and puts those in memory into P. There is no speed limit and no rest in any of them. The protect pass and the look outside the set use the **find** (the pass that looks for the ranges still in memory): if reading a piece (1 MiB) took longer than 2 ms, it reads the hard faults of the service process at once instead of waiting for 8 MiB (at least 20 ms between two reads), and an increase of 8 or more is a miss (measured on the same PC: a range in memory shows +0 to 1 between two reads, a missing 1 MiB piece 16 to 48, so 8 is not reached by the 1 to 5 faults that other threads of the service make in the same 20 ms). A piece that is not slow is read every 64 MiB and then too the increase has to be 8 or more. The disk read needed to notice one missing piece is that piece (1 MiB or less).
- **A hole and a boundary.** When a miss is confirmed, only the next 8 MiB (the following ranges of the list order, also of other files) are skipped without reading, and the point after the skip is **always** checked, whatever the time since the last check (on a real hard disk reading one missing piece can take less than the 20 ms between two checks). If it is in memory, the miss was one hole and the walk goes on. If it is missing too (two points in a row), that point is a **boundary**: the walk stops and the rest behind it (the less important side) is taken out of P in that round. The protect pass has its own disk read cap (`KeepProtectDiskCapBytes`, 8 MiB): past it that point counts as a boundary too and nothing behind it stays in P. The order pass reads at most `KeepOrderDiskCapBytes` (32 MiB) from the disk in a round and ends there when it is exceeded (the protect pass has already touched the whole of P from the most important, so stopping does not break the protection of the most important part; this cap does not count for the cap of the play, and the log says that it was reached): when a batch reads the disk (the range was pushed out in the meantime), only that range is taken out of P (it is not remembered as a hole, the other ranges of the same file are not skipped) and the pass goes on. What was taken out of P is outside the set; the look outside the set of the same round (and of later rounds) checks it again, and it comes back when it is in memory. When the touch at the start stops at a first boundary (and also the touch at the start of another executable of the same game), the same steps build P and the same memory is used; all changes of P and of the holes are made under one lock of the memory, because the touch at the start of a second executable and the round can run at the same time. The memory is used for as long as the game runs (until all registered executables have ended).
- **Looking again outside the set, and the disk read caps.** The look outside the set reads at most 8 MiB from the disk in a round and at most 64 MiB in one play, and **only these reads count for the cap of the play** (the reads of the protect and the order pass do not, because each of them has its own defence above). Past the cap of a round it checks no new range; when the cap of the play is used up the keeping does not end, later rounds look at nothing outside the set and run the two passes on P. When P is empty (the touch at the start did not get to the end, or the service restarted while the game was running) a round does only the look outside the set, with a larger round cap (`KeepEmptySetRoundDiskCapBytes`, 32 MiB; the cap of the play is the same), and the ranges it collected are touched once more by the order pass (they were just checked, so no disk read is expected); when P is empty and the cap of the play is used up, a round has nothing to do and only the reuse total is looked at. Each round logs the size of P, what a boundary cut off, what was left out as holes, and the time and CPU of the order pass and of the find passes.
- **Gates.** Those of the touch at the start: the game's start stream is allowed (game policy, `auto.start_stream_enabled`, not a back-off after a quick exit), the list is in memory, no relocation is in progress, and `memory.standby_ladder` is on. A round is skipped while the available memory is under `prewarm.min_free_ram_mib`.
- **Limiting the effect on the game.** The re-touching has no speed limit and no rest (a pass takes about 5 seconds per GiB by the speed of moving pages; the cap of 256 MiB per second stays only for holding). The reading thread lowers its CPU priority and I/O priority once during a round and restores them after it. Thread background mode is not used, because it would also lower the memory priority of the pages and send them to a lower-priority standby list. It runs under the same serialization lock as the touch at the start, holding and the check, but does not hold it for the whole round: every 128 MiB (or 8 batches) it releases the lock and yields for a moment (a .NET `Monitor` does not guarantee the order of waiting, so a thread that takes the lock again at once may keep a waiting thread out for a long time) and takes the hard fault baseline again after taking it back, so the touch at the start of another executable can come in and the hard fault total of this process is not mixed with the reads of another touch. Consecutive ranges of the same file in the list are mapped as one view (up to 64 MiB of address width). One read of the fault count costs about 4 ms of CPU.
- **The list is computed once per play.** The list to touch (the planned prewarm list, the common part, the importance order) is computed in the first round and reused, and computed again only when its inputs change during the play (the plan, the trace, the prewarm-only file, the volatile mark, the list of files read without the cache, the length and modification time of the block ranking list, or the part the prewarm covered). That computation runs at low CPU priority. Measured on the priority-2 standby list, what survives after memory pressure is the contiguous section that was touched last. Inside one 64 MiB view the lower file addresses go first, so the precision of the order is the size of one view (up to 64 MiB).
- **Cost, and what is not guaranteed.** Measured on cached real game files (the first 1 GiB of the installed Call of Duty ranking list, importance order): a pass costs about 1.1 to 1.3 s of CPU per GiB and about 5 s of time. It puts that much at the back of the standby list, so the cache of other programs is pushed out that much earlier. When the reuse comes in bursts the gap between rounds shrinks to the 10-second minimum and uses more CPU and memory bandwidth (not measured in real play). The disk reads stay within the caps above at low I/O priority, but a request already sent still occupies the HDD head, so disk reads during a match cannot be removed completely (about 2 MiB at the first finding). The fault count is that of the whole service process, so the service's own paging or reads of other threads through file mappings are counted too and can make a miss where there is none (the threshold of 8 makes this rare); then the skipped stretch is remembered as a hole even if it is in memory and is not touched during that play, and a boundary needs two such points in a row. Not guaranteed: the remembered missing ranges, files the game writes during play, blocks in no list, sparse files, and files read without the cache.
- **When it ends.** Only one keeping runs per game, so when executables start one after another (a launcher and then the game), the second one does not run. Each round takes a new lease of the same kind as the start stream, which is canceled when another game starts on the same disk or the game ends. It ends when no registered executable of the game is running or the service stops; it does not end because ranges are missing or because nothing was found in memory (a stretch of missing ranges in front of the most important part does not stop the keeping of the rest). It opens no process and writes nothing.

### The order of the keep list: reads of the match first (2 GiB)

The keep list used to follow the block ranking as it is (the number of plays in which the block had a paging disk read, then the summed disk latency). Now the first 2 GiB of it (`LoadRefillPlanner.PlayFrontBytes`; blocks of sparse files do not count toward the 2 GiB) are put in the order of a **play-phase score**, and the rest stays in the old order, each block once. The ladder and the touch at the start use the same importance order, so they follow it too. The prewarm selection (which blocks fit the prewarm budget), the first 256 MiB (tier0) and the load list are not changed.

- **The score.** For each play in which the block had a paging disk read: 1 point; 3 points (`PlayPhaseWeight`) if the block was touched by one request only and that read came 120 seconds or more after an executable start, that is, outside the load right after the launch (in the match or in a later load). A summary without executable start times, a read before the first start, and a block read more than once in a play (its time cannot be split) count 1 point. The score is saved as the fifth cell of each block in `<game>.trace.json.ranked.json`; a file without it (written by an older build) keeps the old order.
- **Why 2 GiB.** In a cross-validation on this PC (earlier plays of Call of Duty, each play predicted from the plays before it, shares of blocks in the first 2 GiB by the share of general files; sparse files were treated apart), this order covered 22.8% of the paging reads in the match (the old order 16.9%) and 27.8% of those in later loads (old 15.6%). At 3 and 5 GiB the old order was equal or better, so only the first 2 GiB use the score. For the first load after the launch the old order was better and is kept.
- **Limits.** Only what the past records show can be matched: with 5 GiB the first-in-time model put about half of the disk reads in the match inside the list (model time, 75.3 MiB/s, 5,400 rpm), and the rest was not in any earlier play. These figures are estimates from this PC and this game, not measured in real play, so the gain in frames is not known. The prewarm selection did not change, so a block that has a high score but is not in the prewarmed list is not kept. Other games had no disk summaries to check against.

## Holding the cache while the game runs (`memory.keep_hold`)

The cache keeping above only touches the pages on the standby list again in each round, so it cannot stop a page that is pushed out between two rounds. In the 2026-11-21 Call of Duty play (a development build) about 3.3 GiB touched right after the start was gone from the standby list within minutes, and the keeping round of that play stopped at a missing piece early in the list although many blocks after it were still in memory (6 to 13 of 16 sample positions were in memory). So while the game runs, the keep list is held as mapped views of the service. It is on by default (`memory.keep_hold`); when it is off, the standby-list touching above applies. There is no switch in the Settings tab.

- **Method.** For each file the service creates a read-only section, closes the file handle at once, keeps one view open over the whole file (one view per 1 GiB window for files larger than that), and reads only the ranges of the keep list, 1 MiB at a time, into the working set of the service process. The part that is not read uses no memory. Because the view is not closed, the pages are not on the standby list, and neither the game's reads nor other programs' memory use reach them in the reuse order. Only documented calls are used (`CreateFileMapping`, `MapViewOfFile`, `UnmapViewOfFile`, `VirtualUnlock`, `GlobalMemoryStatusEx`, `GetFileAttributesEx`); `VirtualLock` and forcing a minimum working set are not used. No game, launcher or anti-cheat process is opened.
- **Which games.** Games for which the holding gate (the same range as the trace gate, see [Anti-cheat compatibility](ANTICHEAT.md)) does not block holding, and that have had a raw trace at least once. Ricochet games (Call of Duty) are held although pinning is forbidden for them; League of Legends (Vanguard) is not held and the re-touching above keeps it. The start line of an anti-cheat game carries `(anti-cheat: <kind>, hold allowed)`.
- **When and how much.** Right after the game's executable has started (before the touch at the start, see below), the keep list of that play (the importance order from "What it touches" above) is held from the front. The target is the smallest of three values: the existing budget (half of the available memory), the amount that leaves the available memory above the floor after holding, and 5 GiB (the first hold of a play also leaves room for what the game is still expected to take, and when no amount has been learned from the play records it uses a quarter of the available memory instead of half; see below). The 5 GiB comes from the per-block disk reads of the 2026-11-21 Call of Duty play: the first 2, 3, 4, 5 and 6 GiB of the ranking covered 32, 39, 42, 47 and 49% of the cached-read latency during the match, and little more beyond 5 GiB (an approximation from one play). The target is not held at once but 16 MiB at a time, and before each batch the available memory is compared with the floor; holding stops there when it is reached.
- **Missing pieces are skipped.** When a batch mixes in disk reads (the hard faults of the service process rise over the tolerance, the same decision as in "How disk reads are told apart"), the rest of the ranges that follow in the list from the same file are skipped and holding continues with the next file. Disk reads in one round are capped at 32 MiB; past the cap the round ends. The cap is looked at after each 16 MiB batch, so a round can pass it by up to one batch. If the number of disk reads of the process cannot be read at the start or the end of a batch, the batch counts in full as read from the disk against the budget (not for the loading judgment), the walk ends at that batch, and the hold adds no further read from the disk for the rest of the play: no holding again (also not when another executable of the same game starts after everything was released), no continuing, no sample read after the first pass, and no read-back in the check (the reduced ranges are taken off the hold, as when memory is short). What is held stays, and the floor release and the other release decisions go on as usual. This is logged once. The reading thread runs at low I/O priority and low CPU priority.
- **Floor and release.** The floor is 2 GiB (the constant `HoldMinFloorMib`, separate from `prewarm.min_free_ram_mib` of the prewarm). The available memory includes the standby list that can be reused at once, the held pages are not locked so Windows can reduce them when it needs to, and the floor watch releases the less important part every 1 to 5 seconds, so there is no reason to set the floor as high as 4 GiB (with the minimum available memory of 3.9 to 5.7 GiB in two play records on this PC, a floor of 4 GiB would release almost everything; with 2 GiB about 1.9 to 3.7 GiB can stay held by that calculation). The available memory is checked every 5 seconds when it is far from the floor, and every second when it is within the floor plus 2 GiB or in the first 3 minutes after holding (when the game takes the most memory while loading); below the floor, the less important part of what is held (the part held later) is released with `VirtualUnlock` by the missing amount plus 256 MiB. On a range that is not locked it returns FALSE with error 158, but the range leaves the working set and is pushed out of the standby list in the order it was released. A released range is held again only under the conditions of the next item.
- **Holding again.** If the floor released everything that was held, the hold ends but the keeping above goes on, and the 2-minute retry of the hold (the same period as the check) holds again. If the floor released only part of it, the 2-minute check holds that part again in importance order. Both wait until all of these are true: the loading judgment (the service's judgment, once per second, of whether the game is loading, made from the graphics memory of the game and the drive reads; see [Automatic mode](AUTO_MODE.md#6-while-a-game-runs)) says the game is not loading (neither a loading that started with an executable start nor one found by the disk and graphics signals); the disk queue of the game drive in the last one-second sample of the disk performance counter that the play record already reads is 0 (an unknown queue counts as not 0, so nothing is read from the disk then); and the target is at least 64 MiB, where the target is the smallest of 5 GiB, half of the available memory, and the available memory minus the floor minus 1 GiB (`HoldRefillMarginMib`, the same margin as the check uses), so that after holding again the available memory stays at least 1 GiB above the floor. A change of the available memory within that 1 GiB does not make the release and the holding again alternate; with a larger swing across the floor they can alternate, but the holding again is tried only after a 2-minute check (or retry; a second later if the serialization lock was busy), so at most once every 2 minutes, and its disk reads are bounded by the 1 GiB per play. The disk reads of a holding again are 32 MiB per round at no more than 256 MiB/s as before, and 1 GiB in all per play (`HoldAgainDiskCapBytes`); the reads that find a range missing count too, so the total can pass 1 GiB. A round of holding again does not look at what is left of the 1 GiB before it asks: it asks for the released ranges in batches of 16 MiB and stops after the first batch that reads from the disk. A round is tried after each two-minute check (and when the hold itself waits to start again), so even after the 1 GiB is used up each round can still read up to one such batch; this is tracked in #355. When the 1 GiB is used up, only what is still in the cache is held and the holding stops at the first batch that has to read from the disk. The range where a missing stretch was found is given up and not read again; the later ranges of the same file that the holding skipped without looking are tried again at the next check. A file that changed or was closed in that play is not held again. The first hold when the executable starts follows the rules of "When and how much" and none of these conditions applies to it; neither is the release, which is not postponed by any condition. How much holding again shortens the next loading has not been measured: what is held again is released again when the available memory falls below the floor at the next loading.
- **First, before the touch at the start.** The first hold runs right after the executable has started, before the touch at the start. The game takes memory soon after it starts, and the prewarmed pages can leave the standby list while it does, so an earlier hold can find more of the list still in memory (the loading of the game also reads files back into the cache, so this is not always so). The touch at the start that follows this first hold works on what the hold did not take (a held range is in the working set, not on the standby list, so touching it again changes nothing), and the floor watch of the hold goes on in its own thread while the touch runs. The touch at the start of a later executable of the same game, while the keeping already runs, touches the ranges that are confirmed to be in memory and does not leave the held ranges out separately. The gates, the 32 MiB disk read cap of the first pass and the floor are as before. The target of the first hold also subtracts what the game is still expected to take (the amount learned from the play records minus the fall of the available memory since the executable started), so the target leaves room for it (on a PC with little memory this makes the target smaller, and a smaller target should need the floor release less often; not measured); with no learned amount the target takes a quarter of the available memory instead of half (`HoldUnknownFootprintFraction`, not a measured value), because it is not known how much the game will take. The formulas of holding again and of the continuing are unchanged. A game that cannot be held (anti-cheat gate, no volatile file information, the setting off) starts with the touch at the start, as before. The start line of the hold says how many seconds after the watcher noticed the executable the hold began. The start stream is a separate task and is not postponed until the hold ends: the two run at the same time, and the disk reads of the hold (the 32 MiB cap of the first pass, at low I/O priority) share the drive with it (the effect has not been measured). Whether holding earlier raises the amount held in real play has not been measured.
- **Continuing after the first pass.** When the first pass stopped before the whole list was taken (the 32 MiB disk read cap, the floor, or missing pieces), the ranges not taken are remembered in importance order: the ranges skipped after a missing stretch and the ranges not visited (not the range where the missing stretch was found). The hold continues with them under the same conditions as holding again (not loading, drive queue 0, a target of at least 64 MiB, the floor looked at again for each request), checked every second and asking for 4 MiB at a time (`HoldContinueBytes`). Within one check it goes on with more 4 MiB requests, at most 16 (64 MiB), as long as no disk read or missing piece shows up, and ends the check at the first one that does, so a check reads at most one 4 MiB request from the disk (the system may read a little ahead of it). If the number of disk reads of the process cannot be read at the start or at the end of a request, the request is counted in full as read from the disk against the 1 GiB of the play, and the hold adds no further read from the disk for the rest of the play (see "Missing pieces are skipped"). The 4 MiB (the unit in which a disk read is told apart), the one second and the 16 are not measured values; they limit memory-resident ranges to 64 MiB per second (the 256 MiB/s speed limit of holding still applies). A range found missing is dropped together with the ranges of the same file that follow it in the list, so within the continuing the same range is not read from the disk twice; holding again after everything was released, the two-minute check and the keep rounds can read a range again, each within its own cap. The disk reads of the continuing and of holding again share the 1 GiB per play (`HoldAgainDiskCapBytes`); when less than 4 MiB of it is left the continuing stops for the play and drops its candidates, with one log line. A first pass that held 0 MiB continues the same way. If the start touch, a keep round or another path holds the serialization lock, the request is skipped and tried again a second later. The continuing writes nothing to the disk except its log lines. Its log has one line after the first request, one when the candidates are used up or the play's cap is reached, and one each time the kind of the reason for waiting changes (a change of the queue value is the same kind), with the totals so far; the closing line carries the amount held by continuing.
- **Keeping the rest while holding.** While the hold covers only part of the keep list, the re-touching of the section above runs for the rest, starting after the touch at the start has ended; a round is started only while the loading judgment says the game is not loading (a round that has started goes on to its end), with the same reuse threshold and the 10-second minimum gap. The ranges held now are left out of every round (they are in the working set, not on the standby list), and the round follows what the hold holds or has released. The rounds run in their own thread, so the floor release of the hold waits neither for them nor for the serialization lock (it takes only the hold's own internal lock); the two-minute check and the holding again of released ranges do not wait for the serialization lock either (they are skipped and tried a second later). The disk reads of these rounds are those of the re-touching (the caps of that section: per round 8 MiB for the protect pass, 32 MiB for the order pass and 8 MiB for the look outside the set (32 MiB when the set is empty), and 64 MiB per play for the look outside the set), so for a game that is held they are reads that this behavior adds. They are the same caps and passes that the re-touching of a game that is not held already has: the protect and order passes have no total per play (a range that caused a disk read leaves the set, so it is read again only after the game has put it back in the cache and a look outside the set has taken it in again). A game that is not held is kept by the re-touching of the whole list as before.
- **Check.** Every 2 minutes it looks with `QueryWorkingSetEx` (own process, does not touch the accessed bits) whether the held pages are in the working set, and reads back in only those that the memory manager has reduced. Reading the whole held range again would make the pages look recently used, so that when memory is low they could be reduced after pages the game has not used for a while, and it also costs CPU. The cost of querying by page grows with the held amount (1 GiB is 260 thousand pages) and has not been measured at that size; the check line carries its time and CPU. The amount read from the disk while reading back has a 32 MiB cap per check too; past it, that range and the later ranges that have reduced pages are taken off the hold (that is a sign that memory is short, so it is not recovered from the disk). The check does not look at the drive queue (the queue-0 condition belongs to holding again and continuing). While the loading judgment says the game is loading by the reads and graphics signals, the cap is 2 MiB (`KeepLoadingCheckDiskCapBytes`) and a range that reaches it stays held (the next check goes on); while a loading that started with an executable start is judged, the usual 32 MiB applies. The cap is compared after a piece is read, and the disk reads are counted only when the statistics are read (every 64 MiB, sooner when a piece is slow), so the check can pass the cap by up to that interval; this is a known limit, tracked in #355. After a play has shown that the disk reads cannot be told apart (see "Missing pieces are skipped"), the check does not read back at all. If the available memory is under the floor plus 1 GiB the check does not read back what the memory manager reduced and takes those ranges off the hold instead (so the service does not trade pages with the memory manager every 2 minutes). The same check compares the size and modification time of the held files and closes the views of a file that changed at once. The rule that skips a round when the standby-list reuse is small does not apply to held ranges.
- **At the end.** When all registered executables of the game have ended, or the service stops, or the setting is turned off, or an exception occurs, everything is released, the less important first, and the views and sections are closed. If another executable of the same game starts (a game whose stages start different executables) while something is still held, nothing is held again and what is held stays (when everything was released for memory and the hold only waits for its 2-minute retry, that start makes the hold start at once as at an executable start, with the rules of the first hold and without the conditions of holding again); the touch at that start reads the held ranges without faults. An exception while holding ends only this feature and does not stop the other work of the service or the play record.
- **What is not held.** (a) Files marked volatile (those in `<game>.trace.volatile.json` learned from the trace and those that match the name rules, such as the `xpak_cache` the game writes during a session), except the game-written files that meet the conditions of the next item, (b) files whose modification time changed after the block ranking list (or the raw trace if there is none) was made, (c) sparse files, (d) files whose size or modification time changed after they were held (the view is closed at the check), (e) anti-cheat component files (names that the anti-cheat rules know, for example the Ricochet driver), (f) executable images, judged by content (the first two bytes of the file are `MZ`, not the extension; a file that cannot be read is not held either), (g) files under 16 MiB (index and setting files gain little and are likely to be rewritten or shrunk, and the volatile mark may not exist yet for them). The start line says how much was left out for each of these reasons. Volatile files are not held because a write that shrinks a file that has a user mapped view fails with error 1224 (`ERROR_USER_MAPPED_FILE`), and mixing a mapped view with writes that bypass the cache is known to leave stale content in the cache. Also, a game that never had a raw trace is not held, because it is not known which files it writes, and a game whose anti-cheat forbids tracing (the holding gate) is not held either. For a game that is not held the cache keeping above takes over, but with `memory.keep_hold` on it no longer ends at one missing piece; it skips and goes on to the end of the list (within the same 32 MiB cap). There is no rule by game name or extension. Files for which holding would lose more than it gains are not held either, with the game-written files too. While a file has a view, all its reads without the cache (`FILE_FLAG_NO_BUFFERING`) are slower (in a measurement that replayed recorded game reads with a test program, 2.08 times for the held files and 0.96 times for the files not held; 7 to 18 times while holding, 1.5 to 4 times while a view remained, 1 time right after the view was released), and holding gains nothing for those reads. The held amount did not change the slowdown in that measurement, but this is weak evidence (each compared set held only 2 to 6 files). The judgment is per file, over all plays whose read modes were recorded: a file is left out when `L * (2.08 - 1) > 0.4 * G`. `L` is the disk delay of its reads without the cache (paging requests not counted); the summary has no delay per read mode, so it is the delay sum of the file's rows times the fraction of the bytes read without the cache. `G` is the disk delay of the reads through the cache that the file's ranking blocks cover, the delay sum of the same rows times the remaining fraction. 2.08 is the measured slowdown. 0.4 is a cautious estimate of how much of the covered delay holding really removes: in the same measurement holding removed 53.3 s of the 100.8 s of cache-path disk delay it covered in run 1 (0.53) and 27.8 s of 100.6 s in run 4 (0.28). So 100.8 s is the delay that holding covered, not what it reduced; against the 65.0 s and 119.3 s of delay added to the reads without the cache, the net was -11.7 s in run 1 and -91.5 s in run 4. A file without delay records is judged by its request counts: it is left out when the reads without the cache outnumber the reads through the cache and the paging reads. Limits: for files read both ways (through the cache and without it) the real slowdown was not measured, because the replay chose one way per file by the majority, so the 2.08 of the files read in one way is reused; and `G` is an estimate from the ranking list, not a measured gain. In that measurement the files read without the cache were 8 files, 71 MiB, 2.1% of the held list. In the Call of Duty records of this PC (4 plays with read modes) the criterion leaves out 849 files, 155 of them in the 7.62 GiB ranking list (1,407 MiB, 18%). With a 5 GiB target the estimated loss falls by 80% (1,415 to 277 in delay-sum seconds per play) and the estimated gain by 10% (7,072 to 6,352), and 5 GiB is still filled by the next blocks; the reads without the cache that fall on held files are 5% of the game's (8,783 of 173,863 requests) instead of 59%. Leaving out only the files with more requests without the cache than through it removed just 17% of the loss, because two files read mostly through the cache lost more than they gained. "At least one read without the cache" would cover 93% of the ranking list and is not used. The list is saved with the ranking lists (`<game>.trace.json.nocache-read.json`) and rebuilt at the end of a play and at service start when it is missing or old; summaries from before the read modes were recorded count as unknown, and a game with only those is held without this judgment. A file that is first seen losing more than it gains during a play is not released at once; it counts from the next play. The start line carries the amount (`N MiB in files where holding loses more than it gains`).
- **Game-written files (`memory.keep_hold_written_files`).** A file that the game itself writes during a session (the trace marked it volatile because it was opened for write or changed between two plays, for example the `xpak_cache\*.xpakdata` of Call of Duty) is held as well when all of the following hold; otherwise it stays left out. (1) Its size has never shrunk, judged from the NTFS change journal (USN) of the volume: the journal records a truncation itself (`USN_REASON_DATA_TRUNCATION`), so a file that was shortened and grown again within one play is not missed, as it would be when only the sizes at the end of the plays are compared. At the end of every play the service reads the journal (documented `FSCTL_QUERY_USN_JOURNAL` and `FSCTL_READ_USN_JOURNAL`, read only, the service runs as SYSTEM, at low I/O priority, not while the game runs, at most 30 seconds and 512 MiB) and matches the records to the files by file reference number, and the finished plays of the play record (`play_samples.json`) to the journal by time. A play counts only when it started inside the range the journal still covers; for each play, from the end of the play before it, the file is judged as truncated, replaced (created, deleted or renamed; or its file reference number changed), extended or overwritten only, or unchanged. A file is eligible when the 3 most recent finished plays (`WrittenFileHistory.MinSessions`) were all judged by the journal and none of them truncated it (a play among them that is not judged, for example one the journal no longer covers or that could not be read, breaks the chain, and the size records decide until the journal has judged the recent plays again); a truncation once excludes the file for good (the mark stays when old lines drop out). Plays of the play record before the journal's oldest record are not counted and are not guessed. When the journal cannot be read (no permission, no journal, over the limit) the size at the end of the plays is recorded: a file is then eligible after 3 recorded plays, the current size must not be below the last record, and a file that shrank between two records is excluded. Because the journal still has the earlier plays, the first judgment after the update of the service can already cover several plays. The history is `<game>.trace.json.written.json` next to the plan files (at most 8 plays per file and 256 files). (2) The game was not updated since the last finished play ended: at the end of every play the service stores a state mark of the game in the history file (a hash of the current sizes and modification times of the game files the plan knows, without the volatile files because those change in every play, and of the registered executables), and before holding it computes the same mark again. A different mark, or a mark that cannot be computed (no plan, no fingerprints, a file that cannot be read), counts as updated, and nothing game-written is held in that play; when that play ends the new mark is stored and the next play is normal. When there is no stored mark yet (the first play after the update of the service), the modification times of the same set of files are compared with the time the last finished play ended (from the play record): if none is later and every file could be read, the game counts as not changed since that play and the files are held; a later one, no finished play in the record or an unreadable file counts as updated. The modification-time comparison is made also when a mark is stored, and both must pass: the mark is computed when the trace is saved, after the grace period and the merge, so a patch that a launcher finished right after the game exited could already be in it, while the end time of the last play is the time the process disappeared. A play held this way stores the mark when it ends too. Remaining risks: an update that changes only files the plan does not know, and a shader cache that the game regenerates after a graphics driver update, are not noticed by this judgment. The change journal is not read while any registered game runs; if a game starts during the read, the read is cancelled and its result is dropped, so nothing (also not the ranking list) changes during a play. If the working set query of the 2-minute check fails three times for a range, that range is not judged in that check and the error number is logged once. The mark is taken from the current files and not from the fingerprints of the plan, so it still differs after the automatic mode has already rebuilt the plan from the updated files. (3) The file does not change in this play: its size, modification time and creation time at the moment of holding are remembered and compared every 5 seconds (`HoldWrittenCheckEvery`), only for these files, with one attribute query each and without opening the file. When one differs (the game appended to it, overwrote it, replaced it by renaming a temp file, or deleted it), the view of that file is closed at once, the other files stay held, the file is not held again in that play, and the log says which file and when. The check also runs once right after the hold has started, because starting takes seconds to tens of seconds on a hard disk, and a file the game changed during that time is released at once. The 2-minute check of the other held files runs separately. What the check sees is a change of size (an append is seen at once) or of modification time or creation time; in the test on this PC (2026-11-22) the modification time had already changed 10 to 15 ms after a write through a handle that was still open, both for a write without the cache and for one through the cache, but a later write through the same handle was not measured, so an overwrite that leaves the size and (until the handle is closed) the modification time unchanged could be missed.  The file identifier is not compared because that needs an open handle, so a replacement is noticed by the modification time and creation time; a replacement that keeps size, modification time and creation time all equal is not noticed. The gate for the anti-cheat, the sparse files, the anti-cheat files, the executable images and the 16 MiB rule, the floor and the cap apply to these files as to the others. **Ranking.** The blocks of these files go into the block ranking list by the same score as the blocks of other files (the number of plays in which the block was read, then the latency sum), but only blocks read from disk in at least 2 plays (`WrittenMinPlays`), so static and game-written files stand in one order and the cap of the hold takes them in that order. For a file whose history is good (the journal covered at least 3 plays, none truncated or replaced the file; without journal data, 3 size records that never shrank), the reads of the plays in which the game modified the file count too: a position that is already written does not change when the file only grows, so a position read in such a play (inside the size at the start of the play or after the append) exists in the next play as well. A file that was replaced (created, deleted or renamed) in a recent play, or whose history is not good, has the plays in which it was modified left out, as for static files. The ranking list takes the blocks of game-written files without the conditions of the holding: the prewarm and the short touching only read them, and only the holding, which keeps a mapping open, looks at the conditions. Without this the game-written files were left out of the ranking and came after all ranked blocks. The list is rebuilt at the end of a play (or at service start when it is stale), so turning the setting off changes the ranking only then. **Basis.** In the 2026-11-21 Call of Duty play (one play) 38% of the cached-read latency during the match came from the game-written files, 82% of that from files not modified in that play, and 81% of the blocks read from disk in those files (96% of their latency) had been read from disk in an earlier play too. In a test on this PC (2026-11-22, no game) with a read-only view that is not locked and whose file handle was closed, another process wrote to the file without the cache: the write succeeded, no old content was seen through any read path (the pages written leave the working set of the view and are read again), appending succeeded, and only shrinking failed with error 1224; old content was seen only when the view was also locked with `VirtualLock`, which the service does not do. The change journal over 13 hours and 3 plays showed only data-extension records on the `xpakdata` files (the `*.psolib` files are replaced by a temp file and a rename, the `*.xpak` and `*.dcache` files are overwritten). **Risk and what was not checked.** While the file is held, a write by the game that shrinks it fails with error 1224. No shrinking was recorded for these files, but it could not be excluded, so only files that never shrank in the records are held, never right after an update, and the view is closed within 5 seconds of the first change of size, modification time or creation time (right after the hold has started for a change during the start); a shrink in that window would fail, and an overwrite that changes none of these is not seen. How the game reacts to such a failure and how an anti-cheat sees a game-written file kept mapped by another process were not checked, and no vendor statement was found (see [Anti-cheat compatibility](ANTICHEAT.md)). The effect on real play is not measured yet. Whether the game writes these files without the cache or only appends is recorded for the next plays: the I/O summary of a play has `write_files` (per file the number and bytes of writes, of the writes without the cache, the first and last write time and the merged ranges written, at most 64 ranges per file, the 256 files with the most bytes). The switch is `memory.keep_hold_written_files` (on by default; it does nothing when `memory.keep_hold` is off). The size history is kept for every play, with or without a trace in that play: at the end of each play the sizes of the files marked as game-written by the earlier traces are recorded (file attribute queries only, also while another game runs), and it is recorded in this one place for every play, so a play counts once. The files named come from the earlier traces, so a new written file is seen from the play after the next trace. The size samples alone do not see a file that the game truncates and grows back within one play; the change journal judgment does, when the journal of the volume can be read (without it only that case is left).
- **What Task Manager shows.** The working set of the service (`AsterCache.Service.exe`) and the system's "In use" memory grow by the held amount and "Available" shrinks by it. Without holding, the same pages show as standby, that is, available. This happens while the game runs and goes back when it ends.
- **Play record.** The start available memory and the minimum available memory that the play record stores include the held amount. The added amount is capped by the growth of the service working set (the difference from the value before holding): pages the memory manager reduced between checks are already on the standby list, that is, in the available memory, and adding them as they are would count them twice. The memory the game takes by itself (the game's memory use) is learned as "start available minus the minimum available in the first 10 minutes" and used in the prewarm budget; without adding the held amount the game's memory use would be learned too large by what is held and the budget of the next play would shrink. The available memory column of the per-second record is the real value. The service activity of the per-second record also has `hold` (holding), `check` (the check) and `release`.
- **Cost, and what is not guaranteed.** Holding was measured on synthetic files at about 0.3 s of CPU per GiB and releasing at about 0.1 s (real game files may be 3 to 4 times that), and the check costs the CPU of querying the working set state of the whole held amount every 2 minutes and of reading back the parts the memory manager reduced. Not guaranteed: a write that shrinks a file can fail while it is held (the reason volatile files are left out, and game-written files are held only under the conditions above), pages the memory manager reduces are read back only while available memory is at least 1 GiB above the holding floor; otherwise they are taken off the hold, and a file that is read without the cache gets no effect.
- **Basis and what was not checked.** In tests on this PC (no game), 256 MiB in a view that was not closed all stayed after memory pressure (+0 hard faults when touched again), while the control that was closed lost 76 to 100%. With only the section and the view left (file handle closed), another process could overwrite, grow, replace and delete the file and open it exclusively; only shrinking failed, with error 1224. `VirtualUnlock` on a range that is not locked returns error 158 but takes the range out of the working set, and it was pushed out in the release order (the order was confirmed once). Low-priority or sequential-flag reads by another process did not move pages to the front or lower their priority on this PC. Not checked: the effect with the real game's read pattern (cache misses, asynchronous and overlapped reads), the threshold and speed at which the memory manager reduces a held working set when the available memory is low, the cost of holding and releasing real game files, how an anti-cheat sees a section of a game file kept open for long (so the same anti-cheat gate as pinning is used), and how much it reduces stutter in real play.
- **Log lines.** `<game>: cache held while playing (<exe>): N MiB of T MiB target (L MiB list) in F files, V views, in S s (cpu C s, K checks), D MiB read from disk (H hard faults), M missing stretches skipped (B MiB not held), ...` is the result of holding (with the amount skipped, the amount not held because of volatile, changed and sparse files, the reason it stopped at the floor or at the read cap, and possibly the 16-position sample check at the end). `<game>: cache hold released N MiB for memory (<exe>): available A MiB < floor F MiB, H MiB still held, in S s` is a release for the floor. `<game>: cache hold checked (<exe>): N MiB looked up in the working set in S s (cpu C s, K checks), R MiB reduced by the memory manager, M MiB of it read from disk again (H hard faults), ..., X MiB held` is the check (with the amount taken off at the cap and the files released because they changed). `<game>: cache hold ended after K checks (<exe>): ...` is the total at the end (with `, N MiB held by continuing after the first pass (R requests, D MiB read from disk, L MiB left)` when the first pass was continued). `<game>: cache hold continuing after the first pass (<exe>): holding|finished|stopped: <reason>|deferred: <reason>, ...` is a change of the state of that continuing (or a change of the kind of reason for waiting) with the totals so far, and the start line of the hold carries `, started S s after the executable started` (counted from when the watcher noticed it) and `, N MiB left to continue with (A MiB skipped after a missing stretch, B MiB not visited)`. A keep round made while holding ends with `, N MiB held by the hold left out`. `<game>: cache hold while playing skipped (<exe>: <reason>)` is why nothing was held (`anti-cheat: ...`, `no volatile file information yet, no trace was recorded`, `available N MiB leaves no room above the floor F MiB`, `disk yielded`). When a hold is held again, why it waits is logged once until the reason changes: `hold again deferred: loading phase`, `hold again deferred: game drive queue is not 0 or unknown`, `hold again deferred: available memory leaves no room above the floor and the margin`, `hold again deferred: disk yielded`. `<game>: cache held again after the memory floor released it (<exe>): N MiB of T MiB target, D MiB read from disk, disk reads of the play P MiB of 1024 MiB, ...` is the 2-minute check holding the released part again; after a hold that ended because everything was released, the normal `cache held while playing` line ends with `, held again after the memory floor released everything: disk reads of the play ...`. The closing line of a hold has `, N MiB held again after the memory floor released them` when a part was held again. The start line of the hold also says `game-written files: N MiB held in F files, not held by condition: A MiB with too little size history, B MiB that shrank before, C MiB after a game update or with the update unknown`. `<game>: cache hold released a game-written file the game changed (<exe>): <file>, N MiB, S s after the hold started, H MiB still held` is the release by the 5-second check (the file and the time), and the closing line then ends with `, F game-written files (N MiB) released after the game changed them`.

## Keeping the blocks of sparse files while the game runs (`memory.keep_sparse`)

Sparse files cannot be held or touched through a mapping: creating a section for a sparse file drops that file's cache from the whole file (checked on 2026-11-14), while an ordinary buffered `ReadFile` does not drop it and hits the cache. So the holding, the touching and the ladder leave sparse files out, and nothing kept the pages of a prewarmed sparse file in memory during play. In a replay of Call of Duty (2026-11-22) 93% of the disk delay in the middle of a match (170 to 600 s) that fell outside the ranking list was reads of sparse files (242 of 261 s).

- **Which blocks.** The sparse blocks are not a list of their own. When the block ranking list is rebuilt (`<game>.trace.json.ranked.json`), the blocks of sparse files are ranked by the same score as the other blocks (number of plays, then delay sum of the earlier plays), in the same list, with the same exclusions (blocks only read without the cache, files outside the allowed roots, files read only without the cache). There is no fixed share and no size setting for them. The prewarm reads a sparse file by the existing buffered read without a mapping (the log line `MiB of sparse files by buffered read`), so a sparse block takes its place in the prewarm budget by its score, and when the budget is small the sparse blocks with a low score are cut like any other block. What this keeping re-reads is the sparse part of the prewarmed list that the game keeping uses (the list in importance order), so only what fit into the prewarm budget is kept; for a game whose prewarm leaves sparse files out because of the budget (the log line `MiB in sparse files left out of the memory prewarm`) there is nothing to keep, and the ranking list leaves them out too. That is a limit of the present behavior: when the budget is smaller than the list, the sparse ranges are not prewarmed and so nothing of them is kept during that play, and the skipped line `sparse files left out of the memory prewarm, nothing to keep` (see the log lines below) shows that this was the case. The amount is also limited to the same three values as the target of the holding (the smallest of 5 GiB, half of the available memory, and what is above the floor; the first hold of a play is more cautious, as described above). If `memory.keep_sparse` or `memory.standby_ladder` is off, the ranking list is built without sparse blocks, as in 1.0.5 and earlier (from the next rebuild on, as with `keep_hold_written_files`). A ranking list built by 1.0.5 or earlier has no sparse blocks until it is rebuilt after the next play; until then only the sparse ranges that the plan reads are kept. The re-touching and the touching after the start boundary skip sparse files, so the sparse ranges are taken out of their list before its byte limit is applied and do not use it up.
- **Reading.** While the game runs, a separate thread of the game keeping re-reads those blocks from the most important one with ordinary buffered reads only: no mapping, no view, no `PrefetchVirtualMemory`, and no `FILE_FLAG_NO_BUFFERING`. The files are opened with the random-access hint, which turns the read-ahead of the cache manager off, so only what is asked for goes to the disk (see Disk reads for why). The data goes into a reused 1 MiB buffer and is dropped. Files are opened read-only with read, write and delete sharing and closed at the end of each round; a file that cannot be opened is skipped for that round. Anti-cheat component files are left out as in the holding. The reads go in groups of up to 16 consecutive 64 KiB blocks (1 MiB), with a pause of 20 ms after every 16 MiB. Only the I/O priority of the thread is lowered; its CPU priority stays normal, because a low CPU priority lets a game thread delay the copy, and the delay would be counted as a read from disk. The thread does not take the lock that the touching and the hold checks share: a buffered read is not counted among the hard faults of the process (checked on 2026-11-22: reading a 256 MiB file that was not in the cache added 0 hard faults), so it does not mix into their boundary decision.
- **When.** The first round runs right after the start touch, then every 20 s for the first 3 minutes after the start and every 30 s after that (the basis is the standby list reuse measured on one PC on 2026-11-22: at most 1.3 GiB per 20 s and 1.9 GiB per 30 s, less than the 4 to 6 GiB of priority 5 standby memory in the middle of a match). It runs for games that are held and games that are touched, only while the keeping of the cache while the game runs (`memory.standby_ladder`) and the start stream (`auto.start_stream_enabled`) are on, and only when the game has a block ranking list. It follows the same anti-cheat gate as the holding: for a game for which the holding is forbidden (the anti-cheat kinds that forbid tracing: EAC, BattlEye, Vanguard, kernel-level, failed detection, judged from the kind in the settings and the detected kind) nothing is opened or read in the first round, even if a ranking list made from earlier records is still there, and the log says `sparse blocks kept while playing skipped (<exe>: anti-cheat: <kind>)`; Ricochet and games without anti-cheat are kept. A round is skipped when the available memory is below the floor of the holding (2 GiB), and the floor is checked again at every group, so that what is being pushed out is not read again from disk.
- **Disk reads.** Re-reading a block that is in the cache is a memory copy and uses no disk. A block that was pushed out is read from disk again, and this is allowed under the same conditions as the holding again: the loading judgment says the game is not loading, the queue of the game drive is 0 (the last value of the sample loop; unknown counts as not 0), at most 32 MiB per round (`KeepDiskReadCapBytes`), and at most 512 MiB per play (`SparsePlayDiskCapBytes`) that this keeping counts for itself. It is not added to the 1 GiB per play of the holding again (`HoldAgainDiskCapBytes`), so an amount counted wrongly here cannot stop the holding again early; the worst of both together is 1.5 GiB of disk reads per play. The conditions are checked again at every group. A buffered read cannot tell beforehand whether the block is in the cache and does not show up in the hard faults, so it is judged by time: a 64 KiB block that took more than 0.15 ms (0.05 ms plus 1.6 ms per MiB) counts as read from disk (that block only), and a group (16 consecutive blocks) whose times add up to more than 0.85 ms (0.05 ms plus 0.8 ms per MiB) while no single block is over the block limit counts as read from disk as a whole (1 MiB). In the measurements below a block that was not in the cache was over the block limit in 99.9% of the cases, so counting only the slow blocks missed 0.1% of such blocks at most (about 0.2 MiB of 192 MiB), while the groups in the cache that were wrongly counted (0 to 2.1% of the groups, 1 MiB each) now cost only the blocks that were really slow (0 to 0.16% of the blocks). When the conditions allow disk reads, a round ends after the group that brought the counted amount to its cap. When they do not (loading, queue not 0 or unknown, the play total spent), the round reads only the blocks that an earlier round read and so knew to be in memory, and ends at the first of them that is over the limit (it was read from disk by then and is counted); a block that was not read before is not read in such a round, so nothing is read in the first round of a game that starts while loading, and such a round reads about one 64 KiB block from the disk. The next round starts from the front again and goes one block further. What is counted is subtracted by the loading judgment from the game's reads and added to the play total of this keeping; for the I/O summary of the play the whole group that held a slow block or went over the group limit is noted as reads of the service itself, so it is not counted as the game's reads (noting a range without disk reads takes nothing out of the summary).
  - Measured on 2026-11-23 on the hard disk D: with test files of 192 MiB (the sparse attribute set, written without the cache), 3 runs, while the drive optimization (`defrag.exe`) was running on that disk (5 to 14 MB/s of other traffic, queue 1 to 3; it had been running for 13 hours and was not waited for), so the speeds are lower than for an idle disk. Blocks of 64 KiB that were not in the cache, read one after another: median 0.4 to 0.6 ms (22 to 31 MiB/s), over 0.15 ms in 99.9% of the blocks; blocks that were not in the cache, read in scattered order: median 7 to 12 ms (4 to 5 MiB/s), 99.9% over 0.15 ms; blocks in the cache: median 7 to 8 µs, 99.9th percentile 0.03 to 0.21 ms, largest 0.04 to 0.56 ms. With the rule above, 100% of the groups that were not in the cache were counted (all 3 runs, sequential, scattered and mixed), and 0%, 0% and 1.6% of the groups in the cache were counted wrongly in the sequential runs (2.1% of the groups in the cache in the mixed runs 2 and 3, where groups that were not in the cache and groups that were alternate). The volume read counter went up by 197 MiB for 192 MiB read (sequential), 137 MiB for 96 MiB (scattered, 22 s of other traffic included), and 101 MiB for 96 MiB (mixed); the difference is the traffic of the drive optimization, which cannot be separated. A round that was held back read 1.02 blocks on average until the first block over the limit (at most 2) in 40 trials, 3.1 MiB of volume reads for 2.6 MiB requested. So a round with disk reads allowed counts at most 32 MiB plus the group that crossed the cap (1 MiB): about 1.5 s of disk at the sequential speed and 8 s at the scattered speed measured above.
  - The earlier judgment (a 64 KiB block over 2.06 ms, files opened without the random-access hint) missed most of the cold reads: in the same test 77 to 91% of the blocks of a sequential read of a file that was not in the cache were faster than 2.06 ms (9 to 23% were over it, in 3 runs), because the read-ahead of the cache manager and the buffer of the drive returned the following blocks at once, so only about 18 to 44 MiB would have been counted for 192 MiB read. (The check of 2026-11-22, in which 300 of 4,096 blocks were over 2.06 ms, was this effect: the 300 are the ones that were slow, and the other 93% of the blocks that were read from the disk looked like memory.) Not measured: an idle hard disk (the speeds above are with the drive optimization running; the limits were chosen from the gap between the cache and the disk, which is expected to be wide enough that a faster disk would not change it), pages that are in the standby list but not in the system cache working set (their copy needs a soft fault and may be slower than the 8 µs above, which makes the count larger, not smaller), a drive buffer that answers a read of a 64 KiB block that is not in the cache in less than 0.15 ms (not seen on this disk), and an SSD (a read from the disk may finish under the limit, so a round on an SSD may count less than it reads).
- **Memory.** A block kept by the buffered read sits in the standby list, which the available memory includes, so the floor of the holding and the hold target are not touched: this keeping holds nothing (the amount of the holding that the play record adds is not changed). How much the system cache working set grows for a moment while the blocks are read was not measured.
- **Log lines.** `<game>: sparse blocks kept while playing: N MiB in F files` once at the start, and `... ended after R rounds (<exe>): reached A of N MiB of the list, D MiB read from disk (judged by read time), K rounds with disk reads held back (loading phase, game drive queue, or the disk reads of the play spent)` at the end with the reason (the game ended; turned off in the settings). A round that does not run or reads nothing is logged by its reason, once per play for as long as the reason stays the same (`<game>: sparse blocks kept while playing skipped (<exe>: <reason>[, <detail>])`; a round that read something resets it), and the end line adds `, skipped rounds: <reason> xN, ...` and `, N block reads failed`. The reasons: `no ranked block list (no trace of this game)` (the keeping ends), `standby ladder is off`, `layout relocation is running`, `no block reader`, `no prewarm record of a list in memory`, `low memory` (below the floor of the holding), `memory fell below the floor during the round`, `keep list unavailable` (the planned list could not be read), `sparse files left out of the memory prewarm, nothing to keep` (the prewarm budget was smaller than the list, so the prewarm left the sparse ranges out), `no sparse range in the keep list` (the keep list has no sparse range to read), `disk read lease refused`, `disk read lease canceled the round`, and `nothing read: <loading phase | game drive queue is not 0 or unknown | disk reads of the play spent | block reads failed | no room above the floor>`. Not logged: that the side thread is never started (`memory.keep_sparse` is off, there is no reader, or the game keeping itself does not start because `auto.start_stream_enabled` or `memory.standby_ladder` is off) and that another start of the same game finds the keeping already running. The play record line is unchanged. The ranking list line says how much of the list is in sparse files (`M MiB in F sparse files`).
- **Basis and what was not checked.** Experiment on 2026-11-23 (test files on an SSD, three runs): files that were put in the cache in the same way and then re-read with ordinary buffered reads every 10 s, from a thread with low I/O priority, were still 99.9 to 100% in the cache after memory pressure of about 9 GiB of private memory, while the sparse file that was not re-read was 0% in the cache in all three runs. A sparse file and an ordinary file that were both re-read did not differ. Not checked: a hard disk (the cost and starvation of the re-reading differ there; the order in which the memory manager pushes pages out is expected to be the same), a re-reading interval of 20 to 30 s and the blocks of a ranking list instead of the whole file, memory that grows slowly instead of all at once, whether a re-read page moves to a newer place in the standby list or stays active in the system cache working set (either way is expected to give the same result), and the page priority of the service (the experiment set it to 5). This was a test on one PC; the effect in real play is not known: the frame interval record and the disk reads of sparse files in the next plays have to show it. The blocks take part of the prewarm budget and of the cache that other blocks shared before; what that cost the others was not calculated.

## When it runs

All of these must hold. Otherwise nothing is touched.

| Requirement | Detail |
|---|---|
| Setting | `memory.standby_ladder` is `true` (the default). |
| Service rights | The service has administrator rights and a trusted data folder, the same condition as [background memory yield](AUTO_MODE.md#background-memory-yield). |
| No game running on that disk | A touch that misses the cache is a disk read, so it follows the rule that no new background reads go to a disk where a game runs. It stops when a game starts. The one exception is the touch of the game itself, at its start and while it runs, which reads only its own pages from memory and stops at the first one that is not there (see "A touch when a game's executable starts" and "Keeping the cache while the game runs"). |
| Not while a launcher prewarm waits | A launcher's prewarm has priority. SOLAR also skips a stream that was stopped for it, and the group refresh stops when a launcher prewarm starts to wait. |
| Refresh gates | The same gates as the re-prewarm check except the drive load: no relocation in progress, the exit grace period over, the game inside the prewarm budget, and the disk read lease granted. A refresh only touches pages that are in the cache, in memory, so it runs while another program uses the same drive. The gates of the re-prewarm check, which can read the disk again (including the game drive under 4 MiB/s), are unchanged. The lease is refused only while a game on that disk is running and yielding; a refused lease only skips the game and its recorded state stays. |
| Not with `auto.keep_stream_on_game_start` | With this experimental setting a stream is not stopped when the game starts, so SOLAR does not follow it. |

## What it does not do

- It does not keep data in memory by force: it does not lock pages (no `VirtualLock`, no forced minimum working set) and does not change page priority. The ladder, the refresh and the touch at the start keep no mapping open (unlike the optional [Pinning](AUTO_MODE.md#pinning-optional)); the only views kept open are those of holding while the game runs (`memory.keep_hold`). Holding too releases the less important part first when the available memory falls under the floor, and Windows can still reuse these pages when memory is short. The re-touching, the ladder and the refresh only change which pages go first, but holding really changes the working set of the service and the "available" memory (see the holding section above).
- It does not run on a disk where a game is running, except for the touch of that game on its own prewarmed list, at its start and while it runs.
- It does not lower the memory reserve (`prewarm.min_free_ram_mib`) or the cache budget (`prewarm.max_cache_mib`), and it changes neither the prewarm list nor the amount read.
- It does not open any game, launcher, or anti-cheat process, and it opens no process at all. See [Anti-cheat compatibility](ANTICHEAT.md).

## Turning it off

Add this to `config.json`:

```json
"memory": { "standby_ladder": false }
```

There is no switch in the Settings tab. The service re-reads the file and then stops touching the cache. Nothing else changes: the prewarm, the re-prewarm check, and [background memory yield](AUTO_MODE.md#background-memory-yield) keep working and have their own settings. The `memory.standby_ladder` key was added in 1.0.4, and versions 1.0.3 and earlier reject a settings file that contains it, so remove it before rolling back ([Configuration](CONFIGURATION.md)).

To turn off only the holding while the game runs, add `"memory": { "keep_hold": false }`; the standby-list touching above then applies. `memory.keep_hold` was added in 1.0.5, and versions 1.0.4 and earlier reject a settings file that contains it, so remove it before rolling back.

To turn off only the holding of the files that the game itself writes, add `"memory": { "keep_hold_written_files": false }`; they are then left out and no longer enter the block ranking list when it is rebuilt. This key was also added in 1.0.5, and versions 1.0.4 and earlier reject a settings file that contains it, so remove it before rolling back.

To turn off only the keeping of the blocks of sparse files, add `"memory": { "keep_sparse": false }`. This key is new in 1.0.6, and versions 1.0.5 and earlier reject a settings file that contains it, so remove it before rolling back.

## Checking that it runs

Each line goes to `service.log`. `<game>` is the game's name, and a tail such as `, N MiB read from disk`, `, N errors` or `, K MiB in sparse files not touched` is added only when it is not zero (a figure in MiB is left out when it would show 0 MiB). On the ladder, refresh and start-touch lines the kinds of error can follow `, N errors` in parentheses. For example `(open 12 ranges in 3 files (win32 5 ×12 (3 files, 12 ranges, 6.00 MiB requested)); most failures in <file> ×7, <file> ×3, <file> ×2)` means that 12 ranges could not be opened, in 3 files, with Win32 error 5 twelve times, that those 12 ranges asked for 6.00 MiB, and that the files with the most failed ranges failed 7, 3 and 2 times (at most 4 files are named). The per-error figures in the inner parentheses are written for open errors only. The kinds are `open`, `beyond end` (a range past the end of the file), `map` and `read`.

- `<game>: ladder ordered N MiB in S s`: a ladder was made after a prewarm or a re-prewarm check. `<game>: ladder has nothing to touch (K MiB in sparse files not touched)` means every range of the list is in sparse files, so no ladder was made; it is logged when that finding is new (again after a service restart or a new prewarm), not at every check.
- `<game>: cache refreshed in memory: N MiB in S s (R MiB repurposed of A MiB ahead)`: a refresh. `R` is the growth of the reuse count and `A` the amount reused first. A game that was not due itself but was refreshed with the group gets the same line, with its own values.
- `cache refresh deferred: touching time is capped at 2% of wall time, next in N s`: a group refresh was due but the time spent touching has reached that cap; it is logged once when the deferral starts, and again only after the cap has passed and a refresh was deferred again.
- `<game>: prewarm done (...) ..., protected K games (N MiB in S s)` (at the end of the done lines, after `requeued` when both are there): right before the stream read, while it read and right before its ladder, K different other games with a recorded state were touched, N MiB and S seconds in all. When it re-referenced other games more than once, `, R times` is added at the very end (not for one time). It is left out when none was touched, and a `cache refreshed in memory` line stays for each of those games. It is never on the line of a launcher prewarm.
- `<game>: prewarm done (...) ..., requeued N MiB in S s` (and the same at the end of `supplement prewarm done`): the batches the stream touched while reading; left out when nothing was touched or skipped. `requeued N MiB in S s (K MiB in sparse files not touched)` shows the part of the batches that sat in sparse files (see Limits and cautions) and was skipped; the parentheses are left out when it is zero. `, requeue stopped by disk reads` is added when a touch saw disk reads and stopped. A supplement prewarm that read only a window ends with `supplement prewarm read the first …` instead of `done`, and that line carries the same `requeued` text. `, K MiB of sparse files by buffered read` (before `requeued`, on the same lines) shows how much of the stream was read that way instead of through a mapping; it is left out when zero.
- `<game>: cache touched at game start (<exe>): N MiB in S s (cpu C s, V views, K checks), D MiB read from disk`: the touch when the executable `<exe>` started (see "A touch when a game's executable starts"); `D` is the amount the touch saw read from disk and is shown even when it is 0. `<game>: cache touched at game start (<exe>): N MiB of M MiB still in memory (boundary found by hard faults), in S s (cpu C s, V views, K checks), D MiB read from disk (F hard faults), left to the rewarm check`: only the front part of the list was still in memory and only that part was touched; `<game>: cache touch at game start (<exe>) found none of the M MiB list in memory (...)`: none was. When the touch stopped, the lines have the same words as the ladder with `cache touch at game start (<exe>)` in place of `ladder`: `... found data missing from memory after T of N MiB (...), left to the rewarm check`, `... stopped after N MiB`, `... was too slow without disk reads seen (...), skipped`. `<game>: cache touch at game start skipped (<exe>: <reason>)` says why none was made: `last touch S s ago, within 60 s` or `disk yielded` (the lease was refused, for example because another game runs on the same disk).
- `<game>: cache kept while playing (<exe>): N MiB of M MiB in memory, in S s (cpu C s, V views, K checks), D MiB read from disk (F hard faults), B new missing stretches remembered (X MiB of the L MiB list in all), called by R MiB of standby cache reuse`: one round of the re-touching (of the whole list for a game that is not held, of the part the hold did not take for a game that is held; see "Keeping the cache while the game runs"). `M` is what this round tried to touch (without the remembered missing ranges) and `N` is how much of it was in memory. If the reuse total cannot be read it says `called by the fixed period`. `, disk read cap of the round reached` is added when the cap of the round was reached, and `, probe 5/16 in memory (positions 0 211 422 MiB of 3386 MiB)` (the 16-position sample check, only recorded) at the end when there was a boundary. `<game>: cache keeping while playing skipped (<exe>: <reason>)` is why a round was skipped (`available N MiB < reserve M MiB`, `disk yielded`), and `<game>: cache keeping ended after R rounds` is the end (the game ended or the service stopped). `<game>: cache touched at game start (<exe>) past the first missing stretch: ...` is the result of going on to the end of the list, skipping missing pieces, after the touch at the start stopped at a first boundary (when another process of the same game was already running, no new range is searched for and the line ends with `, disk reads skipped (the game is already running)`).
- `<game>: ladder found data missing from memory after T of N MiB (K slow pieces, M MiB read from disk, F hard faults, stopped by slow time), left to the rewarm check`, and the same for `cache refresh found data missing from memory after T of N MiB (...)`: part of the list was not in the cache. For a game that had a recorded state, `, since the ladder M min ago: R MiB repurposed of A MiB ahead` is added at the end of the line (M is minutes since that recorded state was made, R the reuse since then, A the amount reused first now (at the moment the recorded state was dropped, if it was); when the standby-list statistics cannot be read, only the time and no `: R MiB … ahead`). It is left out when there was no recorded state. It helps tell whether the cooling came from a refresh that was late, one that was blocked, or an eviction out of order. The ladder touches in reverse order, so when `T` is close to `N` the missing part is at the front of the list, the most important part. `N` is the whole ladder including sparse ranges that were skipped, so when the line ends with `K MiB in sparse files not touched`, check whether `T` plus `K` is close to `N`.
- `<game>: rewarm check: part of the list is not in memory (found by the ladder), prewarming again (cooldown ignored)`: the next re-prewarm check re-prewarms the game. `..., waiting until N min after the last prewarm attempt` means it waits for the period to pass.
- `<game>: cache refresh skipped, the samples are cold (X/Y over Z ms), left to the rewarm check`, or `the samples could not be read` or `there are no readable samples`: the sample check came before the refresh. These three lines (cold, `could not be read`, `there are no readable samples`) and the `<game>: rewarm check: cold (...), prewarming again (cooldown ignored)` line also get the same `, since the ladder M min ago: ...` tail for a game that had a recorded state (when a refresh dropped the recorded state first, the values from before are kept and added once to the cold line of the re-prewarm check, then discarded; a new recorded state discards them too). A cold sample read while the game drive is busy is skipped without a log line once per recorded state, so that line does not appear then.
- `<game>: ladder stopped after N MiB`, `cache refresh stopped after N MiB`: stopped because a game started or the lease ended; the recorded state stays and a refresh is tried again.
- `<game>: ladder was too slow without disk reads seen (K slow pieces), skipped`, `cache refresh was too slow without disk reads seen (...)`: the touch took long but no disk read was seen, for example under heavy CPU load.
- `<game>: ladder skipped: <exception type>` and `<game>: cache refresh failed: <exception type>` (or `cache ladder failed`): a failure that did not affect the prewarm.

## Limits and cautions

- **The effect in real play has not been measured.** The experiments show that the order can be set and that refreshing cache that is still in memory needs no disk read. They do not show how much load time or stutter changes in a running game. Whether the share of cold re-prewarm checks has fallen has not been checked either.
- **A program that uses again the pages Windows would reuse before the game's pages moves them behind the game's pages, and that cannot be counted.** So the criterion can be late; the re-prewarm check handles that case.
- **The effect of the group refresh, the re-reference before a stream and the ladder after a memory-limit finish has not been checked on an installed build yet.**
- **The cap on touching time has a price.** While another program keeps using a lot of cache, the game's cache is refreshed less often (after a 7-second refresh, not for 350 seconds), so the pages of the other program's cache can be pushed out later than before, but the game's pages can also be pushed out before the next refresh; the re-prewarm check then reads them again from the disk once things have gone quiet. A stream that reads little no longer protects the other games before it reads, so if the reads turn out to be larger than planned, the re-reference during the stream (every 10 seconds at the earliest) and the decision again at the end protect them. The cap (2%) is a chosen value, not a measured one.
- **The refresh runs while the drive is busy too, because it does not read the disk.** When a sample or a touch meets a part that is not in the cache, it does read then: the sample 8 MiB, and a touch up to about 100 MiB before it stops. A cold sample read on a busy drive is passed over once per recorded state (the recorded state is kept, that round's 8 MiB sample read is spent); the second one drops the recorded state and leaves the game to the re-prewarm check, also on a system where the drive load cannot be read. Whether to read from the disk again is still decided only by the re-prewarm check.
- **The effect of re-referencing right before the ladder, of writing the recorded states again as one group, and of lowering the amount reused first by everything the ladder touched when the stream game had no earlier recorded state has not been checked on an installed build yet.** Lowering by everything is a cautious value chosen because the real amount is not known, so it can lower more than the real amount and bring a refresh early (the decision to re-prewarm from the disk is still made only by the re-prewarm check; an early refresh may still read the 8 MiB sample and, when a touch meets a part that is not in the cache, up to about 100 MiB before it stops).
- **The re-reference during a stream, the ladder right after a service start and the log tails have not been checked on an installed build yet.** How much the ladder right after a service start delays the start prewarm has not been measured either (it runs first, for the `S` seconds of its `ladder ordered N MiB in S s` line).
- **It does not stop eviction.** When memory is truly short, Windows still reuses these pages. SOLAR changes only which ones go first and how soon they come back.
- **Files with the sparse attribute are not touched.** Measured on one PC (an HDD, test files): right after a prewarm read, an ordinary file touched through a new mapping (a section) caused no disk read (47 runs), while a sparse file was read again from the disk every time (64 MiB in about 1.1 s). So before it opens a section SOLAR reads the file's attributes (metadata only, once per file in a run) and skips a sparse file. The log shows the skipped amount (`K MiB in sparse files not touched`); it is not counted as touched, as errors or as data missing. The data of such files is not part of SOLAR's order or upkeep and depends only on the prewarm and the re-prewarm check (a buffered-read sample). This is what was measured on that PC, not a statement about how Windows behaves in general. SOLAR only reads the attribute and never changes a file. The prewarm reads such files differently from ordinary ones as well: it does not map them but reads them with an ordinary buffered read of the same ranges in the same order, because on that PC creating a mapping for a sparse test file discarded the cache pages read earlier from that whole file, while buffered reads alone kept them. These reads turn the cache manager's read-ahead off: with it on, a list of scattered 64 to 256 KiB pieces (256 MiB requested) read 13 to 23% more than requested from the disk on that PC, and with it off the disk read stayed within about 1% of the request in the measured runs. How much this helps in a real game has not been measured yet. If every range of a game's list is in sparse files, the log says `ladder has nothing to touch (K MiB in sparse files not touched)` once, and the re-prewarm check does not try the ladder again until the next prewarm stream has judged it again. While the game runs, `memory.keep_sparse` (above) re-reads the prewarmed sparse blocks with buffered reads to keep them in memory; its effect in real play has not been measured.
- **A very long prewarm can lose its own start.** Once, a prewarm of 11,388 MiB for Call of Duty took 322 seconds, and the ladder made right after it already found data missing. The list was close to the capacity of the standby list, so the part read first may have been pushed out while the rest was being read; other programs' reads may have added to it. Separately, in the installed build 1.0.4-dev.7 the batch touch for Call of Duty stopped with `requeue stopped by disk reads` at the same position (3,379 MiB) in different streams, and the ladder also found data missing, so the re-prewarm repeated. A count of file attributes (metadata only, 2026-11-14) found 78 of the 210 `.xsub` files in that game's folder (50.6 GiB) sparse, and no sparse files in the folder of another game whose ladder ended without disk reads. From these three the repetition was judged to come from sparse files; that the file at the stopping position is sparse was not checked, and how much of the first case was pushing out has not been separated. A re-prewarm that reads only the missing part also leaves the rest of the game's pages in the old order of the earlier prewarm, which Windows reuses first; touching each batch right after it is read is meant to prevent that. **Whether the repetition stops once each batch just read is touched again right away and sparse files are skipped has not been checked on an installed build yet.** If the list is larger than what the standby list can hold, the part read first can still be pushed out while the rest is read; the `after T of N MiB` in the log shows how far the ladder got.
- **The 8-place sample check can miss a partly cold cache.** The ladder looks at the whole list, which is why a ladder that finds missing parts leads to a re-prewarm even when the samples look warm.
- **A slow sample counts only when the system's page-read count grew too.** A place is counted as slow only if its read took longer than the limit and, during that read, the system's page-read count grew in proportion to the sample size (at least a quarter of the pages read, 16 pages at the least). Judging by time alone, a sample that is in the cache can read slowly while another program is using the CPU and be taken for a cold one. If the count cannot be read, time alone decides. A rare burst of other programs' reads that overlaps a sample can still cause a wrong call. Not yet checked on an installed build.
- **Other programs' reads can still add to the disk read count, up to a limit.** The page-read count is system-wide, so the time cap only keeps a short burst from counting as a whole view; a burst that overlaps a view that really took long (on a slow or busy disk) can still add up to what that time allows. Whether the false stops (`requeue stopped by disk reads`, `ladder found data missing`) have stopped on an installed build has not been checked yet.
- **The statistic is an undocumented Windows interface.** It was checked on Windows 11 10.0.26200 only. If it cannot be read, the 10-minute fallback is used.
- **The eviction order was checked with test files on one HDD,** for pages of priority 5 only. Raising the page priority to 6 or 7 was refused by Windows (`STATUS_INVALID_PARAMETER`), so it is not used.
- Games on an SSD are skipped by the prewarm, so SOLAR has nothing to do for them.

## Prior art

Each technique in SOLAR has an earlier precedent. Putting a cache's replacement order into a chosen state by reading data in a set pattern from user level was done by Dust ([Burnett et al., USENIX 2002](https://static.usenix.org/event/usenix02/full_papers/burnett/burnett_html/index.html)), there to identify the replacement policy. Touching files periodically to keep them cached is what [vmtouch](https://linux.die.net/man/8/vmtouch) with a scheduled job does. Releasing the memory of background programs only under memory pressure is close to [SmartTrim in Process Lasso](https://bitsum.com/apps/process-lasso/docs/algorithms/smarttrim/), and Windows itself ranks standby pages by value ([SuperFetch](https://learn.microsoft.com/en-us/previous-versions/technet-magazine/cc162480(v=msdn.10))).

What is specific to this program is the combination: one control loop that uses a Windows statistic of the standby list per priority as its signal to decide the eviction order, the timing of the keeping, and the yielding of background memory ([background memory yield](AUTO_MODE.md#background-memory-yield) uses the same statistics), and an importance order that comes from each game's own recorded reads. A search on 2026-11-14 did not find a product, paper, patent, or public code that does the same combination. That is a statement about the search, not proof that none exists. The comparison and the sources are in [prior_art_and_windows_api.md](prior_art_and_windows_api.md#f-solar-선행-기술-캐시-유지-순서-배경-양보).
