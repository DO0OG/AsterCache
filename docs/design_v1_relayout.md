# AsterCache v1 설계: 가로채기 없는 HDD 로딩 가속 (AsterLayout + AsterStream + 재적용 루프)

작성 2026-11-01. 읽기 전용 설계 문서이며, 저장소 파일은 고치지 않았습니다.
근거 표기는 다섯 가지입니다.
- [측정]: 저장소 `results/` 에 있는 이 PC 측정값
- [계산]: 측정값으로 계산한 값
- [가정]: 근거가 없어 실험으로 확인해야 하는 값
- [조사]: `docs/prior_art_and_windows_api.md` 의 출처 확인 항목. 그 문서의 [확인]/[2차] 등급을 그대로 옮깁니다.
- [확인 필요]: 출처를 찾지 못한 기억

## 0. 요약

- HDD 로딩 시간은 "위치 결정 횟수 × 위치 결정 비용 + 바이트 ÷ 전송률 + 요청당 고정비"로 거의 설명됩니다. 현재 합성 트레이스의 콜드 17.8 s 를 나누면 위치 결정(탐색과 회전 대기)이 약 13 s, 전송이 약 2.8 s, 고정비가 약 2 s 입니다[계산].
- 현재 prefetch/ 의 정렬 선읽기는 위치 결정 횟수를 536회로 줄였지만 없애지는 못했습니다. 또 간격 병합 때문에 필요한 바이트의 1.86배를 읽었습니다. 그래서 11.1 s 에서 멈췄습니다[계산].
- **제안 (AsterLayout).** 게임별 트레이스로 고른 핫 블록을 NTFS 의 정식 이동 API(FSCTL_MOVE_FILE)로 한 구간(핫 존)에 모읍니다. 이때 여러 파일의 블록을 섞어, 합의한 접근 순서대로 제자리 이동합니다. 게임의 랜덤 읽기가 물리적으로는 순차 읽기가 되므로 위치 결정 항이 거의 사라집니다. 바이트와 경로가 그대로라서 가로채기 계층도 복사본도 필요 없습니다.
- **AsterStream.** 핫 존을 큰 단위로 한 번에 읽어 OS 파일 캐시에 올립니다. 이 데이터셋의 예상 로딩 시간은 1.5~3.0 s 입니다[계산, 전송률 가정 포함]. SSD 콜드 0.8~1.12 s 의 1.35~3.7배입니다. 현재는 13.9배입니다.
- **정직한 목표.** "HDD 단독으로 SSD 와 같은 시간"은 물리적으로 불가능합니다. 핫 바이트 243.5 MB 를 0.8 s 에 읽으려면 304 MB/s 가 필요합니다. 목표는 "SSD 에 근접"으로 둡니다. 순수 I/O 콜드에서는 SSD 콜드의 2~3.7배를 목표로 하고, 체감 SSD 급은 두 조건에서만 노립니다. (a) 로딩의 CPU 구간(압축 해제, 셰이더)과 스트림이 겹치는 경우 (b) 게임 실행 전에 스트림을 끝내 두는 경우입니다. 이 조건이 실제 게임에서 성립하는지는 E4·E5 로 확인합니다(1.5절, 5절).
- **선행 기술.** 블록 단위 접근 순서 재배치라는 개념은 BORG(FAST'09)가 먼저 내놓았습니다[조사 확인]. 이 설계의 기여는 개념이 아니라 조합과 구현 방식입니다. 드라이버나 복사본 없이 NTFS 제자리 이동만 쓰고, 게임별 로딩 트레이스로 파일 경계를 넘는 블록 범위를 배치하며, 스트림 선읽기와 재적용 루프를 결합합니다(6절).
- **D: 의 WD20EZAZ 는 드라이브 관리형 SMR 로 보도된 모델입니다[조사 2차].** "LCN 이 연속이면 물리적으로도 연속"이라는 가정이 약해지고, 대량 이동 쓰기가 느릴 수 있습니다. 그래서 작은 청크로 순차 쓰기만 하고 실측을 우선합니다. CMR 드라이브에서의 기대치는 따로 적습니다. E1 은 바로 이 가정을 검증하는 실험입니다(7.1절).
- 이동과 ETW 는 관리자 권한이 필요합니다[조사 확인]. 그래서 구조는 "비관리자 사용자 도구 + 관리자 상주 서비스(또는 UAC 승격 헬퍼)"로 나눕니다(2절).

## 1. 물리 모델

### 1.1 식

요청 i 마다 HDD 는 위치를 잡고(탐색 + 회전 대기) 전송합니다. 직전 요청의 끝에서 이어지거나 드라이브 내부 선읽기 버퍼에 이미 있는 요청은 위치 결정이 없습니다.

```
T_load = N_pos × t_pos  +  B / R(z)  +  N_req × t_ovh
```

- N_pos: 실제로 위치 결정이 일어난 횟수. 드라이브 선읽기에 흡수된 요청은 빠집니다.
- t_pos: 위치 결정 평균 비용 = t_seek(거리) + t_rot. 평균 회전 대기는 한 바퀴 시간의 절반입니다.
- B: 디스크에서 실제로 읽은 바이트입니다. 중복 읽기와 과잉 읽기를 포함합니다.
- R(z): 위치 z 의 순차 전송률입니다. 보통 바깥 트랙이 빠르지만 보장되지 않습니다[조사 2차].
- N_req × t_ovh: 요청당 고정비(시스템 호출, 파이썬, 드라이브 명령)입니다. 큐 깊이가 2 이상이면 상당 부분이 전송과 겹칩니다.

### 1.3 현재 측정치를 식으로 설명

**HDD 콜드 17.8 s** (results/prefetch_20261101/final_physical/20261101_211330.json, 3회 17.3~19.0 s)
- 위치 결정: 트레이스 안의 연속 블록은 드라이브 선읽기에 흡수되므로 N_pos ≈ 병합 범위 수 932 로 봅니다. 932 × 13.9 ms = 12.95 s [계산].
- 전송: 243.5 MB ÷ 86.9 MB/s = 2.80 s [계산].
- 고정비: 남는 약 2.0 s 는 4,000 요청 × 약 0.5 ms 입니다. 콜드 p50 이 0.35 ms 로 측정된 것과 맞습니다. 요청의 절반 이상이 위치 결정 없이 끝났다는 뜻입니다.
- 모델 17.75 s, 측정 17.8 s 로 일치합니다.

**같은 데이터셋의 71.2 s 실행** (results/bench_20261101/20261101_204602.json, 55.7/71.2/71.3 s)
- 4,000 요청이 모두 위치 결정을 치렀다면 4,000 × 14.65 ms = 58.6 s, 고정비를 더해 약 60 s 입니다[계산]. 측정값은 이 상한 근처입니다. 이 실행에서는 드라이브 선읽기 흡수가 거의 없었다는 뜻입니다. 동시 디스크 사용 때문으로 추정하지만 원인은 측정하지 않았습니다.
- 결론: 같은 트레이스라도 N_pos 가 932~4,000 사이에서 흔들리고, 이것이 편차의 대부분입니다. 위치 결정 항을 구조적으로 없애면 편차도 함께 줄어듭니다.

**물리 정렬 선읽기 11.1 s** (같은 final_physical 파일 `prewarm_cmd`: 536 요청, 452,067,328 B, 간격 1.2 MB)
- 전송: 452.1 MB ÷ 86.9 = 5.20 s [계산]. 필요한 243.5 MB 의 1.86배이며, 간격 병합으로 구멍까지 읽었기 때문입니다.
- 남는 5.9 s ÷ 536 = 요청당 11.0 ms 입니다. 위치 순으로 정렬해 탐색 거리는 짧지만, 큐 깊이 1 이라 매번 회전 대기(평균 5.56 ms)와 짧은 탐색, 고정비를 치렀습니다[계산].
- 지금 배치에서는 하한(위치 결정 0회, 필요 바이트만 읽기, 2.80 s)에 다가갈 방법이 없습니다. 구멍을 건너뛰면 위치 결정이 늘고, 구멍을 읽으면 바이트가 늘기 때문입니다.

### 1.4 재배치 후 예상

재배치 후 핫 존에는 고유 핫 블록 243.5 MB 가 합의 순서대로 연속으로 놓입니다. 남는 위치 결정은 존에 처음 들어갈 때 1회, 그리고 순서가 어긋난 지점 J 회뿐입니다. 아래 표는 **"LCN 연속 = 물리 연속"(CMR 동작)이 성립할 때**의 값입니다. SMR 에서는 7.1절을 따릅니다.

| 시나리오 | 식 | R = 86.9 [측정 위치] | R = 150 [가정] |
|---|---|---:|---:|
| A. 스트림 없이 게임이 존을 직접 읽음 (QD1, 64 KiB, J = 50 [가정]) | 50×8.6 ms + B/R + 4,000×(0.1~0.35 ms) | 3.6~4.6 s | 2.5~3.5 s |
| B. AsterStream 으로 존 전체를 선읽기한 뒤 RAM 에서 재생 | 14 ms + B/R + 932×0.1 ms(겹침 가정) + 재생 0.05 s | 2.96 s | 1.78 s |
| B'. 간격을 채운 430 MB 를 순차로 읽음 (재배치 없이 빈 곳까지 읽는 경우의 하한) | 430 MB / R | 4.9 s | 2.9 s |
| C. B 와 게임의 CPU 작업이 겹침 | max(T_cpu, T_stream) + ε | — | — |
| D. 게임 실행 전에 B 를 끝냄 | RAM 재생만 | 0.05 s | 0.05 s |

- SSD 대비 배수(B 기준): R=86.9 이면 SSD 0.8 s 대비 3.7배, 1.12 s 대비 2.6배입니다. R=150 이면 2.2배, 1.6배입니다[계산].
- 현재 대비: HDD 콜드 17.8 s 는 1.8~3.0 s 로 6~10배 줄고, 선읽기 11.1 s 는 3.7~6.2배 줄어듭니다[계산].
- 조사 문서의 이론 하한과 같습니다. 핫 블록만 읽으면 150 MB/s 에서 약 1.6 s, 즉 SSD 콜드 0.8 s 의 2배입니다. 간격까지 채운 430 MB 면 2.9 s 입니다[조사 계산]. 재배치가 하는 일은 B' 를 B 로 바꾸는 것, 곧 바이트를 필요한 만큼으로 줄이고 위치 결정을 1회로 만드는 것입니다.

- 간격 0~256 KiB 는 큐 깊이 4 에서 거의 같은 최선 구간입니다. 4 MiB 이상은 간격이 커질수록 전송 바이트가 늘어 시간이 함께 늘었습니다.
- SSD 콜드 기준값은 실험마다 달랐습니다. E1 안에서는 0.77~1.45 s, 스윕 안에서는 0.73~1.47 s 였습니다. 배수는 해당 실험의 중앙값을 기준으로 적었습니다.
- 연속 배치 상한의 179 MB/s 는 데이터셋 위치 바닥 86.9 MB/s 의 약 2배입니다. 드라이브 내장 캐시나 디스크 영역 차이 가능성이 있으나 분리하지 않았습니다. 1 MiB 청크가 4 MiB 보다 빠른 이유도 확인하지 않았습니다.
- 1.4 모델 B(R = 86.9 MB/s, 예상 2.96 s)와 비교하면 실측 합계 1.40 s 는 ±20% 밖입니다. 이 파일에서는 R = 86.9 가정이 시간을 과대 추정했습니다. 따라서 1.4 모델은 채택하지 않습니다.

**E1 판정 (5절 성공 기준):**
- (a) 4 MiB 청크 1.36 s 는 기준 3.2 s 이내이고 76 MB/s 이상이므로 충족합니다.
- (b) RAM 재생 0.040 s 는 기준 0.1 s 이내이므로 충족합니다.
- (c) 버퍼드 직접 재생 1.66 s 는 기준 4.6 s 이내이므로 충족합니다.
- extents 기준(4 이하)은 38 이므로 **미충족**입니다.
- G-A 기준(스트림 + 재생 3.0 s 이내)은 약 1.40 s 로 **충족**합니다. 다만 막 쓴 파일에서 잰 값이므로 SMR 재매핑 영향은 분리하지 못했습니다.
- 판정: **조건부 통과**입니다. 연속 배치의 순차 속도는 확인했지만, 파일 연속성과 SMR 영향은 E1c 와 E3 에서 확정합니다.

**E3 뒤 판정 (2026-11-01, SSD 와 같은 범위).** 합성 데이터셋에서 접근 순서 재배치와 스트림 선읽기는 HDD 콜드 로딩 17.1 s 를 1.1~1.2 s 로 줄여, 같은 조건의 SSD 콜드 로딩(0.76~1.22 s)과 같은 범위에 들어왔습니다. 게임이 읽기만 하고 연산을 하지 않는 극단에서는 스트림 속도(순차 약 160 MiB/s, 243 MB 에 1.4~1.6 s)가 바닥이라 SSD 콜드의 1.35~2.2배입니다(기준 SSD 값에 따라 다릅니다). 요청당 0.25 ms 이상 연산하는 보통의 로딩에서는 동시 스트림으로 SSD 와 같거나 더 짧았습니다. 실제 게임 트레이스, 24시간 지속성, CMR 드라이브는 미검증입니다. 근거는 `results/relayout_e3/20261101_225446/summary.json`, `results/relayout_e3/20261101_235628/summary.json`, `results/stream_tuning_20261101/`입니다.

### 1.5 목표 문구와 성공 기준 (다시 세움)

**목표 문구:** "HDD 단독 SSD 급"이 아니라 **"재배치와 스트림으로 HDD 로딩을 SSD 에 근접시키고, CPU 겹침이나 사전 예열 조건에서는 체감 차이를 없앤다"**로 둡니다.

| 층위 | 성공 기준 | 근거 |
|---|---|---|
| 물리 하한 (참고) | B/R. 243.5 MB, 150 MB/s 기준 1.6 s 로 SSD 0.8 s 의 2배 | [조사 계산] 동일 |
| G-A 합성 콜드, 이 PC(SMR 의심) | 스트림+재생 ≤ 3.0 s (SSD 0.8 s 의 3.75배 이하, 1.12 s 의 2.7배 이하). 현재 11.1 s | 1.4 B, R=86.9 |
| G-A' 합성 콜드, 바깥 존 R ≥ 140 MB/s 를 확인한 경우(CMR 기대치) | 스트림+재생 ≤ 2.0 s (0.8 s 의 2.5배 이하) | 1.4 B, R=150 |
| G-B 스트림 없는 직접 재생 | ≤ 6 s (현재 17.8 s), 실행 간 max/min ≤ 1.3 | 1.4 A + 여유 |
| G-C 실제 게임 체감(E5) | SSD 설치본 대비 로딩 p50 ≤ 1.25배, p95 ≤ 1.5배 (기존 내부 목표). **CPU 겹침 조건이 성립하는 게임에서만** 목표로 하고, 성립하지 않으면 그 게임의 배수를 그대로 보고 | 1.5 아래 식 |
| G-D 사전 예열 | 예열이 끝난 뒤의 로딩이 SSD 콜드 이하 | RAM 적중 |

**왜 불가능하고 언제 근접하는가**
- 순수 I/O 콜드에서 SSD 와 같은 시간을 내려면 R ≥ 243.5 MB ÷ 0.8 s = 304 MB/s 가 필요합니다. 이 HDD 의 매체 속도(바깥 약 155 MB/s, 형제 모델 기준)를 넘으므로 불가능합니다. 핫 집합이 약 120 MB(= 0.8 s × 150 MB/s) 이하인 게임에서만 이론상 같아질 수 있습니다[조사 계산].
- CPU 겹침: SSD 로딩을 T_cpu + T_io,ssd, AsterStream 을 쓴 HDD 로딩을 max(T_cpu, T_stream) + ε 로 두면, T_cpu ≥ T_stream 인 게임은 HDD 가 SSD 와 비슷하거나 더 빠를 수 있습니다. 예를 들어 T_cpu = 10 s, T_stream = 1.8 s, T_io,ssd = 0.8 s 이면 10 s 대 10.8 s 입니다. 다만 이 수치는 식을 보이기 위한 [가정]입니다. 또 이 식은 "게임이 스트림을 앞지르지 않는다"는 전제를 둡니다. SSD 의 합성 성능 향상이 로딩 단축에 비례하지 않는다는 보도는 있으나 정량 자료는 없습니다[조사 2차].
- 핫 바이트가 큰 게임은 근접하지 못합니다. 레벨당 4 GB 를 읽으면 150 MB/s 에서 27 s 가 걸리고 NVMe 는 수 초입니다[계산, 바이트는 가정]. 이런 게임에서는 핫 집합 축소(로딩 구간 첫 부분만 존에 두기) 말고는 방법이 없습니다. 이 한계는 README 에 그대로 적습니다.

## 2. 시스템 구성과 데이터 흐름

### 2.1 권한 분리

- 볼륨 핸들(FSCTL_MOVE_FILE, FSCTL_GET_VOLUME_BITMAP)은 관리자만 열 수 있습니다[조사 확인]. Kernel-File ETW 실시간 세션도 관리자, Performance Log Users 그룹, 서비스 계정만 시작할 수 있습니다[조사 확인].
- 그래서 두 프로세스로 나눕니다.
  - **aster-agent (관리자 상주 서비스 또는 UAC 승격 헬퍼):** 이동 실행, 비트맵 조회, ETW 수집, 배치 상태 감시를 맡습니다. 할 수 있는 일은 "계획 파일에 적힌, 허용 목록 루트 아래 파일의 extent 이동"과 "지정한 게임 프로세스의 읽기 트레이스"로 제한합니다. 임의 명령은 받지 않습니다. 계획 파일은 관리자 전용 ACL 폴더(%ProgramData%\AsterCache)에서만 읽습니다.
  - **aster (사용자 도구, 비관리자):** 트레이스 가져오기, 계획 계산, 스트림 선읽기, 측정, 보고를 맡습니다.
- v1 의 첫 단계(E2·E3)에서는 서비스를 만들지 않고 "관리자 PowerShell 에서 apply 를 1회 실행"으로 시작합니다. 상주 서비스는 재적용 루프(2.3)를 자동화할 때 만듭니다. 서비스 없이도 실험은 진행할 수 있습니다.

- 게임이 보는 것은 같은 경로, 같은 바이트입니다. 바뀌는 것은 NTFS 가 각 파일의 VCN 을 어느 LCN 에 두느냐뿐입니다. 도구를 지워도 데이터는 정상입니다[조사 확인].

## 3. 핵심 알고리즘

공통 단위는 다음과 같습니다.
- 블록 = 64 KiB (현재 트레이스 단위)
- 클러스터 = 4 KiB (D: 의 실제 값은 prefetch.layout.cluster_size 로 확인)
- 블록 키 = (파일 ID, 블록 번호). 경로 대신 NTFS 파일 ID 를 써서 경로 대소문자 문제를 피합니다(코드 검토 결과: 경로 대소문자 불일치 문제).

### 3.1 핫 집합 선정

여러 실행에서 자주 읽히고, 읽히는 순서가 안정적이며, 지금 배치에서 위치 결정을 일으키는 블록을 고릅니다.

```
입력: runs[1..K] (오래된 것부터). 각 run 은 접근 순서대로 늘어선 블록 키 목록
      λ = 0.85 (session_planner.plan_sessions 의 decay 와 같은 값), θ_core = 0.5, θ_tail = 0.2  [가정]
w_k = λ^(K-k)
for 각 블록 b:
    f_b   = Σ_k w_k·[b ∈ run_k] / Σ_k w_k                    # 가중 빈도
    p_b,k = (run_k 에서 b 가 처음 나온 위치) / len(run_k)      # 정규화 순위 0..1
    m_b   = 가중 중앙값_k(p_b,k)                              # 합의 시점
    s_b   = 1 − min(1, 2·가중MAD_k(p_b,k))                    # 순서 안정도 0..1
    c_b   = 1, 단 지금 배치에서 b 가 합의 순서상 앞 블록과 물리적으로 이어지면 0.2
    score_b = f_b · (0.5 + 0.5·s_b) · c_b
core = {b | f_b ≥ θ_core}, tail = {b | θ_tail ≤ f_b < θ_core}
core 를 score 내림차순으로 게임별 존 예산 C_game 까지 채우고, 자리가 남으면 tail 순으로 채움
```

- c_b 는 이미 연속이라 옮겨도 이득이 작은 블록을 뒤로 미룹니다(예: 큰 pak 파일을 순차로 읽는 구간). 그만큼 SMR 쓰기량도 줄어듭니다.
- 실행이 1회(K=1)뿐이면 f_b 는 0 또는 1, s_b 는 1 입니다. 계획은 만들 수 있지만 커버리지는 K ≥ 3 부터 믿습니다(E4 에서 측정).
- **핫 집합 축소 선택지:** 핫 바이트가 RAM 예산이나 "SSD 근접 한계(약 120 MB/s·초)"보다 크면, m_b 가 앞쪽인 블록(로딩 첫 구간)부터 존에 둡니다. 첫 화면까지의 시간을 우선하기 위해서입니다.

### 3.2 접근 순서 선형화 (합의 순서)

실행마다 순서가 조금씩 다를 때 물리 순서 하나를 정합니다. 이상적인 목표는 가중 켄달 거리(뒤집힌 쌍의 수)를 최소로 하는 케메니 순위인데, NP-어렵기 때문에 근사합니다.

```
1. 실행 단위 묶기: 가중치 ≥ θ_core 인 모든 실행에서 b 바로 뒤에 같은 파일의 b+1 이 오면 한 단위로 합침
   → 단위 = (파일 ID, 시작 블록, 블록 수). 같은 파일의 연속 구간은 쪼개지 않으므로 extent 수가 줄어듦
2. 단계 분할: 연속 접근 사이 시간 간격이 1 s 를 넘는 곳을 경계로 표시 [가정]
   경계 표시가 과반인 위치에서 자름 (메뉴 → 레벨 로딩처럼 중간에 사용자 대기가 있는 지점)
3. 단계 안에서 단위를 m_u (합의 시점 중앙값) 오름차순으로 정렬
4. 국소 개선: 인접한 두 단위 (u, v) 에서 W(v→u) > W(u→v) 이면 교환
   W(x→y) = Σ_k w_k·[run_k 에서 x 가 y 보다 먼저]. 교환이 없을 때까지 반복(최대 n 회)
출력: 단위 목록 order[]
```

- Procmon CSV 에 시간 열이 없으면 행 순서만으로 1·3·4 를 하고 2 는 건너뜁니다.
- 순서가 어긋난 지점 J 는 1.4 의 시나리오 A 에서만 비용이 됩니다. 시나리오 B 는 존 전체를 먼저 읽으므로 순서 오차에 둔감합니다.

### 3.3 핫 존 할당

```
입력: order[], 볼륨 비트맵(FSCTL_GET_VOLUME_BITMAP 스냅샷), 파일별 extent, 존 속도 곡선(E1b: LCN 0/25/50/75/100%의 순차 MB/s)
1. 제외 대상: 압축·스파스 파일(이동 단위가 16 클러스터라 v1 제외), EFS, MFT 상주 파일, 시스템 파일,
   FSCTL_MARK_HANDLE 로 보호된 파일. 볼륨이 더티이면(fsutil dirty) 계획 거부. BitLocker 켜진 볼륨은 v1 에서 거부
2. 존 위치: "LCN 이 낮을수록 빠르다"고 가정하지 않음 [조사 2차]. 존 속도 곡선에서 가장 빠른 구간을 고르고,
   그 구간 안에서 크기 S = Σ 단위 크기를 담는 빈 연속 구간 열을 찾음.
   구간 사이 틈 하나는 위치 결정 1회(약 8 ms [가정])로 계산. 틈 수 G 가 S/64 MiB 를 넘으면
   비우기 계획으로 전환: 존 안의 비핫 클러스터를 존 밖 빈 곳으로 먼저 옮김 (쓰기량이 늘어나므로 SMR 상한에 포함)
3. 배치: order 순서대로 단위를 존 커서 위치에 배정. 크기는 클러스터 배수로 맞추고, 파일 끝은 실제 크기의 클러스터 올림까지
   (그 너머의 할당 클러스터는 이동하면 오류가 남 [조사 확인])
4. 섀도 복사본 대응: 원본과 목표의 LCN 차이를 16 KiB 배수(4 KiB 클러스터면 4 클러스터 배수)로 맞추고,
   이동 단위를 16 KiB 보다 크게 함 (어기면 섀도 공간이 늘고 성능이 떨어짐 [조사 확인])
5. 제자리 보존: 단위의 현재 LCN 이 배정 위치와 같으면 이동하지 않음.
   존 밖이라도 "직전 단위와 물리적으로 이어지고 길이 ≥ 8 MiB [가정]"인 구간은 그 자리를 존의 한 조각으로 인정
   (틈 1회 비용이 이동 비용보다 작을 때만)
출력: zone_plan = [(파일 ID, VCN, 클러스터 수, 목표 LCN)], 존 조각 목록, 1.4 식으로 계산한 예상 시간
```

### 3.4 이동 계획 (빈 클러스터 확보 순서, 이동량 최소화, 중단 재개)

```
1. 충돌 그래프: 목표 LCN 범위를 다른 단위나 비핫 데이터가 차지하면 간선을 둠
2. 실행 순서:
   a. 비우기: 목표 범위의 비핫 클러스터를 존 밖 빈 곳으로 (큰 빈 구간부터)
   b. 목표가 이미 비어 있는 존 밖 단위를 바로 이동
   c. 존 안 단위끼리 서로의 자리를 차지하는 순환은 존 밖 임시 구간(가장 큰 단위 이상)으로 끊음
   이동량 = Σ 이동 클러스터. 아래 조건이 거짓이면 계획을 보고만 하고 실행하지 않음:
     이동 시간(2·바이트/R_write + 호출당 비용) < 1회 예상 절감 × 예상 실행 횟수(기본 5회 [가정])
3. SMR 대응 쓰기 규칙:
   - 청크: 한 FSCTL_MOVE_FILE 호출을 1~16 MiB 로 나눔 (한 호출의 최대 크기는 문서에 없음 [조사 미확인])
   - 목표 쪽은 LCN 오름차순으로만 채움 (존 안을 앞에서 뒤로 순차 쓰기, 되돌아가 쓰지 않음)
   - 1회 실행 쓰기 상한 1 GiB [가정], 256 MiB 마다 30 s 유휴 [가정]. E2·E3 에서 쓰기 처리량이 떨어지면 상한을 낮춤
   - 비우기(a)는 쓰기량을 두 배로 만들므로 G 가 작을 때는 비우기 대신 존 조각화를 허용
4. 저널(journal.jsonl): 단계마다 실행 전에 기록
   {step, file_id, path, vcn, clusters, from_lcn, to_lcn, sha256_before(표본), state: planned}
   실행 뒤 extent 를 다시 조회해 to_lcn 이 맞으면 state: done
5. 재개: 시작할 때 저널을 읽고, done 이 아닌 단계마다 현재 extent 를 조회
   - 이미 to_lcn 이면 done, 아직 from_lcn 이면 다시 실행, 둘 다 아니면(다른 프로그램이 옮김) 계획 재계산
   - 저널은 재개 힌트일 뿐이고, 진실은 "extent 재조회 + 해시"임. 이동의 정전 원자성은 문서로 확인되지 않음 [조사 미확인]
6. 해제된 클러스터: 바로 재할당되지 않을 수 있음 [확인 필요]. 대상 점유 오류가 나면 짧게 기다려 최대 3회 재시도, 그 뒤 해당 단위는 건너뜀
7. 속도 조절: 이동 묶음 사이마다 \PhysicalDisk(n)\Disk Bytes/sec 를 확인 (bench/sweep.disk_activity 재사용).
   다른 프로세스 I/O 가 있으면 일시정지. 이동 중에도 다른 프로세스의 읽기·쓰기는 막히지 않고 느려질 뿐임 [조사 확인]
```

### 3.5 스트림 선읽기 스케줄

```
입력: zone_plan (단위 목록, 목표 LCN 순서), 예산
1. 연산 목록: 단위들을 LCN 오름차순으로 두고, 같은 파일의 인접 단위는 합침.
   재배치 뒤에는 prefetch.scheduler.schedule(strategy='physical') 이 이 순서를 그대로 내놓음.
   layout_fn 이 새 extent 를 돌려주므로 새 코드가 필요 없음. 존 안에서는 간격 병합의 gap 이 거의 0
2. 큐 깊이: threads = 1 (기본, prefetch.reader.read_ops 의 threads 재사용).
   재배치 존 튜닝(2026-11-01, `results/stream_tuning_20261101/sweep.json`, 1 MiB, 핸들 닫기 기준 중앙값)에서 큐 깊이 1 이 가장 빨랐습니다: 1 → 1.48 s, 2 → 1.64 s, 4 → 1.66 s. 같은 존에서 핸들 유지(큐 깊이 1)는 1.42 s(`reuse_qd1.json`)였습니다.
   1.4a 의 큐 깊이 4 개선(10.19 s → 7.80 s)은 재배치 전 흩어진 배치에서의 결과이며, 재배치 뒤 존에는 적용되지 않습니다.
   청크 1~16 MiB 는 차이가 없었고, 256 KiB 는 3.9~4.6배 느렸습니다. 기본 청크는 1 MiB 입니다. SEQUENTIAL_SCAN 힌트는 같은 청크·큐 깊이 대비 10.7~16.9배 느려 끕니다.
3. 소비 속도: 기본은 "존 전체를 최대 속도로" 읽기 (243 MB 는 RAM 32 GiB 에 비해 작음).
   게임별 존이 RAM 예산(기본 4 GiB [가정])을 넘을 때만 앞서 읽기 창을 씀:
     창 L = max(64 MiB, r_game × 2 s), r_game = 직전 트레이스의 단계별 바이트/초
   aster-agent 의 ETW 로 게임 커서(존 안 위치)를 알 수 있으면 L 만큼만 앞서 감.
   ByteOffset 은 파일 안 위치이므로 extent 로 LCN 으로 바꿔야 함 [조사 확인]. ETW 가 없으면 시간 기준으로 진행
4. 실행 시점: (a) 게임 실행 직후 (시나리오 B/C), (b) 런처 실행 또는 로그인 직후 낮은 우선순위 (시나리오 D, 사용자 선택)
```

**1.4 예상과의 비교.** 1.4 모델 B 의 예상은 R = 86.9 MB/s 일 때 2.96 s, R = 150 MB/s 일 때 1.78 s입니다. 실측 1.09 s는 두 값보다 짧습니다. 1.4a 절의 연속 배치 실측(1.40 s)과도 맞지 않습니다. 원인은 분리하지 못했습니다. 가장 유력한 설명은 이동 직후 드라이브 캐시(SMR 미디어 캐시·DRAM)의 영향입니다. 같은 드라이브의 안정 순차 속도는 E1b에서 90~110 MB/s였습니다. 이 속도로 243 MB를 읽으면 약 2.5 s이며, 이를 보수적 기대치로 둡니다. 이 값은 SSD 콜드의 약 3.3배입니다. 24시간 뒤 재측정(E1c-24h)으로 지속성을 판정하기 전까지 1.09 s를 지속 성능으로 채택하지 않습니다.

**판정.** E3 G-A는 충족입니다. G-B는 미달입니다. 직접 읽기는 재배치로 17.1 s에서 7.7 s로 줄었지만 6 s에는 못 미칩니다. E2는 무결성과 순서만 확인했습니다. 강제 종료와 chkdsk 시험은 따로 해야 합니다. 다음은 E1c-24h와 E4입니다.

**독자성 주장의 범위:** 블록 단위 접근 순서 재배치 개념은 BORG(2009)가 먼저 내놓았습니다. 이 설계의 기여는 다음 조합과 구현 방식입니다.
1. 드라이버나 복사본 없이 일반 Windows 위에서 사용자 모드와 공식 디프래그 API(제자리 이동)만으로 구현합니다.
2. 게임 타이틀별 로딩 트레이스로 파일 안 블록 범위를 파일 경계를 넘어 한 줄로 이어 붙입니다.
3. 여러 실행의 순서를 합의하고(중앙값 순위 + 인접 교환), 순서 안정도를 선정 가중치로 씁니다.
4. 재배치된 존에 맞춘 스트림 선읽기를 결합합니다.
5. 지문과 extent 감시로 재적용 루프를 돌립니다.

이 조합을 그대로 구현한 제품이나 논문은 조사에서 "찾지 못했습니다". 없다는 증명은 아닙니다[조사].

## 7. 위험과 한계

### 7.1 SMR (최우선 위험)

- 사실: WD20EZAZ 는 WD 가 2020년에 공개한 SMR 목록에 들어 있다고 여러 곳에서 보도됐습니다. 다만 WD 원문 표는 읽지 못했습니다[조사 2차].
- 영향 1 — 배치 가정: DM-SMR 은 드라이브 안에 LBA→물리 간접 매핑과 영속 캐시가 있습니다. 쓴 직후의 연속 LCN 이 물리적으로 연속이라는 보장이 없습니다. 유휴 정리 뒤 밴드 안에서 순차가 되는지도 확인되지 않았습니다[확인 필요].
- 영향 2 — 쓰기 속도: 영속 캐시가 차면 쓰기가 급락하고 수 분 동안 멈출 수 있습니다[조사 2차].
- 대응:
  - E1 과 E1c 로 먼저 실측합니다.
  - 이동은 작은 청크로, 목표 쪽 순차 쓰기만, 쓰기 상한과 유휴 시간을 두고 합니다(3.4-3).
  - 비우기를 줄여 쓰기량을 최소로 합니다(c_b, 제자리 보존).
  - 결과는 "이 PC(SMR 의심)"와 "CMR 기대치(1.4 의 R=150 열, G-A')"로 나눠 보고합니다.
- 최악의 경우: E1 에서 연속 배치가 순차 속도를 내지 못하면, 이 드라이브에서는 재배치 이득이 작고 AsterStream(RAM)만 남습니다. 그래도 이것은 실패가 아니라 측정 결과로 보고합니다.

### 7.2 그 밖의 위험

1. **첫 실행은 이득이 없습니다.** 트레이스가 없으면 핫 집합도 없습니다. 신뢰도는 3회 실행부터입니다.
2. **패치와 정기 최적화가 배치를 깨뜨립니다.** 그래서 2.3 의 재적용 루프가 필수입니다. 패치가 잦은 게임은 이동 쓰기가 되풀이되므로 비용 대비 절감 판정(3.4-2)으로 거릅니다.
3. **존 용량과 게임 수.** 게임당 핫 바이트를 0.25~5 GB, 존을 40 GB 로 잡으면 8~160개입니다[가정]. 빠른 구간은 유한하므로 최근 실행 순으로 우선권을 줍니다.
4. **순수 I/O 콜드의 물리 하한.** 1.5 그대로입니다. SSD 와 같은 콜드 시간은 약속하지 않습니다.
5. **이미 순서대로 패키징된 게임**은 이득이 작습니다.
6. **안티치트.** 바이트, 경로, 서명이 그대로이고 커널 구성요소도 없습니다. 다만 일부 안티치트가 무엇을 검사하는지는 모릅니다[확인 필요]. v1 은 안티치트 게임을 대상에서 뺍니다(README 경고 유지).
7. **DirectStorage 와 언버퍼드 게임.** RAM 이득은 없고 순차화 이득만 남습니다.
8. **RAM 압박.** standby list 는 메모리가 부족하면 먼저 비워집니다. 시나리오 D 처럼 너무 일찍 예열하면 사라질 수 있습니다.
9. **관리자 상주 서비스.** 공격 면이 생깁니다. 이 때문에 권한을 제한합니다(2.1). 서비스 없이 수동 apply 로도 운용할 수 있습니다.
10. **측정 조건.** 비관리자 언버퍼드 대체 콜드, PC 1대, 합성 트레이스입니다. 1.3 의 모델 적합도도 이 조건에 한정됩니다.

### 7.3 (질문 4) 핫 존에 들어가지 않는 긴 꼬리

가로채기가 없으면 SSD 에 둔 데이터는 게임 눈에 보이지 않습니다. **그래서 v1 은 긴 꼬리에 SSD 를 쓰지 않습니다.** 조사 문서는 "SSD 캐시는 잔여 미스에만"을 제안했지만, 가로채기 없이 실현할 방법이 없어 채택하지 않습니다.
- (채택) 2단 존: 핫 존 바로 뒤에 꼬리 존을 둡니다. θ_tail ≤ f < θ_core 인 블록을 같은 합의 순서로 놓고, AsterStream 이 핫 존 다음에 낮은 I/O 우선순위로 이어 읽습니다. 다 읽기 전에 게임이 요청하면 그 한 번만 위치 결정 비용을 냅니다.
- (채택) 손대지 않기: 확률이 θ_tail 미만인 블록은 제자리에 둡니다. 예측할 수 없는 데이터는 어떤 선읽기로도 줄일 수 없습니다.
- (불채택) SQLite SSD 캐시: 게임이 읽지 못하므로 게임 경로에서 뺍니다. API 실험용으로만 남깁니다.
- (범위 밖, 사용자 수동 선택) 게임 전체를 SSD 로 옮기기: "HDD 를 빠르게 쓰기"가 아니므로 다루지 않습니다.

### 7.4 가설에서 바꾼 점과 검토한 대안

- 가설 (1)~(3)은 유지합니다. 바꾼 점은 다섯 가지입니다.
  - 이미 연속인 구간은 옮기지 않습니다(c_b, 제자리 보존).
  - 같은 파일의 연속 접근은 실행 단위로 묶어 extent 가 크게 늘지 않게 합니다.
  - 존 위치는 "바깥 트랙"이라는 가정 대신 실측한 존 속도 곡선으로 고릅니다.
  - SMR 쓰기 규칙을 넣었습니다.
  - 관리자 서비스와 재적용 루프를 구조에 넣었습니다.
- 파일 단위 재배치(Layout.ini 방식): 이 데이터셋에서는 2.1 GB 를 옮기고 2.1 GB 를 읽어야 합니다(전체 읽기 23.9 s [측정]). 블록 단위보다 나빠서 채택하지 않습니다.
- 핫 존 압축(WOF 등): 게임 자산은 대부분 이미 압축돼 있고 파일 표현도 바뀌므로 채택하지 않습니다.
- 가로채기 기반 SSD 캐시(WinFsp, 미니필터): 사용자 지시에 따라 v1 범위 밖입니다.
